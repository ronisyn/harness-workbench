## 1. 背景与目标（一页话）

**背景**：RW 的"通用机制层"已经成熟并跑在 880（TEST）：对话/思考/工具（63 个）/MCP/权限审批审计/护栏预算/契约驱动器/技能/知识/记忆/用量成本，全部是**与业务无关**的机制件。而业务上，RW 目前表现为"一个写代码的通用 Agent"。

**目标**：把「机制（核心 Core）」与「业务身份与能力配置（壳 Shell）」分离——
- **核心**：保持中立、无身份、无业务，像发动机；
- **壳**：定义"我是谁、擅长什么、用什么模型、开哪些工具、带什么知识、从哪个门进、长什么样"，像车身/驾驶室；
- **统一后台**：一处管理所有壳的创建、克隆、启停、工具勾选、模型策略、用量观测。

**一句话验收**：管理员花 10 分钟克隆出一个"供应链助理"壳并绑好域名；用户打开 `scm.ronisyn.com` 时看到的、对话的、能用的，是供应链语境下的 RW——而底层全部复用同一套核心机制，且 880 现有能力不回归。

**非目标（v1 明确不做）**：SaaS 多租户计费、应用商店审核/支付、OS 级沙箱、画布式工作流引擎。

## 2. 用户故事（现象级验收锚点）

| # | 故事 | 现象 |
|---|---|---|
| US1 | 普通用户打开 code 壳 | 输入 `code.ronisyn.com` → 登录 → 对话体验与今天 RW 一致，但默认语境是写代码（自动注入壳说明/技能/知识），默认模型=代码性价比档；**用户完全感知不到"壳"的存在** |
| US2 | 管理员造一个新壳 | 统一后台"新建壳 ← 克隆 code"→ 填身份描述"供应链助理"/勾选工具（高危默认关）/绑知识库/设默认模型与预算 → 生成 `scm.ronisyn.com` → 打开即是供应链语境 |
| US3 | 按壳开关工具 | 后台勾掉供应链壳的 `run_command` → 该壳所有会话**立即**不可用（秒级生效，复用政策版本机制），其它壳不受影响 |
| US4 | 壳间隔离 | 供应链壳的会话/知识/文件/用量与 code 壳互不可见（隔离等级取决于选型 D/A，见 §5） |
| US5 | 统一观测 | 后台一张表看全部壳：用量/成本/工具健康/KPI 周报；任一壳超预算自动停（复用现有护栏） |
| US6 | 停用壳 | 停用 → 该壳域名访问被拒/提示，数据保留可恢复 |
| US7 | 默认路径回归 | 不配壳的老路径（880 直接 IP/默认域名）行为与今天完全一致——现有 22 项平台能力 + 63 工具全量回归 |

## 3. 功能需求（草稿编号）

**FR1 壳生命周期**：创建 / 克隆 / 编辑 / 启停 / 删除（归档保留数据）。

**FR2 壳定义内容**（="壳配置包"字段集，初稿）：
- 身份：persona（人设描述/语气/禁区，供身份层追加；**核心无壳时保持现状中立措辞**（agent.js:176 最小身份行「你是 RW 工作台智能体…」，无业务人设——延续批1 原则））
- 领域：AGENTS 式领域说明（术语/状态机/常见任务）
- 能力：工具启用集（壳级覆盖 preset 三档）、MCP/插件勾选
- 资产：默认技能集（SKILL 引用）、知识范围（global+壳级）、模板/任务档案（联动议题②③）
- 模型策略：默认 provider/model、温度、预算上限、auto 路由偏好（联动议题③）
- 入口：域名绑定、渠道绑定（wechat/feishu）、默认会话 permission
- 品牌：名称/简介/主题色（可选，v0.1 可后置）

**FR3 统一后台**：壳列表+详情+克隆向导+工具勾选矩阵+模型策略+用量成本看板+健康卡（基线 KPI/自检结果）+ 壳配置导出/导入（instance pack，对接发行物机制）。

**FR4 入口路由**：按域名/Host 识别壳；未匹配 → 默认壳（880 现状入口）；会话创建默认归属当前壳。

**FR5 上下文注入**：壳 persona/AGENTS 进入现有系统提示"身份/环境"层（P13 三层的现成接缝）；技能/知识按"会话所属壳"过滤生效。

**FR6 数据隔离**：按选型——D 逻辑隔离：业务表全带 `shell_id` + 文件工作区按壳分目录 + 壳间互查被服务端强制过滤；A 硬隔离：每壳独立 DB/工作区/进程。

**FR7 渠道与无人值守**：微信/飞书消息进入其绑定壳；定时任务/任务契约/驱动器执行归属壳（会话与计量都带壳）。

**FR8 迁移与兼容**：存量数据归入"默认壳"；所有迁移幂等；老 API 不带壳参数时按默认壳语义兼容。

**FR9 与其余待办议题联动（本次只留接口占位）**：壳内预装任务档案与意图词表（②意图重构/③任务档案+路由）；壳级知识库（④）；按壳测评（⑤）；任务资产市场跨壳共享（⑥）。

## 4. 非功能需求

- N1 隔离：按选型，壳 A 故障/超预算不影响壳 B（A 天然满足；D 需进程级护栏+并发限额兜底）
- N2 升级：核心升级一次，所有壳受益（D 天然；A 需逐实例或发布流水线）
- N3 成本：壳级预算上限 + 超限自动停（复用 task_budget 体系，扩展 shell 维度）
- N4 审计：usage_stats / audit_log / tool_calls 带 shell_id；管理操作（建壳/改工具）落审计
- N5 性能：单进程多壳时的总并发上限与单壳限额（可配）
- N6 安全：模型 Key 最小化分配（壳只需要自己那几家的 key，密钥不出 .env/密钥文件）
- N7 可用性：D 方案下 880 现有单点架构不变；A 方案下每壳独立 systemd 单元

4. **业务数据边界**：倾向**推迟到议题⑧（code 壳上线路线）**一并定——知识库并入（本议题）与业务数据/工作台桥接（ideas/tasks/mine）分两步走，避免本议题无限膨胀；但需在 D2 上线清单里显式占位，防止遗忘（对应合并基线 P1 桥接件清单）。

## 附 C：外部平台接入的"最佳方案"设计草稿（2026-09-08 用户场景驱动，讨论中）

**用户场景**：供应链壳连 Shopify/亚马逊/速卖通/Temu/沃尔玛/美客多…；video 壳连抖音/小红书/视频号等短视频数据平台（抓视频、拆解分析）；book 壳连电子书 API（获取书籍自学）。质疑："通用 API 连接器对其他壳完全没用，怎么办？"

**回答：连接器不是"一个通用工具套所有 API"，而是三层结构——引擎通用化、平台适配器化、壳装配化、凭证域化。**

```
┌ 核心层（一套，全壳共用）Connector Engine ─────────────────┐
│ · 凭证库：按(壳×连接器)存密钥，加密存储、脱敏、永不下发    │
│ · HTTP 执行：鉴权(api-key/oauth2/签名)、重试、限流、分页、超时 │
│ · 治理：可选审批、全量审计、幂等键、出站白名单            │
│ · 输出规范化：统一"资源对象"（订单/库存/视频/书目…）      │
└─────────────────────────────────────────────────────────────┘
┌ 注册表（Connector Catalog，按平台一条）★新增 ★议题⑦合流 ──┐
│ 每条 = { 平台, 域标签[], 鉴权类型, 端点/参数(OpenAPI 或薄代码), │
│          限流, 凭证 schema, 来源: 自研|社区MCP|OpenAPI导入|私有 } │
│ 例：connectors.shopify / .amazon_sp / .temu / .wms_xxx      │
│     connectors.douyin / .xiaohongshu / .ebook_xxx …        │
└─────────────────────────────────────────────────────────────┘
┌ 壳装配层：shells.connectors = 勾选清单（连凭证配置一起）─────┐
│ scm 壳 勾 [shopify, amazon, wms]；video 壳 勾 [douyin,…]；  │
│ book 壳 勾 [ebook…]；Agent 只见本壳勾选的连接器工具          │
└─────────────────────────────────────────────────────────────┘
```

- **"通用连接器对其他壳没用"是误解**：引擎+注册表机制对每个壳都有用；**单个平台适配器**当然只对需要的壳有用——这正是"插件项在不同壳里勾选"的意义，不会为每个壳重复造引擎。
- **新增一个平台的成本** = 写/导入一个适配器（半天~1 天：多数平台有 OpenAPI 文档；社区现成 MCP 直接挂），写好后**所有壳可用**（只要勾选）。
- **book 壳"自学"场景** = 连接器（电子书 API 获取）→ 下载 → extract_* → 知识库导入（L2）→ Agent 阅读/总结沉淀 → 形成"儿童心理学"知识域——全是现成机制的组合，无新机制。
- **与既有机制关系**：Connector = 议题⑦"工具/插件注册表"的第一批插件形态；与 MCP 并列（MCP 适配器直接进注册表）；统一后台提供"连接器市场"（浏览/勾选/配凭证）。
- **D3 判定更新**：②壳级代码依然非必需；企业私有协议（WMS/ERP）走"私有连接器"（注册表条目+壳勾选+审计），仍属插件而非壳代码。

## 附 D：code 壳里 RW 的角色与约束模型草稿（2026-09-08，用户问"RW 写码？测试？分配？谁遵守约束？"）

**澄清前提**：RW 的 Agent 循环（runAgent）**同一套机制可承载不同角色**——讨论者、规划者、执行者（写码）、验收者、派工者。区别不在"谁"，而在"这次任务用什么装配"。

**两个模式（都在 code 壳内，由发起方式决定，并存）：**

| | 直接模式（默认，RW 开放本色） | 工单模式（承接 hello 遗产的受控交付） |
|---|---|---|
| 触发 | 用户对话直接说"帮我做 X" | 立项/待办任务/契约（create_contract），可指定执行模型 |
| RW 角色 | 全链路自己干：写码→自测→提交复测 | RW=交付经理：拆任务→派工（子代理/驱动器，可指定模型）→注入验收→收结果→复核→复测放行 |
| 执行者 | RW 自己（当前会话模型） | 工人会话（权限可收紧：write 级+验收强制+只读工作区），**工人可以是 RW 自己，也可以是指定模型** |
| 约束 | 行为准则+护栏（保险丝，可调）+壳装配规则 | 上述 + 任务档案验收 DSL + access_rules + 人工复测放行（candidate_done→confirm 才 done） |

**回答用户的五个小问**：
1. RW 写码吗？→ 默认写（直接模式）；工单模式下可只当经理，把码派给指定模型。
2. RW 测试吗？→ 自己写的自己测（syntax/run_test/验收钩子）；派出去的在收口处复核+复测。
3. RW 分配吗？→ 需要并行/夜间/指定模型时才分配（subagent/driver 现成）。
4. 约束谁遵守？→ **谁执行谁遵守**：约束不是针对"别的 AI"或"RW"的特权差异，而是按"执行会话的装配"生效——工人会话被注入验收与规则（driver 已在做）；RW 直接模式同样受行为准则与护栏约束（诚实/安全类人人遵守；业务类规则是壳级装配，可调可关）。
5. 全局知识库 = RW 设计出来让工人遵守的规矩？→ **不是这个定位**。知识库是**壳的共享资产**，其中"治理类"内容（约束/质量/流程）的语义应**升级为机制**（纪律层/access_rules/验收模板/任务档案——机制对一切执行者生效，包括 RW 自己），"领域类"内容（文档/方法论/词汇）留在知识库供参考。避免 hello 的教训：把治理当"文档+自觉遵守"，约束力弱、且容易变成对 Agent 的人格化死板约束。
6. "以 RW 为主、不被约束死板"如何兼得？→ 默认 code 壳 = 直接模式全能力 + 壳级规则可调；hello 的受控保障以"工单模式+验收/复测模板"形态**默认装配但不锁死**（克隆成实验壳时可卸下）。

## 附 E：code 壳工作模型 · Issue 驱动 + 用户指派 + 观测式评测（2026-09-08 用户定调，讨论深化中）

**用户定调**（原话要点）："待办任务 = git 里的 issue；由**我**下令给哪些模型并行执行；不要同一任务给 A/B 双跑（浪费）；要**长期观测**——给 A 20 个任务、B 另 N 个任务各自跑，每次记录 bug 与复测通过率；任务虽不同，积累后 A/B 在通过率/bug 数/执行时长/token 消耗上的差异会显现，据此评估哪些模型适合 code 壳开发。"

**回答用户之问"待办任务是 code 壳里的对话，还是列表里的任务？"**——两者都不是旧形态，新工作模型三物件：
1. **Issue = 任务真相**（git 平台 issue ↔ 本地镜像，PR 为交付物）；状态流：待指派 → 执行中 → 待复测 → 已完成（打回旁路）；
2. **工单执行会话 = 对话形态的"工人记录"**：每个 (issue, worker) 一次执行=一个专用会话（worker 的对话+轨迹+指标），RW 现有 runAgent/驱动器/子代理机制即其引擎（附 D 工单模式）；
3. **普通对话 = 直接模式**：讨论/即兴/研究仍即时可用，可"转成 issue"再派工。
用户视角界面（原型 `prototype/code-shell-workbench-v1.html`）：总览（脉搏+待指派队列）/ Issue 工单（左列表+中执行流+复测放行/打回）/ Worker 观测榜 / 对话 四视图。

**评测口径（重要修正）**：**不做同任务 A/B 双跑**；采用**观测式评测**——你按 issue 指派不同 worker（任务自然不同），平台自动按 (worker × 难度档) 归集指标：
- 指标集：任务数 / 一次通过率（复测一次过占比）/ 打回 bug 数（每次打回留 bug 原因，自动回流）/ 中位执行时长 / 平均 token / 平均成本 / 自测通过率；
- 难度归一化提示：初期以任务规模估档（小/中/大：验收条数、估时、涉面）粗归一，界面显式标注"观测数据、任务各异、非严格对照、置信度随样本增长"；
- 产出：**code 壳模型选型榜**（可反哺指派建议与默认路由），但**最终派给谁永远由用户下令**（C4 精神延伸：人不被自动路由绑架）。

**承接关系**：该榜即待办⑤"模型测评"在 code 壳的首个落地形态（观测式而非对照式）；issue 源与桥接件对齐 hello 合并基线 P1（issue 单向同步经验可复用）；"指派 worker"由用户操作，worker 名单=壳内模型白名单（可含各厂商 code 档模型）。

**E1–E3 用户拍板（2026-09-08）**：
- E1 ✅ issue 真相源 = **GitHub 远程 issue（MCP github 已接）**，本地镜像缓存；
- E2 ✅ 复测收口 = UI 放行/打回 + 验收钩子自动初筛；**打回必填 bug 原因**（强制归因字段，自动回流模型观测）；
- E3 ✅ 并行粒度 = **每 issue 一个执行模型**；大 issue 拆**子 issue**（父子树），子 issue 各自指派执行模型。

**词汇修订（用户反馈 2026-09-08）**："worker" 用词过低 → 统一改称 **执行模型**；"Worker 观测榜" → **模型观测**（含图表/看板需求，见附 F）。

## 附 F：code 壳信息架构（IA）提案 v0.1（2026-09-08，针对用户 E4 迷思的重构）

### F.1 用户迷思的根因
"总览应该直接是对话页"与"总览=项目脉搏"两个直觉打架，根因=**把"页面"当容器，而没有区分"恒定导航骨架"与"可变中央焦点"**。885 搁置的根因同理：项目→需求→任务是**数据分解树**（传统开发逻辑），而 RW 是**对话驱动的执行体**——两者不是两套页面，而是同一棵树上"讨论/执行"两种动作。

### F.2 提案骨架：恒定三栏 + 中央三焦点（对象化 IA）
```
┌ 左栏·世界（恒定）───────────────┬ 中央·焦点（随对象变）──────────┬ 右栏·焦点之影（随中央变）───┐
│ ① 导航树：                      │ A 焦点=对话/文档讨论            │ · 对话焦点：总结/决策记录/  │
│   项目P1(仓库+知识)             │   （与 RW 直接聊，如同此刻）    │   相关 issue/待确认        │
│   ├ 需求 E1(父issue/文档+验收)  │ B 焦点=Issue 执行              │ · Issue 焦点：验收/指标/   │
│   │   ├ 任务 #101（执行中-GLM） │   （执行流 + 与执行模型对话）   │   相关文档/子 issue/复测    │
│   │   ├ 任务 #102（待复测）     │ C 焦点=需求/项目文档            │ · 需求焦点：验收/拆解/     │
│   │   └ 任务 #103（子任务…）    │   （需求文档+验收+讨论沉淀）    │   关联任务/决策            │
│ ② 我的待办（跨项目汇总）         │                                │                            │
│ ③ 最近对话/执行会话列表          │ 底部输入随焦点变化：            │                            │
│ 顶部：壳切换+模型观测入口        │  A=对 RW 说；B=对该执行模型说； │                            │
│                                 │  C=围绕该需求讨论              │                            │
└─────────────────────────────┴───────────────────────────────┴────────────────────────────┘
```
- **化解"总览 vs 对话"矛盾**：不再有"总览页"；登录落点=**我的待办+最近焦点**（自动恢复上次中央焦点）。左栏导航恒定，中央想聊就聊、想派工就派工。
- **数据树保留传统分解，但节点上挂的是"动作"而非"文档流"**：项目=仓库+AGENTS+项目知识（已有 project 机制）；需求=父 issue 或需求文档（含验收，讨论沉淀回文档，hello requirements.disc 语义）；任务=GitHub issue（可拆子 issue 树）；执行=每个叶子 issue 绑定一个执行会话（一个执行模型）。
- **885 经验的落点**：hello 的"项目→需求→任务"对应导航树第①层；它的待复测/待确认/资源支持三 tab=左栏"我的待办"；晨报=待办聚合推送（合并基线 P0 已有定义，本壳首日可配）。

### F.3 执行会话=可交互会话（回答用户"要不要底层支撑"）
- **要，且已具备**：执行会话复用 runAgent 全栈——SSE 流式（正文/思考增量）、轨迹卡、停止、审批/问询卡、断点恢复（agent_runs）、消息持久化、用量记账。与 880 普通对话**同一渲染与机制**，区别只在绑定 (issue, 执行模型) 与注入验收契约。
- "右边窗口下方与执行模型对话"=向该执行会话**插入用户消息**：模型下一轮携带现场继续（DB 消息+断点），不会丢、不会忘（压缩/折叠有摘要兜底）；执行中打断=停止/插话语义，驱动器无人值守时=need_input 排队（现成）。
- 因此中央焦点 B 的输入框语义="对该执行模型说"，与焦点 A"对 RW 说"唯一区别是消息目标会话不同——底层同一套。

### F.4 词汇（定稿建议）
执行模型（原 worker）/ 模型观测（原观测榜，带图表看板：通过率趋势、bug 数、时长分布、token、成本，按 模型×难度档×时间 可下钻）/ 复测放行·打回（必填原因）/ 子 issue / 我的待办。

### F.5 数据映射（复用为主，增量最小）
项目=仓库目录+AGENTS（现有）；需求=父 issue/文档（GitHub 父子 issue+labels 或需求文档表，待定）；任务=GitHub issue 镜像表（新增 issues 缓存表，MCP github 同步）；执行会话=conversations 加 issue_id+kind=exec（增量列）；复测记录=reviews 表（issue_id, 结果, bug 原因, 放行人）；模型观测=model_telemetry（由 usage/tool_calls/复测事件聚合，视图+图表 API）；我的待办=视图聚合（待指派/待复测/待确认）。

### F.6 开放确认点（原型 v2 前需拍板）
1. 登录落点：直接恢复"我的待办+上次焦点"，无独立首页——认可？
2. 需求载体：父 issue（全 GitHub）还是需求文档（仓库内 md+验收）与 issue 并行？（885 遗产是文档式需求）
3. 中央焦点切换规则：左树点项目→右栏=项目概览卡+中区保持；点需求→焦点 C；点 issue→焦点 B；新对话→焦点 A——认可？

5. 确认后出原型 v2（在 v1 基础上按 F.2 重构三栏与焦点）。

### F.7 用户对 F.2 的否决与修订方向（2026-09-08，F.2 作废，以本节为准）
- **否决点**：F.2 把"项目/需求/任务 + 对话 + 待办"都塞进一根左栏导航树——在规模场景（8 项目/200 需求/1500 任务、每个对话产生多条待确认）必然乱套；且"待办"混同了"结构性任务"与"时间性行动项"。
- **修订：四空间分离**
  1. **对象空间**：项目=一个仓库（GitHub repo）；每项目有自己的 issue 列表；issue=工单（模型按工单要求执行代码，git 内不需要挂文档流转）；需求文档/技术文档是**项目仓库内的文档**，issue 可"关联"它们，但执行面只读工单（用户定调，2026-09-08）；
  2. **会话空间**：对话是线程——分两类：与 RW 的讨论（可挂需求/文档上下文或独立）、与执行模型的执行会话（绑定 issue，全 runAgent 底层可插话）；各自独立成列表，不混入对象树；
  3. **待办空间**：**你的行动队列**（待你指派/待你复测/待你确认），跨对象聚合、处理即消失；来源含对话中未当场答复的 ask/审批（无人值守→need_input 排队）与打回裁决——"对话里待我确认"是待办的一种；任务出 bug=issue 回执行队列（重新指派/换执行模型），若需你裁决同时生成一条待确认；
