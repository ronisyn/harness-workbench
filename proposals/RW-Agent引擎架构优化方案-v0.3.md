## §0 目标与里程碑（v0.3 定稿版）

### 0.1 总目标（一句话）

把现在的 RW 从"与我们平台绑死的单体应用"，改造成**一个能独立运行、能按声明装配、能被别的系统调用、并且能持续自我演进的 Agent 引擎**——它是未来一切上层形态（岗位、行业包、对外接入）的共同底座。

### 0.2 五个目标（产物属性，各自可验收、互不重叠）

| # | 目标 | 含义 | 出口 |
|---|---|---|---|
| **G1** | **可独立运行** | 环境无关：不依赖我们的目录/数据库/账号；存储、模型、沙箱**可替换** | 干净机器 + 一份配置 → 跑通一次对话 + 一次工具调用 |
| **G2** | **可装配** | 增删工具/插件/MCP/技能/连接器**不改引擎代码**（声明式装载） | 装一个新工具 + 一个外部 MCP 后工具面正确；卸载后立即消失 |
| **G3** | **成本结构可控** | 上下文只追加、增量极小、失效可数；信息不丢（溢出可回查） | 达到 **C1–C4**（见 0.3） |
| **G4** | **可演进** | 会话与存储格式带版本与迁移链；旧账按新架构**逐项过账**，不留两套 | 模拟一次版本升级不丢数据；过账清单闭环 |
| **G5** | **可交互** | 对外暴露完整交互契约：**可观测 · 可控制 · 可信 · 跨端语义一致** | 任一客户端仅靠事件流可重建全过程；能停、能续、能审、能回滚 |

> **G5 的边界（重要）**：只含**引擎交互契约**（事件语义、停止/恢复、审批/问询、进度与计划、溢出提示、成本可见）。**不含**布局/动效/组件库/皮肤——那是产品面。
> **明确不做"像素级对标 DS/CD"**：① 它们的界面是为"开发者单机编码"优化的，RW 面对业务人员与运营者；② "接近"无法验收，会变成无止境美术工程；③ 该学的是**交互契约**而非皮肤（清单见 §2.5）。

### 0.3 成本指标 C1–C5（**改名说明**：原 M1–M4 与里程碑 M1–M3 撞名，统一改称 C 系列）

| # | 指标 | 定义 | 目标 | **基线（2026-09-15 实测）** |
|---|---|---|---|---|
| **C1** | 会话整体命中率 | 缓存读 tokens ÷（缓存读 + 未命中） | 长会话 **≥99%**（DS 实测 99.72%，§2.1） | **11.30%**（deepseek 全量 n=2591）／**25.31%**（近 7 天） |
| **C2** | 每轮新增未命中 tokens | 单轮真正新增的 prompt tokens | 中位 **≤1k**，P95 **≤5k** | **中位 22,142**、P95 87,936（7 天 n=900）；全量中位 35,996 |
| **C3** | 单位任务成本 | 同类任务总成本 | 比基线 **↓≥50%**（目标值已可定：见下方基线） | **每 run ¥2.89**（67 runs）· **每会话 ¥4.34**（59）· **累计 ¥255.88** |
| **C4** | **非预期失效次数** ⭐ | 每个任务中"整段前缀作废"的次数（**不含**首轮、切模型、折叠边界、长空闲、工具面变更） | **目标 0**；每次失效必须能说出触发原因 | **近似 47 次**（整段作废候选：命中=0 且未命中>5000） |
| **C5** | 豁免失效（**只报数、不设 0**） | 长空闲后首次请求 · 工具面变更（新段首轮）· 切模型 · 折叠边界 | 如实上报并可归因 | 待专项统计 |

> **基线来源与有效性**：`usage_stats` 全量 2760 行（2,744 轮），窗口 2026-09-04~09-15；**缓存字段零空值**，两厂商均上报（deepseek 2,591 轮命中 11.30%、glm 153 轮命中 58.58%——glm 的高命中证明"网关取不到命中"不是成因）。成本高度集中：**会话 184/185/393 三个长会话占 ¥238/¥255.9（93%）**，其中会话 393 每轮 miss 120k／prompt 124k ≈ 每轮全量重算。
> **潜在收益**：现状输入成本 ≈ ¥242（命中 1.5M + 未命中 104.6M）；若达到 99% 命中 ≈ ¥13 → **输入成本降约 95%**，整体成本预计 ¥256 → ¥27 上下。

> **为什么 C4 才是关键**：命中率的分母是累计上下文，天然就高，会掩盖真正的浪费。DS 实测：**99.72% 的命中率里，0.28% 的未命中高度集中——最大 12 次请求占了全部未命中的 41.4%**。所以真正要工程化的是"**零非预期失效 + 增量最小化**"；RW 现状则是"命中率低 + 增量巨大"，两者都要治。

### 0.4 三个里程碑（含出口标准）

| 里程碑 | 内容 | 出口标准 |
|---|---|---|
| **M1 目标达成** | G1–G5 全部达成 | 干净机器一份配置跑通；装工具/MCP 不改代码；C1–C4 达标；引擎自带自检全绿；任一客户端仅靠事件流可重建全过程 |
| **M2 可交付 · 可调用** | 对外形态（headless → MCP server → JSON-RPC）**＋ 客户内网可装可用** | 外部程序 headless 调用拿到结构化结果；被别的 agent 当 MCP 工具调用成功一次；客户形态机器（无外网 + Windows Server）用自助安装包装上、自检通过、账本可导出 |
| **M3 可自进化** | 三源输入 → 提案 → 人工审批 → 分批落地 → 指标回归 | 连续两个周期产出并落地提案，其中 **≥1 条来自外部对标、≥1 条来自自我体检**；每条附前后指标对比；**全程无自我放行** |

**M3 的三源输入**：① **外部对标**（DS/CD 等实现变化与行业新做法 → 逐条判"适配性"，理由见 §2.6）；② **自我体检**（C4 失效事件、C2 增量、成本结构、失败率、回归结果、质量指标）；③ **业务反馈**（岗位实际绩效与痛点）。

**M3 的优先级判据**（防"自我表演"）：① 能减少 C4 失效 / 降成本 ② 能提高交付速度 ③ 能减少人工介入 —— **三者优先于"加新功能"**。

**M3 的准入前置（硬条件）**：**金标回归 + 失效监控（C4）必须在位**，否则自进化=盲改。

**M3 的三个风险**：① 自我表演（对策=优先级判据 + 前后指标对比）；② 自我放行（对策=产出的是**提案**，改自己代码仍需人工审批，铁律不松）；③ 成本失控（对策=预算护栏 + 计入账本）。

### 0.5 收敛原则（替代"现有功能不回退"）

一律按新架构标准重新判定，三分法 + 逐项过账：

| 判定 | 含义 | 处置 |
|---|---|---|
| **保留** | 已在正确的面上、通过注册表暴露、结果处理合规 | 原样保留 |
| **改造** | 能力对，但位置或实现方式错（典型：大结果整包灌进上下文） | 就地改造 |
| **重写/删除** | 能力以"临时写在循环里的代码"存在，且新架构下有正规载体 | 迁到正确载体后删除旧实现 |

判据与实例见 §6.1。目的：**干净、高效、智能、完善**——旧账要么并入新架构，要么删掉，**不留两套**。

### 0.6 明确不做（防止范围蔓延）

1. 不做岗位包设计（定义书、职责矩阵、SOP 模板）——另有专项。
2. 不做组织协作、验收签字、日报呈现、报价结算——属产品/平台层。
3. 不做原生 iOS/Android App（端侧走响应式网页 + 飞书/企微，见 §5）。
4. 不追求"通用编码 agent 最强"——定位是**可控、可交付、可装配的业务型引擎**。
5. 不做"像素级对标 DS/CD"（见 0.2 的 G5 边界）。
6. 不推倒重写成熟机制（主循环、护栏、账本、审计、金标评测**保留**，只做解耦与抽象）。

**成本结构的三处硬伤（直接决定 C1–C4）**：
1. **原地改写前缀**：`archiveEarlyContext` 就地改写早期 tool/assistant 内容；`maybeCollapseEarly` splice 掉早期区间 → **周期性全量失效**。

## §2 参考基线（DS / CD）

### 2.1 DS 缓存机制实测：**本会话 99.72%**（2026-09-15 读会话日志实算）

分析对象 = 本对话所在会话（`~/.dsh/sessions/--E-projects-harness-workbench--/session-06dd48a6…`；17606 条事件、83 个 zstd 帧、压缩 11MB / 展开 52MB）。

| 项目 | 数值 |
|---|---|
| 逐次尝试数 | 3,032 |
| 命中（缓存读）tokens | **1,340,696,704** |
| 未命中（新增）tokens | **3,819,230** |
| 输出 tokens | 2,499,331 |
| **整体命中率** | **99.72%** |
| 单次请求命中率 | 中位 **99.94%**、P90 **99.98%**；≥99% 的请求 2772/3030 |
| 平均每次 prompt | **443,486 tokens** |
| 未命中占比 | **0.28%**，其中**最大 12 次请求占 41.4%** |

**成本换算**（deepseek 三档价：命中 0.086 / 未命中 2.3 / 输出 8.0 元每百万）：实际输入成本 ≈ **¥124**；若不缓存 ≈ **¥3,092** → **缓存省掉约 96% 的输入成本（≈¥2,970）**。

### 2.2 为什么能做到：五条机制（每条带证据）

1. **会话 = 只追加事件日志，模型输入 = 它的确定性投影**。文档原文："追加的条目保留可复用前缀；`replace` 会从首条被遮蔽消息起使缓存复用失效。" → **只追加 = 前缀永不变**。
2. **系统提示是受保护的第 0 号节点，一个会话只写一次**。证据：17606 条事件里 `system/message` **只有 4 次**（开场 2 + 中途 2）；预设"在首个请求之前组装一次，运行期不再重读"；子代理声明"只写入第一份运行时上下文快照一次"。
3. **系统提示变更不原地改，而是追加进历史之后**：中途的 `request/context` 带 **`systemPromptUpdate: "in-history"`**。文档原文："原地替换系统节点会使请求从该节点第一个 token 起不同……而 `in-history` 时，变更追加到已缓存历史之后，直到历史末尾的前缀仍可复用。" **这是最值钱的一条设计。**
4. **工具 schema 逐字节稳定**。证据：前 6 次请求头（横跨 seq 12→16673，约 1.6 万条事件）40 个工具的 schema 哈希**完全相同**；仅一次 40→73 变化，**那一次付出 574,865 tokens 全量未命中**（全 session 最大单笔）。
5. **让增量尽可能小 + 全程计量**：每轮真实新增中位仅数百至两千 token（大结果走溢出）；每次尝试记录 `inputTokens / cacheReadTokens / outputTokens`，随时可查"贵在哪"。

**外加一条工程纪律**：DS 的**每个包 README 都有强制的「KV Cache 影响」小节**（grep 到上百处），写明"仅追加 / 不触前缀 / 从首条被遮蔽消息起失效"。**缓存影响是一等公民契约，不是事后优化。**

### 2.3 什么时候会掉（四类失效，带数据）

| 触发 | 实测数据 | 教训 |
|---|---|---|
| 会话首次请求 | 必 0% | 无法避免 |
| **切模型** | seq 17460/17472：未命中 265,449 / 272,548，命中 **0** | **换模型 = 缓存彻底作废**（跨模型不共享前缀） |
| 长空闲 | 492 分间隔 → 未命中 574,865；而 6~39 分空闲**未掉**（39 分仍命中 208,896） | 缓存有有效期；小时级空闲必然重算 |
| 工具/schema 变更 | 40→73 工具 → 未命中 574,865 | **中途改工具面是最贵的操作** |
| 折叠边界 | 5 次折叠后命中率降至 **73.7%~84%**，1~3 次请求内回到 99% | 折叠不可避免，但必须**少而整** |
| 其他部分失效 | seq1331（间隔 17 分）：未命中 222,954 且命中 129,280（部分前缀仍在） | 存在**部分失效**，触发点未逐一确认——登记待查 |

### 2.5 交互契约清单（G5 的依据，带来源包）

| 契约 | 来源 | 对 RW 的价值 |
|---|---|---|
| 逐次请求用量/耗时/输入输出可查 | `dsh-client-ui-trajectory` | 用户自己看到"贵在哪" |
| 计划 / 待办 / 作业 / 子代理 / 工作流 各有专属视图 | `client-ui-plan`·`-todo`·`-jobs`·`-subagent`·`-workflow-run` | 长任务"看得见在干什么" |
| 审批与提问是**协议一等事件** | `client-ui-approval`、`client-ui-user-questions`、CD approval flows | 对外调用也能异步审批 |
| "我们省略了什么"提示 | `dsh-output-retention` | 溢出后用户知道信息去哪了 |
| 溢出文件路径直接给出 | `dsh-spill-policy` | 用户可自行回查 |
| 交付物卡片 | `dsh-client-ui-deliverables` | 产物可点开 |
| 会话可查询/导出/回放 | `session-query`、`session-log-export` | 审计与交接 |
| headless / JSON-RPC 同一内核 | CD `codex exec`、`app-server` | 外部集成入口 |

**RW 已有**：工具直播、审批卡、问询卡、计划清单、断点恢复、审计跳转、假完成拦截、成本透出 → G5 是"补齐 + 契约化 + 跨端统一"。

### 2.6 不照搬的两件事（诚实登记）

1. **DS 的复杂度不匹配**：近两百个包 + 依赖注入心智负担，对 RW 当前团队规模过重 → 取"分家方式"，不取"包数量"。
2. **CD 的编译期强制在 JS 里打折**：Rust 的 crate 边界由编译器强制；我们只能用**不变式 + 测试 + 静态检查**模拟 → 因此骨架里的"不变式"必须配 CI 门禁，不能只写在文档里。

## §4 逐面目标设计

### 4.1 运行面（P0 地基）
提示词/工具集/模型/存储/工作区**全部外部注入**；存储走接口；单进程可启动；有版本号与变更说明。→ 验收 G1。

### 4.2 扩展面（P0→P1）
三层分离（契约 / 注册表 / 执行后端）；声明式装载；审批声明化；MCP 双向；连接器=带凭证的执行后端。→ 验收 G2。

### 4.3 能力面
| 部件 | 目标 |
|---|---|
| 模型网关 | 模型能力声明（窗口/工具/视觉/思考）+ 可切云端/客户网关/内网推理 + 断网降级 |
| 执行后端 | 可替换后端；Linux + Windows Server 双平台 |
| 记忆 | **全文检索（FTS5）打底 + 分层召回 + 受限自动沉淀；向量留接口位置后补**（口径以《RW-Agent 架构》§5.6 为准；本行原写"语义检索"，系旧措辞，2026-09-15 随架构自审批同步） |
| 技能 | 打包与版本化，随能力包声明 |

### 4.4 上下文面（成本总开关）
可配置注入；**输出溢出**（预览 + 路径 + 摘要）；溢出文件的权限与保留期；**确定性投影**。

#### 4.4.1 成本与缓存的五条架构规则（由 §2 实测反推，缺一不可）

1. **只追加**：禁止中途改写早期消息（现状 `archiveEarlyContext`/`maybeCollapseEarly` 要改）；折叠只在**段边界整段替换一次**。
2. **前缀冻结**：系统提示会话内不变；技能/知识/目标/时间/快照一律进"**尾巴区**"；确需变更时**追加为 in-history 节点**。
3. **工具面会话内冻结**：工具数组定版后不变；MCP 动态装载 / 改档位 / 换壳 = **新段**，并明确提示"本次变更会重建缓存"。
4. **增量最小化**：大结果一律溢出；给"每轮新增"设阈值并监控。
5. **失效可数**：C4 作为一等观测指标；**任何进入请求前缀的组件都必须声明其缓存影响**（学 DS 的强制小节），并入不变式检查。

### 4.5 编排面
主循环**保留**；补成批编排；定义触发器接口（手动/定时/外部调用/事件），实现归使用方。

### 4.6 保障面
| 部件 | 目标 |
|---|---|
| 权限与审批 | 四档保留 + 声明化；对外调用**必须异步** |
| 沙箱 | 服务 + 按平台后端；**失败语义以《RW-Agent 架构》RD-05/RD-15 为准**：第 2 层（引擎自带沙箱）拿不到模式 → **拒绝启动**；第 1/3/4 层能力缺失 → **显式降级**（留痕 + 提高审批 + 客户可见，禁止静默降级）；降级程度逐次上报 `enforcement: full/partial/none`。（2026-09-15 随架构自审批修订：原"分级：强制/尽力/无"被替换，因其判据不可判定） |
| 凭证 | **新增**：客户系统凭证的存放、引用、轮换 |
| 状态恢复 | 保留断点恢复与快照；补"重启自愈" |
| 预算与审计 | **本地兜底**：无外网/无平台侧时自落账并支持离线导出（默认开启） |

### 4.7 接入面（含 G5 交互契约）
- 对内：现有 HTTP/SSE 保留，补成**成文的事件契约**（事件类型/语义/版本）。
- 对外：**headless → MCP server → JSON-RPC**；一个内核 + 多适配器。
- 交互契约四要素：**可观测**（思考/工具/进度/计划/成本逐步可见）、**可控制**（停/挂/续、断线重连不丢现场）、**可信**（失败如实、危险必拦、可回滚、成本可见）、**跨端一致**（GUI/飞书/API 同一套语义）。

### 4.8 横切 A 可观测与评测
账本**落账在引擎、对账在平台**（口径见《RW-Agent 架构》§2 横切 A）；金标回归**随引擎打包**（M3 准入前置）；评测结果可导出；**新增 C1–C5 仪表**。

### 4.9 横切 B 声明式装载与版本
统一清单规范；**会话与存储格式带版本号与迁移链**；升级与回滚有据可依。

## §6 边界铁律与收敛原则

### 6.1 现有功能收敛原则（含用户点名实例）

判定三分法（§0.5）+ **逐项过账**。**实例：Excel**
- **事实核对**（2026-09-11 读码）：Excel **已经是工具**（`extract_xlsx`，`server/tools/extract.js`），不是"写在 agent 里的代码"。
- **真正的问题在结果处理**：工具返回整表文本（上限 20000 字符），进上下文后被裁到 4000 字符（头 2400 + 尾 1200）——**中间数据丢了，token 照样烧**。
- **处置**：**改造**（判定=位置/实现方式错）→ 只返回"结构摘要 + 行列信息 + 溢出文件路径"，需要明细时按范围二次取数。
- **通则**：**任何"大结果"工具都必须遵守溢出规范**，否则不算符合新架构。

### 6.2 边界铁律（引擎 / 平台 / 产品）

| 归属 | 管什么 | 不该出现 |
|---|---|---|
| **引擎** | 循环、上下文、模型接入、工具注册表与执行后端、记忆与技能、权限沙箱凭证、状态恢复、账本与审计、装载与版本、接入面与交互契约 | 模型广场页、壳的运营配置、定价 |
| **平台**（车间与管理台） | 造包、发版、样例运行、可选管理与汇总、行业知识与模板资产 | 引擎运行时逻辑 |
| **产品/交付** | 岗位定义、组织与职责、验收与签字、安装与培训、报价 | 引擎内部机制 |

**铁律：引擎里不允许出现任何平台专属的东西（路径、库名、账号、页面）。**

## 附录 · 术语表（完整版，v0.3 首次完整打印）

| 术语 | 定义 |
|---|---|
| **引擎** | 本文件的对象：能独立运行、能被装配、能被调用、能自我演进的 Agent 内核 |
| **骨架** | 让各面可替换/可声明/可演进的基础机制：服务注册与替换、契约与协议、声明式配置、不变式、确定性与可重放 |
| **面** | 引擎的功能分区：接入面、编排面、上下文面、扩展面、能力面、保障面、运行面（七面）；另有两条横切（可观测与评测、声明式装载与版本） |
| **工具** | 给模型看的**接口契约**（名称/参数/说明/权限与缓存影响声明） |
| **执行后端** | 真正干活的东西（文件/命令/沙箱/网络/数据库/远端服务），可替换 |
| **插件** | 可装卸的能力包：带声明（依赖/版本/权限/凭证需求/工具面/卸载方式/缓存影响） |
| **MCP** | 标准协议通道：既能把外部服务接成工具，也能把引擎暴露给别的 agent（双向） |
| **连接器** | 带客户凭证的业务系统后端（ERP/电商/数据库）；MCP 或插件是其实现方式 |
| **能力包** | 引擎级可装载单元（工具 + 后端 + 声明 + 可选 UI）的总称 |
| **溢出（spill）** | 大结果落盘，上下文只留"预览 + 路径 + 摘要"，需要时二次取数 |
| **确定性投影** | 同一会话任一时刻投影出的上下文一致（可重放）；缓存与复现的前提 |
| **前缀冻结** | 会话内不改动已发出内容的前缀；变更一律追加到尾部或作为 in-history 节点 |
| **in-history 追加** | 需更新系统提示时，不改第 0 号节点，而把新提示作为新的系统消息追加在已缓存历史之后 |
| **失效事件（C4）** | 一次请求中"整段前缀作废"的事件；**不含**首轮、切模型、折叠边界 |
| **收敛过账** | 对既有功能逐项判定"保留/改造/重写删除"并登记处置的流程 |
| **岗位** | 产品层概念（另有专项）：入驻客户系统、有身份与职责的数字员工；不在本文件范围内 |
