## 1. 现状盘点（事实层，文件:行）

### 1.1 服务器 LLM 调用三种形态
| 形态 | 位置 | 用途 | 超时语义 |
|---|---|---|---|
| `chatOnceWithTools`（非流，`stream:false`） | gateway.js:128-167；agent.js:372 每轮调用 | **全部对话**（问答+任务都走 runAgent 轮环） | `AbortSignal.timeout(p.timeoutMs||90000)`（GLM 180s 总时限） |
| `chatOnce`（非流） | gateway.js:42-57 | 折叠摘要（agent.js:306）、自动续写（agent.js:404）、子任务小调用（tools/index.js:885） | 同上 |
| `chatStream`（真流，async generator） | gateway.js:60-125 | **无任何调用点（死代码）** | 首字节 `min(60s, timeoutMs/3)` + 空闲 `timeoutMs||120s` |

### 1.2 服务器→前端 SSE 通路（index.js:477-644）
- 事件协议：`thinking(agent_thinking)/think/tool_start/tool_done/plan/approval/ask/delta/done/stopped/error` + 15s 心跳（O-8）。
- **delta 仅在整轮结束**后由 index.js:599-603 按 8 字符块模拟发出；注释自述"真实逐字流式对工具模式不适用；分块保持近实时体验"。
- **think 每轮结束后整块**发出（agent.js:388 `if (res.reasoning) emitEv(... {type:'think', text: res.reasoning})`）——一轮 2 万字符思考是一次事件，期间黑盒。

### 1.3 会话活动事件环（旁观/断连兜底，agent.js:14-58）
- `emitEv` 同时写内存环（ACT_MAX 300 条）+ 直发 emit；**已内置 think 增量合并规则**（同轮 3s 内拼接、单条 ≤1800 字符，agent.js:26-34）→ 说明"增量 think"是代码预设形态，只等上游供给。
- `activitySince` 轮询 + `run_end` 回收；前端 Chat.jsx:523 轮询兜底。

### 1.4 前端（Chat.jsx）
- `streamChat` 回调齐全：`onDelta`（拼气泡正文）、`onThink`（增量拼思考区，可折叠灰字）、`onThinking`（思考中指示）、`onToolStart/onToolDone`（工具卡）、`onPlan/onApproval/onAsk/onDone/onError`（Chat.jsx:408-464）。
- 即：**前端早已按"增量流"写好**，缺的只是服务端真正喂增量。

### 1.5 子代理（subagent.js:39-49 childEmit）
- 父代理 emit 事件统一加"子:"前缀透传；不感知内外层传输方式 → 内层改流对子代理透明。

### 1.6 渠道/驱动
- driver.js:146 / wechat.js:67 / feishu-webhook.js:94 均 `runAgent(...)` 后取**最终 content** 回包；无 SSE 消费者、无 thinking 展示需求 → 内层流式对它们语义不变（仍等流结束后得全文）。

### 1.7 MCP（mcp.js）
- 工具是轮内同步 JSON-RPC 调用（execTool 转发），与 LLM 传输协议无关 → 不受流式改造影响。

### 1.8 护栏/计量（agent.js:355-440）
- 每轮判定（工具调用 vs 最终回答）、B6/B6b 假完成打回、自动续写、折叠、usage 三档计量、快照注入——全部基于"整轮完整响应"（`res.toolCalls/res.content/res.reasoning/res.usage/res.finishReason`）。

## 3. 流式的利弊、流派对比、类型适配

### 3.1 流式的"得"
1. 思考过程实时可见（GLM 想 3 分钟 = 看它想 3 分钟，不再黑盒）——解决"没反应"体感；
2. 取消"总时长"概念 → 空闲看门狗（N 秒无字节才判死），**180s/300s 旋钮消失**，与 CLI 同构；
3. 最终正文真流（去掉 8 字假分块）。

### 3.2 流式的"失/成本"
1. **工具轮中间正文语义**：模型可能在输出半句正文后突转 tool_calls——这段正文是"过程的旁白"，不是答案；显示会误导、丢弃又可惜（CLI 惯例：灰字注释行或丢弃）；
2. **tool_calls 碎片累积**：增量 JSON 参数跨块、多工具并发调用，解析复杂 + 厂商差异（→ 回退通道兜底）；
3. **事件量放大**：2 万字符思考逐字推 = 上万事件 → SSE/活动环压力（→ 节流块，非逐字）；
4. **取消透传**：停止/断连必须掐内层 fetch（现状缺口 C3，需实现）；
5. **流式 usage 帧依赖**：计量需流末 usage（有捕获，需兜底）。

### 3.3 有没有更好的办法？——三种流派对比（本分析的核心决策点）

| 流派 | 做法 | 优点 | 代价 | 代表 |
|---|---|---|---|---|
| **A 全流式** | 每轮（含工具轮）都流式；工具轮中间正文作灰字/注释或丢弃 | 最正统、思考全程可见、无任何总时限 | 与现有 B6/B6b 打回/事件协议冲突面最大；tool_calls 累积与多厂商差异全暴露；改动最大 | OpenAI/Anthropic 系 CLI 的形态 |
| **B 折衷（推荐候选）** | **工具轮保持一次性**（快、稳、无中间正文问题）；**无工具/最终轮流式真流**；思考用"节流块"实时可见 | 改动面小；保留现有护栏/打回/计量逻辑；解决两个核心痛点（黑盒、假流式）；回退通道天然存在（工具轮本就不流） | 工具轮内仍等待（但每轮有思考块在动，非黑盒）；非 100% CLI 同构 | 多数"工具型"产品实际折衷形态 |
| **C 现状增强** | 不改传输；仅加失败留痕(②)+空答兜底(③)+"思考中 N 秒"心跳提示 | 改动最小、最稳 | 未兑现流式承诺；假流式仍在；超时旋钮仍可能误杀 | 兜底路线 |

> 备注：reasoning 不必逐字全量。成熟 CLI 也常把思考折叠/隐藏；"节流块 + 可折叠"（前端已支持）即接近 CLI 体验，且事件量可控。

### 3.4 什么类型适合流式 / 适合一次性（适配矩阵）
| 对话/调用类型 | 建议 | 理由 |
|---|---|---|
| Web 主对话·最终问答/长报告/长代码输出 | **流式** | 感知延迟最低；思考可见 |
| Web 主对话·工具密集轮（每轮产出 tool_calls JSON、正文常空） | **一次性** | 无正文可流；JSON 完整即可；避免碎片累积 |
| 折叠摘要 / 自动续写 / 自动标题 / 内部小调用 | **一次性** | 无 UI 消费者；短输出 |
| 渠道回包（微信/飞书/驱动/定时任务） | **一次性** | 无流媒体通道，发最终消息；思考无展示面 |
| 子代理（事件透传给父界面） | 随父形态（流/一次性均可透传） | childEmit 已解耦 |

结论倾向：**流派 B 增强**（工具轮一次性 + 最终真流 + 思考节流块 + ②③），既兑现"流式"承诺与 CLI 对齐，又把冲突面（C1-C6）压到最小。流派 A 作为远期方向记录。

## 4. 开发方案草案（定案后才执行）

### 4.0 决策点（等用户拍板）
- **D1 流派**：A 全流式 / B 折衷（推荐）/ C 现状增强

### 结论
- 🔴 必须作为 A 强制前置（否则必出 CDEFG）：**A5 中止透传、B1 usage 矩阵+兜底、C2 碎片解析+回退**；🟠 需同时排期：A1/A2 替换语义、A7 合帧、C1 旁白不入史、A8 消息状态机。
- **B（工具轮一次性）天然规避 A 组绝大部分与 B1/C2/C1**——这正是 B 风险低一个量级的原因；A 的增量风险几乎全部集中在"工具轮流式"这一环。
- 若定案 A：建议实施顺序 = 先落 B 骨架（协议/合帧/前端灰字区/②③④）→ 再单开"工具轮流式"子批（A5/B1/C2 前置）→ 逐项自测矩阵（含 10 厂商 include_usage 实测、tool_calls 三形态单测、断连压测）。
