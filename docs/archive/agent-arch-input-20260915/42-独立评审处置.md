## 0. 总结论（三句话）

1. **架构的"词汇"和"纪律"在水准之上**：数据出口生效、能力单调不增、申请权与执行权分离、四道失效独立的闸、fail-closed 纪律、术语消歧——这些是真的硬。
2. **但两个结构性硬伤**：**① 平台运营方的权力没有被机制限制**（只靠合同与审计）；**② 首版范围严重过宽**（为"平台公司"设计，不是为"一个开发者 + 第一个客户"）。
3. **最刺眼的反缺口**：**两条真实需求（R2 岗位分期、R12 移动端/脱离本机）0 行落点，而岗位库治理有 336 行。**

## 1. ⭐ 三个架构级 P0（已处置）

### P0-1 · 平台运营方同时掌握"推送权"和"审批权"

**发现**：`01` §3.1 明确 KMS 隔离**优先级下调**（平台持钥）；`33` §4.3 平台级知识**只有运营方写、客户只读**；而解锁受信执行器的**审批中心在控制面**。→ **读和写两条路都通，全程不需要客户参与。**

**判定：成立，且是最严重的一处。** 它让"客户的生产系统只有人能改"变成"只有**平台**能改"。

**处置（已落 `06` §0.1）**：四条缺一不可——① 审批中心落**数据面**；② **审批人必须是客户身份**，平台运营方永不出现在客户的审批链里；③ 运营方的运维动作**在客户审计流里可见**；④ 平台级知识/技能/插件的写权限归**客户技术团队**（平台可提供，**不能单方面推送生效**，已改 `33` §4.3）。

### P0-2 · 模型网关属于哪个面（未定义）

**发现**：`architecture` §4.1 与 `30` §1 都说网关是"唯一出口、三个 agent 共用"，**但从未声明它属于控制面还是数据面**。混合部署承诺"数据不出内网"，**网关若在控制面，每次推理的完整业务上下文都出境**。

**判定：成立，架构级阻塞项。**

**处置（已落 `30` §1.0）**：**网关属数据面**。① 实现落数据面；② **厂商密钥不出数据面**（控制面只存引用）；③ 验收：**混合部署下抓包证明控制面零业务数据**（`31` Q7）。

### P0-3 · 缓存前缀"跨客户一致"= 把跨客户复用写进了设计

**发现**：`30` §4 要求"**同岗位包版本 + 同权限下前缀逐字节一致**"，而"同岗位包"**天生跨客户**；视窗指纹只隔离**权限形状**，不含客户维度 → **A 的缓存条目可被 B 命中**。代持 Key 模式下全体客户还共用一个厂商账户。

**判定：成立。这不是实现疏漏，是设计缺陷。**

**处置（已落 `30` §4 第 4 条）**：① **缓存键第一段是客户**；② 共享网关**默认禁止跨客户前缀复用**；③ 代持 Key 模式下额外要求**账户级隔离**；④ 验收：构造"两客户同岗位包同权限"，**命中率必须为 0**（`31` M10）。

### 5.1 ⭐ "不可后补"的正确用法（从评审 2 提炼，已采纳）

**问题**：文档里"不可后补""一步到位"出现了很多次（`01` 文首、`11` #23、`architecture` §11、`20`、`23`、`39` Z11），**当一切都不可后补，就没有优先级了**。

**我拍一条判据来收住它**：

> **区分"改起来贵的"和"加得上去的"。**
> - **改起来贵的** → **必须现在定死**（数据模型、隔离边界、身份体系、ID 格式、字段名）
> - **加得上去的** → **可以后做**（审批规则、知识层、生态、页面、新连接器）

**判据一句话**：**"这东西后加，要不要动已经有数据的地方？"**
要动 → 现在定死；不要动 → 可以后加。

**已按这条复核过的例子**：
| 项 | 判断 | 依据 |
|---|---|---|
| 数据视窗 | **必须现在**（M0） | 连接器一旦按"不带视窗"接好，**回头加要把每个数据源重过一遍** |
| 客户自定义维度类型 | **必须现在** | 它是 `01` §3.2 的地基，后加要动标识体系 |
| `43` 里的字段名 | **必须现在** | 字段名后改要动数据 |
| 平台库的灰度/签名/血缘 | **可以后做** | 加得上去，不影响已有数据 |
| 移动端 | **可以后做**（发起人已拍） | 复用既有接口，不动数据模型 |
| 审批规则的具体阈值 | **可以后做** | 是配置，不是结构 |
