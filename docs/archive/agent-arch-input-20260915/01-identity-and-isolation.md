> 父文档：`architecture.md` §12 细化路线 第 ① 项

## 0. 修订说明（最新共识）

> 本文写在讨论早期，部分用词与结论已按后续共识修订。**读正文时以本节为准。**

### 0.1 术语变更：「项目」→「工作区」

早期把"项目"理解成"租户内的工作域"。**这个理解是错的。**

真实情况：**"项目"指的是服务器上的一个独立工作单元**——可以是某个客户的某块业务，也可以是服务商自己做的某个产品。它是**跨客户**的，不是租户内的。

| 本文旧写法 | 现在的说法 | 含义 |
|---|---|---|
| `Project` / 项目 | **工作区**（Workspace） | 服务器上的一个独立工作单元 |
| `Tenant` / 租户 | **客户**（Tenant） | 付费与隔离的最高单位；**服务商自己也是一个"内部客户"** |
| `Blueprint` | **岗位包**（Role Package） | 工人的定义：身份 + 提示词 + 技能 + 知识 + 工具授权 + 交付物模板 |
| `Agent Instance` / 工人实例 | **数字员工**（Digital Employee） | 岗位包装到某个工作区上之后的运行体 |
| `Capability Token` | **临时凭证** | 分钟级、绑定单次运行 |
| （原文没有） | **连接器**（Connector） | 接入一个外部系统（ERP、Shopify、Amazon、自研中台）的统一入口 |
| （原文没有） | **引擎 / 壳** → 现为 **agent 引擎 / 平台+agent 运行时** | ⚠️ **"壳"是历史用词，已退休**，见 [`19`](./19-platform-vs-agent-boundary.md) §1 |

**连接器和工作区是两个维度，不是一回事**：一个工作区可以接多个连接器。下文所有出现"Project / 项目 / Agent Instance / Blueprint / 租户"的地方，一律按上表改读。

> ⚠️ **现状提醒**：当前服务器上多个工作区**尚未隔离，混在同一台机器上**。这不是"以后记得做"，而是当下就存在的风险——串了是合同层面的事。

### 0.2 两处结论修订

**① KMS 密钥隔离：优先级下调（详见 §3.1）**
原文主张"每个客户独立加密密钥、第一天就要做"。按实际情况——服务商可以查看客户数据、客户也接受——这条的**紧迫性下降，可以后置**。但设计上**要留着升级余地**，因为"客户接受"会随客户规模变化（小客户接受，上市公司有合规部门就不会接受）。

**② 身份从两层改为三层**
原文只有"租户管理员 + 普通用户"。实际是三层：

| 层 | 是谁 | 能干什么 |
|---|---|---|
| **平台运营方** | 服务商自己 | 最高权限，能碰所有工作区。**这本身就是最大风险点**，要在合同与审计上正面处理 |
| **客户技术团队** | 客户方的开发/运维 | 能配"平台配置层"——插件、连接器、数据范围、触发方式；碰不到内核 |
| **客户业务用户** | 客户方的岗位人员 | 只用岗位，只看自己岗位的活 |

### 0.3 新增一条设计约束

**资源归属 ≠ 岗位归属（详见 §3.2）。** 有些资源被多个工作区/岗位共用——例如一个海外仓的库存被多个销售平台共用。权限不能只按"岗位"切，要能按**资源**（仓、店铺、SKU 段）这种维度组织。

## 1. 设计目标与不变量

隔离模型要保证的不变量（invariants）。任何后续设计都必须维持这几条：

| # | 不变量 | 说明 |
|---|---|---|
| **I1** | **标识自带边界** | 看到任何一个 ID，无需查询就能判断它属于哪个租户、哪个项目。这决定了策略、日志、审计能否做到零成本归因 |
| **I2** | **权限单调不增** | 派生（子 agent / 子任务 / 委托）= 权限只能缩小，永不放大 |
| **I3** | **运行态最短命** | 标识的 TTL 与其权限强度成反比：Run 最短命、权限最大；Tenant 最长命、无运行时权限 |
| **I4** | **失效模式互相独立** | 任何单一隔离机制被绕过，其余机制仍然成立（纵深防御） |
| **I5** | **删除即物理不可恢复** | 租户/项目删除必须是密码学意义上的销毁，而不是标记删除 |

## 2. 标识体系

### 2.1 层级

```
Tenant（租户 = 一家企业，付费与隔离的最高单位）
  └── Project（项目域，如项目 A / B / C）
        ├── Principal（人）        ← 属于 Tenant，可被授权到多个 Project
        └── Agent Instance（数字员工）← 必须绑定单一 Project
              └── Session（会话）
                    └── Run（一次执行）← 唯一携带强权限的标识
```

### 2.2 命名规范

统一用 **SPIFFE 风格 URI**，让身份标识可以直接当资源标识、策略主体、审计字段用（一套字符串贯穿全系统，避免 ID 映射层）：

```
spiffe://<region>.<platform-domain>/t/<tenant-id>/p/<project-id>/<kind>/<id>
```

实例：

```
人：          spiffe://cn.acme-agent.io/t/8f2a.../p/1b7c.../user/u-alice
Agent 实例：  spiffe://cn.acme-agent.io/t/8f2a.../p/1b7c.../agent/a-planner-01
会话：        spiffe://cn.acme-agent.io/t/8f2a.../p/1b7c.../agent/a-planner-01/session/s-7f3a
运行：        spiffe://cn.acme-agent.io/t/8f2a.../p/1b7c.../agent/a-planner-01/session/s-7f3a/run/r-9c21
```

### 2.3 三条关键设计决定

**决定 A：ID 用不可变 UUID，不用客户可读的名字。**
租户可能改名（"华东供应链部" → "供应链中心"），项目可能改名。如果 URI 里放名字，一次改名就会**断掉整条审计链**，历史日志无法归因。
→ 内部标识一律不可变 ID；可读名字只存在于展示层（display name / slug）。

**决定 B：Agent Instance 必须绑定单一 Project，且终生不可迁移。**
这是防止横向移动的**根本机制**，而不是靠策略约束。
如果客户说"我要一个 agent 能看所有项目"——正确的解法不是给它跨项目权限，而是：
**两个（或多个）实例 + 一个上层编排者**，由编排者去汇总。因为编排者本身没有数据权限，它只能调用别的实例，而每个实例的权限仍被各自的 Project 边界锁死。
→ 这条如果妥协（允许"跨项目 agent"），整个隔离模型就退化成"提示词级别的君子协定"。

**决定 C：Run 是唯一携带强权限的标识。**
Session 可以活几小时几天，Run 必须分钟级。
权限跟着 Run 走，不跟着 Session 走 —— 否则一个长期会话就等于一个长期凭证。

## 3. 资源边界清单

对每一层边界，明确"什么共享、什么独占"。**这张表就是"硬隔离"的定义**。

| 资源 | Tenant 边界 | Project 边界 | Run 边界 |
|---|---|---|---|
| **计算** | 独立节点池（Enterprise 档独占；Standard 档共享但强制隔离） | K8s namespace | 一次性 Pod / 微VM |
| **文件** | 独立 bucket + **独立 KMS key** | bucket 内独立前缀 / 独立 PVC | overlay 上层（tmpfs，不可持久化） |
| **网络** | NetworkPolicy 域 + 独立 egress 出口 | 独立出口策略 + 独立代理实例 | 继承 Project，不额外放宽 |
| **凭证** | 独立 Vault 路径空间 | 独立凭据域 + 独立工作负载身份 | Capability Token（分钟级） |
| **数据** | 独立 schema 或 RLS 租户列 | 行级/域级过滤规则 | 查询级参数约束（时间范围、维度） |
| **检索/知识** | 独立命名空间 + 独立数据源 | 独立命名空间 | 只读检索；**先按归属过滤再算相似度**；结果带出处 |
| **密钥** | 独立 KMS key（+ 按项目派生） | 派生 key | 无独立密钥 |
| **配额** | 租户硬上限 | 项目配额 | Run 预算（token/成本/时长） |
| **审计** | 独立审计流 | 附加 project 维度 | 附加 run/session 维度 |
| **配置** | 独立配置域 | 项目级覆盖 | 无（Run 不改变配置） |

### 3.1 KMS key 按客户分离（**优先级已下调**）

加密隔离是**物理的**，不是逻辑的。即使运维误操作、代码有 bug、策略配错，把 A 客户的文件路径给了 B —— **B 也解不开**，因为密钥不同。

**原文主张"每个客户独立密钥、第一天就要做"。按实际情况修订如下：**

- 服务商可以查看客户数据、客户也接受这一前提，**降低了这条的紧迫性** → 可以后置
- **但设计上必须留着升级余地**：密钥是可配置的维度，而不是写死在存储层里
- **触发升级的信号**：客户规模变大（出现上市公司、有合规部门的客户）、或开始做真正的公开多租户 SaaS

> 理由很简单：**"客户接受"是个会变的条件。** 小客户接受服务商看数据；等他变成上市公司，就不会接受了。到时候改不动，是因为当初把密钥写死了，而不是因为当初没做。

### 3.2 资源归属 ≠ 岗位归属（新增）

前面几节默认"隔离边界 = 岗位/工作区"。**这个假设不够。**

现实里有一类资源是**被多个岗位、甚至多个工作区共用**的：

- 一个海外仓的库存，被 Amazon、Shopify、Temu 等多条业务线共用
- 同一个供应商的产能，被多个采购员共用
- 同一批在途货物，牵动多个平台的备货计划

**如果权限只按"岗位"切，就会出现两种事故：**

1. **看不见导致的超备**：每个岗位只看自己那本账，各自按自己的销量备货，合起来必然超备——而且**没有任何一个人能看见这个超备**
2. **越权**：为了让 A 岗位看到仓里的量，把它接进了不属于它的工作区

**正确形态**：权限模型要支持**按资源维度授权**——`资源`（仓 / 店铺 / SKU 段 / 供应商）是独立于`工作区`的一等维度，多个工作区可以引用同一个资源，各自带着自己的权限范围。

→ 这条直接影响 §2 的标识体系：**标识里不能只有"谁"，还要能表达"对哪一类资源"**。

#### ⭐ 修订（Day 3）：维度的**种类必须由客户自定义**，不能是固定清单

上文的"仓 / 店铺 / SKU 段 / 供应商"**只是举例，不能变成代码里的枚举**。

**为什么**：不同企业切内部边界的方式完全不同——有的按**货权团队**切，有的按**区域**、**品类**、**品牌**、**渠道**、**法人**切；同一家企业过两年也会改组。**只要平台写死一份维度清单，客户每换一种切法就得改一次平台——这就是打补丁。**

**定死（我拍）**：

| 谁 | 定什么 |
|---|---|
| **客户技术团队** | **维度类型**（叫什么）+ **维度取值**（有哪些）——如"货权团队：A 团队 / B 团队" |
| **岗位包**（模板） | 只声明**要求**：需要**某类归属维度**的哪个敏感级——**不写死是哪一类、也不写取值** |
| **数字员工实例**（配置） | 填**具体取值**——这个实例看哪个团队的数据 |

**结果**：客户想分几个团队、叫什么名字、归谁，**平台零改动**。这条是 ADR-4"领域无关"在权限侧的落地形态。

**落地机制**：数据视窗 → [`34-data-view.md`](./34-data-view.md)；跨边界的申请/审批/执行 → [`35-cross-boundary-authorization.md`](./35-cross-boundary-authorization.md)。

## 4. 能力令牌签发链路

这是把「身份」与「权限」连起来的核心机制，也是**连接器网关**（[`04-connectors.md`](./04-connectors.md)）的前置依赖。

```
① Run 创建
     │
     ▼
② 编排器向控制面申请：
     { tenant, project, agent_instance, session, run_id, requested_caps }
     │
     ▼
③ 策略引擎评估（**四方交集**，Day 3 由三方扩为四方）：
     ┌─ 触发者授权（人 or 服务身份）
     ├─ **数字员工实例配置**（数据视窗取值，`34`）
     ├─ Blueprint 声明的能力集
     └─ 租户/项目策略允许集
     ─────────────────────────────
     结果 = 四者交集 → 默认拒绝，未声明即拒绝
     │
     ▼
④ 签发 Capability Token
     · 主体：run_id                ← 精确到 Run，不是 Agent Instance
     · 权限：caps 的窄化子集
     · 约束：TTL 5–15 min、调用次数上限、资源范围 project://...
     · 绑定：run_id + 沙箱实例指纹   ← 防令牌被复制到别处使用
     │
     ▼
⑤ 注入沙箱
     · 通过文件 / 环境变量注入，绝不通过命令行参数（避免 ps 泄露）
     │
     ▼
⑥ 能力网关校验每次调用
     · 签名有效 + 未过期 + run 绑定匹配 + 该次调用落在 caps 内
     · 任一不满足 → 拒绝并产生审计事件
```

### 4.1 三条不可妥协的设计

1. **令牌主体是 Run，不是 Agent Instance。**
   否则同一实例的两个并发会话可以互相冒用令牌 —— 隔离在"同一实例内"就破了。

2. **令牌绑定沙箱实例指纹。**
   令牌一旦泄露到沙箱外，拿到也无法使用。

3. **令牌可续期，但不可扩权。**
   续期只能得到 `≤` 原权限的子集。这条保证了长任务不会因为反复续期而权限膨胀。

### 4.2 权限的权威公式

```
Run 的有效权限 = 触发者授权  ∩  **数字员工实例配置**  ∩  Blueprint 声明  ∩  租户/项目策略
```

任何一方未授予 → 无权。**这不是"或"，是"与"。**
这条公式要写进策略引擎的每一处判定，避免任何地方出现"因为 Blueprint 声明了所以允许"这种捷径。

> **Day 3 修正**：原式为三方交集，补上"**数字员工实例配置**"成为**四方**（详见 [`26`](./26-governance-layer.md) §2.2 与 [`34`](./34-data-view.md) §3）。

### 4.3 ⭐ 平台运营方的权限，不等于"agent 能拿到平台身份"（Day 4 第 4 轮自审补）

**这是一个真实存在的漏洞面，必须显式堵死。**

| 事实 | 约束 |
|---|---|
| **平台运营方**是最高权限（`architecture` §7.1、`01` §2.1） | **它是"人"的运维/合规/审计权限** |
| **agent 永远不能以平台运营方的身份运行** | 即使这个 agent 是平台自己部署的参考工人 |
| **agent 能拿到的最大身份 = 数字员工的服务身份** | 其权限 **严格 ⊆ 创建它的管理员**（`architecture` §7.1） |

**为什么必须写这条**：

客户会问一个很具体的问题——**"我授权给 agent 的店铺是 A，它会不会趁你不注意去读 B？"**
如果平台运营方的高权限能被"顺路"用上（比如运维调试时切了个身份、或某个内部工具默认用运营方身份），**这个问题就没有答案了**。

**三条硬规则**：

1. **运行身份只有两种**：**人触发的**（触发者授权）和**无人触发的**（数字员工服务身份）。**没有第三种"平台身份"的运行**
2. **运维操作要留痕，且不能借道 agent**——平台运营方要查数据，走**它自己的运维通道 + 审计**，**不是让某个 agent 替它查**
3. **`26` §3.1 的事件五要素里，"谁"必须能区分**「人」/「数字员工服务身份」/「平台运营方」——`26` 已有，这里明确它**不是形式要求，是追责依据**

## 5. 越界防御的四道闸

回应你的原始诉求："agent 不能随意游离到其他项目"。落地方式是四道**失效模式互相独立**的闸：

| 闸 | 机制 | 拦住什么 |
|---|---|---|
| **闸 1 · 文件** | mount namespace 里只有：本 Project 的只读物料 + 本 Run 的 tmpfs | 文件层面**根本看不到**别的项目。不是"不许读"，是"不存在" |
| **闸 2 · 网络** | NetworkPolicy + egress proxy，只放通本 Project 的服务 | 网络层面**到不了**别的项目 |
| **闸 3 · 权限** | Capability Token 的资源范围硬编码 `project://<id>/...` | 即使绕过前两闸，网关**照样拒** |
| **闸 4 · 检测** | 策略引擎审计 + 越界尝试实时告警 | 不阻止但**暴露**，用于追责与发现攻击 |

**设计要点**：这四道闸的技术栈完全不同（内核 / 网络 / 应用 / 分析），因此不存在"一个漏洞同时击穿四道"的路径。这是纵深防御的真正含义 —— 不是叠加同类机制，而是叠加**不同类**机制。

## 6. 必须提前说清的边界情形

这些是设计评审时最容易被追问、也最容易埋雷的地方。

### 6.1 定时/事件触发时，"谁"是身份？

这是 ADR-2 与 ADR-4 交汇出的一个真问题：定时任务（如"每天早上 8 点跑销量分析"）**没有人在场**，那么 §4.2 公式里的"触发者授权"是什么？

设计：**Agent Instance 自带一个服务身份（service principal）**。

- 创建实例时由管理员显式授予其权限，且**严格 ⊆ 管理员自身权限**（不能授予自己没有的东西）。
- 定时 Run 使用该服务身份，审计上记录为"实例的服务身份在 08:00 发起了查询"。
- 服务身份的权限**不可继承人的临时授权**，避免"某员工离职后定时任务还能跑"。

→ 推论：**每个 Agent Instance 有两类触发者身份**（人的委托 / 实例的服务身份），二者的权限集必须分别维护、分别审计。

### 6.2 跨项目需求

不建议有"跨项目 Agent"。若客户坚持，正确形态是：

```
用户 ──► 编排型 Agent（无数据权限）
              ├─► 项目 A 的 Agent 实例（只见 A）
              └─► 项目 B 的 Agent 实例（只见 B）
```

编排者只做"调用与汇总"，它自己**读不到任何一方的原始数据**。这样跨项目协作是显式的、可审计的，而不是靠一个特权 agent 自由穿行。

### 6.3 租户/项目改名

- 内部 ID 不可变；URI 用 ID。
- 展示名可变，仅存在于控制面元数据与 UI。
- **审计链因此永远不断。**

### 6.4 删除（含合规删除请求）

删除必须是**密码学销毁**：

| 步骤 | 动作 |
|---|---|
| 1 | 撤销全部 Capability Token（即使有未过期的也立即失效） |
| 2 | 销毁全部运行中的沙箱实例 |
| 3 | 删除对象存储数据 + **销毁租户 KMS key**（crypto-shredding，使任何残留密文永久不可读） |
| 4 | 删除检索索引与知识/数据层内容 |
| 5 | 清理缓存与会话态（含 Redis、语义缓存） |
| 6 | 审计日志：**保留**一条"已删除"记录，但不保留内容（合规要求通常要求保留操作事实） |

→ **第 3 步是关键**：只删数据不销毁密钥，"删除"是可以被备份/残留副本打脸的。销毁密钥才能给出"不可恢复"的承诺，这也是能写进合同的能力。

### 6.5 多区域

- 每个 Tenant 归属一个 **home region**，数据不跨区（除非明确配置且合规允许）。
- 控制面可以全局（统一升级、统一计费），数据面必须区域化。
- → 这直接关联 **D1（混合部署）**：如果要做混合数据面，标识体系现在就要把 `<region>` 放进 URI，不能后补。

### 6.6 人员离职

Principal 撤销时，必须级联失效：

- 该人创建的所有委托链（他委托给 agent 的临时授权）
- 但不影响实例的服务身份（业务连续性）
- 审计上标记"该身份已撤销"，历史记录保留归因

## 7. 待讨论的开点

不是选择题，是想听你的判断：

1. **Project 是否对所有人都必填？**
   我倾向：底层模型必须有 Project，但小客户默认自动建一个 `default`，把概念藏起来。你更希望客户**显式管理项目**（清晰但重），还是**默认无感**（轻但后期可能要做数据迁移）？

2. **Agent Instance 的"服务身份"权限边界该由谁定？**
   管理员定（简单，但管理员可能过度授权）vs 审批委员会定（安全，但重）。
   还有个更微妙的问题：**服务身份的权限要不要定期复核**（access review）？企业安全评审基本一定会问这个。

3. **<region> 是否现在就进 URI？**
   代价是现在就要决定区域划分策略；收益是未来做混合部署/多区域不用重构标识。
   我倾向现在就进 —— 因为标识是最不可逆的东西。

4. **"越界尝试"的定义与处置？**
   被策略拒绝算不算一次安全事件？是记日志、还是告警、还是直接终止 Run？
   我的倾向是分级：**单次拒绝 → 记日志；同一 Run 内重复拒绝 → 告警；尝试访问明确不属于本租户的资源 → 立即终止 Run**。你怎么看这个激进度？
