# 第一部分 · agent 是什么

## 1.1 一句话

**agent = 引擎（会想）+ 运行时（能干活）。**

```
┌───────────────────────── agent ──────────────────────────┐
│                                                          │
│  引擎（Engine）—— 可换（ADR-5）                           │
│    认知循环：想 → 做 → 看 → 再想                          │
│    单轮推理：下一步干什么、要不要调工具                    │
│    工具调用「请求」的生成（只是请求，不是执行）             │
│                                                          │
│  运行时（Runtime）—— 自研，是核心资产                     │
│    工具系统 · 上下文组装 · 记忆存取 · 沙箱接口             │
│    子代理机制 · 循环检测 · 预算执行                       │
│                                                          │
└────────────────────────┬─────────────────────────────────┘
                         │ ⇅ 两条接口（§2.3）
                         ▼
      ┌──────────── 平台（不在本文范围）────────────┐
      │ 权限裁决 · 沙箱实现 · 数据裁剪 · 模型网关     │
      │ 会话编排 · 审批 · 账本 · 交付物 · 界面       │
      └────────────────────────────────────────────┘
```

**一期 3 个 agent 并行**：**roni（自研）+ DS harness + codex harness**。
Claude Code 不用 —— 闭源，且 Anthropic 发过逆向下架通知（核实：本机 LICENSE 与公开报道）。

## 1.2 哪些属于 agent，哪些不属于（本文的地基）

| 事项 | 归谁 | 判据 |
|---|---|---|
| 认知循环、单轮推理 | **agent（引擎）** | 这是"想" |
| 工具调用的**请求生成** | **agent（引擎）** | 只是请求 |
| 工具与连接的**实现** | **agent（运行时）** | 引擎不该知道连接器长什么样 |
| **上下文组装机制** | **agent（运行时）** | 放什么进去是机械动作 |
| **记忆的存取机制** | **agent（运行时）** | 怎么存怎么取 |
| **子代理机制** | **agent（运行时）** | 怎么派、怎么收敛 |
| **循环检测** | **agent（运行时）** | 防它自己转圈 |
| 沙箱**接口** | **agent** | agent 只知道"要一个受限环境" |
| 沙箱**实现（含容器/microVM）** | **平台** | 换 agent 不用重做沙箱 |
| 上下文的**准入规则** | **平台** | 安全决策，不能交给可被劫持的一方 |
| 权限与策略的**裁决** | **平台** | 引擎可被注入，权限不能放它那儿 |
| **工具清单的过滤** | **平台** | agent 拿到的是**过滤后**的 |
| 数据视窗的**裁剪** | **平台** | agent 拿到的**已经是裁剪后的值** |
| 预算的**总量与裁决** | **平台** | "烧钱的那个开关"必须在平台手里 |
| **任务编排的调度器** | **平台** | 三个 agent 都要被同一套调度驱动 |
| 模型路由与网关 | **平台** | agent 只声明"我要什么档次的模型" |
| 交付物状态机 / 审批 / 账本 / 审计 | **平台** | 业务与合规概念 |
| 岗位包（九块配置） | **平台产出** | agent 只**读**配置 |

**四条容易搞混、已定死的边界**：

> **上下文：组装归 agent，准入归平台。**
> **沙箱：接口在 agent，实现在平台。**
> **预算：执行在 agent，裁决归平台。**
> **编排：跑起来归 agent；派几个、给多少、谁来汇总归平台。**

## 1.3 为什么"运行时"必须自研，而"引擎"可以换

| 自研件 | 为什么不能外包 |
|---|---|
| 工具系统（声明 + 装载 + 裁剪） | 接的是客户系统，形状由我们定 |
| 上下文组装 | **它是安全边界**（谁能看到什么） |
| 记忆存取 | 记忆是**跨引擎资产**，不能长在引擎里 |
| 子代理机制 | 权限收缩与预算切分在这里落地 |
| 循环检测 | 成本控制的第一道闸 |
| 沙箱接口 | 抽象层，将来换实现不改 agent |

**看这张表就明白"引擎可换"为什么要努力**：运行时几乎承担了所有跟业务、安全、合规相关的部分，**引擎只剩"思考"**。

# 第二部分 · 自研 roni 的技术架构

## 2.1 三件改造（顺序不能反）

| # | 改造 | 为什么这个顺序 |
|---|---|---|
| **①** | **抽引擎边界** | **地基**，②③ 都依赖它 |
| **②** | **移植 DS harness 零件**（借设计，不借代码） | 依赖 ① 的接口 |
| **③** | **补按需召回** | 依赖 ① 的上下文组装 |

### 2.1.1 ① 抽引擎边界的三个动作

| 动作 | 具体 | 验收 |
|---|---|---|
| **系统提示参数化** | 身份、职责、边界由岗位包生成，不写死在代码里 | 换客户环境只改配置 |
| **拆 HTTP 与对话编排** | 对话核心能**脱离 HTTP 单独跑** | headless 调一次能跑通 |
| **工具声明化** | 工具来源从"静态数组"变成 manifest | 加删工具不改核心代码 |

**为什么必须先做 ①**：现在 roni 把系统提示、HTTP 层、工具数组硬编码在一起。
不抽开，②③ 都无处落脚（移植来的零件要挂在接口上）。

### 2.1.2 ② 从 DS harness 移植什么（数值实读源码）

| 件 | 我们的取值 | 关键理由 |
|---|---|---|
| **沙箱** | 借 `SandboxProvider` **契约**；实现在平台（§3、§5） | 换 agent 不用重做沙箱 |
| **工具声明化** | **64 个工具一次性全改 manifest，不分批** | 分一半会让"装载"变成两套逻辑 |
| **大结果落盘（spill）** | 阈值 **32768 字节**（⚠️ **我方拍板值**，非 harness 默认——harness 该项为 opt-in 无默认）；预览**头尾对半**；best-effort | 见 §4.3 |
| **工具结果修剪** | 阈值 **8192 字符**、头 **4096**、尾 **1024**（**4:1**） | 见 §6.4 |
| **压缩** | **比例制**：模型窗口 **80%** 触发、保留 **16%** | 见 §7.3 |
| **循环检测** | 阈值 `[3, 5, 8]` **分级提醒、不熔断** | 见 §10 |
| **技能按需加载** | 系统提示只放目录，用时加载全文 | 见 §7.2 |

### 2.1.3 ③ 按需召回（三件事）

| # | 从 | 改成 |
|---|---|---|
| 1 | 技能全文进系统提示（N × 1.6 万字符） | **只放技能目录**，用时调"加载技能"工具 |
| 2 | 每轮自动注入最近 12 条知识 | 给一个"**查知识**"工具，需要时才查 |
| 3 | 结构化数据靠"记" | ⭐ **连接器精确查询**，**不进上下文、不进向量库** |

**第 3 条最大也最容易被忽略**：历史备货表、库存记录、订单明细——**这些不是"检索"，是"精确查询"**。

## 2.2 上下文工程（成本的主战场）

### 2.2.1 一条总原则

> **上下文是花出去的钱，不是"信息越多越好"。**

每段塞进去的东西付两种费：**token 的钱** + **注意力被稀释的代价**。
**判据：这一段不进上下文，agent 会不会做错？不会，就别放。**

### 2.2.2 五层，按"稳定度"排序（最值钱的一张表）

| 层 | 内容 | 什么时候变 | 放哪 |
|---|---|---|---|
| **系统层** | 岗位包生成的身份、职责、边界 | 只有换版本才变 | **最前** |
| **工具层** | 工具清单（已按权限过滤） | 只有权限变才变 | 紧接系统层 |
| **知识层** | 检索到的知识、技能 | 每次不同 | 中段 |
| **任务层** | 本次任务、目标、交付物结构 | 每次不同 | 中段 |
| **结果层** | 工具返回 | 每次都变 | **最后** |

**这个顺序同时决定缓存和成本。** 成熟框架便宜，很大一部分原因是它**把最稳定的几段做成可复用的**——
同样的前缀重复出现时不用重算。**自研若每次重新拼一遍，前缀永远命中不了，那部分钱就白花。**

⚠️ **诚实标注**：这条是**推断**（`08` §1 已标），不是实测结论。但它和你观察到的
"同模型、成本差 2–3 倍"一致，而且是**最容易验证的一条**：先看每次调用的前缀是否稳定。

**三条落地纪律**：
1. 最稳定的放最前，最易变的放最后——**顺序本身就是钱**
2. 不要为了让提示词"看起来完整"而加东西——加进系统层会让缓存失效
3. **每次运行的系统层 + 工具层应逐字节一致**（同版本岗位包 + 同权限）——不一致就是漏了

### 2.2.3 顺序同时是信任边界

**系统层、工具层是平台生成、可信的；知识层、结果层是外来的、不可信的。**
**可信在前、不可信在后，中间有明确分界** —— 这**不只是**缓存优化。

**三层注入防御**：

| 层 | 做什么 |
|---|---|
| **来源标注** | 每段进来都标清从哪来：用户输入 / 检索文档 / 工具返回 / 外部网页 |
| **信任分级** | 外部内容**不能改写系统指令** |
| **结构隔离** | 外部内容用明确边界包起来，**在结构上就没资格当指令** |

> **核心**：不要指望"在提示词里告诉它别听外面的话"——**要让外部内容在结构上就没有资格当指令。**

⚠️ **一个具体风险**：若允许 agent 把"上次工具返回的内容"写进系统层或知识层，**可信区就被污染**。
**这条要在平台侧堵死，不能靠 agent 自觉。**

### 2.2.4 权限过滤在进上下文之前

**agent 拿到的工具清单是过滤后的**，所以上下文里**根本不存在越权的目标**。
拦的那道可能被绕过，**看不见的没有绕法**。

### 2.2.5 压缩：什么绝对不能压

| 问题 | 答案 |
|---|---|
| 什么时候压 | 接近上限时，**不要等满了才压** |
| 压什么 | 先压最老的、最不相关的（工具返回里的原始细节优先） |
| **绝对不能压** | ⭐ **交付物的依据**（`explain` 要求的那部分）· 审计需要的信息 |
| 压完怎么留痕 | 两份都留：**压缩摘要**进上下文，**原始轨迹**入审计 |

> **"绝对不能压交付物的依据"是个具体的坑**：如果压缩把"为什么算出来是这个数"的来源删了，
> 人复核时看不到解释，`explain: required` 就成了空话，审计链也断了。

### 2.2.6 工具结果是膨胀的主因

绝大多数自研 agent 成本失控，出在"把工具返回原样塞回去"。**四条纪律**：

| # | 纪律 |
|---|---|
| 1 | **结构化，不要倾倒** |
| 2 | **有大小上限**，超过就截断并明确标记"被截断" |
| 3 | **大结果落盘，上下文只留摘要 + 引用** |
| 4 | **保留什么由岗位包声明**，不是引擎临场决定 |

**第 3 条最被低估。** 一次查询返回 5000 行，正确做法**不是**"截前 100 行"（agent 会以为只有 100 行）：

```
上下文里：「查到 5000 行，摘要：……；完整结果在 result://run-123/inventory-1，
          需要时用 fetch 取回指定范围」
```

既没撑爆上下文，也没丢信息，而且 **agent 知道自己不知道什么** —— 这比给它一份残缺数据强得多。

## 2.3 两条接口（agent ↔ 平台）

### 2.3.1 平台 → agent

| 给什么 | 注意 |
|---|---|
| 系统提示 | **由岗位包生成**，agent 不负责描述自己身份 |
| 当前上下文 | **由平台决定准入** |
| **可用工具清单（已按权限过滤）** | agent 看到的是**过滤后**的 |
| 工具调用通道 | **走平台，不直连** |
| 剩余预算 | token / 成本 / 步数 / 时长 |
| 中断信号 | 人随时能打断 |

### 2.3.2 agent → 平台

| 返回什么 | 注意 |
|---|---|
| 工具调用**请求**（结构化） | 是请求，不是执行 |
| 文本输出 | 给人看的部分 |
| 结束原因 | 完成 / 放弃 / 超预算 / 出错 |
| 用量（token 数） | 计量用 |

### 2.3.3 三条不可让渡的边界

| # | 边界 | 为什么不能让 |
|---|---|---|
| **1** | **工具调用必须经过平台** | agent 直连外部系统 = 权限、审计、脱敏全部失效 |
| **2** | **上下文由平台裁定准入** | "放什么进去"是安全决策，不是性能优化 |
| **3** | **结束与预算由平台裁决** | agent 说"我还想继续"不算数。**成本差 2–3 倍，一部分就是"谁有权说停"** |

# 第三部分 · 两个 harness 的实证评估（本文的核心）

> ⭐ **这一部分推翻了本文作者此前的一条判断。**
>
> 此前写法是"**接管优先**：禁用外部引擎的原生工具，只注入我们提供的工具清单"。
> **那个判断建立在一个未验证的前提上**——"它们自带的工具不如我们的"。
> 发起人指出这个前提不对："**如果本身它们就很稳定很好，那就让他们用，就加围栏就行了，
> 不能剥夺人家工具的较好能力和体验**"。
>
> **下面用证据回答：那个前提不成立，判断改掉。**

## 3.1 证据一：DS harness（读本机源码，非猜测）

**位置**：`C:\Users\颜文\AppData\Roaming\npm\node_modules\@deepseek-ai\dsh`

### 3.1.1 它的包结构本身说明了设计水平

| 包 | 官方描述（原文摘录） |
|---|---|
| `dsh-sandbox` | "Abstract process-sandbox **seam** (`ctx.sandbox`)… same-world confinement vocabulary and the **SandboxProvider contract**" |
| `dsh-sandbox-local` | "bwrap、the npm-distributed landlock-run launcher、macOS Seatbelt、or the **Windows ACL restricted-token runner** — functionally probed, **fail-closed**" |
| `dsh-fs-sandbox` | "**Sandbox-enforcing** implementation of the filesystem seam: fences write/edit by the per-call sandbox mode… while reads pass through" |
| `dsh-subagent` | "Abstract subagent **seam** (`ctx.subagents`): **named-provider registry** for delegating to child agents" |
| `dsh-tools` | "Tool **registry and execution pipeline**" |
| `dsh-compaction-basic` | "**Token-meter-driven** compaction policy and LLM summarization backend" |
| `dsh-tool-skill` | "Model-facing **skill loading** tool" |
| `dsh-mcp-client` | "MCP client bridge: connects to MCP servers and **registers their tools on ctx.tools**" |

**读出来的四个设计事实**：

| # | 事实 | 对我们的意义 |
|---|---|---|
| **1** | **沙箱是一个"契约"，不是一个实现** | 我们可以**加 gVisor 作为它下面的一个 provider**，而不是重写沙箱 |
| **2** | **`dsh-fs-sandbox` 在工具层强制沙箱**——"the filesystem and shell families **never confine to different roots**" | 文件工具和 shell 用**同一套根目录**，不会出现"文件被限住但 shell 没限住" |
| **3** | **子代理也是 seam + provider 注册表** | 可以挂我们自己的子代理驱动 |
| **4** | **MCP 工具注册到同一套 `ctx.tools`** | 我们的连接器可以通过 MCP 变成它的工具，**进同一个执行管线** |

### 3.1.2 它自己写明了它管什么、不管什么（关键）

`dsh-sandbox` README 原文（中文版）：

> "这是**同世界隔离**：进程仍与宿主共享内核和文件系统；**需要隔离整个环境时，请使用容器、microVM 或远程执行器**。"

英文版同样：

> "This is **same-world confinement**: the process still shares the host kernel and filesystem;
> **use a container, microVM, or remote executor when the whole environment must be isolated**."

**这句话直接决定了我们的架构**（见 §5）：

> **harness 自带的沙箱 ≠ gVisor。它们是两个层级，不是竞争关系。**
> **gVisor 管"整个环境隔离"（防逃逸、跨租户）；harness 沙箱管"agent 的工作区围栏"（防误写）。**

**而且它还说明**："需要隔离整个环境时请用容器/microVM/远程执行器"——
**它推荐的那一层，正是我们在平台侧要做的。**

### 3.1.3 它还自带一份"平台级"零件清单

`dsh-*` 包里已经有的能力（**全部实读包名 + 描述**）：

| 能力 | 包 |
|---|---|
| 会话持久化 + **格式版本迁移**（v0→v1→v2→v3） | `dsh-session-persistence` / `-format-v0-to-v1` / `-v1-to-v2` / `-v2-to-v3` |
| **检查点策略** | `dsh-session-checkpoint-policy` |
| 会话全量检索（**SQLite FTS5**） | `dsh-session-query-sqlite` |
| **遥测（OpenTelemetry）** | `dsh-session-telemetry-otel` |
| Token 计量 | `dsh-token-meter` |
| 大结果落盘 / 修剪 / 压缩 | `dsh-spill` / `dsh-compaction-tool-result-pruner` / `dsh-compaction-basic` |
| 子代理（fork / spawn / in-process 驱动） | `dsh-subagent-fork-in-process` / `-spawn-in-process` / `-in-process-driver` |
| 计划模式 / 目标 / 待办 / 工作流 | `dsh-plan-mode` / `dsh-goal` / `dsh-tool-todo` / `dsh-workflow` |
| 审批与权限预设 | `dsh-user-approval` / `dsh-permission-presets` / `dsh-authorization` |
| **hooks：Claude Code / Codex** | `dsh-hooks-claude-code` / `dsh-hooks-codex` |
| 凭据管理 | `dsh-credentials` / `dsh-credentials-local` |

> ⭐ **一个值得注意的信号**：它自带 `dsh-hooks-codex` 和 `dsh-hooks-claude-code` ——
> 说明 **DS harness 自己就把"接入其他 harness"当成一等能力**。这与我们"三个 agent 并行"的路子同源。

## 3.2 证据二：Codex harness（核实官方文档）

### 3.2.1 沙箱机制（[sandbox.md](https://github.com/openai/codex/blob/rust-v0.53.0/docs/sandbox.md)）

| 平台 | 机制 |
|---|---|
| **macOS 12+** | **Apple Seatbelt**（`sandbox-exec` + profile，OS 级约束文件系统与网络） |
| **Linux** | **Landlock + seccomp**；需要拆分文件系统策略时**自动走 bubblewrap**；`bwrap` 缺失时回退到随附的 `codex-resources/bwrap` |
| **Windows（实验性）** | AppContainer profile 派生的受限令牌 + capability SID 白名单；**明确声明它挡不住 Everyone 可写目录** |

**三档沙箱模式**（与 DSH 同词汇）：`read-only` / `workspace-write` / `danger-full-access`。

**几条对我们直接有用的原文事实**：

| 事实（原文） | 对我们的意义 |
|---|---|
| "In `workspace-write`, **network is disabled by default**" | ⭐ **默认断网**，而 gVisor 挡不住 `curl` —— 这条必须留着 |
| "Codex requires approval for actions **outside the workspace or for network access**" | 越界与联网要人批 |
| "Policies that would require direct explicit unreadable carveouts… **still fail closed** instead of running with weaker enforcement" | **fail-closed**，与 DSH 同 |
| "In containerized Linux environments… **configure the container to provide the isolation you need** and run Codex with `danger-full-access` inside that container" | ⭐ **官方明说：容器负责隔离、Codex 负责围栏** —— 与 §3.1.2 完全一致 |
| "The seatbelt profile allows writes under the configured writable roots while keeping **`.git`… and `.codex` read-only**" | 连它自己的配置目录都保护 |

### 3.2.2 它能被当子代理驱动（核实官方文档）

| 能力 | 原文/参数 |
|---|---|
| **headless 一次性执行** | `codex exec "任务"` |
| **结构化流式输出** | `--json` → JSONL 事件（`turn/started`、`item/agentMessage/delta`、`turn/completed`…） |
| **结构化结果（Schema 约束）** | `--output-schema <FILE>` |
| **最终消息落文件** | `-o, --output-last-message` |
| **不落盘** | `--ephemeral` |
| **沙箱模式可指定** | `-s, --sandbox read-only\|workspace-write\|danger-full-access` |
| **工作目录可指定** | `-C, --cd <DIR>` |
| **有语义的退出码** | 0 成功 / 2 认证失败 / 3 配置错误 / 4 模型或 API 错误 / 130 被中断 |
| **可以换模型厂商** | `[model_providers]` + `base_url` + `env_key`，**内置 DeepSeek**；任何 OpenAI 兼容端点都行 |

> ⭐ **`--json` + `--output-schema` + 语义退出码 = 它天然适合被当子代理驱动。**
> 这正是 `09` §1 定义的"派活 → 结论"接口所要的东西。

### 3.2.3 ⚠️ 合规红线（必须先解决，否则不能用）

**Codex 默认模型是 OpenAI 的（文档里写 `gpt-5.2-codex`）。而我们的底线是境外模型排除**（`02` 合规约束）。

**处置**：利用它的 `[model_providers]` 机制，**指向境内 OpenAI 兼容端点**（内置支持 DeepSeek）。
这样"用 Codex 的 harness + 用境内模型"成立。

⚠️ **但这条必须做一次真实连通性验证才算数**——"文档说支持"不等于"跑得通"。
**标为"待验证"，列入 §11 待决清单。**

### 3.2.4 ⚠️ 一个必须堵死的逃生门

Codex 有 `--dangerously-bypass-approvals-and-sandbox`（别名 `--yolo`）：**无沙箱、无提示**。

**在服务端部署里这个开关必须被封禁**——不是"约定不用"，是**在调用层不让它出现**
（参数白名单，不允许透传任意 flag）。原因：它是**唯一能一次性废掉整个隔离设计的开关**。

### 3.2.5 它能被约束到什么程度（这决定了围栏可行）

Codex 提供 **execution policies**（Starlark 语法，[官方文档](https://mintlify.wiki/openai/codex/advanced/exec-policies)）：

```python
prefix_rule(
    pattern = ["git", ["status", "diff", "log"]],
    decision = "allow",          # allow | prompt | forbidden
    justification = "只读的版本控制命令"
)
```

- **`allow`** 免批准执行 / **`prompt`** 要人批 / **`forbidden`** 完全禁止
- 原文："Execution policies are evaluated **before sandboxing** and work alongside approval modes
  to provide **defense-in-depth**"
- 支持 `match` / `not_match` 写单元测试

> ⭐ **这是"命令级"的围栏，而且它在沙箱之前评估。**
> 也就是说：**我们不需要剥夺 Codex 的 shell 工具，我们可以在它外面加一层命令策略。**

## 3.3 结论表：接管 vs 围栏

| 维度 | 接管（禁用原生工具，注入我们的清单） | **围栏（让它用原生工具 + 外围约束）** |
|---|---|---|
| 可行性 | 要求引擎支持"只给我指定的工具"——**很多引擎不完整支持** | **两家都支持从外部约束**（见上两节） |
| 能力损失 | **大**：文件编辑、apply_patch、多轮迭代这些体验全丢 | **小**：原生工具的全部体验保留 |
| 我们还能守住吗 | 能 | **能，但守住的方式不同**（见 §5 四层） |
| 审计粒度 | 工具级（我们看得见每次调用） | **命令级 / 策略级**（比工具级粗，但比"无"强得多） |
| 维护成本 | 高：引擎工具变了要跟着适配 | **低**：引擎自己维护它的工具 |

### ⭐ 结论（推翻此前的"接管优先"）

> **采用围栏，不接管。**
>
> **理由**：你的判断是对的——**它们自带的工具确实更好**（都是为"长任务、多轮迭代、真跑代码"打磨出来的），
> 而且**两家都提供了从外部约束的机制**（DS 的 `SandboxProvider` 契约 + fs 围栏；Codex 的三档沙箱 + Starlark 命令策略 + 默认断网）。
> **剥夺它们的工具，是拿确定的能力损失，去换一个我们已经有替代方案的收益。**

**但"围栏"必须围住这四件事，缺一件就等于没围**（见 §5）。

## 3.4 ⚠️ 围栏方案下，一个必须重新设计的点

**这是本文最重要的一个推论，之前没有。**

agent 的原生工具（读文件、跑命令）**不经过我们的连接器网关**。那我们的**数据视窗**（行过滤 × 列规则 × 聚合规则）
怎么对它生效？

❌ **错的答案**："在提示词里告诉它别读那些字段"——**这不是控制措施**（`19` §3.4 已定死）。

✅ **对的答案**：**数据视窗的出口在"喂进沙箱的数据"上。**

```
平台把裁剪后的数据物化成一个工作文件（或一个只读挂载）
        │
        ▼
沙箱内的 agent 只看得见这个文件
        │
        ▼
它的原生工具读的是"已经裁剪过的值"——它根本没有原始数据可读
```

**这条把"数据视窗"从"agent 看不看得到"变成"沙箱里有没有"** ——
**这才是物理隔离，而不是君子协定。**

**推论**：装载时，数据面的职责多一条——**把裁剪后的数据集物化进沙箱**，
而不是让 agent 拿凭据去查原始库。

# 第四部分 · 工具系统

## 4.1 工具的来源（三类，一视同仁）

| 来源 | 怎么进 agent | 谁负责 |
|---|---|---|
| **我们自研的工具** | manifest 声明 → 装载器注册 | agent 运行时 |
| **连接器暴露的能力** | 走平台连接器网关；**也可以经 MCP 注册**（`dsh-mcp-client` 已验证支持） | 平台 |
| **引擎的原生工具** | **保留**（§3 结论），通过沙箱 + 命令策略约束 | 引擎自己 |

**一条纪律**：不管哪来的工具，**都要进同一套"声明 + 装载 + 裁剪"管线**。
**裁剪链不动**，只是"工具来源"变多。

## 4.2 工具 manifest（自研工具）

```yaml
工具:
  名字: inventory_query        # 唯一标识
  描述: "按仓库查库存"          # 给模型看的一句话
  参数: {仓库, SKU}
  权限档: 只读                 # 只读 / 读写 / 需审批 / 完全
  高危: 否
  连接器: inventory            # 归属哪个连接器（独立工具则空）
  版本: 1.0.0
```

**装载器**：启动时读所有 manifest → 注册成工具清单 → 按**已有的裁剪链**裁剪。

**迁移策略：64 个工具一次性全改，不分批。**
理由：分一半会让"装载"变成两套逻辑，更乱；写 manifest 是机械劳动。

**验收**：加/删一个工具，**不改核心代码、不整体重启**。

## 4.3 大结果落盘（spill）

⚠️ **先纠正一个误解**：spill 和"修剪"**不是一回事，发生在两个不同时刻**。

| | **spill** | **修剪**（§4.4） |
|---|---|---|
| 什么时候 | **工具刚返回时** | **压缩会话时** |
| 干什么 | 太大 → 全文存盘 → 上下文只留"头尾预览 + 定位符" | 历史里的旧结果 → 掐中段，留头尾 + 插标记 |

**取值**（机制来自 harness 源码；**数值逐项标注来源，勿一律当"实读源码"**——见补充 补-0）：

| 项 | 取值 | 理由 |
|---|---|---|
| 阈值 | **32768 字节**（**我拍**，非 harness 默认；单位是**字节**不是字符） | harness 默认是"不生效"（opt-in），**但我们不能默认关**（成本是刚需）；32768 = 修剪阈值 8192 的 4 倍，保证"先便宜修剪、超了才存盘" |
| 预览 | **头尾对半分** | 预览是"已存盘文件的采样"，头尾同等重要（**与修剪的 4:1 不同**） |
| 存储 | 按运行/会话隔离，**随生命周期销毁** | 不持久化，避免数据留存负担 |
| 取回 | 配 `fetch_spill` 工具按范围取 | agent 需要细节时主动取 |
| 失败 | **best-effort，保留原内容** | ⭐ **存盘失败不能影响工具调用的成败** |
| 跳过 | `read` 工具跳过 | 避免 `read → spill → read again` 死循环 |

**提示格式**：`(Omitted N bytes. Full formatted result stored at: <定位符>. <取回指引>)`——**带精确省略量**。

## 4.4 工具结果修剪

**默认值**（实读 harness 源码；**作者原先编的 2000/2000 是错的**）：

```js
{ thresholdChars: 8192,   // 超过才修剪
  headChars:      4096,   // 保留开头
  tailChars:      1024 }  // 保留结尾
```

> ✅ **2026-09-15 独立复算确认**（实读 `dsh-compaction-tool-result-pruner` 源码：`thresholdChars: 8192`、`headChars: 4096`、`tailChars: 1024`）。

**关键：头尾比是 4:1，不是 1:1。** 头比尾重要得多——工具结果开头通常最有信息量（表头、列名、结论）。

**其它要点**：
- **标记固定为 `[... tool result middle pruned ...]`**
- **按 Unicode 码点切片**（不切断代理对）
- 校验约束：`headChars + marker + tailChars ≤ thresholdChars`
- **回放安全**：追加一条 `compaction/prune` 事件，记录被替换的原节点

## 4.5 工具结果膨胀的四条纪律

见 §2.2.6。**核心一句**：大结果落盘 + 上下文只留"摘要 + 定位符"，
**让 agent 知道自己不知道什么**。

# 第五部分 · 隔离（四层，缺一层就破）

> ⭐ **这是本文最需要你确认的一节**，因为它推翻了"两个沙箱选一个"的旧写法。

```
第 1 层  gVisor（或 microVM）        ← 平台侧，属"沙箱实现"
   整个环境隔离：防逃逸、跨租户、跨项目
   ⚠️ 它挡不住 curl —— 网络要另管
              │
第 2 层  harness 自带沙箱            ← 引擎侧，属"引擎能力"
   workspace-write：只允许写工作区
   read-only：拒绝一切变更
   fail-closed：拿不到模式就失败，不降级运行
              │
第 3 层  工具层围栏                  ← 谁提供工具，谁负责
   DSH：dsh-fs-sandbox 在工具层强制，文件与 shell 同根目录
   Codex：Starlark execution policies（allow / prompt / forbidden），在沙箱之前评估
              │
第 4 层  网络出口                    ← 平台侧
   默认断网；需要联网走白名单代理
   ⭐ 这一层是 gVisor 与 harness 沙箱都覆盖不到的
```

## 5.1 为什么这四层不是冗余

| 层 | 挡什么 | 谁挡不住它 |
|---|---|---|
| gVisor | 内核漏洞利用、容器逃逸、跨租户 | 挡不住"本租户内越权写文件" |
| harness 沙箱 | 本环境内的越界写 | **挡不住逃逸**（它自己说了是同世界隔离） |
| 工具层围栏 | 危险的命令语义（`rm -rf`、`git push`） | 挡不住绕过 shell 的路径（如原生文件工具） |
| 网络出口 | **数据外泄、下载恶意载荷** | —— |

**四层各挡一类，没有一层能单独顶住。**

## 5.2 ⭐ gVisor 怎么和 harness 沙箱共存（这条是本文新增）

DS harness 把沙箱做成了**契约 + provider 注册表**（`ctx.sandbox` + `SandboxProvider`）。
所以正确做法**不是二选一，而是**：

| 层 | 我们做什么 |
|---|---|
| **平台侧** | **把 gVisor 作为 agent 的运行环境**（每个运行一个 gVisor 实例 / microVM 给敏感场景） |
| **agent 侧** | **挂载 harness 自己的沙箱后端**（`dsh-sandbox-local` 的 bwrap / Landlock / Seatbelt / Windows ACL），在 gVisor 内部再收一层工作区围栏 |
| **结果** | 外层防逃逸与跨租户，内层防误写。**两层都留着，因为它们的失败模式不同** |

**"能不能加一个 gVisor provider"标为 ⚠️ 待验证**（§11）——
契约在，但"在一个已经隔离的环境里再挂一个进程级沙箱"是否会冲突（例如 bwrap 在 gVisor 内不可用），
**必须实测，不能推断**。

## 5.3 平台侧还要管的四件事（这些 agent 侧不管）

| # | 事项 | 为什么 |
|---|---|---|
| 1 | **网络出口** | gVisor 与 harness 沙箱**都不管这个**；默认断网 + 白名单代理 |
| 2 | **数据物化**（§3.4） | 把裁剪后的数据放进沙箱，agent 才有"合法的数据"可读 |
| 3 | **凭据不进沙箱** | 连接器凭据留在平台侧，agent 只有工具、没有钥匙 |
| 4 | **`--yolo` 类开关封禁**（§3.2.4） | 参数白名单，不让逃生门出现 |

## 5.4 沙箱的生命周期（成本关键）

**沙箱是一次性的**：用完即毁（不变量 S1）。

⚠️ **等人复核时，沙箱必须销毁**：

```
agent 产出草稿 → 运行进入"等待人工确认"
                        │
                        ├─ ❌ 错误：沙箱挂着等
                        │     → 一个等待复核的任务占着一个沙箱几小时
                        │     → 50 个单子同时在等人 = 50 个沙箱空转
                        │
                        └─ ✅ 正确：**沙箱立即销毁**
                              人复核完 → 重建沙箱继续
```

**为什么重要**：沙箱是这套系统的主要成本之一，而"等人"天然是慢的。
**如果沙箱跟着等，成本曲线就被"人的响应速度"决定——那是最糟糕的一种成本结构。**

# 第六部分 · 会话与运行

## 6.1 四种寿命必须分清

| 概念 | 寿命 | 说明 |
|---|---|---|
| **交付物** | 长期（月/年） | 有版本、有状态、有复核记录 |
| **会话** | 天 / 周 | 人机交互的容器，可跨天 |
| **运行** | 分钟 / 小时 | 一次执行 |
| **沙箱** | **分钟级** | **用完即毁** |

⚠️ **这四种都在"一个数字员工之下"**——数字员工本身是第五种寿命（月～数年）。
**分界**：本文管"一次干活的寿命"。

**关键推论**：运行可以等几小时（等人复核），**但沙箱不能等**——两件事必须解耦。

## 6.2 两种触发，结构不同

| | 有人触发 | 无人触发（定时 / 事件） |
|---|---|---|
| 有会话吗 | **有**——人机交互 | **没有**——就是一个独立运行 |
| 特点 | 可以多轮、可以追问 | 一次跑完就结束 |

**别硬把定时任务塞进"会话"里**——它没有对话，塞进去只会让会话状态机难以理解。

## 6.3 运行状态机

```
排队 ──► 启动中 ──► 执行中 ──┬──► 已完成
                              ├──► 等待人工确认 ──┬──► 已确认 ──► 已交付
                              │                    └──► 被退回 ──► 执行中
                              ├──► 预算耗尽 ──► 已中止（保留部分结果）
                              └──► 失败
```

⚠️ **"等待人工确认"是一个独立状态，不是"还在跑"。**
混了的话：对外接口会让客户的集成一直等不到结果；对内监控、计费、超时策略处理完全不同。

## 6.4 三种中断，恢复方式不同

| 中断原因 | 能不能继续 | 怎么继续 |
|---|---|---|
| **人主动打断** | ✅ | 接着跑，上下文还在 |
| **预算耗尽** | ✅ **但要追加预算** | **不能自动续**，否则预算就是纸糊的 |
| **系统故障** | ✅ | **从检查点重建** |
| **策略拒绝 / 越界** | ❌ | 不恢复，等人工处理（**这可能是安全事件**） |

## 6.5 检查点存什么、不存什么

| 存 | 不存 |
|---|---|
| 上下文摘要 | **沙箱状态** |
| 已完成到哪一步 | 沙箱里的临时文件 |
| 已产出的交付物（已独立存在） | 内存里的凭据 |
| 剩余预算 | —— |

⭐ **核心：恢复 = 重建一个干净沙箱 + 重放上下文摘要。**
**不是"把沙箱恢复回来"**——沙箱是一次性的，指望它活着本身就是设计错误。

> **归属定死**：检查点**既不是**工作区记忆**也不是**数字员工记忆，它是**运行的附属物**——
> 寿命跟着运行走。**推论**：运行结束/终止后，检查点按审计周期保留，
> **但不进任何"记忆召回"的候选集**。

## 6.6 ⭐ 验收钩子（机器判定 vs 人的业务判断）

| | **验收钩子**（自动） | **人复核** |
|---|---|---|
| 谁做 | **系统** | 人 |
| 什么时候 | 运行产出后**立刻** | 排在人的待办里，可能几小时后 |
| 判什么 | **机器可判的**：结构对不对、必填字段有没有、有没有突破硬阈值 | **业务判断**：这个数合不合理、要不要改 |
| 结果 | 通过 → 进人复核队列；不通过 → **当场打回给 agent 重试**（省掉人白看一遍） | 改 / 批 / 驳 |

**三条规则**：
1. **钩子只判"机器可判"的**，判不了的一律交给人（**不许用模型冒充业务判断**）
2. **钩子不通过 → 先让 agent 自己修**（可配重试次数）
3. **钩子结果进账本 + 进经验**

> **一句话**：**钩子管"格式和硬线"，人管"业务判断"。**

## 6.7 会话的归属、过期与并发

- **归属**：会话**属于工作区**，不属于平台，也不属于人
- **并发**：**同一会话串行**（不会两个人同时用同一个会话打架）
- **三种寿命不同**：**会话过期 ≠ 产出过期 ≠ 记忆过期**，分别管

# 第七部分 · 按需召回与记忆

## 7.1 真正的根因

**不是"没有向量检索"，是"预先注入太多"。** roni 现在每轮都注入：

| 每轮注入 | 量级 |
|---|---|
| 技能全文 | 单技能上限 **1.6 万字符** |
| 知识 | **12 条**（自动注入） |
| 项目说明 | **1.6 万字符** |
| 系统提示（身份/环境/纪律） | 几百行 |
| 运行时快照 + 最后 8 条 git 提交 | 每轮都变 |

**轮次越多、注入越多，成本线性叠加。** 原则反过来：**能"按需取"的，绝不"预先塞"。**

## 7.2 四件事

| # | 从 | 改成 |
|---|---|---|
| **1 技能** | 全文进系统提示 | 系统提示只放**技能目录**；用时调"**加载技能**"工具取全文 |
| **2 知识** | 每轮注入最近 12 条 | 给"**查知识**"工具，需要时才查 |
| **3 结构化数据** | 靠"记" | ⭐ **连接器精确查询**，**不进上下文、不进向量库** |
| **4 会话历史** | —— | 比例制压缩（§7.3）+ 中段修剪（§4.4） |

## 7.3 压缩：比例制 > 绝对值

| 配置 | 取值 | 含义 |
|---|---|---|
| `thresholdRatio` | **0.8** | 在模型上下文窗口的 **80%** 触发压缩 |
| `retainRatio` | **0.16** | 保留最近上下文为模型窗口的 **16%** |
| 摘要输出上限 | 8192 tokens | |
| 重试 | 压缩后仍超阈值再试 1 次；溢出后恢复重试 1 次 | |
| 触发时机 | 自动，在**步边界** | |

> ✅ **2026-09-15 独立复算确认**（实读 `dsh-compaction-basic` 源码：`DEFAULT_THRESHOLD_RATIO = .8`、`DEFAULT_RETAIN_RATIO = .16`）。

> **为什么比例制更对**：换一个小窗口的模型，阈值**自动跟着变小**，不需要改配置。
> 绝对值换模型就失效。

## 7.4 全文 vs 向量

**先做全文检索（FTS5）打底，向量作为"留位置、后补"的增强。**

**三条理由**：
1. harness 就没用向量（它的包列表里没有 vector / embed / rag 相关）——说明对 agent 场景**够了**
2. 向量要额外成本：embedding 调用 + 向量库维护，是**持续开销**
3. 中文业务术语全文够用："备货计划""库龄""头程时效"这类词，全文匹配很准

**什么时候才真需要向量**：当"**语义相似但用词不同**"成为刚需时
（问"库存积压情况"，资料写"库龄过高"——全文匹配不到，向量能匹配到）。

**这是"接口留位置"**：检索接口设计成**可换检索后端**，将来插向量库不用重构。

## 7.5 记忆的四个层次（agent 侧只管存取的机制）

⚠️ **记忆的"归属与权限"归平台**（`26` §1.2 归属链）；**agent 侧只管"怎么存、怎么取"**。

| 层 | 存什么 | 谁写 | 寿命 |
|---|---|---|---|
| **工作区记忆** | 这个工作区的事实 | 平台 | 长期 |
| **数字员工记忆** | 这个员工学到的 | 平台 | 长期 |
| **会话记忆** | 这次对话的上下文 | agent | 天/周 |
| **任务现场**（= 检查点） | 跑到哪一步了 | agent | **跟着运行走** |

> ⚠️ **"任务现场"不是记忆，是检查点**（`13` §3.1 已对账）。
> **推论**：运行结束后它**不进任何"记忆召回"候选集**。

# 第八部分 · 子代理与编排

## 8.1 子代理的价值是"上下文隔离"，不是"能力增强"

⚠️ **搞反会白白烧掉很多钱。**

| 该用 | 不该用 |
|---|---|
| 任务能并行（多个独立调查） | 简单任务（拆了反而更贵） |
| 需要大量试错的脏活，但只要一个干净结论 | 需要共享大量上下文的（拆了要反复传，**传的就是钱**） |
| 需要一个"不同性格"的执行者（如专门挑错的审查者） | 单线程的线性任务 |
| 上下文会爆炸，必须隔开 | —— |

**判据**：解决的是"**这一大堆中间过程不该污染主上下文**"，不是"多个人干活更快"。
**每次派活都有传递成本，收益必须来自"隔离掉的上下文"，否则纯亏。**

## 8.2 四条硬约束

| # | 约束 | 说明 |
|---|---|---|
| **1** | **权限 ≤ 父级** | 通常**严格小于**——只给这个任务需要的 |
| **2** | **预算切分，不共享** | 它超支不能拖垮父级 |
| **3** | **深度限制** | **建议上限 2 层**（⚠️ 这个 2 是我拍的，见 §11） |
| **4** | **结果收敛** | 只回传结构化结论，**不回传原始上下文** |

第 4 条两个理由：**防上下文爆炸** + **防污染**（子代理读到的外部内容不该流进主上下文）。

## 8.3 统一接口（平台看到的是同一个东西）

```
派活(
  任务说明,
  上下文切片,        ← 只给它需要的那部分
  预算额度,          ← 切分出来的，不是共用
  权限子集           ← 父级的真子集
)
  ↓
结论(
  结构化结果,        ← 符合声明的结构（Codex：--output-schema）
  消耗了多少,
  用了哪些能力,      ← 审计
  结束原因           ← Codex：语义退出码 0/2/3/4/130
)
```

**这是 ADR-5 的第二次考验**：换引擎不该改业务资产，**换子代理引擎同样不该**。

> ⭐ **本文 §3.2.2 的评估说明 Codex 天然满足这个接口**（`--json` + `--output-schema` + 退出码）。
> **DS harness 的子代理也是 seam + provider 注册表**（§3.1.1）。**两家的接口形状与我们的定义是一致的。**

## 8.4 权限收缩在 agent 侧的落点

**子代理的工具清单 = 岗位包能力 ∩ 它声明要用的能力，过滤后下发。**

查库存的子代理，清单里**只有** `inventory.query`——
物流、写库、外发**根本不出现**（不是"出现了但被拦"）。

## 8.5 预算怎么切

| 规则 | 为什么 |
|---|---|
| 切出去的是**额度**，不是共享池 | 一个子代理失控不能烧掉整个任务 |
| **父级必须留一部分给自己** | ⭐ 不预留的话，子代理跑完，父级发现自己**没钱把结果汇成交付物** |
| 没花完的**显式回收** | **不自动回流**——否则并发时会出现"两个子代理都以为还有余额" |
| 按**复杂度**分，不平均 | 平均分会让简单任务浪费、复杂任务不够 |

## 8.6 与平台的分工

```
岗位包：声明「备货 = 销量子代理 + 库存子代理 + 物流子代理 + 验证子代理 → 汇总」
平台：  拆解 + 权限收缩 + 预算切分 + 并发调度 + 回收 + 汇总 + 审计
agent： 提供「跑一个子代理」的能力（引擎 + 工具）
```

**agent 侧只负责"跑起来"**；"派几个、给多少、谁来汇总"归平台。
理由：三个 agent 都要能跑同一套编排，调度逻辑不能长在某个 agent 里。

# 第九部分 · 循环检测与成本控制

## 9.1 循环检测：分级提醒，不熔断

**照搬 harness（实读源码）。**

| 项 | 做法 |
|---|---|
| **阈值** | `[3, 5, 8]`——连续相同调用到 3 / 5 / 8 次分别触发 |
| **性质** | **分级提醒，不是熔断**。原话："enriches post-execute decisions... **without vetoing or rewriting calls**" |
| 第 3 次 | 温和提醒："你在用完全相同的参数重复同一个调用。仔细分析之前的结果；如果没完成，换方法或换参数。" |
| 第 5 / 8 次 | 详细提醒：点名工具、连续次数、参数 |
| **参数比较** | **深度 key 排序后再比**（否则 `{a:1,b:2}` 和 `{b:2,a:1}` 会被当成不同参数） |
| 参数预览 | 截断到 **500 字符** |
| 来源标记 | 标为"插件"，**防止被渲染成用户提示** |

> ✅ **2026-09-15 独立复算确认**（实读 `dsh-repeat-tool-reminder` 源码：`thresholds: z.array(z.number()).default([ 3, 5, 8 ])`、`argumentsPreviewChars: z.number().default(500)`）。

**为什么不用熔断**：熔断会**误杀合法的重复调用**（轮询任务、等外部系统就绪）。

**和预算配合**：提示到 8 次仍不收敛，**由预算软着陆兜底**——**不再叠一层熔断**。

## 9.2 预算软着陆（而不是硬停）

**预算总量与裁决归平台**（§1.2 边界三），**agent 侧负责"被执行"**。

**四种预算同时管**：token · **钱（最硬）** · 步数 · 墙钟时长。

```
消耗到 70%  →  提示 agent 收敛（减少探索、少做检索）
消耗到 85%  →  换便宜模型
消耗到 100% →  优雅中止（**保留已产出的部分结果**）
```

**硬停会让人白等一场**，软着陆至少给出一个可用的部分结果。

## 9.3 省钱的顺序（按性价比）

1. **别放不该放的进上下文**（§2.2）——零成本，收益最大
2. **大结果落盘**（§4.3）——零模型成本
3. **按需召回**（§7.2）——省的是"每轮都付"的那部分
4. **压缩**（§7.3）——要花一次摘要的钱，但省后续每轮
5. **换便宜模型**（§9.2 的 85% 档）——最后手段，因为会影响质量

## 补-1 前缀与缓存纪律（成本结构的架构级结论）—— 实测

**RW 现状（代码证据）**：三个"原地改写前缀"的动作会让前缀缓存**周期性全量作废**——
`archiveEarlyContext` 就地改写早期 tool/assistant 内容；`maybeCollapseEarly` splice 掉早期区间；`refreshSys()` 每轮重写 `msgs[0]`，且 `skill_load` 把技能全文拼进系统消息。

**DS 实测**（2026-09-15，本对话所在会话 3032 次请求）：命中 **1,340,696,704** tokens / 未命中 **3,819,230** → **整体命中率 99.72%**；中位单次命中 99.94%；**未命中的 41.4% 只来自 12 次请求**。
**四类失效（实测）**：① 首轮必 0%；② **切模型＝命中归零**（seq 17460/17472 各 26–27 万 tokens 全未命中）；③ 长空闲（小时级；而 6~39 分钟的空闲**未掉**）；④ **工具 schema 变更＝最贵单笔**（40→73 个工具，一次 574,865 tokens 未命中）。折叠边界会短暂掉到 73.7%–84%，1–3 次请求内恢复。

**五条纪律（架构级约束，缺一不可）**：
1. **只追加**：禁止中途改写早期消息；折叠只在**段边界整段替换一次**。
2. **前缀冻结**：系统提示会话内不变；技能/知识/目标/时间/快照一律进"**尾巴区**"；确需变更时**追加为 in-history 节点**（DS `request/context` 实测带 `systemPromptUpdate: "in-history"`）。
3. **工具面会话内冻结**：工具数组定版后不变；MCP 动态装载 / 改档位 / 换壳 = **新段**，并明确提示"本次变更会重建缓存"。
4. **增量最小化**：大结果一律溢出（§4.3）。
5. **失效可数**：失效事件是一等观测指标；**任何进入请求前缀的组件必须声明其缓存影响**（DS 的每个包 README 都有强制的「KV Cache 影响」小节，grep 到上百处）。

**指标口径的权威**：`proposals/RW-Agent引擎架构优化方案-v0.3.md` §0.3（C1–C4）——**C4「非预期失效次数」才是工程目标**；单独的"命中率"会掩盖浪费（分母是累计上下文，天然就高）。

## 补-2 骨架（服务注册与替换 · 契约 · 声明式 · 不变式 · 确定性）—— 引用

**结论**：七面只回答"由哪些职责组成"；让这些职责**可替换/可声明/可演进**的是另一层承重结构——**骨架**。缺了它，七面只是功能清单，做出来仍是硬编码单体。

## 补-4 交互契约（可观测 · 可控制 · 可信 · 跨端语义一致）—— 引用

**与 `13` 的分工**：`13` 定**状态机语义**（"等待人工确认"是独立状态等）；本节要的是**对外事件契约**（事件类型/语义/版本）。

## 补-5 交付与跨平台（Windows Server / 无外网 / 账本导出）—— 引用

**实测事实**：RW 的提示层与工具层**写死**"Linux 服务器 + bash + `/srv` 路径"→ 客户用 Windows Server 直接跑不起来；Codex 的 Windows 沙箱是**实验性**（AppContainer，官方明写挡不住 Everyone 可写目录，本文 §3.2.1）；DS 的 Windows ACL 后端是 **same-world**（本文 §3.1.1）。
**处置**：执行后端抽象 + 双平台；**云侧用 gVisor/microVM、客户侧用平台原生等价物（不搞一刀切 gVisor）**。
**权威**：v0.3 §5 + M2 出口（无外网 + Windows Server + 自助安装包 + 账本可导出）+ D2/D3；本体系内相关：`14`／`05` §4 网络默认断／`16`／`44`。

## 补-6 自进化（对标学习 + 自我体检 + 业务反馈）—— 引用

**三源输入**：外部对标（DS/CD 机制变化，**逐条判适配性**）· 自我体检（C4 失效、C2 增量、成本、失败率、回归）· 业务反馈。

**权威**：v0.3 M3；本体系内相关：`47`／`29` §4。
