## 0. 先把两个角色分开

这是整块设计的地基，分开之后很多问题会自己消失：

| | **审批** | **受信执行器** |
|---|---|---|
| 是什么 | **人做的决定**（要不要放行） | **机器做的动作**（执行已批准的决定） |
| 有什么权限 | 判断权，**没有执行权** | 执行权，**没有判断权** |
| 能读业务数据吗 | 能（要看清才能批） | **不能**（只读回滚所需的最小信息） |

**为什么要分开**：这样"谁有权改生产"这个问题只有一个答案——执行器。而它自己不会做任何决定，只听已批准的请求。

于是 agent 从头到尾**没有碰过写路径**——不是靠提示词约束，是它根本没这个能力。

### 0.1 ⭐⭐ 审批中心属于哪个面、谁能批（Day 7 定，P0-1）

**独立对抗性评审的一号发现**（必须正面回答）：

> **平台运营方同时掌握"给数据面下配置/策略"和"审批中心"两把钥匙 —— 读写两条路都通，且全程不需要客户参与。**
>
> 而 §0 的整个前提是"**审批人有判断权、没有执行权**"——**这个前提在运营方身上不成立**。

**这是本条设计里最严重的一处**：它让"客户的生产系统只有人能改"变成了"只有**平台**能改"。

**我拍四条（缺一不可）**：

| # | 规则 | 理由 |
|---|---|---|
| **① 审批中心落在【数据面】** | 与执行器同侧。**控制面不得持有"批准"这个动作** | 审批是"决定放行"，它必须和"执行"在同一信任域里；分开就等于给控制面留了一条万能写路径 |
| **② 审批人必须是【客户身份】** | 平台运营方**永远不能作为审批人**出现在客户的审批链里。运营方的权限是**运维与合规**，不是**业务授权** | 这是 ADR-7 三层身份的必然结论：**授权的权力属于资产所有人** |
| **③ 平台运营方的所有动作都是"可被客户看见的事件"** | 运维操作（改配置、下发策略、排查）**全部进客户可读的审计流**，且**不能借道 agent** | `01` §4.3 已定"运维通道与 agent 通道分离"，这里补"且客户可见" |
| **④ 平台级知识 / 技能 / 插件的写权限归【客户技术团队】** | 平台方可以**提供**，**不能单方面"推送生效"** | `33` §4.3 现在写的是"平台级知识只有运营方写、客户只读"——**那等于运营方能往客户数字员工的脑子里塞东西**（见 `33` §4.3 的修正） |

> **一句话**：**平台方可以提供能力，不能代替客户做决定。**
> **"最高权限是最大风险点"这句话，靠合同和审计是挡不住的——要靠"审批权不在平台手里"。**

**加进验收**（`31` G16–G18）：
- 客户的审批链里**不出现任何平台方身份**
- 运营方的每次运维动作**在客户审计流里可见**
- **拔掉控制面，客户的数据面能继续独立跑**（含审批与写回）

## 1. 一次写请求的完整生命周期

```
① agent 产出交付物（草稿态）
        │
        ▼
② 人复核、修改            ← 这一步同时是「学习闭环」的数据来源
        │  点"提交审批"
        ▼
③ 审批人看到：改了什么、为什么、影响范围、风险提示
        │  批准 / 驳回（可带意见）
        ▼
④ 受信执行器执行（幂等、可回滚、留回执）
        │
        ▼
⑤ 审计：谁提请、谁批、批了什么、执行结果
```

**关键在 ①→② 之间**：agent 的工作**到此为止**。它产出的是草稿，不是动作。

## 2. 写操作要分级，不能一刀切

把所有"写"都当成高危，会导致没人愿意用；都当成无害，会出事。分五级：

| 级别 | 是什么 | 谁批准 | 例子 |
|---|---|---|---|
| **L0** | 沙箱内写 | 无需审批 | 在临时目录写中间文件，随沙箱销毁 |
| **L1** | 产出交付物 | **复核**（一人） | 生成计划表、报表 |
| **L2** | **草稿态写** | 复核 + 一次确认 | 在 ERP 里建一张"待提交"的单据 |
| **L3** | 生效写 | 审批（可能双人） | 提交单据、改状态 |
| **L4** | 高风险写 | 双人 + 时间窗 + 必须可回滚 | 改权限、改组织结构、改金额阈值 |

### 2.1 L1 和 L2 的区别是"复核"和"审批"的区别

这两个词在中文里常被混用，但在这套设计里必须分开：

- **复核（L1）**：看一眼这个结果对不对 → 是**质量把关**
- **审批（L2/L3）**：决定这个动作能不能发生 → 是**授权**

L1 不该做得像审批那么重，否则人嫌麻烦就不用了。**L1 的界面应该像"改一份自己的文件"，不是"签一份文件"。**

### 2.2 L2 是"一步做到底"的落点

你之前说过"等稳定了、信任高了，再一步做到底"。**L2 就是那个形态的技术实现**：

> agent 在 ERP 里把单子**填好**，状态停在"草稿/待审"，**人检查无误后点提交**。

好处：
- agent 的活确实干到底了（录入这个最烦的环节全免了）
- 但**没有任何生产数据被改动**——草稿不算数
- 人的工作量从"从头开一张单"变成"扫一眼、点确认"
- 风险仍极低，可以比想象的更早上

> ⚠️ **待确认（已登记在交接文档）**：客户的 ERP 是否支持"草稿/待审"状态。这决定 L2 能不能落地。如果不支持，就只能停在 L1（产出 Excel）。
> **✅ Day 2 已确认：客户 ERP 支持。** 所以 L2 可以落地。

### 2.3 ⭐ L3 的首跑护栏（Day 3 新增：客户选了"允许不可逆写"）

**背景**：客户的很多系统**没有测试环境**（外采 ERP SaaS、Shopify、Amazon 都只有生产）。但客户要的就是"**帮我真下单**"。
**所以平台选了 A 方案：允许不可逆写，但首跑必须有人监督 + 小范围。**
**这条选定的代价是——不能靠"承诺小心"，必须靠机制。**

#### 2.3.1 先分清"预演"和"dry-run"（最容易被糊过去的一步）

| | **技术 dry-run** | **业务预演（Rehearsal）** |
|---|---|---|
| 做法 | 真发请求 + 不生效标记 | **渲染一份"如果执行会是什么样"的完整方案，不发请求** |
| 需要什么 | **目标系统支持测试模式** | **什么都不需要** |
| 适用 | 有测试环境的连接器 | **无测试环境的外采系统** |

> ⭐ **没有测试环境时，唯一能做的"预演"是"把要执行的动作完整渲染给人看"**——不是发一个假请求。

**按连接器可测性分三种处置**：

| 可测性 | 上岗联调 | 首跑护栏 |
|---|---|---|
| **`full`**（有测试环境） | 双跑对比，写操作在测试环境真跑 | **技术 dry-run**（最充分） |
| **`readonly`**（生产可读） | 生产只读探测 | **业务预演**（渲染方案 + 反向动作） |
| **`none`** | 靠代理指标 + 客户确认 | **业务预演** + 更严护栏 |

#### 2.3.2 第 0 步：不可逆操作清单必须先定

**危险等级不能靠模型判断，必须是配置。**

```yaml
连接器: ERP
能力: submit_purchase_order
  写级别: L3
  可逆性: 不可逆          # 三档见 §2.3.5
  批量上限: 1             # 首跑强制 1
  时间窗: 工作日 9:00-18:00
  预演期要求: 连续 3 次成功
```

**谁定**：**客户技术团队在接入连接器时声明**（`32` §7 第二步），平台方复核，**agent 不可改**。

#### 2.3.3 预演期怎么运作

```
agent 想执行不可逆操作
      │
      ▼
① 不执行，先生成【执行预演单】★
     · 完整参数（哪张单、哪几条、多少钱、什么时间）
     · 预期效果
     · 【反向动作提案】⭐（§2.3.4）
     · 风险提示（触没触阈值、有没有异常）
      │
      ▼
② 人看预演单 → 批准 / 驳回
      │  批准的是"这一种操作可以真执行"，不是"你可以随便写"
      ▼
③ 受信执行器真执行（首次全程监督）
      │
      ▼
④ 【自动验证】（§2.3.6）：实际结果 vs 预期效果
      │
      ▼
⑤ 记账本：第 N 次成功  →  达到阈值则退出预演态（数据说的，不是模型说的）
```

#### 2.3.4 ⭐ 反向动作提案：预演期最值钱的产出

**`06` §3 说"一键回滚是人敢批的前提"。没有测试环境时，"有没有回滚路径"这件事本身就要靠预演去发现。**

**预演单里必须有一条：如果这个动作错了，怎么撤回？** 三种答案对应三种处置：

| 答案 | 处置 |
|---|---|
| **系统支持撤销/作废** | 记录撤销路径；预演期内**每次执行后主动提示"可撤销窗口剩 X 小时"** |
| **只能冲销**（反向单） | 预演单里**同时生成反向单草稿**，一键可发 |
| **真不可逆** | **明确标记 → 自动升级**：更严审批 + 更小批量 + 更强事后验证 |

#### 2.3.5 可逆性三档 × 处置（落地照着配）

| 档 | 例子 | 预演要求 | 审批 | 事后 |
|---|---|---|---|---|
| **可撤销** | 建草稿单、改一个字段 | 首次必做 | 单人 | 提示撤销窗口 |
| **只能冲销** | 提交单据、改状态 | 每次预演单含反向单草稿 | 首次双人 | 自动生成冲销草稿 |
| **真不可逆** | 下采购单、上架、发 offer、改价 | 首次必做 + **反向动作提案必填** | 首次**双人 + 时间窗 + 小批量** | 强验证 + 告警 |

#### 2.3.6 ⭐ 自动验证：让"首跑即测试"真正成立

**"首次人工监督"如果只是"人盯着看"，既不可靠也不可扩展。** 所以每次 L3 执行后**必须自动验证**：

```
执行成功 → 自动验证（不需要人参与）
   · 目标系统里这条记录的状态对不对？
   · 关键字段值是不是我们提交的？
   · 下游有没有异常（库存变了但销量没动）？
   │
   ├─ 通过 → 计入成功计数 → 喂给 `29` 经验库（"这么干是对的"）
   └─ 失败 → ① 立即告警 + 转人工
             ② 本次不计成功
             ③ 降回预演态
             ④ 相关经验按 `29` §4.2 标"可疑"
```

**这一步接上三件事**：`28` §3 的学习闭环（机器判定版）、`29` 经验、`36` 的成熟度阶梯。

> **一句话**：**"没有测试环境"靠"每次真实执行都自动验收"来补偿**——它比测试环境更真实，**它测的是真系统**。

#### 2.3.7 ⭐ 成熟度阶梯：用数据放行，不用感觉放行

**"人监督、小范围"必须是可计算的状态。**

```
预演态        →   收敛中        →   稳定期
每次预演单+人批    抽检（如每 5 次抽 1）   按 L3 常规审批（§2）
批量 1           批量可放大到中档        批量到常态值
```

**升级条件（全部满足）**：

| 条件 | 数据来源 |
|---|---|
| 连续 N 次成功 | 计数（复用 §5 的阈值机制） |
| **自动验证零失败** | §2.3.6 |
| 人工驳回率为 0 | 审批记录 |
| 无异常告警 | 审计 |
| 经过 T 天（防止一天刷过去） | 时间 |

**降级条件（任一命中，自动且立即）**：

- 自动验证失败 1 次
- 触发风险告警（金额异常、目标系统报错、下游异常）
- 客户主动降级
- **连接器目标系统变更**（`04` 数据新鲜度发现源变了）

> ⚠️ **降级必须自动、立即**。人工申请太慢——**出错时需要的不是流程，是立刻上护栏**。

**两条不可逾越的底线**：

| 底线 | 内容 |
|---|---|
| **批量上限永远存在** | 成熟度再高，单次操作也**不得超过客户设的硬上限**；超上限必须走**单独更高一级的审批**（不是不能做，是不能"悄悄做"） |
| **L4 永远是 L4** | 改权限、改金额阈值、改组织结构**不因成熟度降级**（§2 已定：双人 + 时间窗 + 必须可回滚） |

> **第一条尤其重要**：成熟度是"这个员工在正常范围内可信"，**不是"它想下多少就下多少"**。模型不能学出"老板信任我所以我可以下 10 万单"。

#### 2.3.8 首跑必绑的四个约束

| 约束 | 值 |
|---|---|
| 批量 | **1**（一条、一张、一个 SKU） |
| 时间窗 | 客户业务时段（**不在夜里无人时跑首单**） |
| 审批 | **双人**（业务 + 管理/安全，§7 #3） |
| 监督 | 必须有人**在线**（不是"事后看"） |

#### 2.3.9 未验证能力台账

选了"允许不可逆写"，就意味着**有些能力带着"从未验证过"的状态上生产**。**这个事实必须上墙**（客户界面可见，不是藏在配置里）：

```
连接器: ERP      · submit_purchase_order   ⊘ 无测试环境   首跑: 未发生   成熟度: 预演态
连接器: Shopify  · product.publish         ⊘ 无测试环境   首跑: 未发生   成熟度: 预演态
                 · price.update            ⊘ 无测试环境   首跑: 3/20     成熟度: 收敛中(2/5)
```

**三条规则**：① **客户可见**（出事了双方都清楚这是已知风险，不是隐瞒）；② 客户技术团队必须看一次并确认；③ 首跑完成后自动更新。

## 3. 审批界面必须给人这五样（否则就是橡皮图章）

**没有这些，人会闭眼点"同意"——那审批就等于不存在，还不如不要。**

| # | 给什么 | 为什么 |
|---|---|---|
| 1 | **改了什么**（agent 原来的 vs 现在的 diff） | 人最想知道的就是这个 |
| 2 | **为什么**（agent 的解释） | 否则他无法判断改动是否有道理 |
| 3 | **影响范围**（涉及多少条 / 多少钱 / 影响哪些下游） | 判断风险大小 |
| 4 | **风险提示**（有没有触阈值、有没有异常） | 主动把可疑的地方指出来 |
| 5 | **一键回滚** | 批错了能撤——**这是人敢批的前提** |

**第 5 条最容易被省掉，但它决定人敢不敢用。** 一个不能撤销的审批界面，人的行为会退化成"全部驳回"。

---

## 4. 受信执行器的六条纪律

| # | 纪律 | 为什么 |
|---|---|---|
| **1** | **它是唯一的执行者** | agent 和人都不直接调它；它是唯一有生产写权限的东西 |
| **2** | **只执行已被批准的具体请求** | 不接受自由指令。批准的是"这一张单子"，不是"你可以写 ERP" |
| **3** | **幂等** | 同一个请求重复执行不产生副作用（网络会重试，这是必然会发生的） |
| **4** | **可回滚** | 执行前记录原状态，保留回滚所需的最小信息 |
| **5** | **不读业务数据**（**唯一例外：只读回执**，见 §4.1） | 它只写，防止它变成一个新的数据泄露点 |
| **6** | **全量留回执** | 执行结果、耗时、目标系统返回，全部入审计 |

> **第 2 条是核心**：审批的粒度是**一次具体的写**，不是"授信额度"。这样即使执行器被攻破，它能做的也只是"把已批准的那些单子再执行一遍"（幂等还会挡住），而不是"随便写"。

### 4.1 ⭐ 只读回执：第 5 条纪律的唯一例外（Day 7 补，解除一处真窟窿）

**独立评审（施工队试读）指出的最严重一条**：

> §2.3.6 要求 L3 执行后"**比对目标系统实际状态**"，而第 5 条纪律说执行器"**不读业务数据——它只写**"。
> **谁来读？没写。** 若由 agent 读回，它要过数据视窗，可能遮蔽它自己的写结果 → **验证永远失败 → §2.3.7 永远降回预演态 → 该岗位永远上不了生产。**

**我拍三条补上**：

| # | 规则 | 说明 |
|---|---|---|
| **① 新增独立通道：只读回执** | 它是**受信执行器的一部分**（同一信任域），**只读它刚刚写过的那条记录的状态字段**，不读其他任何业务数据 | 它只回答一个问题："**我写的那张单子，现在是什么状态**" |
| **② 回执不过数据视窗** | 回执读的是**执行器自己写的那条记录的元状态**（状态码 / 时间戳 / 成功标志），**不是业务数据** | 这是它与"agent 读回"的本质区别——**不存在"被视窗遮蔽自己的写结果"** |
| **③ "验证做不了"是可降级场景** | 若目标系统连"查状态"都不支持（老 ERP 常见），**不是"永远停在预演态"**：走 §2.3.9 的**未验证能力台账 + 客户签字确认**，然后允许在"**验证缺位**"标记下继续 | 与 `36` §4.2 的"不可测 ⊘"同一种处理方式 |

**一句话**：**执行器读的只有"自己那张单子的状态"，不是客户的业务数据。** 界线划清，§2.3.6 才落得下去。

## 5. 审批规则是配置，不是代码

挂在**客户策略**上（不是岗位包）：

```yaml
审批规则:
  提交单据:
    需要角色: [计划主管]
    级数: 1
    阈值:
      - 金额 > 10万 → 升级为 2 级
      - 涉及新供应商 → 强制 2 级
    超时: 24小时 → 自动拒绝      # ← 默认拒绝，不是默认通过
  修改权限: 
    需要角色: [管理员, 安全负责人]   # 双人
    时间窗: 工作日 9:00-18:00
```

**两条不可妥协的默认值：**

1. **超时 = 自动拒绝**（不是自动通过）。"没人管"不等于"同意"
2. **阈值判断不交给模型**。金额、条数、是否新供应商——这些是**规则算出来的**，不是让模型"感觉一下"

## 6. 审计

每一次都要能回答：

- 谁提请的（人 / 数字员工的服务身份）
- 基于哪个交付物的哪个版本
- 谁复核的、改了什么
- 谁批的、什么时候
- 执行器做了什么、目标系统返回了什么
- **能不能撤销，撤销了没有**

**这份审计链是 ADR-6 那条自检问题的另一半**："我卖出去的每一次调用能不能倒推"——这里是"我改出去的每一次写，能不能倒推"。

## 7. 待决问题

1. **L1 复核和 L2 确认，要不要合成一步？**
   分开 = 概念清楚但操作多一步；合并 = 省事但"质量把关"和"授权"混在一起。
   **我倾向分开**，因为将来 L1 会大量存在（每天都产出报表），而 L2 少得多，合并会让 L1 变得没必要地重。

2. **受信执行器的回滚，做到什么程度？**
   ERP 的写往往不好回滚（提交了就进流程了）。可能的做法：能撤销的撤销、不能撤销的走"反向单"（冲销）。
   **这个要问客户 ERP 支持到什么程度**，先按"能记原状态就记"来设计。

3. **双人审批的两个人，能不能是同一个部门的？**
   合规上通常要求职责分离。**我倾向要求不同角色**（业务 + 管理/安全），但小客户可能只有两三个人，会卡死。需要留一个"小客户降级模式"。

4. **审批通道要不要对外暴露 API？**
   暴露 = 客户能把自己的审批系统接进来（体验好）；不暴露 = 只能用平台界面。
   **我倾向第一批不暴露**，先跑通自有界面；但接口设计上留位置，别做死。
