# 自研 Agent 架构（独立成册）

> **本文只讲 agent 本身。** 平台、岗位包、多租户、审批、账本、数据视窗、交付物——**一概不在本文范围内**。
> 出现它们的地方，一律标注为「**接口**」——意思是"agent 只负责这里，那边的事归平台"。
>
> **为什么不和平台混着写**：agent 是**可插拔零件**，平台是**管理器**。两者寿命不同、可替换性不同、
> 出事影响面也不同。混着写会出现"改 agent 顺手改了平台"这种事。
>
> 来源：本文是 [`25`](./25-agent-overview.md) 的重新组织——**按"只属于 agent"过滤一遍**，
> 其余 08 / 09 / 13 / 18 / 20 / 22 / 23 / 24 的 agent 部分收拢到这里，数值不重写、直接引用。

## 0. agent 是什么

**agent = 引擎（会想）+ 运行时（能干活）。**

```
┌─────────────────────── agent ───────────────────────┐
│                                                      │
│   引擎（Engine）—— 可换                              │
│     认知循环：想 → 做 → 看 → 再想                     │
│     单轮推理：下一步干什么、要不要调工具               │
│     工具调用"请求"的生成（只是请求，不是执行）          │
│                                                      │
│   运行时（Runtime）—— 自研，是核心资产                │
│     工具系统 · 上下文组装 · 记忆的存取 · 沙箱接口       │
│     子代理机制 · 循环检测 · 预算的执行                │
│                                                      │
└──────────────────────┬───────────────────────────────┘
                       │  ↑↓ 两条接口（见 §3）
                       ▼
        ┌──────────── 平台（不在本文范围）────────────┐
        │  权限裁决 · 沙箱实现 · 数据裁剪 · 模型网关     │
        │  会话编排 · 审批 · 账本 · 交付物 · 界面       │
        └────────────────────────────────────────────┘
```

一期 3 个 agent：**roni（自研）+ DS harness + codex harness**。Claude 不用（闭源，Anthropic 发过逆向下架通知）。

## 1. 哪些属于 agent，哪些不属于

**这张表是本文的地基。** 右列出现的东西，本文后面一律不再展开。

| 事项 | 归谁 | 一句话判据 |
|---|---|---|
| 认知循环、单轮推理 | **agent（引擎）** | 这是"想" |
| 工具调用的**请求生成** | **agent（引擎）** | 只是请求 |
| 工具与连接的**实现** | **agent（运行时）** | 引擎不该知道连接器长什么样 |
| **上下文组装机制** | **agent（运行时）** | 放什么进去是机械动作 |
| **记忆的存取机制** | **agent（运行时）** | 怎么存怎么取是 agent 的事 |
| **子代理机制** | **agent（运行时）** | 怎么派、怎么收敛 |
| **循环检测** | **agent（运行时）** | 防它自己转圈 |
| 沙箱**接口** | **agent** | agent 只知道"要一个环境" |
| 沙箱**实现** | **平台** | 换 agent 不用重做沙箱 |
| 上下文的**准入规则** | **平台** | 是安全决策，不能交给可被劫持的一方 |
| 权限与策略的**裁决** | **平台** | 引擎可被注入，权限不能放它那儿 |
| **工具清单的过滤** | **平台** | agent 拿到的是**过滤后**的清单 |
| 数据视窗的**裁剪** | **平台** | agent 拿到的**已经是裁剪后的值** |
| 预算的**总量与裁决** | **平台** | "烧钱的那个开关"必须在平台手里 |
| 任务编排的**调度器** | **平台** | 三个 agent 都要能被同一套调度驱动 |
| 模型路由与网关 | **平台** | agent 只声明"我要什么档次的模型" |
| 交付物状态机、审批、账本、审计 | **平台** | 业务与合规概念 |
| 岗位包（九块配置） | **平台产出** | agent 只**读**配置，不生产配置 |

> **两条最容易搞混、已定死的边界**：
> 1. **上下文：组装归 agent，准入归平台。**
> 2. **沙箱：接口在 agent，实现在平台。**

## 2. 自研的部分是哪些（而且必须自研）

**自研的是「运行时」，不是「引擎」。** 引擎可以换（ADR-5），运行时不能外包。

| 自研件 | 为什么不能外包 |
|---|---|
| 工具系统（声明 + 装载 + 裁剪） | 接的是客户的系统，形状由我们定 |
| 上下文组装 | **它是安全边界**（谁能看到什么） |
| 记忆的存取 | 记忆是跨引擎资产，不能长在引擎里 |
| 子代理机制 | 权限收缩与预算切分在这里落地 |
| 循环检测 | 成本控制的第一道闸 |
| 沙箱接口 | 抽象层，将来换实现不改 agent |

## 3. 两条接口（agent ↔ 平台）

### 3.1 平台 → agent（给什么）

| 给什么 | 注意 |
|---|---|
| 系统提示 | **由岗位包生成**，agent 不负责描述自己的身份 |
| 当前上下文 | **由平台决定放什么**——最重要的一条边界 |
| **可用工具清单（已按权限过滤）** | agent 看到的是**过滤后**的清单 |
| 工具调用通道 | **走平台，不直连**——agent 没有直连外部系统的能力 |
| 剩余预算 | token / 成本 / 步数 / 时长 |
| 中断信号 | 人随时能打断 |

### 3.2 agent → 平台（返回什么）

| 返回什么 | 注意 |
|---|---|
| 工具调用**请求**（结构化） | 是请求，不是执行 |
| 文本输出 | 给人看的部分 |
| 结束原因 | 完成 / 放弃 / 超预算 / 出错 |
| 用量（token 数） | 计量用 |

### 3.3 三条不可让渡的边界

| # | 边界 | 为什么不能让 |
|---|---|---|
| **1** | **工具调用必须经过平台** | agent 直连外部系统 = 权限、审计、脱敏全部失效 |
| **2** | **上下文由平台裁定准入** | "把什么放进上下文"是安全决策，不是性能优化 |
| **3** | **结束与预算由平台裁决** | agent 说"我还想继续"不算数。**成本差 2–3 倍，一部分就是"谁有权说停"** |

> ⭐ **第 1 条的一个关键推论**：**没权限的工具根本不出现在清单里**——
> 不是"出现了但调用会被拒"。这样即使 agent 被提示词注入劫持，**它也没有可越权的目标**。
> 这比"调用时再拦"强得多。

## 4. roni 的三件改造（顺序不能反）

| # | 改造 | 为什么这个顺序 |
|---|---|---|
| **①** | **抽引擎边界**：系统提示参数化 / 拆 HTTP 与对话编排 / 工具声明化 | **这是地基**，②③ 都依赖它 |
| **②** | **移植 DS harness 零件**（借设计，不借代码） | 依赖 ① 的接口 |
| **③** | **补按需召回**：技能按需加载 / 知识按需检索 / 结构化数据走查询 | 依赖 ① 的上下文组装 |

**① 的三个动作**：
1. **系统提示参数化**——身份、职责、边界由岗位包生成，不写死在代码里
2. **拆 HTTP 层与对话编排**——对话核心能**脱离 HTTP 单独跑**（headless 调一次）
3. **工具声明化**——工具来源从"静态数组"变成 manifest

## 5. 上下文工程

### 5.1 一条总原则

> **上下文是花出去的钱，不是"信息越多越好"。**

每段塞进去的东西付两种费：**token 的钱** + **注意力被稀释的代价**。
**判据：这一段不进上下文，agent 会不会做错？不会，就别放。**

### 5.2 五层，按"稳定度"排序（最值钱的一张表）

| 层 | 内容 | 什么时候变 | 放哪 |
|---|---|---|---|
| **系统层** | 岗位包生成的身份、职责、边界 | 只有换版本才变 | **最前** |
| **工具层** | 工具清单（已按权限过滤） | 只有权限变才变 | 紧接系统层 |
| **知识层** | 检索到的知识、技能 | 每次不同 | 中段 |
| **任务层** | 本次任务、目标、交付物结构 | 每次不同 | 中段 |
| **结果层** | 工具返回 | 每次都变 | **最后** |

**这个顺序同时决定缓存和成本。** 成熟框架便宜，很大一部分原因是它**把最稳定的那几段做成可复用的**——
同样的前缀重复出现时不用重算。**自研如果每次重新拼一遍，前缀永远命中不了，那部分钱就白花。**

**三条落地纪律**：
1. 最稳定的放最前，最易变的放最后——**顺序本身就是钱**
2. 不要为了让提示词"看起来完整"而加东西——加进系统层会让缓存失效
3. **每次运行的系统层 + 工具层应逐字节一致**（同版本岗位包 + 同权限）——不一致就是漏了

### 5.3 顺序还是信任边界

**系统层、工具层是平台生成、可信的；知识层、结果层是外来的、不可信的。**
**可信的在前、不可信的在后，中间有明确分界**——这不只是缓存优化。

**三层注入防御**：

| 层 | 做什么 |
|---|---|
| **来源标注** | 每段进来都标清从哪来：用户输入 / 检索文档 / 工具返回 / 外部网页 |
| **信任分级** | 外部内容**不能改写系统指令** |
| **结构隔离** | 外部内容用明确边界包起来，**在结构上就没资格当指令** |

> **核心思路**：不要指望"在提示词里告诉它别听外面的话"——
> **要让外部内容在结构上就没有资格当指令。**

⚠️ **一个具体风险**：若允许 agent 把"上次工具返回的内容"写进系统层或知识层，可信区就被污染。
**这条要在平台侧堵死，不能靠 agent 自觉。**

### 5.4 工具结果是膨胀的主因

绝大多数自研 agent 成本失控，出在"把工具返回原样塞回去"。**四条纪律**：

| # | 纪律 |
|---|---|
| 1 | **结构化，不要倾倒**——连接器返回的是结构，不是一大段文本 |
| 2 | **有大小上限**——超过就截断，并明确标记"被截断" |
| 3 | **大结果落盘，上下文只留摘要 + 引用** |
| 4 | **保留什么由岗位包声明**，不是引擎临场决定 |

**第 3 条最被低估。** 一次查询返回 5000 行，正确做法**不是**"截前 100 行"
（agent 会以为只有 100 行），而是：

```
上下文里：「查到 5000 行，摘要：……；完整结果在 result://run-123/inventory-1，
          需要时用 fetch 取回指定范围」
```

既没撑爆上下文，也没丢信息，而且 **agent 知道自己不知道什么**——这比给它一份残缺数据强得多。

### 5.5 压缩：什么绝对不能压

| 问题 | 答案 |
|---|---|
| 什么时候压 | 接近上限时，**不要等满了才压** |
| 压什么 | 先压最老的、最不相关的（工具返回里的原始细节优先） |
| **绝对不能压** | ⭐ **交付物的依据**（`explain` 要求的那部分）· 审计需要的信息 |
| 压完怎么留痕 | 两份都留：**压缩摘要**进上下文，**原始轨迹**入审计 |

> **"绝对不能压交付物的依据"是个具体的坑**：如果压缩时把"为什么算出来是这个数"的来源删了，
> 人复核时就看不到解释，`explain: required` 就成了空话，审计链也断了。

**触发条件见 §7.3**（比例制：模型窗口 80% 触发、保留 16%）。

### 5.6 权限过滤在进上下文之前

**agent 拿到的工具清单是过滤后的**，所以上下文里**根本不存在越权的目标**。
拦的那道可能被绕过，**看不见的没有绕法**。

## 6. 工具系统

### 6.1 声明化：64 个工具一次性改成 manifest，不分批

**分一半（一半声明、一半静态数组）会让"装载"变成两套逻辑，更乱。**
写 manifest 是机械劳动，不是重写逻辑，一次做完更干净。

```yaml
工具:
  名字: inventory_query        # 唯一标识
  描述: "按仓库查库存"          # 给模型看的一句话
  参数: {仓库, SKU}
  权限档: 只读                 # 只读 / 读写 / 需审批 / 完全
  高危: 否
  连接器: inventory            # 归属哪个连接器（独立工具则空）
  版本: 1.0.0
```

**装载器**：启动时读所有 manifest → 注册成工具清单 → 按**已有的裁剪链**裁剪。
**裁剪链不动**，只是"工具来源"从静态数组变成 manifest。

**验收**：加一个工具、删一个工具，**不改核心代码、不整体重启**。

### 6.2 大结果落盘（spill）

⚠️ **先纠正一个误解**：spill 和"修剪"**不是一回事，发生在两个不同时刻**。

| | **spill** | **修剪**（§6.3） |
|---|---|---|
| 什么时候 | **工具刚返回时** | **压缩会话时** |
| 干什么 | 太大 → 全文存盘 → 上下文只留"头尾预览 + 定位符" | 历史里的旧结果 → 掐中段，留头尾 + 插标记 |

**我们的取值**（数值来自实读 harness 源码）：

| 项 | 取值 | 理由 |
|---|---|---|
| 阈值 | **32768 字节**（单位是字节，不是字符） | harness 默认是"不生效"（opt-in），**但我们不能默认关**（成本是刚需）；32768 = 修剪阈值 8192 的 4 倍，保证"先便宜修剪、超了才存盘" |
| 预览 | **头尾对半分** | 预览是"已存盘文件的采样"，头尾同等重要（**与修剪的 4:1 不同**） |
| 存储 | 按运行/会话隔离，**随生命周期销毁** | 不持久化，避免数据留存负担 |
| 取回 | 配 `fetch_spill` 工具按范围取 | agent 需要细节时主动取 |
| 失败 | **best-effort，保留原内容** | ⭐ **存盘失败不能影响工具调用的成败** |
| 跳过 | `read` 工具跳过 | 避免 `read → spill → read again` 死循环 |

**提示格式**：`(Omitted N bytes. Full formatted result stored at: <定位符>. <取回指引>)`——**带精确省略量**。

**验收**：10 万字节结果 → 上下文只有"头尾预览 + 定位符 + 精确省略量"，`fetch_spill` 能取回；
**存盘失败时调用仍成功（不报错）**。

### 6.3 工具结果修剪

**默认值**（实读 harness 源码；**我原先编的 2000/2000 是错的**）：

```js
{ thresholdChars: 8192,   // 超过才修剪
  headChars:      4096,   // 保留开头
  tailChars:      1024 }  // 保留结尾
```

**关键：头尾比是 4:1，不是 1:1。** 头比尾重要得多——工具结果的开头通常最有信息量（表头、列名、结论）。

**其它实现要点**：
- 标记固定为 `[... tool result middle pruned ...]`
- **按 Unicode 码点切片**（不切断代理对）
- 校验约束：`headChars + marker + tailChars ≤ thresholdChars`
- **回放安全**：追加一条 `compaction/prune` 事件，记录被替换的原节点

**验收**：2 万字符结果 → "头 4096 + 标记 + 尾 1024"，省略量明确，**全程无额外 LLM 调用**。

## 7. 按需召回（不预先塞）

### 7.1 真正的根因

**不是"没有向量检索"，是"预先注入太多"。** roni 现在每轮都注入：

| 每轮注入 | 量级 |
|---|---|
| 技能全文 | 单技能上限 **1.6 万字符** |
| 知识 | **12 条**（自动注入） |
| 项目说明 | **1.6 万字符** |
| 系统提示（身份/环境/纪律） | 几百行 |
| 运行时快照 + 最后 8 条 git 提交 | 每轮都变 |

**轮次越多、注入越多，成本线性叠加。** 原则正好相反：**能"按需取"的，绝不"预先塞"。**

### 7.2 四件事

| # | 从 | 改成 |
|---|---|---|
| **1 技能** | 全文进系统提示（每轮都带着 N × 1.6 万字符） | 系统提示里**只放技能目录**（名字 + 什么时候用）；需要时调"**加载技能**"工具取全文 |
| **2 知识** | 每轮自动注入最近 12 条 | 给一个"**查知识**"工具，需要时才查 |
| **3 结构化数据** | 靠"记" | ⭐ **连接器精确查询**：按 SKU / 时间 / 平台查，**不进上下文、不进向量库** |
| **4 会话历史** | —— | 比例制压缩（§7.3）+ 中段修剪（§6.3） |

**第 3 条是最大的一块，也最容易被忽略**：历史备货表、库存记录、订单明细——
**这些不是"检索"，是"精确查询"**。

### 7.3 压缩：比例制 > 绝对值

**触发条件与保留量用"模型窗口的比例"，不用绝对 token 数。**

| 配置 | 取值 | 含义 |
|---|---|---|
| `thresholdRatio` | **0.8** | 在模型上下文窗口的 **80%** 触发压缩 |
| `retainRatio` | **0.16** | 保留最近上下文为模型窗口的 **16%** |
| 摘要输出上限 | 8192 tokens | 生成摘要用 |
| 重试 | 压缩后仍超阈值再试 1 次；溢出后恢复重试 1 次 | |
| 触发时机 | 自动，在**步边界**触发 | |

> **为什么比例制更对**：换一个小窗口的模型，阈值**自动跟着变小**——不需要改配置。
> 绝对值换模型就失效。

### 7.4 全文 vs 向量

**先做全文检索（FTS5）打底，向量作为"留位置、后补"的增强。**

**三条理由**：
1. harness 就没用向量（它的包里没有 vector / embed / rag 相关）——说明对 agent 场景**够了**
2. 向量要额外成本：embedding 调用 + 向量库维护，是**持续开销**
3. 中文业务术语全文够用："备货计划""库龄""头程时效"这类词，全文匹配很准

**什么时候才真需要向量**：当"**语义相似但用词不同**"成为刚需时
（问"库存积压情况"，资料里写"库龄过高"——全文匹配不到，向量能匹配到）。

**这是"接口留位置"**：检索接口设计成**可换检索后端**，将来插向量库不用重构。

## 8. 子代理

### 8.1 价值是"上下文隔离"，不是"能力增强"

⚠️ **这一点搞反会白白烧掉很多钱。**

| 该用 | 不该用 |
|---|---|
| 任务能并行（多个独立调查） | 简单任务（拆了反而更贵） |
| 需要大量试错的脏活，但只要一个干净结论 | 需要共享大量上下文的（拆了要反复传，**传的就是钱**） |
| 需要一个"不同性格"的执行者（如专门挑错的审查者） | 单线程的线性任务 |
| 上下文会爆炸，必须隔开 | —— |

**判据**：子代理解决的是"**这一大堆中间过程不该污染主上下文**"，不是"多个人干活更快"。
**每次派活都有传递成本，收益必须来自"隔离掉的上下文"，否则纯亏。**

### 8.2 四条硬约束

| # | 约束 | 说明 |
|---|---|---|
| **1** | **权限 ≤ 父级** | 通常**严格小于**——只给这个任务需要的 |
| **2** | **预算切分，不共享** | 它超支不能拖垮父级 |
| **3** | **深度限制** | **建议上限 2 层** |
| **4** | **结果收敛** | 只回传结构化结论，**不回传原始上下文** |

第 4 条两个理由：**防上下文爆炸**（把子代理整个上下文倒回来等于没隔离）+ **防污染**
（子代理读到的外部内容不该流进主上下文）。

### 8.3 ⚠️ 外部引擎自带工具 —— **Day 12 已改：用围栏，不接管**

**这是 agent 侧最要紧的一条。**

Codex、Claude Code 这类引擎**自带一批工具**：读写文件、执行命令、访问网络。
直接当子代理跑起来，**它们会用自己的工具，绕过连接器网关、权限和审计。**

```
你以为的：  Codex ──► 你的连接器网关 ──► 审计 ✓
实际发生的：Codex ──► 它自己的文件/shell/网络工具 ──► 审计 ✗  权限 ✗  脱敏 ✗
```

### ⚠️ 结论已于 Day 12 修正：**用围栏，不接管**

> **原结论**（已作废）："接管优先——外部引擎如果不能被接管工具，就只能走围栏，而围栏更粗。"
> **错在哪**：这个判断默认了"**引擎自带的工具不如我们的**"，而**该前提未经验证**。
>
> **实证后**（[`50`](./50-agent-tech-architecture.md) §3，本机源码 + 官方文档）：
> 两家引擎自带工具**都比我们自研的好**，**且两家都提供从外部约束的机制**。
> **剥夺它们的工具，是拿确定的能力损失，去换一个我们已经有替代方案的收益。**

| 路线 | 做法 | 结论 |
|---|---|---|
| ~~接管~~ | 禁用它的原生工具，只注入我们提供的工具清单 | ❌ **不作主路线**：能力损失大，且很多引擎不完整支持 |
| **围栏** | 让它的原生工具在**沙箱里**跑，受沙箱、网络白名单、执行策略约束 | ✅ **主线** |

**围栏必须围住四件事，缺一件等于没围**：
① 写越界（引擎沙箱模式）② 危险命令（执行策略）③ ⭐ **网络出口**（默认断网）④ ⭐ **逃生门**（参数白名单，禁透传 `--yolo` 类开关）

> ⭐ **修正后的引擎选型判据**：判据**不是**"能不能被接管工具"，而是——**能不能被围栏**。
> 问四句：① 有没有沙箱模式 ② 沙箱拿不到时是否 fail-closed ③ 网络能不能默认断 ④ 参数能不能白名单化。

> ⚠️ **围栏带来的连带设计**：agent 的原生工具不经过连接器网关，所以**数据视窗的出口要挪到
> "喂进沙箱的数据"上**——平台把裁剪后的数据**物化**成沙箱内的工作文件，agent 根本没有原始数据可读。
> 详见 [`50`](./50-agent-tech-architecture.md) §3.4。

### 8.4 预算怎么切

| 规则 | 为什么 |
|---|---|
| 切出去的是**额度**，不是共享池 | 一个子代理失控不能烧掉整个任务 |
| **父级必须留一部分给自己** | ⭐ 不预留的话，子代理跑完，父级发现自己**没钱把结果汇成交付物** |
| 没花完的**显式回收** | **不自动回流**——否则并发时会出现"两个子代理都以为还有余额" |
| 按**复杂度**分，不平均 | 平均分会让简单任务浪费、复杂任务不够 |

### 8.5 子代理的自述不可信

它可能：只做了一部分但报告说完成了 / 拿到了不该拿的数据 / 用了一个你不认识的能力。
所以回传的东西**必须能验证**（用了哪些能力、消耗多少、结束原因都要独立记录）。

### 8.6 与平台的分工

```
岗位包：声明「备货 = 销量子代理 + 库存子代理 + 物流子代理 + 验证子代理 → 汇总」
平台：  拆解 + 权限收缩 + 预算切分 + 并发调度 + 回收 + 汇总 + 审计
agent： 提供「跑一个子代理」的能力（引擎 + 工具）
```

**agent 侧只负责"跑起来"，"派几个、给多少、谁来汇总"归平台。**
理由：三个 agent 都要能跑同一套编排，调度逻辑不能长在某个 agent 里。

**权限收缩在 agent 侧的落点**：子代理的工具清单 = **岗位包能力 ∩ 它声明要用的能力**，
**过滤后下发**——查库存的子代理，清单里**只有** `inventory.query`，
物流、写库、外发**根本不出现**（不是"出现了但被拦"）。

## 9. 会话、运行、中断恢复

### 9.1 四种寿命必须分清

| 概念 | 寿命 | 说明 |
|---|---|---|
| **交付物** | 长期（月/年） | 有版本、有状态、有复核记录 |
| **会话** | 天 / 周 | 人机交互的容器，可跨天 |
| **运行** | 分钟 / 小时 | 一次执行 |
| **沙箱** | **分钟级** | **用完即毁** |

⚠️ **这四种寿命都在"一个数字员工之下"**——数字员工本身是第五种寿命（月～数年）。
**分界**：本文管"一次干活的寿命"。

**关键推论**：运行可以等几个小时（等人复核），但**沙箱不能等**。这两件事必须解耦。

### 9.2 两种触发，结构不同

| | 有人触发 | 无人触发（定时 / 事件） |
|---|---|---|
| 有会话吗 | **有**——人机交互 | **没有**——就是一个独立运行 |
| 特点 | 可以多轮、可以追问 | 一次跑完就结束 |

**别硬把定时任务塞进一个"会话"里**——它没有对话，塞进去只会让会话状态机变得难以理解。

### 9.3 运行状态机

```
排队 ──► 启动中 ──► 执行中 ──┬──► 已完成
                              ├──► 等待人工确认 ──┬──► 已确认 ──► 已交付
                              │                    └──► 被退回 ──► 执行中
                              ├──► 预算耗尽 ──► 已中止（保留部分结果）
                              └──► 失败
```

⚠️ **"等待人工确认"是一个独立状态，不是"还在跑"。**
混了的话：对外接口会让客户的集成一直等不到结果；对内监控、计费、超时策略的处理完全不同。

### 9.4 三种中断，恢复方式不同

| 中断原因 | 能不能继续 | 怎么继续 |
|---|---|---|
| **人主动打断** | ✅ | 接着跑，上下文还在 |
| **预算耗尽** | ✅ **但要追加预算** | **不能自动续**，否则预算就是纸糊的 |
| **系统故障** | ✅ | **从检查点重建** |
| **策略拒绝 / 越界** | ❌ | 不恢复，等人工处理（**这可能是安全事件**） |

### 9.5 检查点存什么、不存什么

| 存 | 不存 |
|---|---|
| 上下文摘要 | **沙箱状态** |
| 已完成到哪一步 | 沙箱里的临时文件 |
| 已产出的交付物（已独立存在） | 内存里的凭据 |
| 剩余预算 | —— |

⭐ **核心：恢复 = 重建一个干净沙箱 + 重放上下文摘要。**
**不是"把沙箱恢复回来"**——沙箱是一次性的，指望它活着本身就是设计错误。

> **归属定死**：检查点**既不是**工作区记忆**也不是**数字员工记忆，它是**运行的附属物**——
> 寿命跟着运行走。**推论**：运行结束/被终止后，检查点按审计周期保留，
> **但不进任何"记忆召回"的候选集**。

### 9.6 ⭐ 验收钩子（机器判定 vs 人的业务判断）

| | **验收钩子**（自动） | **人复核** |
|---|---|---|
| 谁做 | **系统** | 人 |
| 什么时候 | 运行产出后**立刻** | 排在人的待办里，可能几小时后 |
| 判什么 | **机器可判的**：结构对不对、必填字段有没有、有没有突破硬阈值 | **业务判断**：这个数合不合理、要不要改 |
| 结果 | 通过 → 进人复核队列；不通过 → **当场打回给 agent 重试**（省掉人白看一遍） | 改 / 批 / 驳 |

**三条规则**：
1. **钩子只判"机器可判"的部分**，判不了的一律交给人（**不许用模型冒充业务判断**）
2. **钩子不通过 → 先让 agent 自己修**（可配重试次数）
3. **钩子结果进账本 + 进经验**——它是"机器判定"那一支的前置

> **一句话**：**钩子管"格式和硬线"，人管"业务判断"。**
> 两者串起来，人才不会把时间浪费在"连必填字段都缺"的产出上。

### 9.7 ⚠️ 等人复核时，沙箱必须销毁（成本关键）

```
agent 产出草稿 → 运行进入"等待人工确认"
                        │
                        ├─ ❌ 错误：沙箱挂着等
                        │     → 一个等待复核的任务占着一个沙箱几小时
                        │     → 50 个单子同时在等人 = 50 个沙箱空转
                        │
                        └─ ✅ 正确：**沙箱立即销毁**
                              人复核完 → 重建沙箱继续
```

**为什么重要**：沙箱是这套系统的主要成本之一，而"等人"天然是慢的。
**如果沙箱跟着等，成本曲线会被"人的响应速度"决定——那是最糟糕的一种成本结构。**

## 10. 循环检测（防它自己转圈）

**照搬 harness 的分级提醒，不熔断。**

| 项 | 做法 |
|---|---|
| **阈值** | `[3, 5, 8]`——连续相同调用到 3 / 5 / 8 次分别触发 |
| **性质** | **分级提醒，不是熔断**。原话："enriches post-execute decisions... **without vetoing or rewriting calls**" |
| 第 3 次 | 温和提醒："你在用完全相同的参数重复同一个调用。仔细分析之前的结果；如果没完成，换方法或换参数。" |
| 第 5 / 8 次 | 详细提醒：点名工具、连续次数、参数 |
| **参数比较** | **深度 key 排序后再比**（否则 `{a:1,b:2}` 和 `{b:2,a:1}` 会被当成不同参数） |
| 参数预览 | 截断到 **500 字符** |
| 来源标记 | 标为"插件"，**防止被渲染成用户提示** |

**为什么不用熔断**：熔断会**误杀合法的重复调用**（轮询任务、等外部系统就绪）。提醒让模型自己判断。

**和预算机制配合**：如果提示到 8 次仍不收敛，**由预算软着陆兜底**
（消耗 70% 收敛提示 → 85% 换便宜模型 → 100% 优雅中止，见 §5.6）——
**不需要在循环检测里再叠一层熔断。**

**验收**：同一工具 + 相同参数连续第 3 次 → 温和提醒；第 5 次 → 详细提醒；
**全过程调用不被阻止**。

## 11. 预算与成本的软着陆

**预算总量与裁决归平台**（§1 的边界三），**agent 侧负责"被执行"**。

**四种预算同时管**：token · **钱（最硬）** · 步数 · 墙钟时长。

### 11.1 接近预算时逐级降级（而不是硬停）

```
消耗到 70%  →  提示 agent 收敛（减少探索、少做检索）
消耗到 85%  →  换便宜模型
消耗到 100% →  优雅中止（**保留已产出的部分结果**）
```

**硬停会让人白等一场**，软着陆至少给出一个可用的部分结果。

## 12. 验收标准（agent 侧）

### 12.1 抽边界

| # | 标准 |
|---|---|
| A1 | 同一份 agent 核心，**换个客户环境只改配置、不改代码** |
| A2 | 对话编排核心能**脱离 HTTP 单独跑**（headless 调一次） |
| A3 | **加/删工具不改核心代码、不整体重启** |

### 12.2 成本

| # | 标准 |
|---|---|
| B1 | 10 万字节的工具结果 → 上下文只有"头尾预览 + 定位符 + 精确省略量"，`fetch_spill` 能取回 |
| B2 | **存盘失败时，工具调用仍成功**（不报错） |
| B3 | 2 万字符结果被压成"头 4096 + 标记 + 尾 1024"，省略量明确，**全程无额外 LLM 调用** |
| B4 | **换一个小窗口的模型，压缩阈值自动跟着变小**（不改配置） |

### 12.3 按需召回

| # | 标准 |
|---|---|
| C1 | 一个**不用知识**的轮次，上下文里**一条知识都没有**（对比现在固定 12 条） |
| C2 | 一个**不用技能**的轮次，上下文里**只有技能清单、没有技能全文** |
| C3 | 查历史 SKU 备货量走**精确查询**，不进上下文 |

### 12.4 编排与子代理

| # | 标准 |
|---|---|
| D1 | 查库存的子代理，工具清单里**只有** `inventory.query`（物流/写库/外发**根本不出现**） |
| D2 | 一个子代理失败 → 交付物照出，**标注"该块数据未取得"**，不整体崩 |
| D3 | 一个子代理烧钱失控，**只烧它自己的额度**，拖不垮整个任务 |

### 12.5 上下文与安全

| # | 标准 |
|---|---|
| E1 | 同一版本岗位包 + 同一权限，**两次运行的系统层与工具层逐字节一致** |
| E2 | **数据视窗在数据出口生效**——agent 拿到的是裁剪后的值，**不是"看到了但被告知别说"** |
| E3 | **没有用提示词替代数据视窗**（"你别泄露 X"不是控制措施） |
| E4 | 子代理的视窗**只能比父级更窄**（能力单调不增） |
| E5 | 我等人工确认期间，**沙箱已被销毁** |
| E6 | 连续相同调用第 3/5 次出现提醒，**调用不被阻止** |
| E7 | 压缩后，**交付物的依据仍在**（`explain` 拿得到解释） |

### 12.6 会话与运行

| # | 标准 |
|---|---|
| F1 | "等待人工确认"与"执行中"在接口、监控、计费、超时上**被当作两个状态** |
| F2 | 系统故障后能**从检查点重建**（重建干净沙箱 + 重放摘要） |
| F3 | 预算耗尽后**不能自动续**，必须追加 |
| F4 | 检查点**不进任何记忆召回候选集** |
| F5 | 定时任务**不套一个空会话** |
