# 19 · 平台（Ronisyn）vs agent 职责边界

> 状态：**已确认（Day 2）。** 本文是"平台/agent 归属划分"的正式依据，取代之前"引擎/壳"的模糊叫法。
> 前置：`17`（RW 现状）、`18`（抽引擎边界）、`07`（旧"引擎/壳"边界，已退休）

---

## 0. 一条判据

> **"管"的归平台（Ronisyn），"干"的归 agent。**

凡是**跨 agent 共享**的、或**防止 agent 作恶**的，属于平台；凡是**这个 agent 自己怎么干活**的，才属于 agent。

---

## 1. 三层结构（统一语言，取代旧"引擎/壳/岗位包"）

| 层 | 是什么 | 谁 | 换不换 |
|---|---|---|---|
| **平台（Ronisyn）** | 管：多租户、账本、审计、交付、治理、模型网关、岗位包、**任务编排调度**、对外接口 | 自研 | **只有一个** |
| **agent** | 干：引擎（思考）+ 运行时（工具 / 上下文 / 记忆 / 沙箱 / **子代理机制**）。**可插拔零件** | roni（自研）+ DS harness（开源）+ codex harness（开源） | **可插拔，一期 3 个** |
| **岗位包** | 业务配置：身份、提示词、技能、知识、工具授权、交付物模板、**任务编排模板**、触发方式 | 配置 | 一个岗位一个 |

> ⚠️ **"壳"这个词退休。** 它之前把"平台级"（多租户/账本/审计）和"agent 级"（工具/记忆/沙箱）混在一起了。现在拆成"平台"和"agent 运行时"两层。

---

## 2. 逐项归属表

| 概念 | 归谁 | 为什么 |
|---|---|---|
| **多租户** | 平台 | agent 不该知道有别的客户，它只是"在某租户的工作区里跑" |
| **账本 / 计费** | 平台 | 记账要跨 agent、跨客户统一；agent 只**上报**消耗 |
| **审计** | 平台 | 审计不能由被审计对象自己记（防篡改/防洗白） |
| **交付物流程**（状态/复核/审批/存档/版本） | 平台 | 工人产出零件，但"合格没、给谁、存哪"是平台的事 |
| **交付物内容** | agent | agent 产出内容 |
| **治理**（权限/策略/审批规则） | 平台 | agent 不能自己给自己放权 |
| **模型网关 / 路由 / 成本** | 平台 | 跨 agent 统一管模型、管成本、管降级 |
| **岗位包管理** | 平台 | 跨 agent 统一装配 |
| **对外接口** | 平台 | 对外暴露的是"派活"，不是"某个 agent" |
| **引擎（思考循环）** | agent | 每个 agent 自己的 |
| **工具 / 记忆 / 子代理机制** | **agent 自带，平台托管** | 见 §3.3 |
| **上下文的组装机制**（怎么拼、怎么压） | **agent** | 每个 agent 自己的实现 |
| **上下文的准入**（什么能进、哪段不可信） | **平台** ⭐ | **安全决策**——交给 agent 等于把注入防御交给可被劫持的一方（见 §3.4） |
| **数据视窗**（这个数字员工能看到哪些行、每个字段看到什么值） ⭐ | **平台** | **在数据出口生效**，agent 拿到的**已经是裁剪后的值**。见 §3.4 补充和 [`34`](./34-data-view.md) |
| **跨边界授权**（能不能跨出隔离边界、怎么跨） ⭐ | **平台** | agent 只能**发起申请**，**不能执行**——申请权与执行权分离（[`35`](./35-cross-boundary-authorization.md)） |
| **沙箱** | **接口在 agent、实现在平台** | 见 §3.5 |
| **任务编排 / 调度**（并发、权限收缩、预算切分、结果回收、汇总） | **平台** | 跨 agent 统一；防止 agent 自己给自己放宽权限或超预算 |
| **任务编排模板**（"备货 = 销量+库存+物流+验证子代理 → 汇总"的声明） | **岗位包** | 稳定的任务结构应固化，不让模型每次现场想"派谁" |

## 3. 三个关键点

### 3.1 审计：agent 只产生事件，不记审计

审计必须由"**不被审计对象控制的一方**"记。如果 roni 自己记自己的审计，roni 被注入劫持时就能洗掉痕迹。

→ **agent 产生事件**（"我调了这个工具、读了这个数据"），**平台统一记录、统一保管、不可篡改**。

### 3.2 账本：agent 有"上报"，没有"账本"

账本只有一个（平台级）。agent 每次跑完上报"用了多少 token、跑了多久"，平台归集到"**哪个客户 → 哪个岗位 → 哪个 agent**"这个维度下。

→ 类比：员工（agent）提交报销单（上报），财务（平台）记账。**员工绝不自己记账本。**

### 3.3 工具 / 记忆 / 子代理：agent 自带，平台托管

工具、记忆、**子代理机制**是 **agent 自带的运行时能力**（roni 的 64 个工具 + 子代理族、DS harness 的、codex 的各自不同）。

**但**：执行工具的地方（沙箱）、权限判定、审计，以及**任务编排的调度**，必须由**平台统一提供**——否则就回到 `09` 那个坑：**外部 agent 自带工具，绕过你的权限和审计。**

→ 一句话：**agent 带"家伙"，平台划"圈"，家伙只能在圈里用。**

> 补充（Day 2 修订）：**"任务编排"拆成三层**——模板（岗位包声明）→ 调度（平台执行）→ 子代理机制（agent 提供）。之前把"子代理编排"笼统归给 agent，是不准确的；调度权必须在平台手里，否则 agent 可以自己给自己扩权限、超预算。

### 3.4 上下文：组装归 agent、准入归平台 ⭐

**这是本轮复盘修掉的一个真冲突**——之前 `07`/`08` 说"上下文由壳组装（安全决策）"，而本文说"上下文是 agent 自带的"，**两句打架**。

**修法（拆成两层）：**

| 层 | 归谁 | 是什么 |
|---|---|---|
| **组装机制** | **agent** | 怎么拼、怎么排、怎么压——每个 agent 自己的实现 |
| **准入规则** | **平台** ⭐ | **什么能进上下文、哪一段"不可信"、外部内容不得改写指令** |

**为什么准入必须在平台**：把"外部内容能不能当指令"交给 agent，等于把**注入防御交给一个可被注入劫持的对象**——防不住。**平台把关，agent 装配。**

> ⭐ **补充（Day 3）：数据视窗也属于"准入"**（[`34`](./34-data-view.md)）。
> 裁剪发生在**数据出口**（连接器网关），**agent 拿到的就已经是裁剪后的值**。
> 所以这不是"agent 看到了但不能说"（那是软约束，一定守不住），而是"**agent 从没有过那个值**"。
> 由此产生一条不可违反的设计约束：**禁止把"别泄露 X"写进提示词来替代数据视窗。**

### 3.5 沙箱：规格由平台定、agent 只是使用

> ⚠️ **Day 9 重写**：原文"接口在 agent、实现在平台"读起来别扭，**因为它把两件事混在一句话里**。
> 发起人提出"**把平台分成业务侧 / 设计侧**"之后（见 [`45`](./45-capability-and-scenarios.md) §5），这条才说得清：

| 场景 | 谁需要 | 在哪一侧 |
|---|---|---|
| **研发 agent 时**：它需要"能跑命令的地方"来开发和调试 | agent（我们自己） | **研发后台**（开发工作区规格，**能写代码**） |
| **客户跑任务时**：agent 要"受限的执行环境" | 客户的数字员工 | **业务平台**（只读取数规格，**写要审批**） |

**所以正确的说法是三条**：

| # | 归谁 | 内容 |
|---|---|---|
| **① 沙箱的实现** | **平台** | gVisor 等，两个侧用同一套实现（统一、受控、可审计） |
| **② 沙箱的规格集合** | **平台** | 有哪些档、每档什么语义，**平台定义**（`05` §1.1/§1.2） |
| **③ 用哪一档** | **配置** | 设计侧给开发规格，业务侧给只读规格；agent **只是使用其中一种** |

**为什么别写成"接口在 agent"**：那样听起来像"agent 定义了沙箱长什么样"，
**实际上是"平台定义了规格集合，agent 使用其中一种"**。

→ 结果不变：**换 agent 不用重做沙箱；换沙箱实现也不用改 agent。**
