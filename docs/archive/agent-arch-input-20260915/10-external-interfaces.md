# 细化 ⑩：对外接口

> 父文档：[`architecture.md`](./architecture.md) §12 细化路线 第 ⑩ 项
> 对应你最初的诉求：**"打造 agent 壳，给壳封装成产品，带 API"**、**"可以嵌入其他网站"**。
> 状态：草案，待讨论。

---

## 0. 一句话：接口暴露的是"派一个岗位干活"，不是"给模型发消息"

这条定调决定了后面所有细节，也是 ADR-6（不卖 token）在接口层的落地。

| ✅ 接口暴露 | ❌ 接口不暴露 |
|---|---|
| 派一个岗位干活 | 给模型发消息 |
| 取交付物 | 取 token 用量 |
| 任务状态（跑到哪了） | 模型名称 / 单价 |
| 人工修改率 | token 余额、充值 |

**如果接口长成"发消息、收消息、看 token 消耗"，你在监管和上游眼里就变成了一个 API 中转站。**

---

## 1. agent 的活大多是"长活"——这是和普通 API 最大的不同

普通 API 是秒级的；**agent 的活可能跑几分钟到几十分钟**（要查多个系统、多轮推理、还要等人复核）。

**HTTP 撑不住 20 分钟。** 所以接口必须区分两种：

| | 短活 | 长活 |
|---|---|---|
| 典型时长 | 秒级 | 分钟～小时，**甚至要等人** |
| 形态 | 同步 + 流式 | **异步 + 回调 + 状态查询** |
| 例子 | 问一句、看个数 | 出一份计划、等复核 |

**长任务三件套**：① 提交 → 立刻返回任务 ID（不阻塞）　② 查询 → 状态　③ 回调 → 完成时通知。

> ⚠️ **一个容易设计错的地方**：任务的状态不只是"跑没跑完"。按 [`06`](./06-approval-and-executor.md) 的交付物状态机，还有 **"等人复核"**、**"已确认待执行"**、**"已交付"**。
> **别把"等复核"当成"还在跑"**——那会让客户的集成逻辑永远等不到结果。

---

## 2. 六种接入形态

| 形态 | 用途 | 关键点 |
|---|---|---|
| **REST + SSE** | 业务系统集成 | 幂等键、流式、长活转异步 |
| **Web SDK / 内嵌** | 嵌入客户网站 | **身份传递**（见 §3，最麻烦的一个） |
| **IM 机器人** | 飞书 / 企微 / 钉钉 | 身份映射、会话绑定到工作区 |
| **定时 / 事件** | 排程任务（如每月 1 号、15 号） | 用**服务身份**；多轮检索后**只能写到草稿态**（L2） |
| **Webhook 回调** | 结果通知 | 签名、重试、幂等 |
| **MCP** | 把本平台作为工具暴露给别的 agent | **权限必须收缩**（铁律二）——外面的 agent 不能借你提权 |

## 3. 嵌入式最麻烦的问题：**"用户是谁？"**

> ⚠️ **先分清两类人（Day 8 补，之前混在一起）**：
>
> | | **客户网站的访客**（本节） | **客户的员工**（`44` §1.7） |
> |---|---|---|
> | 例子 | 客户官网的浏览者 | 备货专员 / 复核人 / 采购 |
> | 要不要账号 | **不要**——只判权限，不做认证 | **要账号**——他们要复核、审批、留痕 |
> | 身份从哪来 | 客户透传 + 签名 | **飞书登录 / 手机号密码**（客户自己就是飞书用户） |
> | 我们的角色 | **只做权限，不做认证** | **做账号**（但优先让飞书做认证，我们不存密码） |
>
> **本节只讲访客那一类。员工的那一套见 [`44` §1.7](./44-loading-standard.md)。**

你要把 agent 嵌进客户的网站，第一个撞上的就是这个问题。三个方案：

| 方案 | 做法 | 问题 |
|---|---|---|
| A · 平台自己的账号 | 客户网站的用户到你这儿注册 | **客户不干**（多一套账号体系） |
| B · 客户透传身份 + 签名 | 客户传 `user_id` + 签名，你校验 | 要信任客户；客户不传时要能降级 |
| C · 匿名会话 | 不识别用户 | **做不了权限，也做不了记忆** |

**推荐 B，但要加一条纪律：**

> **透传过来的 `user_id` 只用于"权限判定"，不用于"身份认证"。平台不承担认证责任。**

**为什么这条重要**：一旦你的平台开始"认证"**客户网站的访客**，你就变成了一个身份提供方——那是另一套合规义务（账号、密码、找回、等级保护）。**你只想做权限，不想做认证。**

> ⚠️ **这条纪律的适用范围是"访客"，不是"员工"**（Day 8 明确）。
> **员工的账号我们会建**——但**优先走飞书认证，我们不存密码**；只有在客户不用飞书时才自建密码体系（那种情况下合规责任由我们承担，是明知的取舍）。

### 3.1 会话归谁

同一个客户网站的用户第二天回来，还接得上吗？**取决于会话的归属和留存策略。**

- 会话**属于客户的工作区**，不属于平台
- 留存多久，由**客户策略**定（也受合规约束：不能非法留存使用者输入）
- 跨天续接要靠"数字员工记忆"（[`03`](./03-role-package.md) §1.1），不是靠把历史全留着

## 4. 幂等：不做的话一定会出事

业务系统会重试（网络抖动、超时、人为重发）。**而 agent 跑两遍的代价很大**——产出两份交付物、发两次通知、写两次草稿。

**做法**：客户提供幂等键（通常是它自己的业务单号）。

```
同一个幂等键重复提交 → 返回同一个任务，不重新跑
```

**这条对 agent 尤其重要**，因为 agent 不像普通 API 那样"重跑一遍无副作用"——它可能已经改了东西、已经通知了人。

## 5. 配额与限流

| 维度 | 为什么 |
|---|---|
| 客户级配额 | 防止一个客户拖垮平台 |
| 数字员工级配额 | 防止一个岗位失控 |
| **并发任务数** | **← 这是成本的关键闸门**，因为每个任务吃一个沙箱 |
| 单次运行预算 | 最后一道（[`08`](./08-context-engineering.md) §6） |

> **"并发任务数"值得单独盯**：它是你和客户之间的成本闸门。客户写个循环一次提 500 个任务，你的沙箱池就爆了，钱也烧了。**这个限流比 token 限流重要得多**，而且在 ADR-6 之后，它也是你唯一能主动控制的成本杠杆。

## 6. 回调的安全

Webhook 是最容易被忽略的攻击面：

| 要做 | 为什么 |
|---|---|
| 签名（HMAC） | 防止伪造回调 |
| 时间戳 + 防重放 | 防止旧回调被重放 |
| 客户侧幂等 | 你会重试，客户要能去重 |
| 重试策略 + 死信 | 客户挂了不能把你的队列堵死 |
| **回调内容最小化** | **只回"任务 ID + 状态"，不回业务数据**——回调是明文出网，别把敏感数据塞进去 |

## 7. 待决问题

1. **第一批暴露哪些接口？**
   我倾向**只做 REST + SSE + Webhook**，把长活跑通。Web SDK 内嵌、IM 机器人、MCP 后置——因为内嵌会立刻撞上 §3 的身份问题，那是个需要和客户谈的事，不是技术问题。

2. **嵌入式到底是"iframe"还是"客户自己画界面、只调你的 API"？**
   - iframe：快，但样式和体验受限于你，且客户可能不接受"我的页面上有个别人的框"
   - 自己画：体验好，但客户要开发
   **我倾向两个都提供**，先做 iframe 快速验证，API 给愿意自己画的客户。

3. **会话状态要不要对外开放读写？**
   开放 = 客户能自己接管会话（灵活）；不开放 = 简单可控。
   **我倾向不开放**——会话状态涉及记忆和权限，开放出去容易失控。客户要的是"结果"，不是"会话"。

4. **MCP 出口要不要现在就做？**
   把本平台作为工具暴露给别的 agent，是个很自然的扩展，但**它也是"权限收缩"最容易破的地方**（外面的 agent 拿到的可能是超集）。**我倾向后置**，等前面的权限模型跑稳。
