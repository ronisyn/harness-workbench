# 35 · 跨边界授权（Cross-Boundary Authorization）

> 状态：方案，技术决策由我拍。**新增能力**（Day 3 与 `34` 配套）。
> 前置：`01` §3.2（资源维度）· `06`（审批与受信执行器）· `26` §2.3（策略层级：只能收紧）· `34`（数据视窗）
> 由来：客户规则——**"货权之间是隔离的；想知道对方有多少货可以借调，但必须经过上级部门操作和协调；没有把自己的货给别人的权力。"**

---

## 0. 一句话

**隔离不能是绝对的墙，必须是"有门的墙"——`35` 定义的就是门。**

| 只有 `34` | 加上 `35` |
|---|---|
| A 看不到 B 的数据 | A 可以**申请**看/调，但**不能自己动手** |
| 业务被卡死（该协作的协作不了） | 协作走正门，**每次都留审计** |

**三条核心原则**：

1. **默认隔离**——面向"没被授权"的那一侧，默认不可见、不可动
2. **想动 ≠ 能执行**——**申请权与执行权分离**，这是本机制的灵魂
3. **审批方是配置，不是代码**——客户想叫什么角色就叫什么，**架构里不出现具体岗位名**

---

## 1. 先把两种"边界"分开（很容易混）

| | **数据边界** | **流程边界** |
|---|---|---|
| 是什么 | 看不到对方的数据 | 动不了对方的东西 |
| 例子 | "B 团队有多少货" | "把 B 团队的货划给我卖" |
| 谁来管 | `34` 数据视窗 | **本文** |
| 跨越的动作 | **读** | **写 / 归属转移** |
| 回到默认 | 读完了就回到隔离 | **状态改变了，不可自动回滚** |

**⚠️ 两者必须分开设计，但共用同一条授权链**：

- 只给"可见"授权，不等于给了"可动"授权
- 给了"可申请"，不等于给了"可执行"
- **一次跨越里两者可以同时发生**（申请时看到了量，批准后发生了转移）

---

## 2. 三种授权（按"能做什么"分，不是按岗位分）⭐

**平台里不出现"供应链""运营总监"这种词**。平台只提供三种**抽象的授权档位**，由客户策略配置谁能拿到：

| 档位 | 允许什么 | 不允许什么 |
|---|---|---|
| **① 可见** | 看到对方范围内的数据（**可能只给档位化/折算值**，见 `34` §2.3） | 动任何东西 |
| **② 可申请** | **发起**一次跨边界请求（附理由、附目标） | **自己执行**、自己批准 |
| **③ 可执行** | **真正完成**归属转移 / 跨边界写 | 判断该不该做（那是审批人的事） |

**组合关系（都在客户策略里配）**：

```
能看见 + 能申请 + 不能执行   →  "可以谈，但要有人点头"（最常见）
不能看见 + 能申请            →  "连有多少都不知道，但可以提需求"
能看见 + 不能申请            →  "能看到全局，但没资格要"
能执行（必然含可见）          →  "被指定为协调方"（少数角色）
```

> **⚠️ 第 3 条最容易做错**：把"能执行"直接挂到某个**特定岗位**上。
> 一旦平台写死"某个岗位能执行跨边界"，**客户改组就得改平台**——这就是打补丁。
> **正确做法**：平台提供"可执行"这个档位，**客户策略决定谁拿**。

---

## 3. 一次跨边界请求的完整链路（复用 `06`，不另造一套）⭐

**本机制不新建审批引擎**——`06` 已经有生命周期、写分级、规则路由（角色 / 级数 / 阈值 / 超时默认拒绝）。**本文只是把 `06` 接到"边界"上。**

```
① 数字员工 H 想动边界外的资源
      │  （它的数据视窗里有"可申请"，没有"可执行"）
      ▼
② 产出【跨边界申请单】（结构化交付物，见 `28`）
      内容：想动什么、动多少、为什么、目标边界
      │  ⚠️ 它提交的是**申请单**，不是**动作**
      ▼
③ 路由到审批方 —— **审批方由客户策略决定，不是平台写死**
      规则：需要角色 / 级数 / 阈值 / 时限（`06` §5）
      │
      ▼
④ 审批人看到：谁申请、要动什么、影响面、历史先例（同 `06` §1 ③）
      │  批准 / 驳回（可带意见）/ 超时自动拒绝
      ▼
⑤ 受信执行器执行归属转移（幂等、可回滚/可冲销、留回执）
      │  ⚠️ 只有它碰得到写路径（`06` §0）
      ▼
⑥ 审计：谁申请 → 谁批 → 执行了什么 → 结果（`06` §6）
```

**关键在 ①→② 之间**：**数字员工的权限到此为止**。它产出的是申请，不是动作。
**这和 ADR-2 是同一条原则**：不加新机制，只是把它用在"客户内部边界"上。

---

## 4. 归属转移：数据属主变了，连带什么要变 ⭐

**"把 A 的货给 B 卖"不是改一个字段就完了。** 一次归属转移会连带影响：

| 连带项 | 要处理什么 |
|---|---|
| **数据归属** | 该资源的维度取值从 A 改成 B（**改的是归属，不是数据**） |
| **在途/占用** | 已经被 A 的计划占用的量怎么办（转移前要释占） |
| **已有的交付物** | A 已产出的计划单里含这批货 → **标记"依据已变更"**，不静默改 |
| **经验与记忆** | A 的经验里写着"这批货的量" → 留在 A 的历史里，**不能被 B 当成自己的** |
| **审计链** | 完整保留：谁申请、谁批、哪一刻归属变了 |

**我拍**：**归属转移必须是一个"事件"，不是一个"更新"。** 事件带前后状态、带审批依据、可追溯。

> **⚠️ 为什么这条重要**：如果归属转移只是"UPDATE 一个字段"，那么**审计链就断了**——事后没人说得清"这批货是什么时候、凭什么从 A 变成 B 的"。
> 这类错误在做对账和纠纷处理时**一定会暴露**，而且**无法回溯修复**。

---

## 5. 可见授权的"反推开不了口子"

**"允许看见"本身也会泄露**——看见别人的动态库存，就能推出**它的销量和节奏**。

**我拍三条限制**：

| 限制 | 做法 |
|---|---|
| **范围受限** | 可见授权限定**维度取值子集**和**字段子集**（不是"看全部"） |
| **时间受限** | 可见授权带**有效期**（用完自动收回，默认不长期开放） |
| **形态受限** | 敏感量默认给**档位化值**（"充足 / 偏紧 / 紧张"）而不是精确数；精确数要单独授权 |

**为什么**：**"看得见"是数据视窗的一个特例，不是绕过它。** 可见授权只应该**放宽数据视窗的某个维度**，而不是**关掉数据视窗**。

> 一条硬规则：**任何"可见授权"都要落回 `34` 的数据视窗表达**（作为一条更宽的视窗），**不另开一条读取路径**。否则就会出现"授权通道"和"正常通道"两套逻辑——**两套逻辑必然不一致**。

## 6. 与既有设计的接口

| 机制 | 怎么接 |
|---|---|
| **`06` 审批与执行器** | **完全复用**。`35` 只是给"边界"这个场景提供申请单模板和审批路由 |
| **`26` §2.3 策略层级** | 扩成**双向**：下级只能收紧（负向），**上级可显式放开**（正向）。放开必须有**授权记录**，不是"改个配置" |
| **`34` 数据视窗** | 可见授权 = 一条更宽的视窗；**审批通过后视窗按申请单临时放宽**（带时限） |
| **`28` 交付物** | 跨边界申请单就是**一种交付物**，走同一套状态机（草稿→复核→确认→已交付） |
| **`03` 岗位包** | 只声明"**这个岗位需要跨边界能力**"（要哪种档位），**不写具体是谁** |
| **`29` 经验** | 跨边界的先例（"上次这么申请被批了"）**进经验库**，供审批人参考 |
| **多级边界** | 跨**两级以上**边界（A → 公司 → B）时，**审批路由按层级逐级**，不能一次跳到底 |

## 7. 审计与不可抵赖

**跨边界是风险最高的动作**（它同时改变数据和归属），审计要求比普通写更高：

| 记什么 | 为什么 |
|---|---|
| 申请方（数字员工 + **触发它的人**） | 分清"agent 自己想的"和"人让它干的" |
| 依据（理由 / 关联任务 / 交付物版本） | 事后能说清"凭什么" |
| 审批方 + 审批意见 | 责任人 |
| **视窗的前后状态** | 授权放宽了什么、什么时候收回 |
| 执行结果 + 回执 + 是否可撤销 | `06` §6 |
| **反悔路径** | 能撤销的撤销，不能的走反向单（冲销） |

**不可抵赖**：申请单和审批记录**不可篡改**（同 `26` §3.3）。

## 8. 验收标准

| # | 标准 |
|---|---|
| B1 | 数字员工**没有"可执行"档位时，无法完成任何跨边界写**（能力上做不到，不是被劝退） |
| B2 | 它**能发起**跨边界申请，申请单**没有产生任何实际变更** |
| B3 | 审批方**由客户策略配置**——换一个审批角色，**平台零改动** |
| B4 | 审批通过后，**视窗按申请单临时放宽**，且**到期自动收回** |
| B5 | 归属转移**是一个事件**（带前后状态与审批依据），不是一次静默 UPDATE |
| B6 | 归属转移后，**A 的历史交付物不被静默改写**，而是标记"依据已变更" |
| B7 | 归属转移后，**A 的经验不会被 B 当成自己的** |
| B8 | 可见授权**只放宽视窗的某个维度**，不产生第二条读取路径 |
| B9 | 审批超时 = **自动拒绝**（沿用 `06` 的默认值，不自动通过） |
| B10 | 一次跨边界动作的审计能完整回答**申请 → 审批 → 执行 → 结果**，且不可篡改 |
| B11 | 跨两级以上边界时**逐级审批**，不能一次跳到底 |
| B12 | 岗位包里**不含任何具体的审批角色名 / 边界名** |

## 9. 这一步顺带拍掉的决策

| # | 问题 | 我拍 |
|---|---|---|
| 1 | 隔离是绝对的还是有例外的？ | **默认隔离，但允许显式授权跨越**——绝对的墙会让业务做不了 |
| 2 | 谁能跨边界？ | **不是某个特定岗位**，而是**被策略授予了档位的任何主体**——平台不写死岗位 |
| 3 | 申请和执行能不能合并？ | **不能**。合并 = "想动就能动"，隔离形同虚设 |
| 4 | 要新造审批引擎吗？ | **不要**。完全复用 `06`，`35` 只提供申请单和授权档位 |
| 5 | "能看见"是不是就等于"能拿"？ | **不是**。三种档位独立配置 |
| 6 | 授权放宽后要不要收回？ | **要**。可见授权带有效期，默认不长期开放 |
| 7 | 归属转移怎么实现？ | **事件，不是 UPDATE**——否则审计链断裂 |
| 8 | 跨多级边界怎么办？ | **逐级审批**，禁止一次跳到底 |

## 10. 与 `36`（数字员工生命周期）的接口 ⚠️

**"数字员工退出"本质上就是一次跨边界 + 跨生命周期的资产处置**，所以两件事必须一起定，不能在这里切碎：

| 退出时要处置的资产 | 和本文的关系 |
|---|---|
| 数据视窗 | 收回（`34`） |
| 跨边界授权 | **全部立即失效**（本文）——尤其"可执行"档位 |
| 进行中的跨边界申请 | **撤回**（`36` §7 第 6 项：待确认项按超时规则关闭） |
| 经验与记忆 | 留 / 转 / 销（`36` §7.1：**留在原归属**；带毒的销毁） |
| 交付物归属 | 保留在归属链上（`28`） |

- 数字员工退出的那一刻，它的所有跨边界授权立即失效。

**⚠️ "立即失效"的精确含义（Day 4 自审补，避免两个"立即"打架）**：

| 项 | 精确规则 |
|---|---|
| **新授权的签发** | **立刻停止**（一纳秒都不给） |
| **"可执行"档位** | **立刻不可用**——包括**正在跑的那次运行**里后续的跨边界写 |
| **"可见"档位** | 立刻失效；但**已经取回、已在上下文里的数据**按 `36` §7 的资产处置走（不追溯删上下文） |
| **正在执行中的归属转移** | **让它执行完**（`06` 的执行器有幂等与回执），**不中途杀**——中途杀会留下"半转移"状态，比让它完成更糟 |
| **未开始的跨边界申请** | **全部撤回**（`36` §7 第 6 项） |

> **为什么区分"签发"和"在途"**：`36` §7 定了"跑完当前运行再停"。
> **两者的分界是**：**授权（准入）是立即的，动作（原子操作）是让它做完的。**
> 否则就会出现"执行器写了一半被断电"——**那是数据不一致，不是安全**。
