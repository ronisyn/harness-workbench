# 38 · 交付物送达

> 状态：方案，技术决策由我拍。**补空白**（Day 5）。
> 前置：`28`（交付物流程）· `10`（对外接口）· `04`（连接器）· `34`（数据视窗）· `03`（岗位包的交付物定义）· `26` §4.5（用户与角色）
> 由来：客户场景——**"备货计划现在就是计划专员做，其他人只是申请或者审核"** + **"产出怎么给人：界面查看导出 / 对话下载 / 飞书发文件 / 邮件"**。

---

## 0. 一句话

**`10` 定义了"活怎么派进来"，本文定义"结果怎么送出去"。这是两个方向，之前只做了一个。**

```
派进来（`10`）        客户系统 ──► 平台       6 种接入形态
送出去（本文）        平台 ──► 人             界面（底座）+ 飞书 / 邮件 / 对话（推送）
```

**核心判断（本文最重要的一条）**：

> **送达渠道不能让 agent 自己挑。**
> 如果 agent 能决定"发到哪个邮箱、哪个飞书群"，那它就能把成本表发到不该发的群里——
> **这是绕过数据视窗的一条后门**（`34` 管的是"看不看得见"，送达管的是"推送给谁"）。

**所以送达按我们一直用的那条分层办**：**岗位包声明、实例配置、平台提供能力**（同 `03` §1.3）。

## 1. 先分清三个东西（之前混在一起）

| | **可见**（`03` 第 4 块的 `可见:`） | **送达**（本文） | **送达确认**（本文 §5） |
|---|---|---|---|
| 回答什么 | **谁有权看** | **谁会被通知、走哪个渠道** | **送到了没有** |
| 谁在用 | 权限系统（`34` 数据视窗） | 发送系统 | 监控与审计 |
| 默认 | 最窄（`34` §3.1） | **只给必须的人** | —— |
| 例子 | "复核人能看这份计划" | "计划一出，**飞书发给复核人 + 抄送申请人**" | "飞书回执：已读 / 发送失败" |

> ⚠️ **`03` 里写的 `可见: [岗位本人, 复核人, 下游岗位]` 是权限，不是送达。**
> **"能看"不等于"会被通知"。** 这两个必须分开配——否则会出现"有权限但没人知道计划出来了"。

## 2. 岗位周围的三种人（Day 5 补，来自客户场景）

客户的原话：**"备货计划现在就是计划专员做，其他人只是申请或者审核。"**

这句话定义了岗位的完整周边：

```
① 申请人（提需求）        ──►  ② 计划专员（干活的数字员工）  ──►  ③ 复核人（把关）
   谁来提？                      它产出交付物                        谁来批？
   提给谁？                      谁会被送达                          谁会被通知？
```

| 角色 | 在哪声明 | 说明 |
|---|---|---|
| **① 申请人** ⭐ | **岗位包第 4 块**（本文新增字段） | **之前完全漏了**——"别人只是申请"这句话在系统里必须有落点。由**客户角色**决定谁能提（`26` §4.5） |
| **② 执行者**（数字员工） | 就是岗位包本身 | 它被触发的入口之一：**接受申请单** |
| **③ 复核人** | `03` 第 4 块已有 | 复核是本岗位流程的一部分（`28` §3） |

**"申请人"这条链要能走通**：申请人提交 → 转成一次运行（`13` §1 的"有人触发"）→ 产出交付物 → 送达**申请人 + 复核人**。

## 3. 送达的两层：底座 + 推送

| 层 | 渠道 | 必备？ | 说明 |
|---|---|---|---|
| **底座** | **界面：查看 + 导出** | ✅ **永远在** | **它是兜底，也是复核/审批/追溯的唯一场所**。客户没配任何推送、或推送全失败时，东西在这里 |
| **推送** | **飞书 / 企微 / 钉钉**（IM 机器人） | 可选 | 发文件 + 卡片（卡片可带"去复核"的入口） |
| | **邮件** | 可选 | 发附件 + 正文摘要 |
| | **对话里给下载** | 可选 | 人在会话里问一句，agent 把文件给他 |
| | **推给客户系统**（Webhook） | 可选 | **不是给人看的**，是给系统对接用的（`10` §2 的回调） |

> ⭐ **界面为什么必须做成底座，而不是"众多渠道之一"**：
> ① 客户可能一个推送渠道都没配（尤其是第一批）；② 推送会失败（邮件进垃圾箱、飞书应用被停）；
> ③ **复核、审批、版本对比、审计追溯这些动作，只能在界面上做**——它们不是"通知"，是"流程"。

## 4. ⭐ 谁能配送达（分层，同 `03` §1.3）

| 谁 | 定什么 | 禁止 |
|---|---|---|
| **岗位包**（模板，跨客户复用） | **声明要求**：本岗位的交付物需要走哪几类渠道、送给哪几类角色 | **不许出现具体邮箱、具体群、具体人** |
| **数字员工实例**（客户配置） | **填取值**：具体发到哪个群、哪个邮箱、谁是复核人 | —— |
| **平台** | 提供渠道能力 + 凭据托管 + 限流 + 审计 | 不许替客户决定发给谁 |

**岗位包里的写法（示例）**：

```yaml
deliverables:
  - id: replenishment-plan
    名称: 备货计划
    # ── 流程（原有）──
    状态机: 草稿 → 复核中 → 已确认 → 已交付
    复核: required
    验收标准: [ ... ]
    解释: required

    # ── 送达（Day 5 新增）──
    申请:                              # 谁能提需求（岗位周围的第①种人）
      谁能提: [业务角色: 运营/采购]      # 由客户角色决定（`26` §4.5）
      入口: [界面, 飞书, 接口]
    送达:
      底座: 界面                       # 不可关
      推送:                            # 全部可选，按角色配
        - 渠道类: [IM, 邮件]
          对象类: [复核人, 申请人]      # ⚠️ 角色，不是具体地址
          时机: [待复核, 已确认]        # 状态变化时送
          附件: [xlsx]                 # 发什么形态
```

**实例里的写法（客户填）**：

```yaml
送达配置:
  复核人: [张三@邮箱, 李四(飞书)]
  申请通道: [飞书群「备货申请」]
  推送目标:
    IM:   [飞书群「供应链计划」]
    邮件: [supply-chain@客户域名]
```

> **判据**：**岗位包里出现一个具体邮箱或群名 → 这个包就只能卖给这一家客户。** 同 `03` §4.1 的"结构性 vs 表述性"。
> **送达对象的声明是结构性的**（客户不能自己加一个"抄送我"），**具体地址是取值性的**（客户自己填）。

## 5. 送达的三个检查点 ⭐（否则送达成了一条绕过权限的路）

**一次送达，动作上是"平台把交付物推给某人"，但审批上要走三道闸**：

| # | 检查 | 为什么 |
|---|---|---|
| **1** | **预览必过数据视窗** | 收件人看到的内容，按**收件人自己的视窗**裁剪（不是按发件人的）。同一个交付物，复核人看到的成本口径可能和申请人不同（`34` §2.2 的派生） |
| **2** | **附件必须能按视窗重生成** | 交付物内部是结构化数据（`28` §1），**导出是渲染**。所以给不同的人可以给不同口径的附件——**这是"内部结构化"的一个白拿的好处** |
| **3** | **"可能被一群人看到"的目标必须显式授权** | 飞书群、邮件列表、抄送——默认**禁止**，除非客户技术团队显式开启，且**只能包含已配置的地址** |

> ⚠️ **第 3 条是必须的**：数据视窗是按"人"裁的，**群聊是"一对多"，视窗没法按人裁**。
> 所以群的语义只能是"**这个群里的所有人本来就都该看**"——这个判断**只能由客户做**，不能让系统猜。

## 6. 送达状态 ≠ 交付物状态（别混成一个状态机）

| | **交付物状态**（`28` §2） | **送达状态**（本文） |
|---|---|---|
| 是什么 | 这个交付物**在流程里走到哪了** | 这次**推送送到了没有** |
| 取值 | 草稿 / 复核中 / 已确认 / 已交付 / 作废 | 待发送 / 已发送 / 已送达 / 失败 / 已读（渠道支持才记） |
| 失败了怎么办 | 状态**不回退** | **重试 + 降级**，不影响交付物 |

**一条硬规则**：

> **送达失败绝不回退交付物状态。**
> 计划表已经在界面上可看了（底座），**飞书发失败只是"少了一次提醒"**，不是"计划没出来"。

**降级链**（可配）：

```
主渠道（飞书）失败 → 备用渠道（邮件） → 都失败 → 【界面角标提醒 + 待办】
```

**长活的通知**（`10` §1 的长任务三件套）：**回调**给客户系统、**推送**给人，是两条并行的线，都要发。

## 7. ⚠️ 凭据问题：用谁的飞书应用 / 谁的邮箱发（必须定死）

**发飞书要有应用凭据，发邮件要有 SMTP 凭据。这些凭据归谁？**

| 方案 | 做法 | 判断 |
|---|---|---|
| **① 客户自己的应用** ⭐ | 客户在自己的飞书里建应用，把凭据配进平台；邮件用客户的发信域 | ✅ **推荐**、也是 `02` A 路径的形态 |
| **② 平台统一的应用** | 所有客户共用一个平台应用发消息 | ❌ **不行**：消息记录在平台身上、且平台变成客户内部系统的身份提供方（同 `10` §3 拒绝的那个角色） |
| **③ 人工导出再发** | 平台只生成文件，人自己发 | ⚠️ 兜底，但**送达链断了**（没有回执、没有留痕） |

**硬约束（放在 `02` 的 C 系列里）**：

> **平台不代持客户内部系统的凭据。** 但"客户自己配置、平台在运行时使用"是允许的——
> 因为这与"客户自持模型 Key"（`02` 路径 A）是同一个形态：**凭据归属客户，平台只是执行者。**
> **两者都要满足同一条红线**：**agent 永远拿不到凭据**（ADR-6 / `30` §2）——发送由**平台的送达服务**做，不是 agent 做。

## 8. 送达的审计

| 记什么 | 为什么 |
|---|---|
| 送了哪个交付物的**哪个版本** | 版本会变（`28` §2），"发给你的那份是哪一版"必须能答 |
| 送到**哪个渠道、哪个目标**（群/邮箱） | 追责基础 |
| 发送时的**数据视窗摘要** | 证明"发出去的内容是按收件人权限裁过的" |
| 渠道回执（成功/失败/重试次数/已读） | 送达确认 |
| 谁触发了这次送达（系统自动 / 人手动转发） | 分清"平台发的"和"人自己转的" |

**不记业务数据内容**（同 `26` §3.2 的脱敏原则）。

## 9. 验收标准

| # | 标准 |
|---|---|
| T1 | **界面永远是底座**：关掉所有推送，交付物仍能在界面查看、导出、复核、审批 |
| T2 | 岗位包里**不含任何具体邮箱、群名、人名**（可复用性判据） |
| T3 | 送达对象**按角色声明**（复核人 / 申请人 / 下游），**实例才填具体地址** |
| T4 | **agent 不能决定发给谁**；它只能产出交付物，送达由平台按配置执行 |
| T5 | 群 / 邮件列表这类"一对多"目标**默认禁止**，必须客户显式开启 |
| T6 | **收件人看到的内容按收件人自己的视窗裁剪**（同交付物、不同人、可不同口径） |
| T7 | 导出的附件**能按视窗重生成**（内部结构化 → 外观可渲染，`28` §1） |
| T8 | **送达失败不回退交付物状态**；按配置重试与降级，最终落到界面角标 + 待办 |
| T9 | 推送用**客户自己的凭据**（飞书应用 / 发信域）；**agent 永远拿不到凭据** |
| T10 | 每次送达能回答：**哪个版本、送到哪、以什么视窗、回执如何、谁触发的** |
| T11 | **申请人**这个角色有落点：能提交申请、能收到结果，且**谁能提由客户角色决定** |
| T12 | 长活**两条线都发**：回调给客户系统 + 推送给人 |

## 10. 这一步顺带拍掉的决策

| # | 问题 | 我拍 |
|---|---|---|
| 1 | 交付物怎么给到人？ | **界面是底座（必备）+ 推送层（飞书/邮件/对话/Webhook，可选）** |
| 2 | 渠道能不能只做一个？ | **界面必须做**（它是复核审批追溯的唯一场所）；**推送可以一个都不配** |
| 3 | 谁决定发送给谁？ | **岗位包声明角色 + 实例填地址 + 平台执行。agent 不能决定** |
| 4 | `可见` 和 `送达` 是一回事吗？ | **不是**。可见是权限，送达是通知。**分开配** |
| 5 | "谁申请"之前有落点吗？ | **没有，本文补的**。它是岗位周围的第①种人，由客户角色决定 |
| 6 | 送达失败要不要回退交付物状态？ | **不要**。送达失败只是"少一次提醒"，东西在界面上一直在 |
| 7 | 群聊/邮件列表能随便发吗？ | **默认禁止**，必须客户显式开启——因为视窗没法按"群里的每个人"裁 |
| 8 | 用谁的飞书应用和邮箱发？ | **客户自己的**（同 `02` 路径 A 的形态）；**平台不代持客户内部系统凭据，agent 永远拿不到凭据** |
| 9 | 同一个人和不同的人，收到的附件要一样吗？ | **可以不一样**——内部结构化、导出是渲染，**按各自视窗重生成** |
| 10 | 送达要不要审计？ | **要**：哪个版本、送到哪、以什么视窗、回执、谁触发的；**不记内容** |

| 文档 | 关系 |
