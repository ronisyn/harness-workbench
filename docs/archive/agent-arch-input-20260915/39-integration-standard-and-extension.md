# 39 · 外部系统接入标准与扩展机制

> 状态：方案，技术决策由我拍。**补空白**（Day 6）。
> 前置：`04`（连接器契约）· `27`（服务器多项目治理）· `03` §1.3（声明与配置分离）· `14`（混合部署）
> 由来：客户三句话——**① "不管外部系统有没有接口，我们都要出一个官方、客观、有效的接入标准和实施方案，人家缺什么、补不补是它的事"**；
> **② "接跨境客户多站点，能在平台层面不断新增的能力，是不是就在连接器部分开发"**；
> **③ "要保证平台未来的扩展性，适配多样化业务，不断扩充能力"**。

---

## 0. 一句话

**平台的扩展性只有一条路：连接器生态的广度。**

```
新增一种业务能力  →  只需要新增连接器（写代码的地方）
新增一个站点/系统  →  只需要新增连接器实例（配置的地方）
新增一个岗位      →  只需要写岗位包（不写代码的地方）
                    ↓
              平台本身不动
```

> **这解决了客户第 ③ 句话**：**"不断扩充能力"不是靠平台变得更复杂，是靠连接器变得更多。**
> 平台越稳定越好，**变化都发生在生态层**。

---

## 1. 第 ① 句话：接入标准是**我们出的**，不是跟客户商量的

客户的判断完全正确，我把它定成一条原则：

> **我们对任何外部系统一视同仁。**
> **标准是我们出的，实施方案是我们出的。对方缺什么、要不要补，是对方的事——我们只负责"我们这一侧能对接任何外部系统"。**

**为什么这条必须写死**：如果接入标准变成"看客户系统有什么再定"，那么：
- 每接一个客户就要重新设计一次 → **交付成本随客户数线性上升**，交付杠杆失效
- 客户会以为"接入方式"是可以谈的 → **每次都要谈判**
- **我们的产品边界会被客户的系统现状定义**——那是最糟的结果

**正确的姿态**：我们给一份**标准 + 配套实施方案**，然后出一份**《对接缺口清单》**告诉对方"你这边要达到什么程度"。**它补不补，我们不管。**

---

## 2. ⭐ 外部系统的四档成熟度（客观、可判定）

**"缺口清单"不能凭感觉说，必须挂在客观标准上。** 所以先把外部系统分档：

| 档 | 判定（只看客观事实） | 我们怎么接 | 对方要补什么 |
|---|---|---|---|
| **A · 现代 API** | 有 REST/GraphQL 接口 + 鉴权 + 可获取凭据 | **API 连接器**（首选） | 基本不用补 |
| **B · 有数据出口** | 有数据库读权限 / 能定时导出文件 / 有报表接口 | **文件导入 或 只读库连接器** | 开一个只读账号 / 配一个定时导出 |
| **C · 只有界面** | 只能人工在网页/客户端里点 | **RPA 连接器**（兜底） | 提供一个专用操作账号 + 页面稳定承诺 |
| **D · 什么都没有** | 纸质 / 离线 / 明确拒绝配合 | ⛔ **`04` §4.4 的标准答案：直接说不接** | —— |

**三条使用纪律**：

1. **分档是客观判定，不是谈判结果**——按事实对号入座，不许"我觉得他们算 A 档"
2. **缺口清单只写"要达到什么"，不写"你们该怎么做"**——后者是对方的技术选择
3. **D 档明确拒绝**，不为了签单硬接（`04` §4.4 已定：**"拒绝接入"是产品能力，不是服务态度问题**）

### 2.1 ⭐ 一个关键的区分：不是"有没有 API"，是"有没有数据出口"

**这是最容易被误判的一档，也是最能省事的一档。**

| 对方的回答 | 真实的档位 |
|---|---|
| "我们没有 API" | **很可能不是 D 档** |
| "但我们的 ERP 能导出 Excel" | → **B 档**（文件导入） |
| "我们数据库可以开只读账号" | → **B 档** |
| "我们有报表系统，能定时发邮件" | → **B 档** |

> **客户的常见误解是"没 API 就接不了"。**
> **我们的标准要明确写出**：**"有没有 API"是 A 档的要求，"有没有数据出口"是 B 档的要求——两者相差一个数量级的对接成本。**
>
> **这条写进标准，能直接救回一批本来会被判 D 档的客户。**

## 3. ⭐ 第 ② 句话：渠道连接器的语义契约（多站点扩展的真正机制）

**客户问**：接跨境多站点，是不是在连接器层不断新增？——**是，但有一个前提条件，这个条件不写清楚，多站点扩展会变成一场灾难。**

### 3.1 灾难长什么样（不写契约的后果）

```
Amazon 连接器   →  amazon.get_sales_report()
Shopify 连接器  →  shopify.fetch_orders()
AliExpress      →  aliexpress.queryOrderList()
TikTok Shop     →  tiktok.search_order()
```

**每个站点一套字段名** → 岗位包里会写成 `如果站点是 Amazon 用这个，是 Shopify 用那个` →
**岗位包被渠道绑死，每加一个站点就要改一次岗位包** → **交付杠杆当场失效**（`03` §1.3、`37` §0 反复强调的那条）。

### 3.2 正解：渠道连接器不是"多接一个系统"，是"多实现一套同一个契约"

```
        ┌─────────────── 渠道能力契约（平台定义，固定）───────────────┐
        │  渠道·销售数据   渠道·库存   渠道·订单   渠道·商品   渠道·价格  │
        └───────────────────────────┬─────────────────────────────────┘
                                    │ 每个站点连接器都要实现同一组能力名
      ┌──────────┬──────────┬───────┴────┬──────────┬──────────┐
   Amazon     Shopify   AliExpress   TikTok    拼多多    （将来）
```

**两条规则**：

| 规则 | 内容 |
|---|---|
| **能力名由平台定，站点连接器只是实现它** | 站点连接器**不许发明新能力名**，只能实现契约里的那组 |
| **参数与口径归一** | 时间范围、金额单位、库存口径、订单状态枚举，**在连接器里翻译成统一口径** |

**结果**：**岗位包里写的是"渠道·销售数据"，不是"Amazon 的销售报表"。**
→ **新增一个站点 = 写一个连接器实现，岗位包一行不改。** 这才是可扩展。

### 3.3 渠道能力的四组（最小集，够开始）

| 能力组 | 干什么 | 站点差异最大的地方 |
|---|---|---|
| **渠道·销售数据** | 拉某个时间段的销量/销售额 | 报表口径、时区、退货怎么算 |
| **渠道·库存** | 查某个 SKU 在某个站点的可售库存 | 是否有仓的概念、预留怎么算 |
| **渠道·订单** | 拉订单明细、查订单状态 | 状态枚举、多币种、拆单 |
| **渠道·商品** | 上下架、改价、改详情 | **写操作**，`06` 的首跑护栏在这里最重要 |

> ⚠️ **"渠道·商品"包含写操作**（上下架、改价）——这是**不可逆且直接影响生意**的一类（`06` §2.3.5 的"真不可逆"档）。
> **站点连接器的可测性也是能力级的**（`04` §2.1）：Shopify 有开发店可以测，Amazon 没有 → 走首跑护栏。

### 3.4 顺带定死：平台里有两类能力，别混

| | **外部系统连接器** | **渠道连接器** ⭐ |
|---|---|---|
| 对接谁 | ERP / WMS / 中台 / 邮件 / IM | 电商平台（Amazon / Shopify / AliExpress / TikTok / 拼多多…） |
| 数量 | **每家不同，一家一个** | **一组平台，共享同一套语义契约** |
| 复用方式 | **靠适配**（写连接器） | **靠统一契约**（实现同一组能力名） |
| 岗位包里怎么写 | 写"我需要 ERP 的采购价能力" | 写"**我需要渠道·销售数据**"——**不写具体站点** |
| 加新的要动什么 | 加一个连接器 | 加一个连接器实现 + **零改岗位包** |

**这一条是"适配多样化业务"的技术含义**：**渠道类靠契约收敛，系统类靠适配扩展。**

## 4. 第 ③ 句话：扩展性的完整机制（一张图收口）

```
客户需求变了 / 要接新东西
        │
        ├─ 是新的一种"渠道"（新站点）？
        │     → 写一个渠道连接器实现（**平台侧开发**）→ 岗位包不动
        │
        ├─ 是新的一个"系统"（客户的 ERP/WMS/中台）？
        │     → 按 §2 判档 → 写一个连接器 → 岗位包只声明"要哪类能力"
        │
        ├─ 是新的一个"岗位"？
        │     → 写岗位包（`37`）→ **不写代码**
        │
        └─ 是平台本身要支持的新机制（新的审批方式、新的沙箱规格…）？
              → ⚠️ **必须改平台** —— 这时候要问一句"是不是我的抽象漏了"（`architecture` §1 的量化验收）
```

**四层扩展的判据**：

| 扩展类型 | 动不动平台 | 动不动代码 | 谁做 |
|---|---|---|---|
| 新站点 | ❌ | ✅（连接器） | **平台方**（这是资产，`37` §6） |
| 新系统 | ❌ | ✅（连接器） | 平台方 / 客户技术团队（受控模板，`04` §9） |
| 新岗位 | ❌ | ❌ | 交付团队（`37`） |
| 新机制 | ✅ | ✅ | 平台方 |

> **判据一句话**：**"这次扩展，平台动了没有？"**
> 动了 → 要么是真机制升级，**要么是抽象漏了**（后者是缺陷，不是正常扩展路径）。

## 5. 验收标准

| # | 标准 |
|---|---|
| Z1 | **接入标准与实施方案由平台方发布**，不随单个客户系统现状改变 |
| Z2 | 外部系统按 §2 的**四档客观判定**，产出**《对接缺口清单》**（只写"要达到什么"，不写"你们该怎么做"） |
| Z3 | **"没有 API"不等于接不了**——标准里明确 B 档（有数据出口）与 A 档的区别 |
| Z4 | **D 档明确拒绝**，不为签单硬接 |
| Z5 | **渠道连接器实现统一契约**：能力名由平台定义，站点连接器不得发明新能力名 |
| Z6 | **岗位包里不出现具体站点名**（写"渠道·销售数据"，不写"Amazon 报表"）——多站点扩展的可复用性判据 |
| Z7 | **新增一个站点 = 新增一个连接器实现，岗位包零改动**（可测） |
| Z8 | **口径归一在连接器里做**（时区、币种、状态枚举、退货口径），不上抛给岗位包 |
| Z9 | 渠道类与系统类**分属两套扩展方式**（契约收敛 vs 适配扩展），文档里明确区分 |
| Z10 | **"这次扩展平台动了没有"** 是一道必答的题；动了且不属于"真机制升级" → **判定为抽象漏洞** |
| Z11 | 多币种：**金额一律带币种字段**（`{amount, currency}`），**归一口径时不做隐式汇率换算**——汇率是业务决定，不是平台决定 |

> **Z11 顺带回答了一个悬着的问题**：多币种**现在不做汇率换算，但字段现在就带上**。
> 理由：不带币种的金额是**将来必然要重构的字段**；而汇率换算涉及"用哪天的汇率、谁定的价"，**那是业务规则，属于岗位包/策略，不属于平台**。

## 6. 这一步顺带拍掉的决策

| # | 问题 | 我拍 |
|---|---|---|
| 1 | 接入标准谁出？ | **我们出**。标准 + 实施方案 + 缺口清单，**不跟客户的系统现状商量** |
| 2 | 外部系统怎么分档？ | **四档客观判定**（现代 API / 有数据出口 / 只有界面 / 什么都没有） |
| 3 | "没有 API"就接不了吗？ | **不是**。**有数据出口（能导出/能开只读账号）就是 B 档**——这条能救回一批客户 |
| 4 | D 档接不接？ | **不接**。拒绝接入是产品能力，不是服务态度问题 |
| 5 | 多站点扩展在哪一层？ | **连接器层**。每加一个站点 = 一个连接器实现，**岗位包零改动** |
| 6 | 怎么保证岗位包不被渠道绑死？ | **渠道能力契约**：能力名由平台定，站点连接器只实现它；**岗位包里不出现站点名** |
| 7 | 渠道类和其他系统类一样吗？ | **不一样**。渠道类**靠统一契约收敛**；系统类**靠适配扩展**。两套方式 |
| 8 | 平台本身要不要为"多样化业务"变得更复杂？ | **不要**。**平台越稳定越好，变化都发生在生态层**（§0） |
| 9 | 多币种怎么处理？ | **字段现在就带币种，不做隐式汇率换算**——汇率是业务决定，归岗位包/策略 |
| 10 | 怎么判断一次扩展是"正常"还是"抽象漏了"？ | 问一句"**这次平台动了没有**"；动了且不是真机制升级 → **是缺陷** |
