# 需求原话存档与设计意图

> **这份文档的用途**：把项目发起人的**原话**和**真实需求**固化下来，作为**对质基准**。
> **为什么需要它**：设计文档是"结论"，容易越写越自洽；**一旦结论脱离了原始需求，就会出现"用自己写的东西验证自己"的循环论证**（已实际发生过一次：把行业常见场景误当成真实需求，写进了覆盖度盘点）。
>
> **规则（对所有读者，包括 AI）**：
> 1. **本文收录的才是"需求"**。设计文档里出现的场景、系统名、行业形态，**若本文没有，不得当成需求**。
> 2. 需要新增需求时，**必须先在这里补一条原话**，再改设计。
> 3. **"我的知识背景"不等于"这个项目的需求"。** 行业里常见的做法（钉钉/学习通/投委会/多币种/A2A…）**如果没有原话，就是不需要设计的东西**。
>
> 状态：**原话存档（Day 6 建立）**。原话逐字保留，不做改写。

## 0. 一句话：这个项目要做什么

**发起人的原话（2026-09，项目第一次发言）**：

> 我现在在设计一个 agent 平台，提供企业级 agent 服务，我现在要与你讨论平台的整体架构

---

## 1. 起点：全部原始诉求（第一次发言全文）

> 我的预想目标是自己开发一个类似 harness 这样的 agent，可以集成 codex、Claude 作为子 agent
> 它在服务器环境工作，比依赖于本地电脑
> 它可以作为 agent，封装相应的技能、知识等，可以嵌入其他网站，例如作为供应链计划员，或代码工程师等工人
> 我还要给它配一个开发平台，去开发可以搭载的 skill，插件，知识库
> 它可以通过 api，桥接到其他项目中，那这样就涉及到多租户隔离，每个租户单独计费，单独配 KEY
> 另外，它是独立渠道其他环境下工作，所以它得有自己的沙箱环境，不能去其他环境了就任意改东西，但是他还得获得一定的授权，读取其他环境的数据，例如供应链专员去读取销量数据，形成销量分析表
> 我在服务器给它工作环境也要配置相应的安全，平台是一个独立项目，还可能有项目 A/B/C 等等，项目之间不应该受到干扰，但 agent 也不能随意去在服务器游离到其他项目，它的工作环境必须受限才安全
>
> 上述我描述了一些基本想法，我们可以构建：
> 1. **平台**：给 agent 配置模型，厂商，路由；开发插件市场、skill 市场；接入多个 agent；打造 agent 壳，给壳封装成产品，带 api
> 2. **agent**：定义它的工具、会话、沙箱等等
> 3. **服务器环境**：沙箱、权限、部署方案等等

## 2. 逐条真实需求（全部标原话出处）

### R1 · 服务器上多项目隔离（含 agent 不得游离）

> **原话**："我说的项目，是我自己服务器的多个项目，比如咱们现在在讨论设计 agent 算一个项目，然后我之前做的 agent 也算一个项目，这就是在服务器内的工作区要分开，**现在是没分开的**；另外，我还有一个客户，做**电子元件的电商平台和进销存系统**，这也是两个项目"
>
> **原话**："**agent 也不能随意去在服务器游离到其他项目，它的工作环境必须受限才安全**"

**设计落点**：`27`（服务器多项目治理 + 代码层隔离）、`01`（标识与隔离）、`05`（沙箱）

### R2 · 岗位优先级（分期路线）

> **原话**："**供应链的所有岗位都要先做**：备货计划、采购、发货/物流、仓储、包括供应链部门管理者（刚才我只是举例，岗位不是只有 12 个）。**供应链岗位是第一优先级**；然后包含但不限于**运营岗位**，详情页优化，APP 运营，广告运营，红人运营，媒体投放，运营负责人（看数据分析数据的），这几个运营岗位是**第二优先级**；**第三优先级是产品经理**，他们生产、研发新品上架，调研新品，做文档做数据分析等等；**第四优先级是 IT**，他们有研发部门，可以用我们的 agent 做研发更好，但他们现在自己也在用 Claude，只是没有一个**团队性质的 IT 项目管理平台并同时接入 agent 做全局管理**；其他岗位靠后慢慢来"

**设计落点**：⚠️ **尚未落进任何文档**（`architecture` §11 只有"能力成熟度"里程碑，没有业务岗位优先级）

### R3 · 每个岗位只干到自己的节点

> **原话**："本质上都是把活干了，但**只干到那个岗位的需要**……每个岗位有自己的节点，agent 服务某个岗位，**达成某个节点即可**，未来稳定了，信任高了，不出错了，再'一步做到底'"

**设计落点**：`06`（写操作分级 L0–L4）、`28`（交付物状态机）、ADR-2

### R4 · 外部接口现状与 RPA 兜底

> **原话**："这些接口都有，**越知名的电商平台接口越完整越稳定**，**ERP 和自研系统的接口属于定制化的，需要逐个开发**"
> **原话**："能保证 **80% 的接口都是稳定取的**，只有非常少数的小平台接口不太稳，但没关系，**如果接口不支持，我就让 RPA 去做 excel 订单导入**"

**设计落点**：`04`（连接器四种形态含 RPA/文件）、`39`（接入标准与四档成熟度）

### R5 · 数据形态

> **原话**："**备货计划是 excel 表，采购计划是 excel 表，发货计划是 excel 表；采购单是 ERP 单据，发货单是 ERP 单据**；关联的 ERP 单据还有：**入库单、质检单、退货单、调拨单**等等，这里不全，后续慢慢补充即可"

**设计落点**：`03` §2（交付物：内部结构化、Excel 只是外观）、`28`、`33` §1（数据层 vs 知识库）

### R6 · 仓库与货权

> **原话**："多平台有**共用海外仓**，也有独立自己平台的仓库，叫**平台仓**，但**海外仓也会分团队库存（团队库存就是指不同销售平台的货权库存）**"
> **原话**："**头程时效**，头程物流服务商会给一个报价单过来，带着去全球每个国家的时效，这里是固定的，但也是参考，**实际运输是浮动的**，根据船运当时的情况发生波动"

**设计落点**：`01` §3.2（资源维度）、`34`（数据视窗）、`35`（跨边界授权）

### R7 · 数据权限隔离（客户举的两个真实例子）

> **原话**："运营问 agent，8 月份采购的那批货成本多少，这时候要求这个 agent **不能暴露成本价**，因为运营无权知道真实成本，他们这个岗位知道的成本都是**供应链原始采购价上加了一部分利润的**"
> **原话**："A 平台和 B 平台都在销售同一个 SKU，A 没货了……他问一句现在这个 SKU 还有多少货，然后 agent 马上**暴露了 B 团队的库存余量**，这也是不行的"
> **原话**："虽然 A 平台和 B 平台都用的是运营这个数字员工，同样属于运营这个岗位包，但**他们之间也必须有数据权限隔离**"

**设计落点**：`34`（数据视窗：行/列/派生/防推演）、`35`（跨边界授权）

### R8 · 数字员工如何退出

> **原话**："我比较关心，**数字员工如何退出**，之前我们在对外契约上只讨论了有几种方式接入，但**一直没有讨论如何退出**"

**设计落点**：`36`（五态 + 退出清算十一项 + 就业账本）

### R9 · 引擎与 agent

> **原话**："我希望也接入 **codex、Claude、deep seek harness 三个引擎**……那这三个引擎我可以直接拿去封装成岗位，在设置岗位的时候配它；另外，我自研的 **roni 引擎也要继续自研**到成功，这个引擎和另外三个现成的引擎是并列关系……我希望 **rw 在某些方面表现突出**一点，能够在市场中有一席之地"
> **原话（定位澄清）**："**RW 是 roni workbench 的简称，workbench 是工作台，就是平台，就是壳，而 roni 是 agent**……平台就是平台，agent 就是 agent，**agent 是平台中可拔插的零件**……平台叫 **Ronisyn**，自研 agent 叫 **roni**，其中还要插入两个开源 agent：**DS harness** 和 **codex harness**；既然 Claude 不让用，咱就不用它了，**一期做 3 个 agent 也够了**"

**设计落点**：ADR-5、`19`（平台/agent 边界）、`20`/`23`（移植零件）、`15`/`16`（harness 评估）

### R10 · 模型厂商（国内）

> **原话**："就国内的吧，deep seek，kimi，豆包，百度，阿里，work Buddy，火山方舟、智谱清言，minimax，足够了"

**设计落点**：`30`（模型网关）、`02`（合规：不转售、不聚合中转）

### R11 · 混合部署（客户数据中台在客户服务器）

> **原话**："**要做混合部署，而且现在就要做**，客户现在的数据中台就是独立项目，在他们的服务器上，如果要把手脚安装上去，就得混合部署，如果我们只留位置，不进路线图的话，那我们的手脚拿来这些数据，存在哪呢？怎么处理呢？"

**设计落点**：`14`（混合部署）、ADR-8（控制面不碰业务数据）

### R12 · ⭐ 脱离本机 + 移动端 + 定时任务在服务器跑

> **原话**："**harness 的确开源了，但那都是 dsh 环境，也就是接入本机的开放的，我们能在服务器去用吗？假如我关了电脑，客户关了电脑，但是定时任务还是在服务器跑起来？** 我一直和你说，**希望有一个可以脱离本机的 agent，未来我们还要做移动端的东西，让客户在手机、在任何电脑上都能随时操作和使用 agent**"

**设计落点**：`16`（harness 服务器化）、`10` §2（六种接入形态）、`architecture` §4.4
⚠️ **覆盖不完整**：**"移动端"与"脱离本机"没有被作为一条需求显式验证过**

### R13 · 数据存档与投喂

> **原话**："过去几期的备货计划表，有历史存档吗？**有存档，有历史，在客户备货计划专员那里**，回头我给他部署项目的时候让她把文件给 agent，或者放知识库，或者你说安排我让客户把文件怎么放，我照做就行"

**设计落点**：`33`（数据层 / 知识库 / 摄入管线）、`28` §6（归档与精确查询）

### R14 · 交付物怎么给到人

> **原话**："要么**做到界面**，别人可以查看、导出；要么**通过 agent 对话**，让别人可下载；支持**飞书发文件、发邮件**"

**设计落点**：`38`（交付物送达：界面底座 + 推送层）

### R15 · 商业模式

> **原话**："目前是**我开发**，但他们有技术团队，可以协助维护，给他们权限而已，**我开发好，卖给他们，赚钱**"
> **原话**："让客户自己用 key，但如果他没有 key，也可以用我们的，到时候**对账**就行了，**我不赚 token 差价**"

**设计落点**：`02`（合规：不卖 token，ADR-6）、`30` §7（计费：席位 + 任务数）

### R16 · 岗位包与数字员工（命名与定位）

> **原话**："**岗位包**我认为不用改了，和员工包定义相同，叫什么不重要，咱们就叫岗位包吧；**岗位实例确实可以改成数字员工**"

**设计落点**：`03`（岗位包九块）、`36`（数字员工生命周期）、`37`（岗位包编写）

### R17 · 服务器上的代码与项目互不干扰

> **原话（Day 6）**："**基于一个服务器，多个项目的场景**……当前我们设计的这个平台，就是一个项目，agent 和平台，我们要写这些代码，要提交更新这些代码，**这是我们自己的项目**；其次，这个服务器还有可能有其他项目……官网，也包含给客户定制开发……**这些代码提交的时候，项目和项目之间都不可以受干扰，应该是干净的独立的**"
> **原话**："给平台内开发的有关代码的东西，比如 **MCP、插件、更新工具**之类的，那都属于**咱们平台/agent 项目的优化、迭代开发**"

**设计落点**：`27` §6（代码层隔离）

### R18 · 外部系统接入标准由我们出

> **原话（Day 6）**："你也不用管客户的系统是不是自有的，要不要开发接口，**这是客户的事情**，对于我们而言，那都是把我们的数字员工接到外部的系统中，**不管这个外部系统有没有接口，我们都要出一个官方的、客观的、有效的对外接入的标准和实施方案**，然后人家缺什么，它要不要补是它的事情，我们不管，我们只要保证我们自己设计的东西能够**有效的对接任何外部的系统，不管是 saas 还是自研系统**"

**设计落点**：`04` §3.2、`39`（接入标准与扩展机制）

### R19 · 多站点扩展

> **原话（Day 6）**："我们在连接器这个部分开发的时候，肯定是要**接跨境客户的多站点**的，**我们能连接的站点越多，岗位包能支持的站点就越多**，它是不是在平台这个层面去不断新增的？也就是我们说的**连接器的部分去开发**的呢？……我们要保证这个平台的**未来的扩展性，可以适配多样化的业务，不断扩充能力**"

**设计落点**：`39` §3（渠道连接器语义契约）、`architecture` §1 原则六

### R20 · 成本是核心焦虑

> **原话**："为什么是 4000，只因为是现在已经有的吗？如果现在已有的方案是不合适的呢？**现在 harness 是怎么做的？**"
> **原话（RW 现状里的自我诊断）**："贵不是因为它乱花，而是因为**每轮全量重发 + 固定注入大 + 工具结果大 + 多轮**这四个必然项"
> **原话**："这些数值**经过验证了吗**？还是我们参考 harness 的成熟方案？"

**设计落点**：`architecture` §1 原则七、`23`（数值全部对齐 harness 真值）、`24`（按需召回）

### R21 · 方法论要求（对 AI 的要求本身也是需求）

> **原话**："你的思考应是**长期、准确、有效、完整的，不应该把一些工作丢给后续**，只要我们设计的架构是完善的，我们就要**一步到位，不要一改再改**"
> **原话**："你要把我的**场景、需求，转化成架构设计的思路**，补充这些架构层面无法支持的东西，让我们的架构完整，**不至于做一套东西出来，东拼西凑打补丁**"
> **原话**："这一类问题我是没有经验、能力、知识能够帮你做决策的，你应该**基于自己对 agent 领域足够的专业判断，给与我方案**，告知我理由和这样设计的结果是怎样的"
> **原话**："**用户不会比你更专业，因此他总是会漏掉某些重要事项**，而你总是站在全局的角度，长远的角度，思考和设计"

**设计落点**：`11`（决策清单，架构师拍板制）、`31` §6（通用性判据：客户自定义维度/角色，平台零改动）

### R22 · 业务节奏（发起人 Day 7 明确的三步）

> **原话**："**等我们架构设计好了，下一步是融合现有的 RW 做开发优化，再下一步就是接入现有的项目管理平台、和一个 shopify 平台**"

```
① 架构设计（进行中——本文档集）
② 融合现有 RW 做开发优化
③ 接入现有的项目管理平台 + 一个 Shopify 平台
```

**这条回答了一个之前一直悬着的问题**：**开发按什么顺序推进**——不是按能力成熟度论文式排序，**是按发起人的业务节奏**。
→ `architecture` §11 的里程碑表因此改为"**实现顺序参考**"，而**架构本身保持完整**。

### R23 · 第一个岗位包（发起人指定）

> **原话**："**第一个岗位包可以定两个，一个是备货计划专员，一个是软件工程师**"

**⚠️ 注意：这是产品决定，不是架构输入。** 架构只保证"**任意岗位包都能被生成、配置、装载**"（见 [`44`](./44-loading-standard.md)）。
**但它有两个架构含义**：
① 备货计划专员 → 需要**只读 + 文件导入**型连接器（Phase M0 覆盖）
② **软件工程师 → 需要"开发工作区"规格 + `R3` 运行时档**（`05` §1.1/§1.2）——**这条之前在 `11` 里被拍成"第一批不做"**，现在**要重新评估**（见 `05` 的修正）

### R24 · 装载必须可行（发起人 Day 7 的关键补充）

> **原话**："**你设计的架构，当我要给客户开发第一个岗位包的时候，它支持岗位包的生成、配置、挂到平台，然后有个东西，不管叫 API 还是 SSH 还是什么，我不懂那个，但是要有，客户要看什么指南，知道这个岗位包如何装载到它的平台，不管他的平台是 saas 还是 erp 还是什么，都有指南能够充分描述，能够装进去。如果你架构不支持，或者到时候出问题，我做成岗位包，可不知道怎么装，我也不知道怎么装，那不是白做吗**"

**设计落点**：[`44-loading-standard.md`](./44-loading-standard.md)（装载契约 + 三种形态清单 + 自检工具 + 责任边界）

### R25 · 数字员工用谁的身份读客户数据（发起人 Day 8 追问）

> **原话**："**我们定的数字员工，怎么配置，按客户的 ERP 账号，还是按什么配置，这些都不知道呢，怎么给客户交付呢？比如就备货计划专员，这个数字员工什么都做好了，数据也写进去了，但是怎么给客户挂到他的系统里面去呢？**"

**设计落点**：[`44` §1.6](./44-loading-standard.md)——
**三层身份**（客户系统账号 / 平台服务身份 / 运行临时票据）· **客户建专用账号**（不用个人账号）· **凭据三种给法**（含"数据不出内网时我们连密文都拿不到"）· **配置链六步** · **备货专员完整例子** · **凭据变更与退出的双向撤销**

### R26 · 客户的员工怎么登录、怎么进对的组织（发起人 Day 8）

> **原话**："登录支持：**手机号+验证码**，**飞书第三方登录**，**飞书组织账号接口传回来的整套组织架构信息**，为组织内的手机号码**生成默认密码**，靠**手机号+密码登入，自动属于这个组织**，**不破坏组织架构和权限**"

**发起人已确认**：① **客户就是飞书用户** ② **两条登录都开**（飞书 + 手机号密码） ③ **"默认密码"改成"邀请链接"**（同意）

**设计落点**：[`44` §1.7](./44-loading-standard.md)——双轨身份 · 组织同步**只读单向可撤销** · **不重建部门树** · **权限不从组织架构继承** · **邀请链接激活（无默认密码）** · 离职自动停用 · 与计费的关系
