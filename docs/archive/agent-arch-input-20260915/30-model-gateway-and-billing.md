# 30 · 模型网关 + 计费（平台侧第 4 步）

> 状态：方案，技术决策由我拍。
> 前置：`architecture` §4.1/§8（总览级）· `26`（归属链）· `02`（合规：不卖 token）
> 由来：这是平台侧**最薄**的一块——模型网关在总览里只出现 4 次，计费只有总览级描述。

---

## 0. 一句话

**模型网关 = 所有 LLM 调用的唯一出口（三个 agent 共用）；计费 = 内部算成本、对外算"干的活"。**

---

## 1. 模型网关：统一出口 + 多 agent 隔离

**为什么必须统一出口**：不统一，就没法计量（不知道花了多少钱）、没法合规（不知道数据去了哪）、没法降级（模型挂了没法切）。

### 1.0 ⭐ 网关属于哪个面？—— 属于【数据面】（Day 7 定，架构级阻塞项）

**独立对抗性评审的第一号发现**：`architecture` §4.1 与本文都说网关是"**唯一出口、三个 agent 共用**"，但**从未声明它属于控制面还是数据面**。

**后果**：混合部署（`14`）承诺"数据不出客户内网"，**如果网关在控制面，每一次推理的完整业务上下文都要出境**——ADR-8 当场被违反，而且是**每天都在违反**。

**我拍：模型网关是数据面组件。** 三条连带规则：

| 规则 | 内容 |
|---|---|
| **① 实现落在数据面** | 网关进程随数据面部署（客户内网 / 平台数据面集群）。**控制面只下发路由策略与配额，不参与调用** |
| **② 厂商密钥不出数据面** | 密钥在数据面解密使用。**控制面只保存密钥的引用与归属，不保存明文、不解密**。这是对 `01` §3.1"KMS 优先级下调"的必要补强——**下调的是"每客户独立密钥"，不是"密钥不得出境"** |
| **③ 验收要能证伪** | 硬验收：**混合部署下抓包证明控制面零业务数据**。已加入 `31` 验收清单（Q7） |

**为什么这条必须现在定死**：它是 ADR-8 与 ADR-1 的交汇点。
**网关放错面 = 隔离从第一天就破了，而所有其他隔离设计都白做。**

> ⚠️ 顺带修一处含糊：`architecture` §2 总图上"模型网关"画在**控制面**框里，**那个画法是错的**。

### 1.1 只接境内已备案模型

**境外模型（GPT / Claude / Gemini）一刀切排除**（`02` 定的刑事风险最高处）。

### 1.2 不对外暴露

**平台不对客户暴露原始模型接口，不提供"一个 Key 调所有模型"的聚合中转**（ADR-6）。
→ **模型路由是内部能力，不是对外产品。**

### 1.3 多 agent 共用，但要隔离（我拍）

三个 agent（roni / DS harness / codex harness）共用一个网关，**必须做四层隔离**：

| 隔离 | 目的 |
|---|---|
| **配额** | 一个 agent 不能吃掉全部额度 |
| **限流** | 一个 agent 刷爆 QPS 不影响别人 |
| **故障** | 一个 agent 的失败重试不拖累别人 |
| **归因** | 每次调用能归到 `客户 → 工作区 → 数字员工 → 运行`（`26` §1.2） |

## 2. 密钥：客户自持为主，agent 永远看不到

| 模式 | 说明 | 允许 |
|---|---|---|
| **客户自持**（主力） | 客户以自己主体去厂商注册、持有 Key | ✅ 成本天然归客户，零授权风险 |
| **服务商代持** | 平台采购额度供客户用 | ⚠️ 需官方伙伴授权（`02` §4） |
| **私有部署** | 内网模型 | ✅ |

**密钥怎么存怎么用（我拍）**：
1. **加密存储**（KMS），只有网关能解
2. 调用时解密 → 调完即弃，**不落日志、不进上下文**
3. **agent 永远看不到 Key**——走 `01` 的"凭证代理"模式
4. **审计记"用了哪个 Key"，不记 Key 本身**（`26` §3.2 脱敏）

---

## 3. 路由：三个维度的策略

| 维度 | 规则 |
|---|---|
| **数据敏感级** | `机密` → 只能走私有部署；`内部` → 指定区域；`公开` → 便宜模型 |
| **任务复杂度** | 规划/推理 → 强模型；抽取/格式化/收尾 → 便宜模型 |
| **成本与可用性** | 超预算降级；主模型故障时切备用 |

**降级链**由岗位包声明（`preferred` + `fallback`），网关执行。

**多模型可切换在合规上是加分项**——它把产品定性为"一个 agent 产品（底层可换模型）"，而不是"某家 token 的转售通道"（`02`）。

## 4. ⭐ 缓存：成本的第一杠杆

**这是 roni"为什么贵"最重要的解法之一**——你实测 DeepSeek 缓存命中价与未命中价**差 27 倍**。

**我拍：网关必须保证"可缓存部分逐字节一致"。**

```
可缓存（前缀）  →  系统层 + 工具层（`08` 五层上下文的前两层）
                  ← 同一岗位包版本 + 同一权限下，必须逐字节一致
不可缓存（尾部）  →  任务层 + 结果层
```

**陷阱**：任何"每轮都变"的东西混进前缀，缓存全废。比如：
- 时间戳、随机 ID 写进系统提示
- 运行时快照放在前面（roni 现在把它挪到末尾了，做对了）
- 工具清单顺序不稳定

**网关要做的**：
1. **校验前缀稳定性**（同一岗位的两次调用，前缀应逐字节相同；不同就告警）
2. **暴露缓存命中率指标**（客户看不见，你用它优化）
3. **⭐ 缓存键必须带"数据视窗指纹"**（`34` §6）——否则 A 数字员工查到的东西会被 B 数字员工命中，**缓存会变成一个跨权限泄露通道**
4. **⭐⭐ 缓存必须按【客户】硬分区**（Day 7 补，独立对抗性评审的 P0-3）

> ⭐⭐ **第 4 条必须单独说清**：
>
> 本文原先只说"带视窗指纹"，而**视窗指纹只隔离"权限形状"，不含客户维度**。
> 更危险的是：本文要求"**同岗位包版本 + 同权限下前缀逐字节一致**"，而"**同岗位包**"天生是跨客户的——
> 于是 **A 客户的缓存条目可以被 B 客户命中**。走"服务商代持 Key"模式（§2 模式二）时，全体客户还共用同一个厂商账户，**连账户级隔离都没有**。
>
> **这不是实现疏漏，是"把跨客户复用写进了设计"。**
>
> | 规则 | 内容 |
> |---|---|
> | **缓存键第一段是客户** | `客户 → 工作区 → 岗位包版本 → 权限形状（视窗指纹） → 前缀哈希`。**跨客户永不命中** |
> | **共享网关默认禁止跨客户前缀复用** | 同一客户的多个工作区可以复用；**跨客户复用需显式开启，默认关闭** |
> | **代持 Key 模式下额外要求账户级隔离** | 每客户独立的账户视图与配额桶；**不能"全体客户一个账户 + 一个缓存池"** |
>
> **验收**：构造"两个客户、同岗位包、同权限"的场景，**缓存命中率必须为 0**（已加入 `31` 验收清单 M10）。

> ⚠️ **这两件事不冲突，但必须分清**：
> - **前缀**里放**策略约束**（"你只能看某类归属维度下的数据"）——**跨实例一致，不破坏缓存复用**
> - **前缀里禁止放视窗的具体取值**（"你看的是 A 团队"）——否则每个实例的前缀都不同，缓存全废
> - **取值差别的隔离靠数据层**（数据视窗在数据出口生效），**不靠提示词**
>
> 换句话说：**缓存复用发生在"同一权限形状"的实例之间，泄露风险由"指纹"这一环挡住。**

## 7. 计费：两层计量 + 单位定义

### 7.1 两层计量（沿用并深化）

| | **内部**（算成本） | **对外**（出账单） |
|---|---|---|
| 单位 | token、调用次数、缓存命中 | **干的活** |
| 精度 | 每次调用 | 每次交付 |
| 谁能看 | 只有你 | 客户可见 |

### 7.2 ⭐ "干的活"到底是什么（**Day 11 重写：席位 + 用量，用量按任务档位**）

**发起人 Day 11 明确**：**"收费按席位 + 任务数也行"**，并追问：**"但『任务』如何定义单价呢？一个任务消耗多少 token？我们怎么定价？"**

**这个问题的答案是三层：先定义任务 → 再分档 → 最后才是定价。**

#### 7.2.1 第一步：**"一次任务"怎么定义**（不定义就没法计费）

**我拍：一次任务 = 一个人明确发起、或一次定时触发、且最终有明确结束的一次执行。**

| 算一次 | 不算 |
|---|---|
| 客户说"帮我出一份备货计划" → 跑完（含派子代理、含等人复核） | **翻修**：复核人打回让它再改一遍 → **算新的一次** |
| 定时任务触发一次 | agent 内部派出的**子代理**（那是同一次的内部步骤） |
| 客户在对话里追问一次（**如果它又跑了一轮完整执行**） | 单纯闲聊/查询（**那算"咨询"，可以免费或按轻量计**） |

**四条必须写进条款的规则**（否则一定扯皮）：

| # | 规则 | 为什么 |
|---|---|---|
| **① 计费单位是"交付物产出"，不是"运行次数"** | 一次任务内部可能跑 3 轮、派 5 个子代理——**对客户来说那是"一次活"** | 否则客户看不懂账单 |
| **② 打回重做算新的一次** | 但⚠️ **如果是我们岗位包的问题导致反复打回，举证后免掉** | 不能让客户为我们的质量付钱 |
| **③ 客户可以在发起时"锁定档位"** | 见 §7.2.2 | 防"预期轻活变成重活" |
| **④ 超档要客户先同意** | 跑到一半发现超了 → **停下问客户**，同意才继续 | 同 `08` §6 的预算软着陆 |

#### 7.2.2 ⭐ 第二步：**任务分档**——这是"怎么定价"的正解

**为什么不能按 token 计价**：**同一个"备货分析"，消耗可以从几十万到几百万 token**——
客户无法预估，我们也无法报价，**对双方都是坏的**。

**我拍：分三档，按"客观可测的重量"定档，每档一个固定价。**

| 档 | 什么活 | 客观判据（**配置里声明，不是模型当场判断**） | 相对成本 |
|---|---|---|---|
| **轻** | 查一次数、算一个指标、答一个问题 | **不派子代理、单轮、无大文件** | 1× |
| **标准** | 出一份带分析的产出（如备货计划） | **派 1–3 个子代理、≤3 轮、数据量中** | 3–5× |
| **重** | 多源交叉、批量、跨系统、要反复验证 | **派 4+ 子代理、多轮、大数据量、含写操作** | 10×+ |

**三条关键设计**：

| # | 设计 | 理由 |
|---|---|---|
| **① 档位由【岗位包 + 实例配置】声明** | 客户看得见"这个员工跑一次大概多少钱" | **不在运行时让模型判断**——那是 `06` 的"阈值判断不交给模型"同一条纪律 |
| **② 档位可由【历史数据】校正** | 跑一段时间后，用真实成本回填档位 | 见 §7.2.4 |
| **③ 客户能看见"为什么这活贵"** | 展示"派了 3 个子代理、查了 4 个系统" | **把成本翻译成客户听得懂的话** |

> **对客户的一句话**：**"简单的活便宜，复杂的活贵，每档多少钱你可以先看到。"**
> **这比"按 token 计费"好解释一百倍**，而且**客户能自己控制成本**（选轻档还是标准档）。

#### 7.2.3 ⭐ 第三步：**定价怎么算**——不能拍脑袋

**发起人问的"一个任务消耗多少 token"，诚实的答案是：现在不知道。**

**`architecture` 的改造（按需召回、缓存、修剪、压缩）会让成本**显著**下降——
但**降多少，必须有实测数据才能说。** 拍脑袋定价 = 要么亏，要么贵得卖不出去。**

**我拍一条定价方法（不是数字）**：

| 步骤 | 做什么 |
|---|---|
| **① 先精确记账，不对外定价** | 网关本来就记每一笔 token（`30` §7.1）。**第一版跑真实任务，只看成本分布** |
| **② 看分布，不看看均值** | 取**P50（中位）与 P90**——**均值会被个别重型任务拉歪** |
| **③ 按 P75 + 目标毛利定价** | 定价 = **P75 成本 × (1 + 目标毛利率)** + 分摊的基础设施成本 |
| **④ 首批客户用"创始客户价"** | 明确告知"**价格在调整中，给你锁定 12 个月**" |
| **⑤ 每季度复核一次** | 成本结构变了（换模型、优化了召回）→ 重新算 |

**⭐ 一条我必须提醒你的判断**：

> **在你没有跑过 100 次真实任务之前，任何单价都是猜的。**
> **所以正确顺序是：先精确记账 → 跑一批真任务 → 看成本分布 → 定价。**
> **而这件事恰好和你的业务节奏吻合**（`40` R22：架构设计 → 融合 RW 开发 → 接入项目管理平台 + 一个 Shopify）。
> **接入那个真实客户之后，你自然会拿到一批真实成本数据**——**那时候定价，一次就准。**

#### 7.2.4 客户账单长什么样

```
席位费：数字员工 × 4 个（备货计划员 / 采购专员 / 库存专员 / 数据面运维）  × ¥X/月
任务用量：
  · 轻任务   312 次 × ¥a
  · 标准任务  48 次 × ¥b
  · 重任务     3 次 × ¥c
  ────────────────────────────────
模型成本：¥Y（客户自持 Key 时不出现此行；我们代持时按实际对账，不加价）
────────────────────────────────
本月合计：¥Z
```

**三条纪律**：

| # | 纪律 | 理由 |
|---|---|---|
| **① 客户界面不出现 token 单价与余额**（ADR-6） | 出现就是"卖 token" |
| **② 月账单可设上限**，超了要客户同意才继续 | 客户最怕"账单失控" |
| **③ 每一档的单价在签约时就锁定**，不随月度浮动 | 客户要可预期 |

### 7.3 模型成本 = 成本转嫁，不是利润中心

- **BYOK**：客户自付，平台只计服务费
- **代持**：按实际消耗**平价对账**（不赚差价，`02`）

## 8. 配额熔断与毛利监控

### 8.1 三层熔断（我拍）

```
客户级硬上限  →  工作区级配额  →  单次运行预算
   （月）           （部门）         （单任务）
```

任一超限即停，**并向上一级告警**。

### 8.2 ⭐ 毛利监控（新，很重要）
**每周算一次：每个客户的实际成本 vs 收入。**

| 情况 | 动作 |
|---|---|
| 毛利 < 阈值 | **告警**——这个客户在亏钱 |
| 持续亏 | 触发定价复核 |

**为什么必须做**：你的成本是**变量**（token 消耗随客户用量涨），收入如果是**固定**的（席位费），**用量一大就亏**。这个监控是"卖得越多亏得越多"的刹车。

> 这也是你最初对成本的焦虑的正解——不是"省着用"，而是**算清账**。

### 8.3 ⭐ 模型观测：两个视角，别只做一个（Day 4 第 2 轮自审补）

`17` §1 记录 roni 有"**模型观测**"。**新架构只写了"毛利监控"，那是平台方的视角**——缺了**客户技术团队的排查视角**。

| 视角 | 谁看 | 看什么 | 目的 |
|---|---|---|---|
| **平台方 · 毛利** | 运营（§8.2） | 每客户成本 vs 收入 | 别亏 |
| **客户方 · 行为** ⭐ | **客户技术团队** | 每轮：用了哪个模型、多少 token、缓存命中率、**失败/重试/降级了几次**、慢在哪 | **排查"今天怎么变慢了/变贵了/变笨了"** |
| **交付团队 · 质量** | 交付团队 | 同一岗位包在不同客户上的：人工修改率、验收失败率、平均成本 | **判断这版包好不好**（`03` §5 的判据数据来源） |

**三条硬规则**：

1. **客户视角里绝不出现 token 单价与金额明细**（ADR-6 / `02`）——只给**相对指标**（"今天比平时多用 30%"），**不给"花了 8.7 元"**
2. **观测数据要能归因四层**（`客户→工作区→数字员工→运行`，`26` §1.2），否则排查时找不到是谁
3. **交付团队视角是跨客户的** → 必须**脱敏 + 聚合**，不能看到任一客户的业务内容（同 `26` §3.2）

> **为什么这条重要**：客户问"今天怎么变慢了"时，**你不能只回答"我们这边没问题"**。
> 没有这个视角，第一反应只能靠猜——而模型行为的变化（`30` §5 的重试/降级）恰恰是最常见的原因。

## 9. 验收标准

| # | 标准 |
|---|---|
| M1 | 所有 LLM 调用**都经网关**（绕过的调用在审计里查得到） |
| M2 | **agent 永远拿不到 Key**（上下文、日志、审计里都没有） |
| M3 | 同一岗位的两次调用，**可缓存前缀逐字节一致**；不一致会告警 |
| M4 | 模型故障时**自动退避重试**（1s→2s→4s…≤30s，±20% 抖动），**且进程崩了重试不丢** |
| M5 | 一次调用能归因到 `客户→工作区→数字员工→运行` 四层 |
| M6 | 客户账单上**只有"席位 + 任务数"，没有 token 单价** |
| M7 | 任一客户**毛利低于阈值时告警** |
| M8 | 配额三层任一超限即停，并向上告警 |
| M9 | **计量是 replay-aware 的**：崩溃/恢复/重放**不重复计费**（借 harness `dsh-token-meter` 的"replay-aware"做法，Day 4 第 3 轮自审补） |
