# 44 · 装载标准：数字员工怎么进客户的系统

> **这份文档解决什么**：发起人原话——
> > "**你要定义的是，当我要给客户开发第一个岗位包的时候，它支持岗位包的生成、配置、挂到平台，然后有个东西，不管叫 API 还是 SSH 还是什么，我不懂那个，但是要有，客户要看什么指南，知道这个岗位包如何装载到它的平台，不管他的平台是 saas 还是 erp 还是什么，都有指南能够充分描述，能够装进去。如果你架构不支持，或者到时候出问题，我做成岗位包，可不知道怎么装，我也不知道怎么装，那不是白做吗**"
>
> **所以本文回答一个问题**：**"我把岗位包做出来了，然后呢？"**
>
> 前置：`36`（生命周期）· `39`（接入标准）· `14`（混合部署）· `04`（连接器）· `43`（字段规格）· `32` §7（连接器三步）
>
> ⚠️ **本文的位置**：`39` 管"**数据怎么进来**"（连外部系统取数），本文管"**数字员工怎么进去**"（装到客户的业务里）。**两件事，两个方向。**

---

## 0. 一句话

> **装载不是"装软件"，是【开通一个数字员工 + 给客户一份能自证的清单】。**

**三个"不是"**（先把误解排掉）：

| ❌ 不是 | ✅ 是 |
|---|---|
| 往客户服务器上装一个我们的大系统 | **开通一个数字员工**，让它能访问客户的系统（多数情况下我们什么都不装到客户那儿） |
| 一份 200 页的部署手册 | **一份"装载清单"**（客户照着准备 + 我们照着核对），**装载过程有自检工具** |
| 一个接口（API / SSH / 别的） | **三种服务形态**（云端 / 数据面 / API），**同一份标准，第一步分支** |

---

## 1. ⭐ 核心原则：一样的标准，不同的分支

**发起人担心的是**："客户是 SaaS、是 ERP、还是什么都行，都得有指南能装进去。"

**解法**：**标准只有一份，第一步就分流。**

```
① 判形态（只有三种，没有第四种）
      │
      ├─ 云端形态：客户什么都不装 ──────────► 走 §4 清单的「最小集」
      ├─ 数据面形态：客户内网装我们的数据面 ──► 走 §4 清单的「完整集」
      └─ 桥接形态：客户的应用调我们的接口 ──► 走 §4 清单的「集成集」
      │
      ▼
② 其余六步完全一样（准备 → 装载 → 自检 → 验收 → 交付 → 运行）
```

**判据表**（客户按事实对号入座，**不谈判**）：

| 客户的环境特征 | 形态 | 谁装什么 |
|---|---|---|
| 数据可以出内网 / 用 SaaS（如 Shopify、Amazon） | **云端** | **客户什么都不装**，只提供账号授权 |
| 数据不能出内网 / 有自研中台在客户服务器上 | **数据面** | 客户装**一个容器**（我们给的镜像 + 一条命令） |
| 客户有自己的系统要调我们的员工 | **桥接** | 客户**不改我们的东西**，只调接口 |
| 三种都有一点 | **混合** | 第一步分流后各自走 |

> **关键判断**：**"客户的数据能不能出内网"决定形态**——这一条就能定 90% 的情况（`14` 已有此判据）。

## 1.6 ⭐ 数字员工用【谁的身份】去读客户的数据（Day 8 补：这是"怎么交付"的核心）

**发起人的追问**：

> "**我们定的数字员工，怎么配置，按客户的 ERP 账号，还是按什么配置，这些都不知道呢，怎么给客户交付呢？**"
> "**就备货计划专员，这个数字员工什么都做好了，数据也写进去了，但是怎么给客户挂到他的系统里面去呢？**"

**这是"最后一公里"的核心问题，之前确实没写。答案是三层身份，每一层归不同的人。**

### 1.6.1 三层身份（看清"谁的身份、谁能撤"）

```
┌─ 第 ① 层：客户系统里的身份 ─────────── 客户自己建、自己管、自己撤
│   例：ERP 里一个叫「Agent-备货计划」的账号（或一个 API Key）
│   权限：只有该员工需要的那几个查询
│
├─ 第 ② 层：我们平台里的身份 ───────────── 我们建，客户能看见
│   「数字员工的服务身份」+ 数字员工实例
│   权限：客户策略 ∩ 实例配置 ∩ 岗位包声明 ∩ 触发者
│
└─ 第 ③ 层：一次运行用的临时票据 ────────── 平台自动签发
    分钟级、绑定单次运行、用完即废、绝不进沙箱
```

**一句话**：**客户管"门钥匙"，我们管"谁在什么时候拿它开门，开哪扇门"。**

### 1.6.2 ⭐ 关键设计：**不用客户的个人账号，要一个专用账号**

**这是必须给客户讲清楚的第一个决定**（否则客户会以为"你把我的账号拿走了"）：

| 方案 | 客户会问什么 | 判断 |
|---|---|---|
| ❌ **用客户某个员工的账号** | "那个人离职了怎么办？""他改密码了怎么办？""出事算谁的？" | **禁用** |
| ✅ **客户建一个专用账号**（例：`Agent-备货计划`） | "我要给它什么权限？""我怎么撤？" | **标准做法** |

**为什么专用账号是唯一可行解**（三条，任何一条都够）：

| # | 理由 |
|---|---|
| **1** | **客户能精确控制权限**——只给它需要的几个查询，不给全库 |
| **2** | **客户能随时吊销**——停用/退出时撤一个账号即可（`36` §7），不影响任何人 |
| **3** | **审计可追责**——客户系统里能看出"是哪个账号在什么时候查了什么"，**不会和真人混在一起** |

### 1.6.3 ⭐ 凭据怎么给（三种方式，按客户系统的能力选）

| # | 方式 | 客户要做什么 | 适用 |
|---|---|---|---|
| **A** | **客户建账号 + 我们在界面上填** | 建账号 → 在我们给的页面里填地址/账号/密码（**加密存储**） | 大部分 ERP |
| **B** | **客户生成 API Key + 填一次** | 在自己系统里生成一个**只读** Key → 填进我们页面 | SaaS（Shopify / Amazon 走 OAuth 授权） |
| **C** | **完全不给凭据**（客户握在自己手里） | 客户**在自己的内网**装我们的数据面，凭据**填在数据面里，不进我们平台** | 数据不出内网的客户 |

> **方式 C 是对"我们不碰客户凭据"最彻底的实现**：凭据**只在客户内网的那台机器上**，我们连密文都拿不到。
> **代价**：客户要装一个容器（`44` §4.3 的 D1–D7）。

### 1.6.4 ⭐ 配置链：从岗位包到"能查数"要经过六步

**每一大步都是一次"声明 + 取值"的配对**（`03` §1.3 的总原则）：

```
① 岗位包声明       "我需要【某类归属维度】【安全库存】【在途】这几个能力"
                   ——只写能力名，不写哪个系统
        ↓
② 实例配置         "用客户 ERP 的这两个查询、范围是 A 团队"
        ↓
③ 连接器绑定       "ERP 连接器 → 环境=生产 → 凭据引用=客户刚填的那个"
        ↓
④ 数据视窗         行（团队=A）× 列（成本价=派生）× 聚合（跨范围=禁）
        ↓
⑤ 服务身份         创建「数字员工的服务身份」，权限 = 四方交集
        ↓
⑥ 自检            跑一次真查询，确认"拿到的确实是裁剪过的"（§5）
```

**六步走完，客户侧只做了两件事**：**建了一个专用账号** + **填了一次凭据**。**其余都是我们在平台上配。**

### 1.6.5 ⭐ 完整例子：备货计划专员（照这个给客户讲）

**客户要做的（4 件事，约 1 小时）**

| # | 做什么 | 在哪做 |
|---|---|---|
| 1 | 在 ERP 里建一个账号，取名 `Agent-备货计划`，**只给这几项权限**：查库存、查在途、查历史入库；**不给**：查成本、改数据、导全表 | 客户 ERP |
| 2 | 在 Shopify / Amazon 后台**授权一个只读应用**（或用客户自己的 API Key） | 电商后台 |
| 3 | 把过去几期的备货计划 Excel 放到指定位置（一个共享目录 / 或直接传给我们） | 客户自己的电脑/网盘 |
| 4 | 填一次凭据 + 指定复核人、申请人名单 | **我们的页面** |

**我们要做的（平台上配置，客户看不见细节）**

| # | 做什么 |
|---|---|
| 5 | 建数字员工实例 → 绑工作区 → 引岗位包 |
| 6 | 绑连接器：ERP（生产环境）+ 渠道（Shopify） |
| 7 | 配数据视窗：能看库存/在途/销量；**成本价派生、真实成本不可见** |
| 8 | 配触发：定时（每月 1 号 / 15 号）+ 手动 |
| 9 | 配送达：界面（底座）+ 飞书/邮件推给复核人 + 申请人 |
| 10 | 跑自检 → 出报告 → 客户签收 |

**做完之后，这个员工是这样工作的**

```
每月 1 号（平台自研调度器触发）
   → 用「Agent-备货计划」这个 ERP 账号，读库存 + 在途（只读）
   → 用渠道连接器读 Shopify 销量
   → 读历史备货表（数据层，精确查询）
   → 生成备货计划表（结构化）→ 导出 Excel
   → 验收钩子自检格式 → 送复核人（飞书 + 界面）
   → 复核人改 + 确认 → 送达采购（下一岗位）或导出给采购
```

**客户要知道的三条边界**（写进指南）：

> ① **它只能读到你在第 1 步给它的那几项**——多一项都读不到（自检报告会证明）
> ② **真实成本它看不到**——它用的是"结算价"口径（`34` §2.2）
> ③ **它不会改你的数据**——产出是 Excel，要人点确认才流转（ADR-2）

### 1.6.6 人员与凭据变化怎么管（交付后一定会遇到）

| 情况 | 怎么办 |
|---|---|
| 客户的 ERP 改密码了 | 连接器报"认证失败" → 通知客户技术团队在页面上重填 → **只改凭据，不动员工**（契约不变） |
| 客户给账号加/减权限 | 自检会失败（读不到了）→ 走 `36` §6 的"停用 → 调整 → 复职" |
| 客户要换一个账号 | 同上：**改凭据引用，不动员工身份** |
| **员工退出** | 我们吊销服务身份 + 客户吊销那个 ERP 账号（**两边都要撤**，`36` §7 第 4 项） |
| 客户怀疑凭据泄露 | 客户自己改密码即可 —— **我们手上只有密文，改密码立刻失效**（方式 C 下我们连密文都没有） |

> **最后一条是给客户的安全感**：**客户永远握着"一改就断"的开关。** 这句话要写在指南里。

## 1.7 ⭐⭐ 客户的员工怎么登录、怎么进对的组织（Day 8 定：双轨身份）

**发起人的原话（这就是需求）**：

> "登录支持：**手机号+验证码**，**飞书第三方登录**，**飞书组织账号接口传回来的整套组织架构信息**，为组织内的手机号码**生成默认密码**，靠**手机号+密码登入，自动属于这个组织**，**不破坏组织架构和权限**"

**发起人已确认的三条**：① **客户就是飞书用户** ② **两条登录都开**（飞书 + 手机号密码） ③ **"默认密码"改成"邀请链接"**（同意）

### 1.7.1 双轨设计（飞书在前，本地兜底）

```
┌─ 轨道 A · 飞书（主）───────────────────────────────────────
│  客户在飞书里装我们的应用 → 授权
│    → 同步组织架构（部门 / 人 / 手机号）——【只读】
│    → 为每个手机号【预建账号】（不占席位、不能登录）
│    → 员工用【飞书一键登录】或【手机号 + 自设密码】进去
│    → 自动落到这个组织，不用手工分配
│  ⭐ 走这条时【认证是飞书做的，我们不存密码】
│
└─ 轨道 B · 本地（备选，客户不用飞书时）─────────────────────
   客户管理员生成【邀请码】→ 员工手机号 + 邀请码 → 自己设密码
   ⚠️ 走这条时我们自建密码体系 → 【合规责任由我们承担】（明知的取舍）
```

**为什么把飞书放前面**：走飞书时，**认证责任在飞书**，我们不做密码找回、不存密码、不做登录风控——**这一大块合规义务直接省掉**。

### 1.7.2 ⭐ "不破坏组织架构和权限"——我这样落实（这一条最重要）

**发起人的要求背后是一个真风险**：*同步组织架构 ≠ 接管客户的权限体系*。做错就会变成"我们成了客户的 HR 系统"。

**所以定死三条边界**：

| # | 规则 | 为什么 |
|---|---|---|
| **① 同步是【只读、单向、可随时撤销】** | 只读飞书的组织信息；**绝不回写、绝不修改客户飞书的任何设置**；关掉同步不会影响客户飞书 | 客户对我们没有"组织管理"的授权，也不该有 |
| **② 我们【不重建部门树】，只存一条归属关系** | 只记住"这个人属于这个组织的这个部门（一个字符串）"；**不在我们这边维护一套可以改的部门结构** | 客户的组织架构只有一份，在飞书里；我们这边是**快照**，不是副本 |
| **③ 权限【不自动从组织架构继承】** | 飞书里是"供应链部主管"，**不等于**在我们这里自动有审批权。**角色必须单独分配** | 这条是对 `26` §4.5 的必要收紧——**否则客户在飞书里改个部门就能提权** |

> **一句话**：**我们只从飞书"读人和手机号"，不读它的权力。**
> **组织架构同步解决的是"他怎么进来"，不解决"他能干什么"。**

### 1.7.3 预建账号的激活：用【邀请链接】而不是【默认密码】

**发起人已同意这个改法。** 两者效果一样（手机号登入、自动属于组织），但风险不同：

| | 默认密码 | **邀请链接** ⭐ |
|---|---|---|
| 怎么给到人 | 明文过 IM / 邮件 | 飞书内通知，或管理员转达一条一次性链接 |
| 员工会不会改 | **常常不改** | **必须自己设**，不存在"没改的默认密码" |
| 泄露风险 | 密码在传输途中被看到 | 链接一次性、有时效 |
| 审计 | 分不清是不是本人第一次登录 | 首次激活**留痕** |

**三条规则**：① 链接**一次性 + 有时效**（默认 7 天）② 激活才占席位、才能登录 ③ **未激活的预建账号不计费**（见 §1.7.5）

### 1.7.3-b 短信：只在"不用飞书"时启用，且优先用客户自己的通道（Day 10 补）

**发起人明确"短信也要加"。** 但做法要克制——**单人不该为"找回密码"建一整套短信基础设施**：

| 场景 | 要不要短信 |
|---|---|
| 客户用飞书（**我们的客户就是**） | **不需要**——飞书自己管登录与找回 |
| 客户不用飞书（轨道 B） | **需要**——密码找回、首次验证 |

**做成"连接器能力"，不写死在平台里**：

| 优先级 | 用谁的短信通道 | 说明 |
|---|---|---|
| **① 优先** | **客户自己的** | 客户已有短信服务（阿里云/腾讯云短信等）→ 配进来即可。**凭据归客户**，符合 `44` §1.6.3 的"凭据不入平台" |
| **② 兜底** | **平台代持的** | ⚠️ **这是全平台唯一一处我们代持第三方凭据的场景**——要单独标注、写进条款、且**只在客户没有自己的通道时启用** |

**三条纪律**：

1. **短信只用于"验证与找回"，不用于营销**
2. **平台代持通道时的费用**：计入成本，**并按 §5 对账**（不赚差价）
3. **能不用就不用**：优先推"飞书登录"或"邀请链接"——**短信是最后手段**

### 1.7.4 组织同步怎么做（细节，但都会遇到）

| 项 | 规则 |
|---|---|
| **同步什么** | 部门（名字 + 层级）、人（姓名 + 手机号 + 部门）、在职状态 |
| **同步什么节奏** | 首次全量；之后**每天增量**（客户飞书变更是异步的，不要求实时） |
| **同步什么不碰** | 不碰飞书的权限、角色、审批流、群 |
| **离职怎么处理** | 飞书标记离职 → 我们**停用账号**（同 `26` §4.5 的"人离职"动作：**撤销授权、转交待审批项**）——**不是删账号**（审计要留痕） |
| **手机号变了** | 视为"换号"：旧号停用、新号重发邀请链接；**历史记录仍挂原账号** |
| **一个人属于多个组织** | **允许**（登录后选组织，或按上次进入的组织）；不同组织里可以是不同角色 |
| **客户不用飞书了** | 同步停掉，**已有账号继续用轨道 B（手机号 + 密码）登录**——不会因为停用飞书就进不来 |

> **最后一条挺重要**：**客户换 IM 不该导致员工进不了系统。** 所以本地账号体系**永远保留**，飞书只是"更好的一条路"。

### 1.7.5 与计费的关系（`30` §7.2）

| 问题 | 答案 |
|---|---|
| 预建账号算不算席位？ | **不算**。**激活才计**（否则客户 500 人组织会被白收 500 个席位） |
| 一个人属于两个组织算几个？ | **按组织各算一次**（席位是"组织 × 人"的关系，不是"人"） |
| 离职停用后还计费吗？ | **不计**（停用即释放；但**记录保留**，用于审计） |

### 1.7.6 验收标准

| # | 标准 |
|---|---|
| O1 | **两条登录都可用**：飞书一键登录 + 手机号密码 |
| O2 | 飞书授权后**组织架构自动同步**，员工登录**自动落到正确组织**，无需手工分配 |
| O3 | 同步是**只读、单向、可随时撤销**；**不动客户飞书的任何设置** |
| O4 | **不维护可编辑的部门树**——只存归属关系快照 |
| O5 | **权限不从组织架构自动继承**——飞书里的头衔 ≠ 平台里的角色，**角色单独分配** |
| O6 | 预建账号用**一次性 + 有时效的邀请链接**激活；**不存在默认密码** |
| O7 | **未激活的预建账号不计费**；激活才算席位 |
| O8 | **离职自动停用**（撤销授权 + 转交待审批项 + 保留记录） |
| O9 | **客户停用飞书后，员工仍能用手机号密码登录** |
| O10 | 首次激活、手机号变更、离职停用**都有审计记录** |

## 2. 那个"东西"叫什么、是什么（发起人说"不懂那个"）

**它不是一个接口，是四样东西的组合。** 这是本文最重要的定义：

| # | 叫什么 | 是什么 | 给谁 |
|---|---|---|---|
| **①** | **数字员工服务地址**（Endpoint） | 一个 **HTTPS 地址 + 租户标识**。客户的系统、人、IM 都往这里发请求 | 客户技术团队 |
| **②** | **访问凭据**（Access Credential） | **两选一**：<br>· **服务号**（API Key，机器对机器）<br>· **SSO 登录**（人对人，用客户自己的身份体系） | 客户技术团队 / 业务用户 |
| **③** | **装载清单**（Onboarding Checklist） | **一份可核对的清单**：这个数字员工需要客户准备什么、我们提供什么、谁做什么。**见 §4** | 客户技术团队 |
| **④** | **自检工具**（Self-check） | **一个能自己跑的命令/页面**，跑完出一份报告："这个员工在你这儿到底通没通" | 客户技术团队 |

**为什么是这四样**：**①** 是"门牌号"，**②** 是"钥匙"，**③** 是"说明书"，**④** 是"**证明它真的装好了**"。
**缺 ④ 就是"装完了但不知道通没通"**——这正是发起人担心的"出问题我不知道怎么办"。

> ⚠️ **关于 SSH**（发起人提到的"不管叫 API 还是 SSH"）：
> **SSH 不作为装载方式**（Day 11 发起人已确认）。理由：SSH 进客户生产服务器 = **我们持有客户系统的执行权限**，这是最高风险的一类（`06` §2.3 的"真不可逆"档都要靠审批，SSH 直接绕开一切）。
> **替代方案就是下面的"一条命令"**——客户自己复制粘贴执行，**效果一样，但权力边界清楚**：客户知道"你给我的就是一个容器"，而不是"你进到我服务器里了"。
>
> ⚠️ **完全离线的情形不再支持**（Day 11 发起人确认："客户不会完全没有外网的，现在我的客户都有外网"）。
> 所以**离线升级包降为"理论上支持、不做实现"**——`D2` 只保留"能出网"这一种要求。

## 3. 客户会问的 8 个问题（指南必须能回答）

**发起人说"客户要看什么指南"**——指南不是技术手册，**是回答客户这 8 个问题的东西**：

| # | 客户会问 | 指南必须给 |
|---|---|---|
| 1 | 我要准备什么？ | **输入清单**（账号/权限/凭据/网络/人） |
| 2 | 你们给我什么？ | **交付清单**（地址/凭据/员工说明/文档） |
| 3 | 多久能好？ | **时间预期**（每步的预估） |
| 4 | 我要动我的系统吗？ | **明确回答"不用改代码"**（除非桥接形态要加一个调用） |
| 5 | 我的数据会出去吗？ | **数据流向图 + 形态说明**（数据面形态：**数据一步都不出内网**） |
| 6 | 我怎么知道装好了？ | **自检报告**（§5） |
| 7 | 出问题找谁？ | **责任边界表**（§7） |
| 8 | 怎么停 / 怎么退？ | **停用与退出**（`36` §6/§7 的客户版说明） |

> **第 4 和第 5 条最重要**——**它们是客户签字同意的前提**，也是我们和客户之间最容易起争议的两点。

## 4. ⭐ 装载清单（三张，按形态选一张）

### 4.1 通用部分（三种形态都要）

| # | 项 | 谁 | 必填 | 说明 |
|---|---|---|---|---|
| G1 | 工作区与租户信息 | 我们 | M | 归属链第一位（`26` §1.2） |
| G2 | 数字员工实例配置 | 我们 + 客户确认 | M | 按 `43` §2 的字段表 |
| G3 | 员工说明（它干什么、不管什么） | 我们 | M | 客户业务用户要看得懂的那一页 |
| G4 | 相关人名单（复核人/申请人） | 客户技术团队 | M | `43` §2 的 `contacts` |
| G5 | 送达渠道配置 | 客户技术团队 | M（可空） | `38` §4；**界面永远有**，推送可空 |
| G6 | 自检报告 | 我们 + 客户 | M | §5，**没有它不算装载完成** |

### 4.2 云端形态（客户什么都不装）

| # | 项 | 谁 | 说明 |
|---|---|---|---|
| C1 | 外部系统授权 | 客户 | 给一个**只读**账号或授权（Shopify/Amazon 走 OAuth） |
| C2 | 数据出口确认 | 客户 | 确认"这些数据可以出内网" |
| C3 | 触发入口 | 我们 | 客户的 IM 群 / 网页 / 接口 |
| C4 | 网络白名单 | 客户 | 放行我们的出口 IP（**只出站，不要求入站**） |

> **云端形态的关键卖点**：**客户侧零安装、零改动**。这是最快的形态（**Phase 0 就用这个**）。

### 4.3 数据面形态（客户内网装一个容器）

| # | 项 | 谁 | 说明 |
|---|---|---|---|
| D1 | **环境前置检查** | 客户 | 一台 Linux 主机：CPU/内存/磁盘/内核版本的**最低要求**（清单给数字） |
| D2 | **网络要求** | 客户 | ① 能访问客户自己的 ERP/中台 ② 能访问我们的控制面（**出站即可**）③ 若完全隔离 → 走离线升级包 |
| D3 | **部署命令** | 客户 | **一条命令**（我们给镜像 + compose 文件）。**客户不需要看懂** |
| D4 | **凭据注入** | 客户 | 客户自己填给自己系统的凭据；**我们不要客户的凭据**（`02`） |
| D5 | **数据面注册** | 我们 | 数据面向控制面报到，绑定租户与工作区 |
| D6 | **连通性自检** | 双方 | §5 的自检工具 |
| D7 | **升级与回滚** | 我们给包，客户执行 | 离线包里带版本与回滚说明 |

> ⚠️ **D2 的"完全隔离"要单独说**：内网完全无出口的客户，**升级靠离线包**（拷进去、跑一条命令）。**这条不写清，后面每次升级都要现场跑。**

### 4.4 桥接形态（客户调我们）

| # | 项 | 谁 | 说明 |
|---|---|---|---|
| B1 | **接口说明** | 我们 | REST + 回调；**OpenAPI 描述文件**（不靠人读文档） |
| B2 | **身份传递方式** | 双方 | 客户透传 `user_id` + 签名（**平台不做认证**，`10` §3） |
| B3 | **幂等键约定** | 我们 | 客户重试不会重复干活（`10` §1） |
| B4 | **长活回调** | 客户 | 提供一个回调地址；我们签名 + 重试 |
| B5 | **沙箱联调** | 双方 | 用测试租户跑通一次（`36` §4.2） |

## 5. ⭐ 自检工具：客户能自己证明"装好了"

**这是对"出问题我不知道怎么办"的直接回答。**

**它是什么**：一个命令（`selfcheck`）或一个页面，**跑完出一份报告**。内容是 `36` §4.2.1 那七项检查的**客户可执行版本**：

| 检查 | 客户能看到的结果 |
|---|---|
| 系统可达 | ✅ 能连上 / ❌ 连不上（附排查提示） |
| **数据权限正确** | ✅ 只能查到该查的 / ❌ **多查到了**（**这条最值钱**） |
| 交付物能产出 | ✅ 生成了一份样例 |
| 触发能生效 | ✅ 手动/定时/接口都能触发 |
| **送达能到达** | ✅ 飞书群/邮箱收到了（含反向通路：客户系统回调能到我们） |
| 成本上限生效 | ✅ 跑一次的实际消耗 vs 上限 |
| 版本与凭据 | ✅ 版本号、凭据有效期 |

**三条纪律**：

| # | 纪律 | 理由 |
|---|---|---|
| **① 报告要带环境指纹 + 时间戳** | 证明"这份报告是哪个环境、什么时候的"（`36` §4.2.1） |
| **② 不通过就**不过**装载** | **只有"数据权限正确"这一项没有例外**（`36` §4.2.6） |
| **③ 报告是交付物** | 走 `28` 的状态机；**客户签收的就是它**（不是口头说"装好了"） |

## 6. 装载七步（三种形态通用）

```
① 判形态       客户按 §1 判据表对号入座 → 拿到对应清单
② 准备         客户按清单准备（账号/网络/机器/人）；我们准备实例配置
③ 装载：按形态分支
     云端 → 我们开通，客户授权
     数据面 → 客户跑一条命令
     桥接 → 客户接接口
④ 自检         跑 selfcheck → 出报告（§5）
⑤ 验收         "数据权限正确"必须过；其余项可带"不可测"标记 + 客户签字（`36` §4.2.6）
⑥ 交付         交四样（地址/凭据/员工说明/自检报告）+ 相关人通知
⑦ 运行         进日常（含升级、监控、退出路径）
```

**每一步的产出都是文件，不是"口头确认"**——这是"可核对"的含义。

## 7. 责任边界（客户签字前必须看到）

| 项 | 我们负责 | 客户负责 |
|---|---|---|
| 数字员工的产出质量 | ✅（含验收标准 `37` §4.1） | 复核与业务判断 |
| 平台的可用性 | ✅ | 网络与出口 |
| **客户系统的账号与权限** | ❌ **不碰**（客户自己建、自己管） | ✅ |
| **客户数据的正确性** | ❌ | ✅ |
| 数据面主机的运行 | 容器的正确性 | **主机、磁盘、网络、备份**（我们给要求，客户执行） |
| **写回生产的后果** | 提供草稿 + 审批通道（ADR-2） | **点"提交"的是客户的人** |
| 定时任务的触发 | ✅（自研调度器，`16` §1.1） | 数据面主机保持在线 |

> **一句话**：**我们负责"数字员工干得对"，客户负责"他的系统和他的数据"。**
> 这张表要**放进客户指南的第一页**。

## 8. 验收标准

| # | 标准 |
|---|---|
| N1 | **三种形态的判据表存在**，客户能按事实对号入座（不谈判） |
| N2 | **四样"东西"齐备**：服务地址 / 访问凭据 / 装载清单 / 自检工具 |
| N3 | 每种形态都有**可执行的清单**（不是散文），每项有"谁做、必填与否" |
| N4 | **自检工具有客户可执行版本**，跑完出**带环境指纹与时间戳**的报告 |
| N5 | **"数据权限正确"不通过 → 不许完成装载**（唯一无例外项） |
| N6 | 报告**作为交付物**走 `28` 状态机，**客户签收的是它** |
| N7 | 客户指南**回答 §3 的 8 个问题**，且**第一页是责任边界表** |
| N8 | **数据面形态只需一条命令**；**完全隔离客户有离线升级包路径** |
| N9 | **SSH 不作为常驻装载通道**；例外情形要客户开、客户关、全程留痕 |
| N10 | **客户不需要改自己的代码**（云端/数据面形态）；桥接形态只加一次调用 |
| N11 | 装载完成后，**升级与退出路径都在指南里**（不是"以后再补"） |
| N12 | **换一个客户、换一种环境，标准不变**——只换清单的那一段分支 |
| **N13** | **每个数字员工在客户系统里有一个【专用账号】**，不用任何员工的个人账号 |
| **N14** | 凭据的三种给法（界面填 / API Key / 数据面本地）**都有文档**，且**方式 C 下平台拿不到客户凭据** |
| **N15** | 客户指南里写明：**客户握着"一改密码就断"的开关**（凭据归属客户） |
| **N16** | **停用/退出时两边都撤**——我们吊销服务身份，客户吊销那个专用账号 |
| **N17** | 客户侧要做的动作**不超过 4 件**（建账号 / 授权 / 放文件 / 填凭据），且**不需要改代码** |

## 9. 这一步顺带拍掉的决策

| # | 问题 | 我拍 |
|---|---|---|
| 1 | "装载"到底是什么？ | **开通一个数字员工 + 给客户一份能自证的清单**，不是"装一个大系统" |
| 2 | 那个"东西"叫什么？ | **四样组合**：服务地址 / 访问凭据 / 装载清单 / 自检工具。**缺自检工具等于"装完不知道通没通"** |
| 3 | 客户有 SaaS、有 ERP、有自研，怎么统一？ | **标准一份，第一步分流**（云端 / 数据面 / 桥接）。判据是"**数据能不能出内网**" |
| 4 | 要不要 SSH？ | **不作为常规通道**。例外：完全无外网的客户，用**一次性部署会话**（客户开客户关、当天作废、不留常驻） |
| 5 | 客户要改自己的系统吗？ | **云端与数据面形态：不用改代码**。桥接形态：加一次调用 |
| 6 | 怎么知道装好了？ | **自检工具 + 报告**，报告作为交付物由客户签收 |
| 7 | 哪一项不能通融？ | **"数据权限正确"**——多查到数据 = 装载失败，无例外 |
| 8 | 完全隔离的客户怎么升级？ | **离线升级包**（拷进去跑一条命令），包内含版本与回滚说明 |
| 9 | 责任怎么分？ | §7 的表，**放客户指南第一页** |
| 10 | 这三张清单谁来维护？ | 我们（**平台资产**，同 `39` 的接入标准）——**不随单个客户改** |
| **11** | **数字员工用谁的身份读客户的数据？** | **客户建一个专用账号**（给这个员工用），**绝不用员工的个人账号**。三层身份：客户系统账号（客户管）/ 平台服务身份（我们管，客户可见）/ 运行临时票据（自动签发） |
| **12** | **凭据放哪？** | 三种：① 界面填（我们加密存）② 客户给只读 API Key ③ **数据不出内网时，凭据只填在客户内网的机器上，我们连密文都拿不到** |
| **13** | **客户怎么保证安全？** | **改密码即断**——凭据归属客户，我们只是使用者。**这句话要写进指南** |
| **14** | 客户侧要动几件事？ | **4 件，约 1 小时**：建专用账号 / 授权只读应用 / 放历史文件 / 填一次凭据 |
