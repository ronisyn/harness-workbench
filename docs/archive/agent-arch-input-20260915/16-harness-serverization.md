## 0. 结论先行

**harness 已经是"引擎核心 + 服务器面"分离的 client-server，服务器化在架构上成立。** 但它现在是**单机单用户**，要变成**服务器多租户**，需要动四处——其中"多租户隔离"是你自研工作量的真正所在。

## 1. ⚠️ 可复用性核查（Day 7 重做：原表有三处误用）

> **触发原因**：独立评审的取证子代理**实读了本机 harness 源码与 README**，发现原表有三行**引用时丢掉了关键限制条件**。
> **原表的三处误用已在下表标出并给原文。**

| 能力 | harness 包 | ⚠️ 实读原文（关键限制） | 能不能复用 |
|---|---|---|---|
| 浏览器界面 | `dsh-web-app` + `dsh-web-frontend` | ⚠️ **"cannot bind all network interfaces"** —— **默认只能本机访问** | ❌ **原表写"移动端的天然基础"是错的**。它能当**界面代码的起点**，但**不能当"服务端可访问"的证据** |
| 无界面跑任务 | `dsh-headless` | ⚠️ **"One-shot task mode… the process opens no ports and leaves nothing running behind"** | ❌ **原表写"证明引擎核心与服务器面已解耦"是过度解读**。它是**一次性 CLI**，跑完什么都不留——**不构成服务器化证据** |
| 定时 | `dsh-schedule` | ⚠️ **"Session-local durable reminders"**；**"delivery requires a live root agent: closed sessions keep reminders overdue until resumed"**；**"Delivery never uses email, SMS, push, or browser notifications"**；**"repeating reminders run on a fixed interval only"** | ❌❌ **最严重的一处**。它**根本不是调度器**：① 是"会话内的提醒" ② **必须有一个活着的 root agent 才能投递** ③ **只支持固定间隔，连"每月 1 号"都不支持** ④ 不走邮件/推送 |
| 会话持久化 | `dsh-session-persistence`（**JSONL**）+ `dsh-session-query-sqlite` | 日志与索引是两件事 | ✅ 可复用 |
| 会话恢复 | `dsh-session-projection-cache` + `dsh-session-checkpoint-policy` | 持久检查点 + 语义检查点 | ✅ 可复用 |
| 后台任务 | `dsh-jobs` | "owner isolation + 轮询 / 取消 / 完成监听" | ✅ 可复用（**注意 owner 是本地用户**） |
| 服务器 | `dsh-host-webserver` + `dsh-api-remotes` | HTTP 路由 + Remote BFF | ✅ 可复用 |

### 1.1 ⭐ 结论：定时任务必须【自研】，不要再引用 `dsh-schedule`

**这一条直接影响 R12**（发起人的原话："**关了电脑，定时任务还在服务器跑吗？**"）。

**原 `16` §3 的写法是"`dsh-schedule` 是 durable 的，但有几个未验证的问题"**——
**错在前提**：它不是"有未验证问题"，而是**语义上就不是我们需要的那个东西**。**不存在"验证一下能不能用"这条路。**

**我拍**：**平台自研持久化调度器**，并把它列为 **M1 的交付项**。生产化要求六条：

| # | 要求 | 防什么 |
|---|---|---|
| **1** | **持久队列**（调度状态落库，不依赖进程存活） | 进程重启/宕机丢任务 |
| **2** | **幂等**（同一触发重复执行不产生副作用） | 重试导致重复干活/重复写 |
| **3** | **重试 + 退避**（失败分类：可重试 / 不可重试） | 瞬时故障直接丢任务 |
| **4** | **错过补偿**（宕机期间错过的触发怎么办：补跑 / 跳过 / 合并，**按岗位配置**） | 停机后任务静默消失 |
| **5** | **监控与告警**（队列积压、连续失败、长期未触发） | 任务死了没人知道 |
| **6** | **状态可见**（客户能看见"下次什么时候跑、上次跑成没跑成"） | 客户不敢依赖它 |

> **为什么"定时"是刚需而不是锦上添花**：`03` 岗位包第 6 块（触发方式）里**"定时"是一等公民**，
> 而"每月 1 号、15 号出备货计划"是**这个业务里最自然的用法**。
> **调度器不成立 = 一大类岗位没法交付**。所以它不能等到 M3。

## 2. 要改造的四处（自研工作量所在）

### 2.1 多租户隔离（最关键，最费工）

harness 的 "owner isolation" 是**本地用户**级别。要升级成我们 `01` 里定的三层：

```
客户（硬隔离）→ 工作区 → 会话
```

具体要动：存储按客户分（SQLite/对象存储/交付物目录）、凭证域分离、网络边界、权限判定加"客户"维度。**这就是 `01` / `05` 两份文档存在的原因——harness 没做这块。**

### 2.2 部署形态

- Host 部署到服务器、**常驻运行**（这是"关了电脑任务还跑"的前提）
- 数据目录按客户分、加备份
- 加监控、日志轮转、优雅重启

### 2.3 对外暴露与认证

- 域名 + TLS
- **认证升级成三层身份**（平台运营方 / 客户技术团队 / 客户业务用户）——harness 现有的 web 认证是否支持这个，**未验证**
- 限流、防刷

### 2.4 计费与计量

- harness 有 `dsh-token-meter`（内部计量），但**没有多客户账单**
- 要接：按"干的活"计价、客户看板、预充值红线（ADR-6 / `02`）

## 3. 定时任务的生产化（要验证的点，先记下）

`dsh-schedule` 是 durable 的，但生产级调度还有几个**没验证**的问题：

- 到了触发时间但 Host 正好重启 / 宕机，任务**错过**了怎么办？
- 触发失败，会不会重试？
- 任务状态可见吗（谁在什么时候跑了什么）？

**生产级调度通常需要：持久队列 + 幂等 + 重试 + 监控。** 这些 harness 有没有、到什么程度，是服务器化改造前必须先摸清的。

---

## 4. 诚实边界

- 以上判断来自**包名 + 官方描述**，**没读实现**。
- "多用户"具体到什么程度、`dsh-schedule` 的健壮性、web 认证方式——**都没验证**。这几条在动手前必须逐个确认，否则"能复用"会变成"看着能复用、实际要重写"。

## 5. 待决

1. **服务器化是不是第一批就做？**
   我倾向**是**——因为"脱离本机"是你的硬需求，而它又牵动部署、认证、多租户隔离，后做会更痛。

2. **多租户隔离从第几个客户开始硬做？**
   你现在 1 个客户（+ 你自己）。硬做多租户的成本，要等第 2、第 3 个客户来才有回报。**我倾向：骨架先按多租户设计（不后补），但隔离的"硬"程度可以随客户数升级**（先逻辑隔离，大客户升物理）。
