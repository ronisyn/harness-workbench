> - **agent 内部：引擎 vs 运行时**（思考循环 vs 工具/沙箱/上下文）→ **本文**

> 🔔 **背景**：ADR-5 已定为"**平台（Ronisyn）自研 + 三个 agent 可插拔**"（roni / DS harness / codex harness）。**多 agent 更需要干净的内部分界**，所以下面的接口分析仍然成立。

> ⚠️ **一处已被 `19` 修正**：本文 §3 说"上下文由壳组装"，`19` §3.4 进一步拆成"**组装机制归 agent、准入规则归平台**"——以 `19` 为准。

## ⚠️ 本文的"壳"字怎么读（Day 4 自审补：不要再靠读者猜）

**本文是"重定位"后的文档，正文里保留了大量历史用词"壳"。** 为了不再产生歧义，统一按下表读——
**"壳"在本文里同时包含两层东西，读的时候要按语境拆开**：

| 本文写 | 实际指 | 归谁（按 `19` §2 的正式归属） |
|---|---|---|
| 壳 · **多租户 / 账本 / 审计 / 配额 / 计费** | 平台级 | **平台** |
| 壳 · **权限判定 / 审批 / 沙箱实现 / 凭证 / 出口代理** | 平台级 | **平台** |
| 壳 · **上下文组装 / 工具调度 / 记忆存储 / 预算裁决** | agent 运行时级 | **agent**（但"准入规则""预算上限"这类**规则**归平台） |
| **引擎** | agent 的思考核心 | **agent** |

> **一句话**：**本文的"壳"= 平台 + agent 运行时，不要把整块当成"平台自研"那一坨。**
> **权威归属一律以 [`19`](./19-platform-vs-agent-boundary.md) §2 的逐项归属表为准。**

## 0. 一条判据

> **引擎负责"怎么想"，壳负责"能做什么、看到什么、被允许做什么、产出算不算数"。**

换个说法：**引擎是那个会思考的零件，壳是那个决定"思考结果能不能变成行动"的系统。**

---

## 1. 分开：谁负责什么

### 引擎负责（**可换**）

| 职责 | 说明 |
|---|---|
| 认知循环 | 想 → 做 → 看 → 再想 |
| 单轮推理 | 下一步该干什么、要不要调工具 |
| 内部上下文压缩 | 引擎自己那套"塞不下了怎么删" |
| 工具调用**请求**的生成 | 只是"请求"，不是执行 |

### 壳负责（**自研，是核心资产**）

| 职责 | 为什么必须在这儿 |
|---|---|
| **工具与连接的实现** | 引擎不该知道连接器长什么样 |
| **权限与策略执行** | 引擎是可被注入的，权限不能放在它那儿 |
| **沙箱与隔离** | 同上 |
| **上下文的组装** | 放什么进上下文，是安全决策（谁能看到什么） |
| **记忆的存储与检索** | 记忆是跨引擎的资产，不能长在引擎里 |
| **交付物的结构与状态机** | 草稿 / 复核中 / 已确认，是业务概念 |
| **审批与代执行** | 唯一的写路径（ADR-2） |
| **审计与计量** | 换引擎不能丢历史 |
| **会话与运行的编排** | 生命周期是平台的事 |
| **界面** | 品牌在这里 |

**看这张表就能明白为什么"引擎可换"是要努力的**：壳几乎承担了所有跟业务、安全、合规相关的部分，引擎只剩"思考"。

---

## 2. 接口：两边互相给什么

这是能不能真换的关键。

### 壳 → 引擎

| 给什么 | 注意 |
|---|---|
| 系统提示（**由岗位包生成**） | 引擎不负责怎么描述身份 |
| 当前上下文（**由壳决定放什么**） | ← 最重要的边界，见 §3 |
| **可用工具清单（已按权限过滤）** | 引擎看到的是**过滤后**的清单 |
| 工具调用通道（**走壳，不直连**） | 引擎没有直连外部系统的能力 |
| 剩余预算 | token / 成本 / 步数 / 时长 |
| 中断信号 | 人随时能打断 |

### 引擎 → 壳

| 返回什么 | 注意 |
|---|---|
| 工具调用**请求**（结构化） | 是请求，不是执行 |
| 文本输出 | 给人看的部分 |
| 结束原因 | 完成 / 放弃 / 超预算 / 出错 |
| 用量（token 数） | 计量用 |

> **一个关键设计**：**引擎拿到的工具清单必须是"已经按权限过滤过的"。**
> 没权限的工具**根本不出现在清单里**——不是"出现了但调用会被拒"。
> 这样即使引擎被提示词注入劫持，**它也没有可越权的目标**。这比"调用时再拦"强得多。

## 3. 三条不可让渡的边界

| # | 边界 | 为什么不能让 |
|---|---|---|
| **1** | **工具调用必须经过壳** | 引擎直连外部系统 = 权限、审计、脱敏全部失效 |
| **2** | **上下文由壳组装** | "把什么放进上下文"是安全决策（决定谁能看到什么），不是性能优化 |
| **3** | **结束与预算由壳裁决** | 引擎说"我还想继续"不算数。**烧钱的那个开关必须在壳手里** |

第 3 条尤其重要：你观察到的成本差 2–3 倍，一部分就是"谁有权说停"。如果引擎能把预算撑开，成本就没有天花板。

## 4. 换引擎的真实成本（诚实版）

**完全可换很难。** 不同引擎对上下文格式、工具协议、记忆的处理方式差别很大，指望"插拔"是不现实的。

**现实目标应该是**：

> **换引擎 = 重写一个"适配器"，不重写业务资产。**

适配器要翻译的东西：

| 翻译什么 | 举例 |
|---|---|
| 工具描述的格式 | 各家的 JSON Schema 表述不同 |
| 消息 / 历史的格式 | 角色定义、多模态结构不同 |
| 流式事件 | 什么时候吐字、什么时候报工具调用 |
| 停止原因 | "完成"和"我不想干了"各家叫法不同 |
| 用量返回 | token 计法不同（缓存怎么算） |

**只要适配器是唯一需要改的东西，ADR-5 就成立了。**

## 5. 于是"用现成还是自研"怎么选

把上面的表看一遍会发现：**壳已经把业务、安全、合规全占了，引擎只剩"思考"这一个核心。**

| | 现成引擎 | 自研引擎 |
|---|---|---|
| 思考质量、省 token 的功力 | 成熟（你实测过，差 2–3 倍） | 你现在打不过 |
| 业务、合规、差异化 | **都在壳里，跟引擎无关** | 一样 |
| 可控性 | 需要适配器 | 完全可控 |
| 你要维护什么 | 适配器 | 整个认知循环 |

**所以倾向很清楚：先用现成引擎，壳自研。**

> 🔔 **Day 2 最终结论（取代上面这句）**：**平台（Ronisyn）自研 + 三个 agent 可插拔**——**roni 继续自研，同时接入 DS harness / codex harness 并列发展**。见 [`19`](./19-platform-vs-agent-boundary.md) 与 ADR-5。**下面"只有两种情况值得自研"的判断随之失效**（自研是既定方向，不是备选项）。

**但——这是你的决定，我不替你拍。** 我只把判断依据摆出来：

**只有两种情况值得自研引擎：**
1. 现成引擎**做不到**你需要的形态（例如极长的工具链、特殊的子 agent 编排、特定的中断/恢复要求）
2. 你打算**把引擎本身当产品卖**

如果两条都不成立，自研引擎就是把力气花在了别人的赛道上——而你的差异化（懂业务、连接器、岗位包、学习闭环）一分钱都没多花。

> 这也正好回应你第二次失败的成本问题：**那个差距在"怎么喂给模型"，而"怎么喂"属于壳的职责**（上下文组装、工具清单、预算裁决）。**修好壳，成本自然下来——不需要重写引擎。**

## 6. 待决问题

1. **第一个接哪个引擎？**
   你的候选是 Codex、Claude Code、harness。选择依据我建议是：**哪家的"工具调用协议"最干净、最容易写适配器**，而不是哪家最聪明（聪明会变，协议干净能省你几个月）。

2. **适配器做到什么程度就算"可换"？**
   做到"能接两个引擎"就算，还是等到真需要换的时候再说？**我倾向：一开始就把适配器层留出来（哪怕只有一个实现），因为它决定了后面会不会变成大手术。**

3. **引擎的"内部上下文压缩"要不要接管？**
   我倾向**部分接管**：壳决定"放什么进去"，引擎决定"塞不下时删什么"。但如果引擎压缩时把关键依据删了（比如删掉了那个"为什么是这个数"的来源），审计链就断了。**这个要在适配器里解决，不能指望引擎自觉。**

4. **子 agent 编排（⑧）放在壳还是引擎？**
   这是接下来要定的。我倾向**放壳**——因为子 agent 的权限收缩、预算切分是安全决策，而 Codex/Claude 作为子 agent 被集成时，**它们必须拿到父级的权限子集**（铁律二）。
