# 18 · RW 引擎边界抽离（三件改造的第 1 件）

> 状态：决策辅助。**前提是"RW = 壳"这个待确认的判断**；本方案不替用户拍板，只把"抽边界"具体化，帮他判断"先做哪件"。
> 依据：用户提供的 RW 现状总结里的"三处硬耦合"，**没有读 RW 代码**。
> 🔔 **Day 2 定位已定**：平台 = **Ronisyn**，agent = **roni + DS harness + codex harness**，见 [`19`](./19-platform-vs-agent-boundary.md)。本文里的"四引擎"应读作"三个 agent"。
> ⚠️ **Day 4 自审补（术语）**：本文的"**壳**"是历史用词。按 `19` §1 的正式叫法，**RW = 平台 + agent 运行时**；本文的"RW 壳"主要指**平台级那部分**（HTTP/界面/计费/审计/多租户）。
> **读法**：本文的"壳 ↔ 引擎" = **平台 / agent 运行时 ↔ 引擎**；**权威归属一律以 `19` §2 的逐项归属表为准。**

## 0. 一句话

**三件改造里，"抽引擎边界"必须最先做**——因为它是另外两件的**地基**，也是"四引擎并列"的前提。地基不打，楼盖不起来。

---

## 1. 三处硬耦合 → 三个动作

用户总结里已经写清了 RW 的三处硬耦合，每个对应一个具体动作：

### 动作 1：系统提示"参数化"

**现状**：系统提示把 RW 的运行环境写死（`/srv/harness-workbench`、`/srv/rw-workspace`、MySQL、联网搜索）——换个客户环境，这些话就全错了。

**改成**：把"环境相关的部分"从系统提示里抽出来，变成**运行时注入的变量**。系统提示只保留"岗位身份 + 职责边界 + 纪律"这些**稳定**的部分。

> 这正好对应我们 `08` 的"五层上下文"：**系统层要稳定、可缓存**。环境信息写死 = 每次换个客户就得改系统提示 = 缓存也废了。

### 动作 2：拆 HTTP 层与对话编排

**现状**：HTTP 层与对话编排混在一个 2392 行的文件里（路由、上下文组装、计费落库、SSE 全搅在一起）。

**改成**：拆成两层——
- **引擎核心**（对话编排）：一个干净的可调用入口——"喂任务、拿结果、报告用量、报告结束原因"
- **HTTP 壳**：只负责"接收请求 → 调引擎核心 → 推流/落库"

> 这是 `07` 里"引擎/壳边界"在 RW 内部的落地。拆完之后，harness/Codex/Claude/自研四个引擎才能通过适配器接进同一个位置。

### 动作 3：工具"声明化"

**现状**：工具是"代码里的静态数组 + 数据库行"，不能按客户装卸；壳也只是 DB 里的 JSON 字段，不是真正的插件边界。

**改成**：每个工具变成一份**声明（manifest）**——名字、能力、权限要求、参数 schema；加一个**装载器**按声明装载。

> 这对应 `04`（连接器）+ `12`（技能/插件）里的"能力声明 + 运行时 default-deny"。工具声明化之后，岗位包才能"只给这个岗位它需要的工具"。

---

## 2. 为什么"抽边界"必须先做

| 后续工作 | 为什么依赖"抽边界" |
|---|---|
| **移植 harness 零件**（沙箱/压缩/spill） | 这些零件要插进引擎，得先有"插口"——没有边界，移植进来又和 HTTP/系统提示耦合死 |
| **补按需召回**（向量检索/分层记忆） | 记忆和上下文要变成独立组件，才能"按需"而不是"每轮全量" |
| **四引擎并列** | 这是最直接的——没有干净引擎接口，适配器根本没地方接 |

**一句话：抽边界是"打地基"，另外两件是"盖楼"，四引擎是"住人"。顺序不能反。**

---

## 3. 抽完之后是什么样

对照 `07` 的"壳 ↔ 引擎"接口，RW 抽完之后：

```
岗位包（身份/工具/技能/交付物）
   ↓ 配置
RW 壳（HTTP/界面/计费/审计/多租户——RW 已经很强，不动）
   ↓ 干净接口（喂任务/拿结果/报用量/报结束原因）
引擎（可换：harness / Codex / Claude / RW 自研核心）
   ↓ 适配器
工具执行（沙箱内 / 连接器网关）
```

**RW 已经很强的部分（多租户、账本、审计、交付、治理）一行不用动**——抽边界只动那三处硬耦合。

---

## 4. 一个诚实的提醒

"抽边界"听起来是重构，但它不是"推倒重来"——是**把三处已经"半分开"的耦合解干净**（用户总结里说 RW 的模型接入、工具、子代理、MCP 已经分出来了，只剩这三处）。

但重构有**实打实的风险**：动了 2392 行的核心文件、改了系统提示的结构，短期可能引入 bug、成本暂时回不到最优。所以"先抽边界"是对的，但要**留好回滚**（RW 有审计和归档，正好用得上）。
