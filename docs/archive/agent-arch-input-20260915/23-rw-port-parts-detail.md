# 23 · 移植零件：细节收口

> 状态：方案，技术决策由我拍。前置 `20`（移植零件总览）。
> 本文把 `20` 里剩下四块的细节定死：工具声明化、spill、工具结果修剪、压缩组件化。

---

## 1. 工具声明化（= 抽边界的第 3 个动作，一起做）

### manifest 长什么样（我拍）

```yaml
工具:
  名字: inventory_query          # 唯一标识
  描述: "按仓库查库存"            # 给模型看的一句话
  参数: {仓库, SKU}               # 参数表
  权限档: 只读                   # 只读/读写/需审批/完全（映射 roni 已有四档）
  高危: 否                       # 是否属于高危 7 个
  连接器: inventory              # 归属哪个连接器（独立工具则空）
  版本: 1.0.0
```

### 装载器

启动时读所有 manifest → 注册成工具清单 → 按 roni **已有的裁剪链**（会话档位 ∩ 壳档位 ± 强制开关）裁剪。**裁剪链不动，只是"工具的来源"从静态数组变成 manifest。**

### 迁移策略（我拍：一次性声明化，不分批）

**理由**：分一半——一半声明、一半还是静态数组——会让"装载"变成两套逻辑，更乱。而且写 manifest 是机械劳动，不是重写逻辑，一次做完更干净。

**结果**：64 个工具全部变成 manifest；加/删工具 = 加/删一份 manifest，不改核心代码。

**验收标准**：加一个工具、删一个工具，不改核心代码、不整体重启（热载或重启后自动注册）。

## 2. 大结果落盘（spill）

> **数据来源：实读 harness 源码**（`dsh-spill` / `dsh-spill-policy` / `dsh-output-retention`），非猜测。

### 先纠正一个架构误解

spill 和"修剪"（§3）**不是一回事**，它们在**两个不同时刻**：

| | **spill** | **修剪（§3）** |
|---|---|---|
| 什么时候 | **工具刚返回时** | **压缩会话时** |
| 干什么 | 太大 → 全文存盘 → 上下文只留"头尾预览 + 定位符" | 历史里的旧结果 → 掐中段，留头尾 + 插标记 |

### harness 的真实做法

| 项 | harness 实际 |
|---|---|
| **阈值单位** | **字节**（不是字符）；配置项 `maxInlineBytes`，**默认不配置 = 完全不生效**（opt-in） |
| **预览分配** | **头尾对半分**（`headBytes = ceil(budget/2)`，`tailBytes = floor(budget/2)`）——注意**与修剪的 4:1 不同** |
| **预算扣减** | budget = `maxInlineBytes` − notice 占用 − 2（保证"预览+提示"不超阈值） |
| **适用内容** | **只处理纯文本**；含非文本块的一律不动 |
| **跳过 read** | `read` 工具跳过，避免 `read → spill → read again` 死循环 |
| **失败处理** | **best-effort**：无会话、无后端、存盘失败 → 保留原内容。**绝不把成功的调用变成报错** |
| **存储作用域** | 按**会话**隔离 |
| **提示格式** | `(Omitted N bytes. Full formatted result stored at: <定位符>. <取回指引>)`——带**精确省略量** |

### 我们怎么落地（我拍）

| 项 | 决定 | 理由 |
|---|---|---|
| 阈值 | 用**字节**；**建议默认 32768 字节** | harness 默认是"不生效"，但**我们不能默认关**（成本是刚需）；32768 = 修剪阈值 8192 的 4 倍，保证"先便宜修剪、超了才存盘" |
| 预览 | **头尾对半分**（照搬 harness） | 预览是"已存盘文件的采样"，头尾同等重要 |
| 存储 | 按运行/会话隔离，随生命周期销毁 | 不持久化，避免数据留存负担 |
| 取回 | 配 `fetch_spill` 工具按范围取 | agent 需要细节时主动取 |
| 失败 | best-effort，保留原内容 | 存盘失败不能影响工具调用的成败 |

**验收标准**：给一个 10 万字节的工具结果 → 上下文里只有"头尾预览 + 定位符 + 精确省略量"；`fetch_spill` 能取回；**存盘失败时调用仍成功（不报错）**。

## 3. 工具结果修剪（tool-result-pruner）

> **数据来源：实读 harness 源码**，非猜测。**我原先编的 2000/2000 是错的。**

### harness 的真实默认值（源码里的 `DEFAULTS`）

```js
{
  thresholdChars: 8192,   // 超过这个字符数才修剪
  headChars:      4096,   // 保留开头
  tailChars:      1024    // 保留结尾
}
```

**关键：头尾比是 4:1，不是我以为的 1:1。** 头比尾重要得多（工具结果的开头通常是最有信息量的：表头、列名、结论）。

其它实现要点：
- 标记固定为 `[... tool result middle pruned ...]`
- **按 Unicode 码点切片**（不切断代理对）
- 有校验约束：`headChars + marker + tailChars ≤ thresholdChars`
- **回放安全**：追加一条 `compaction/prune` 事件，记录被替换的原节点

### 我们怎么落地（我拍）

**照搬 harness 的默认值：阈值 8192 字符、头 4096、尾 1024。**

理由：harness 注释写明这是"为 coding-agent 工具输出设计的低摩擦默认值"，而我们的业务工具输出（查数、报表、日志）在结构特征上同类——头是表头/列名，尾是汇总/异常。**这是经过实测调优的默认值，比我拍的 2000/2000 有依据。**

差异点：我们可能**按工具类型微调**（比如日志类结果尾部更重要，可以调高 tail），但**默认先照搬，不自己发明**。

**验收标准**：一个 2 万字符的结果被压成"头 4096 + 标记 + 尾 1024"；省略量明确标注；**全程没有额外的 LLM 调用**。

## 4. 压缩组件化（compaction）

> **数据来源：实读 harness 源码。我又用了 roni 的绝对值，但 harness 是比例制——而这才是更对的设计。**

### harness 的真实默认值（源码里的配置接口）

| 配置 | 默认 | 含义 |
|---|---|---|
| `thresholdRatio` | **0.8** | 压缩在**模型上下文窗口的 80%** 触发 |
| `retainRatio` | **0.16** | 保留最近上下文为**模型窗口的 16%** |
| `maxTokens` | 8192 | 摘要生成的输出上限 |
| `compactionRetries` | 1 | 压缩后仍超阈值，再试 1 次 |
| `maxOverflowRetries` | 1 | 上下文溢出后的恢复重试 |
| `auto` | true | 自动在步边界触发 |

### 关键洞察：比例制 优于 绝对值

| | roni 现状 | harness |
|---|---|---|
| 触发依据 | 6.5 万字符 / 90 条消息（**绝对值**） | **模型窗口的 80%**（比例） |

**为什么比例制更对：**
1. **换模型就错**——32K 窗口和 128K 窗口，同一个"6.5 万字符"占比完全不同
2. **跨厂商可比**——各家 token 计法不同，但"占自己窗口的比例"是统一的
3. **正好是 ADR-5"多 agent 可插拔"的前提**——三个 agent 可能配不同模型，压缩策略必须自适应

### 我们怎么落地（我拍）

**改成比例制**：阈值 = **模型窗口的 80%**，保留 = **16%**；roni 现有的绝对值（6.5 万字符 / 90 条）作为**兜底**（拿不到模型窗口信息时用）。

**验收标准**：换一个上下文窗口小得多的模型，压缩阈值**自动跟着变小**（不用改配置）。

## 5. 顺序与结果总览

**顺序修正**（按 harness 的真实结构）：spill 和修剪**不在同一时刻**——spill 是"工具刚返回"的钩子，修剪是"压缩流程里的一步"。所以顺序改为：

```
① 工具声明化（跟着抽边界一起做）
② spill（工具执行后的钩子，独立）
③ 压缩组件化（先把框架搭起来，比例制）
④ 修剪（作为压缩流程里的一步，依赖 ③ 的框架）
```

**四块做完后的总结果**：
- 工具能装卸、按岗位裁剪，三个 agent 统一登记
- **刚产生的大结果** → spill 存盘，上下文只留"头尾预览 + 定位符 + 精确省略量"（阈值 32768 字节、头尾对半）
- **历史里堆积的旧结果** → 压缩时修剪中段（阈值 8192 字符、头 4096、尾 1024）
- 压缩按"**模型窗口的 80%**"触发、保留 16%，**换模型自适应**
- **成本下降的三大件**（spill + 修剪 + 按需召回）里，这里完成了前两件；第三件"按需召回"是议题 ③
