# 细化 ③：连接器契约

> 父文档：[`architecture.md`](./architecture.md) §12 细化路线 第 ③ 项
> 状态：草案，待讨论。
> 为什么第三个做：**它是 agent 唯一能看到外部世界的窗口**。窗口有多宽、能看到什么、看到的东西新不新鲜，决定了 agent 能干什么、以及沙箱该放什么权限。

---

## 0. 一句话

**连接器 = 把"一个外部系统"变成一个 agent 能用的"能力"，并且把这个能力关进笼子里。**

"关进笼子"和"变成能力"同等重要。只做前者，agent 干不了活；只做后者，agent 会把生产库拖空。

---

## 1. 为什么必须统一门面

底下可能是三种完全不同的实现：**API / RPA / 文件导入**。

**对 agent 来说，它们必须长成一个样子。** 理由三条：

1. **换实现不用改 agent。** 某个平台哪天从 RPA 换成 API，只改连接器，agent 一行不动
2. **治理在一层收敛。** 权限、限流、脱敏、审计、重试只做一遍，不用每个 agent 各写一遍
3. **今天用 RPA 兜底，不会变成明天的技术债。** 兜底方案被隔离在一个可替换的适配层里

---

## 2. 连接器的四个面

一个连接器不是"一个接口"，它同时有四张脸：

| 面 | 给谁看 | 内容 |
|---|---|---|
| **能力面** | agent | 有哪些语义化的能力可以用、参数是什么、返回什么 |
| **实现面** | 平台自己 | 底下是 API / RPA / 文件；认证方式；重试策略 |
| **治理面** | 策略引擎 | 谁可以用、用多少、行级过滤规则、审计埋点 |
| **健康面** | 运维 + 岗位包 | 可用性、**数据新鲜度**、上游变更告警 |

> 大多数人设计连接器时只做"能力面 + 实现面"，**漏掉治理面和健康面**，然后在 agent 算错数的时候才发现问题。

### 2.1 ⭐ 每个能力必须声明三样"执行属性"（Day 3 新增）

**背景**：客户的外部系统**大部分没有测试环境**（外采 ERP SaaS、Shopify、Amazon 都只有生产）。**所以"这个能力能不能安全地试一下"必须是连接器的显式声明，不能靠猜。**

**每个写能力在接入时声明三个字段**（`32` §7 第二步，**客户技术团队签字，agent 不可改**）：

| 字段 | 取值 | 用途 |
|---|---|---|
| **可测性** | `full`（有测试环境）/ `readonly`（生产可读）/ `none` | 决定联调怎么做、首跑用什么护栏（[`06`](./06-approval-and-executor.md) §2.3.1） |
| **可逆性** | 可撤销 / 只能冲销 / 真不可逆 | 决定审批力度和事后动作（`06` §2.3.5） |
| **批量上限** | 单次最多几条 + 常态值 | **成熟度再高也不能超**；超限走单独审批（`06` §2.3.7） |

**为什么这三样必须在连接器上声明**：

> **危险等级是配置，不是模型的判断。** 靠模型自己觉得"这个操作危不危险"，是最不可靠的一环。

**连带一条**：连接器的**"环境声明"（指向测试还是生产）也因此必须显式登记、客户签字**——
判错的后果极严重（系统会把"真的写进生产"当成"测试环境的 dry-run"，**所有保护措施一起被绕过**）。
**待确认时一律按"生产 + 最严格"处理**（fail-closed，同 [`34`](./34-data-view.md) §3.4）。

## 3. 核心设计决定：给"能力"，不给"通道"

这是整个连接器设计最重要的一条：

| | ❌ 通道（透传） | ✅ 能力（语义化） |
|---|---|---|
| 长什么样 | `db.query(sql)` / `http.request(url, method, body)` | `inventory.query({ 仓库, SKU })` |
| agent 能看到 | 整张表、整个网络 | 只有它该看的那部分 |
| 行级权限 | 做不了 | 在连接器里做 |
| 审计 | 只记"执行了一条 SQL" | 记"谁在什么时候查了哪个仓" |
| 上游改了 | agent 跟着崩 | 连接器吸收掉 |

**为什么要坚持这条**：透传等于把"能不能访问"的决定权交给了模型——而模型是可以被提示词注入劫持的。**权限必须在 agent 够不着的地方执行。**

### 3.1 粒度怎么定

| 粒度 | 例子 | 判断 |
|---|---|---|
| 太粗 | `数据查询` | 等于透传，没用 |
| 太细 | 每个字段一个接口 | 能力爆炸，agent 也选不明白 |
| **合适** | **一个业务动作一个能力** | `查库存`、`查销量`、`查在途`、`查物流时效` |

**判据**：如果一个能力需要 agent 自己拼参数才能表达业务意图，那它太细；如果它能让 agent 绕开业务含义直接摸到数据，那它太粗。

### 3.2 ⭐ 对任何外部系统一视同仁（Day 6 定：接入标准是我们出的）

**这条是产品边界问题，不是技术问题，所以必须写在最前面。**

> **不管外部系统有没有接口、是不是自研、是谁开发的——对我们而言都是"把数字员工接到一个外部系统上"。**
> **接入标准和实施方案由我们出**；**对方缺什么、要不要补，是对方的事情。**

**为什么必须这样定**（三条后果，任何一条都够）：

| 如果标准可以谈 | 后果 |
|---|---|
| 每接一个客户重新设计一次 | **交付成本随客户数线性上升**，交付杠杆失效（`37` §0） |
| "接入方式"变成可谈判项 | 每次都谈判，**产品边界被客户系统现状定义** |
| 我们跟着对方的接口走 | 对方接口一改，**我们的岗位包跟着改** |

**完整标准（四档成熟度 / 缺口清单 / 渠道连接器语义契约 / 扩展机制）见 [`39-integration-standard-and-extension.md`](./39-integration-standard-and-extension.md)。**

**两条最实用的推论**（都来自 `39`）：

- ⭐ **"没有 API"不等于接不了**——**"有数据出口"（能导出文件、能开只读账号、有报表邮件）就算 B 档**，对接成本比 A 档高不了多少。**客户最常见的误解是"没 API 就接不了"**，标准里要正面纠正它
- ⭐ **渠道类（Amazon / Shopify / …）和其他系统类不一样**：渠道**靠统一语义契约收敛**（新增站点零改岗位包），系统**靠适配扩展**。**别把两类混成一套做法**

## 4. 返回值规范

连接器返回的不是"数据"，是**带出处和保质期的数据**。

每个返回值必须带：

| 字段 | 为什么要 |
|---|---|
| **数据时间戳** | agent 基于 3 天前的库存算出来的结果，是错的。没时间戳，你不知道它是错的 |
| **来源** | 哪个系统、哪张表、什么口径。出问题要能追 |
| **口径版本** | 同一个指标口径改了，历史结果就不能混着比 |
| **行数 / 是否被截断** | agent 拿到"前 100 行"当全部，是经典的静默错误 |

### 4.1 失败了要能分清是哪种失败

这块最容易被糊成一个 `error`，然后 agent 就懵了：

| 失败类型 | agent 该怎么做 |
|---|---|
| **无数据**（查询成功，就是没有） | 正常继续，把"没有"当事实 |
| **无权限** | **停下来**，不要重试、不要绕路 |
| **参数错** | 修正参数重试 |
| **系统故障 / 超时** | 可重试；多次失败要上报 |
| **数据过期** | 按岗位包声明的策略：要么拒绝用，要么降级并标注 |

> ⚠️ **"无权限"和"系统故障"绝对不能混。** 混了以后，agent 会把"你没权限看"理解成"暂时拿不到，我再试试"，然后不停重试——**这在审计上看起来就像在试探越权**。

### 4.2 数据新鲜度是一等公民

岗位包要能声明"**这个能力的数据不能超过 N 小时**"。超了就按策略处理（拒绝 / 降级 / 标注）。

**理由**：这是"结果不可信"最常见的来源，而且它**不会报错**——agent 会拿着过期数据算出一个看起来很正常的答案。**静默错误比报错危险得多。**

## 5. 四种实现形态

| 实现 | 适用 | 要注意 |
|---|---|---|
| **API** | 有稳定接口的平台（越知名的电商平台接口越完整） | 首选。要处理限流、分页、增量 |
| **RPA** | 没有 API 的小平台 | **很脆**（界面一改就坏）→ 必须有"取不到数"的告警；需要登录凭据 → 凭据存哪、跑在谁的网络上要提前定 |
| **文件导入** | 只能导 Excel 的 | 要定格式、要校验、要能识别"格式变了" |
| **MCP** | 对方已经提供了 MCP server | 见 §5.1 —— **必须包在连接器后面** |

**ERP 和自研系统的接口通常是定制开发的**，工作量在这里，不在 agent 本身。

### 5.1 ⭐ MCP 与连接器的关系（常见误区）

**很多人把 MCP 当成连接器的替代品，其实不是——它们是两个层次的东西：**

| | **MCP** | **连接器（我们的）** |
|---|---|---|
| 是什么 | 一个**通信协议标准** | 平台侧的一个**受控入口** |
| 解决什么 | **怎么连**（怎么发现工具、怎么调用、怎么传数据） | **谁能用、用多少、记什么、出事怎么办** |
| 管权限吗 | ❌ 不管 | ✅ 管 |
| 管审计吗 | ❌ 不管 | ✅ 管 |
| 管脱敏吗 | ❌ 不管 | ✅ 管 |

> **一句话类比**：**MCP 像 USB 接口标准；连接器像带保险丝和电表的插座。**
> USB 只管"插得上"；插座还要保证"**过载跳闸、谁用了多少电记表**"。

**结论：MCP 是连接器的一种"底层实现方式"**，和 API / RPA / 文件并列。

### 5.2 ⚠️ 一条必须坚持的架构原则

**MCP 必须在连接器后面。不能让数字员工直连 MCP server。**

**为什么**：MCP 本身不管权限和审计。数字员工直连，就回到 `09` 那个坑——**外部工具绕过你的权限和审计**：它调了什么、读了多少，你全不知道。

**连接器的价值恰恰是"把 MCP 关进笼子里"。**

> **顺带一个对称**：MCP 在两边都出现——
> - **进来**（本节）：我们**消费** MCP server，把它包成连接器
> - **出去**（[`10`](./10-external-interfaces.md)）：我们把数字员工**暴露成** MCP server，给别的 agent 用

> **RPA 的位置问题（容易埋雷）**：RPA 跑在客户的网络里，还是你的服务器上？
> - 跑在客户网络里 → 数据要出来
> - 跑在你的服务器上 → 要能连进客户内网
> 这两条决定了数据怎么走、以及合规上说得清说不清。**要和沙箱、网络策略一起定，不能单独决定。**

## 6. 健康与变更管理

连接器是**长期维护负担**，不是一次性开发。必须内建：

| 监控 | 为什么 |
|---|---|
| **取不到数** 告警 | 不能让 agent 静默算错 |
| **数据新鲜度** 监控 | 同上，最常见的静默错误来源 |
| **上游接口变更检测**（字段变了 / 返回空 / 报错率上升） | 电商平台和 ERP 的接口会改，改了不会通知你 |
| **调用量异常** | 可能是 agent 陷入循环，也可能是有人在拖库 |

> **一个反直觉的点**：连接器的运维工作量，很可能**长期大于 agent 本身的运维工作量**。19 个外部系统，每个都可能在某天悄悄改点什么。这个成本要在方案阶段就认下来。

---

## 7. 权限与审计

**每次调用都要记**：谁（哪次运行、哪个岗位）、用了什么能力、什么参数、返回多少行、耗时、成败。

三条原则：

1. **行级过滤在连接器里做**，不下放给 agent，也不下放给模型
2. **连接器不持有长期凭据**——它从凭证代理处按次获取，用完即弃。agent 更不可能看到凭据
3. **限流与配额挂在连接器上**，而不是指望 agent 自律

---

## 8. 与岗位包的关系

岗位包装配时**声明它允许用哪些能力**：

```yaml
connectors:
  - inventory.query        # 查库存
  - sales.query            # 查销量
  - logistics.timeliness   # 查物流时效
```

**这条声明不是文档，是运行时生成沙箱策略的依据**（default-deny：没声明的一律拒绝）。

所以两个文档是咬合的：

- **岗位包**说"这个岗位需要什么能力"
- **连接器**说"这个能力是什么、怎么实现、谁能用"
- **策略引擎**取两者的交集，生成这次运行的权限

## 9. 待决问题（需要你拍）

1. **能力清单谁定义——你还是客户？**
   你定（统一、可复用、能跨客户带）vs 客户定（贴合，但每个客户各写一套）。**我倾向你定能力清单、客户在覆盖层里裁剪**，因为能力清单是你跨客户复用的资产。

2. **连接器要不要对客户技术团队开放"自建"？**
   开放 = 客户能自己接新系统，你不必做每个连接器；不开放 = 质量可控。**我倾向分两级**：客户可以在**受控模板**里配参数（配地址、配凭据、配字段映射），但不能写连接器代码。

3. **数据新鲜度的阈值谁定？**
   你按能力类型定默认值（库存可能要求 1 小时内，销量可能 1 天），客户能改吗？我倾向默认你定、可覆盖。

4. **连接器的"能力清单"要不要做成一等公民的注册表？**
   即：所有可用能力有个总表，岗位包从这里挑，库里的"连接器包"可以复用。这会显著提升复用，但也增加了平台要维护的东西。**我倾向要做**，因为这是 ADR-4 说的那半条护城河。
