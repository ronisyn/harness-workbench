# 32 · 技能库 / 插件库（发布与安装）

> 状态：方案，技术决策由我拍。
> 前置：`12`（技能/插件/market → 现改为技能库/插件库）· `03`（岗位包）· `26`（三层身份与策略层级）
> 由来：用户场景——**平台研发新技能放进技能库，客户在设置面板上给数字员工"拔插"**

---

## 0. 一句话

**平台发布 → 客户安装到数字员工 → 随时可拔插。**

```
平台侧                              客户侧
技能库 / 插件库
  ├─ 技能A v1.2  ────发布───→   设置面板看到"可装/有新版"
  ├─ 技能B v2.0                  点安装 → 装到数字员工
  └─ 插件C v1.0                  点卸载
```

**你只维护平台侧一份**，客户侧通过面板自助装卸。

---

## 1. ⭐ 关键设计一：装到**哪一层**（粒度）

**同一个客户内部，不同数字员工需要的东西不一样**——供应链的要"备货技能"，运营的不需要。

**我拍：支持三层粒度，默认最小。**

| 装到哪 | 谁操作 | 适用 |
|---|---|---|
| **单个数字员工**（默认） | 客户业务用户 | 这个岗位特有的 |
| **工作区**（整个部门） | 客户技术团队 | 这个部门都用 |
| **客户**（全公司） | 客户技术团队 | 全公司统一 |

**层级可覆盖**：客户级装了，工作区可以关掉某个（`26` §2.3 的"只能收紧不能放宽"在技能上同样适用）。

---

## 2. ⭐ 关键设计二：客户能装**哪些**（范围限制）

**不能让客户随便装**——否则"备货计划员"能被装成"财务专员"，**岗位的职责边界就废了**（`03` §1.2 说职责边界是生成权限的依据）。

**我拍：技能自己声明"适用范围"，系统只显示"这个数字员工能装的"。**

```yaml
技能: 备货量分析
  版本: 1.2.0
  适用岗位: [备货计划员, 供应链管理者]     # ← 声明适用哪些岗位
  所属层: 平台技能库                       # 平台 / 客户私有
```

**结果**：
- 平台发布时声明适用范围
- 客户在面板上**只看到这个数字员工能装的技能**（不会看到不相关的）
- **不需要岗位包维护白名单**——技能自己声明，更简洁

---

## 3. 技能 vs 插件的装卸，**管控强度不同**

沿用 `12` 的"分开治理"：

| | 技能（声明式） | 插件（代码） |
|---|---|---|
| 风险 | 内容投毒、注入 | **RCE、越权** |
| **谁能装** | **客户业务用户** | **只有客户技术团队** |
| 需要什么 | 无 | **平台签名 + 能力声明 + 平台把关** |
| 卸载 | 随时 | 需检查依赖 |

**结果**：技能像装 App 一样简单；插件像装驱动，必须受控。

> ⚠️ **插件的运行环境是独立的第二个沙箱**（`12` §3.4）：**WASM 优先、容器兜底**，
> **与 agent 自己的 gVisor 沙箱（`05`）不是一回事，也不互相替代**。
> 理由：**"声明即边界"在 WASM 上是物理成立的**（没导入的能力它连入口都没有），容器只是策略挡着。

---

## 4. 设置面板长什么样（按三层身份分）

| 身份 | 看到什么 | 能做什么 |
|---|---|---|
| **客户业务用户** | "我这个数字员工能装的技能" | 装/卸技能（在适用范围内） |
| **客户技术团队** | + 插件、连接器配置 | 装/卸插件、配连接器、配数据范围 |
| **平台运营方** | 全部 | **发布**技能/插件的新版本、下架 |

**面板要显示的关键信息**（否则客户不敢装）：
- 这个技能**干什么**（一句话）
- **谁维护的**（平台 / 自己人）
- **版本 + 最近更新时间**
- **它要什么权限**（插件必显示）

---

## 5. 升级策略

平台发了新版本，已装的客户怎么办？

**我拍：默认"通知 + 手动升级"，但安全补丁强制。**

| 版本类型 | 策略 | 理由 |
|---|---|---|
| **patch**（修 bug） | 通知，可选自动 | 风险低 |
| **minor**（加功能） | **通知 + 手动确认** | 可能改变行为 |
| **major**（破坏性） | **通知 + 手动确认 + 列出不兼容点** | 会破坏客户已调好的东西 |
| **安全补丁** | **强制升级** | 漏洞不能等客户 |

**为什么不一刀切自动升级**：技能的输出格式一变，客户下游的数字员工可能就接不上了。

---

## 6. 拔插的安全性（三个必须处理的点）

| 问题 | 我拍的处理 |
|---|---|
| 数字员工**正在跑**，卸载了怎么办？ | **当前运行结束后才生效**，不中途拔 |
| 卸载后，用它学到的**经验**怎么办？ | **经验保留**——它已经变成这个数字员工的记忆/策略了，不该跟着技能走（归属与退出清算见 [`36`](./36-digital-employee-lifecycle.md) §7.1） |
| 别的技能**依赖**它怎么办？ | 卸载前**检查依赖**，有依赖就提示"要先卸 X" |

---

## 7. 连接器不一样：**接入 → 配置 → 授权** 三步

连接器不能像技能那样"装上就能用"——它要连外部系统、要凭据。

```
① 接入     平台/技术团队把连接器接进来（写代码、声明能力）
② 配置     客户技术团队填地址、填凭据、配数据范围
             ⭐ 并【显式声明】四样（Day 3 新增，见 `04` §2.1）：
                · 环境：指向测试还是生产          ← 判错的后果极严重，必须签字
                · 可测性：full / readonly / none
                · 可逆性：可撤销 / 只能冲销 / 真不可逆
                · 批量上限：单次最多几条
             ⚠️ 未确认时一律按"生产 + 最严格"处理
③ 授权     把这个连接器授权给哪些数字员工
```

**结果**：连接器是**三步**，技能/插件是**两步**（选 + 装）。

> ⭐ **为什么第二步要加这四样声明**：客户的系统大部分没有测试环境，**"能不能安全地试一下"必须显式登记**。
> 靠默认值或推断，会出现"以为在测试、实际写进生产"——**那是所有保护措施一起失效**的场景（`04` §2.1、`06` §2.3）。
> **agent 不可改这四样**（它是接入配置，不是运行时参数）。

## 9. 验收标准

| # | 标准 |
|---|---|
| P1 | 平台发布新技能后，**客户的设置面板能看到**（不用改代码） |
| P2 | 客户**只看到这个数字员工适用**的技能（不适用的不出现） |
| P3 | **技能**可由业务用户装；**插件**只有技术团队能装 |
| P4 | 装/卸**不需要重启**数字员工；卸载在**当前运行结束后**生效 |
| P5 | 卸载技能后，**已学到的经验还在** |
| P6 | major 版本升级会**列出不兼容点**；安全补丁**强制升级** |
| P7 | 装插件时，面板**必须显示它要什么权限** |
| P8 | 连接器是"接入→配置→授权"三步，**不能跳过配置直接授权** |

---

## 10. 这一设计带来的实际好处

**对你**：
- 只维护**一份**平台技能库 → 新技能一次发布，所有客户可用
- 客户自助装卸 → **你不用帮每个客户手动装**

**对客户**：
- 有自主权（自己能装技能）
- 但**不会越界**（只看到适用的，插件受控）

**对"第 12 个岗位的成本"**：技能库越厚，新岗位做得越快——**这正是你要的交付杠杆**。
