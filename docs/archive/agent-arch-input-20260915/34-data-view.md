# 34 · 数据视窗（Data View）

> 状态：方案，技术决策由我拍。**新增能力**（Day 3 复盘发现的最大权限缺口）。
> 前置：`01` §3.2（资源归属 ≠ 岗位归属）· `04`（连接器 · 行级过滤）· `19` §3.4（上下文准入）· `26`（治理层 · 策略引擎）· `33` §6.1（知识检索）
> 由来：客户场景——**同一家公司两条业务线，货权隔离；运营不能看到真实成本，也不能看到别的团队有多少货。**

---

## 0. 一句话

**数据视窗 = "这个数字员工在这个任务里，能看到什么数据"的唯一权威定义。**

**它解决的是"隔离"这个词被用得太粗的问题**：

| 之前的"隔离" | 实际含义 | 够不够 |
|---|---|---|
| 客户隔离 | 客户 A 看不到客户 B | ✅ 够 |
| 工作区隔离 | 工作区 A 看不到工作区 B | ⚠️ 太粗 |
| **数字员工级的数据隔离** | **同一工作区内，两个数字员工看到的数据不一样** | ❌ **之前完全没有** |
| **字段级的数据遮蔽** | **同一个字段，不同人看到不同的值** | ❌ **之前完全没有** |

**判据**：**权限的生效点在数据出口，不在提示词。**

> **agent 没有能力泄露一个它从未见过的值。**
> 所以"别告诉用户成本价"这种写法**是错的**——它把防泄露交给了最容易被绕过的对象。

## 1. 为什么需要它（三个真实场景，都不涉具体业务）

| 场景 | 之前的规则为什么挡不住 |
|---|---|
| **同一岗位、不同团队，各有各的货** | A、B 两个数字员工同岗位包、同工作区 → 按客户/工作区过滤**都放行** |
| **同一个数，对不同岗位含义不同**（成本价 vs 对外结算价） | 只会"给整列"或"整列不给"，**没有"给一个不同的值"这条路** |
| **想动别人的东西，必须先审批** | 数据隔离是"看不见"，但业务上**需要"看得见但动不了"**——那是两件事（见 `35`） |

**共同点**：它们都不是"客户之间"的问题，而是**客户内部的边界**。而客户内部怎么切边界，**是客户的自由**。

## 2. 数据视窗的三个维度 ⭐

> ⚠️ **用词纪律（Day 4 自审修正）**：本节是**三个维度**（行 / 列 / 聚合）。
> **"三档"这个词已经被 [`03`](./03-role-package.md) §4.1 的"覆盖三档"占用**（结构性 / 表述性 / 取值性）。
> 另有一处"三"是 §2.2 的**列规则三选一**（可见 / 遮蔽 / 派生）——它是**一个维度内的三种取值**，不是第四个维度。
> **三个"三"各指什么，必须分清**——写代码时最容易在这里错。

```
数据视窗 = ① 行过滤（能看哪些行）
         × ② 列规则（每个字段看到什么 → 可见 / 遮蔽 / 派生 三选一）
         × ③ 聚合规则（汇总/总数怎么给）
```

### 2.1 ① 行过滤：能看哪些行

由**一组 (维度, 取值集合)** 决定：

```
维度 = 客户自己定义的类型（货权团队 / 区域 / 品类 / 品牌 / 渠道 / 法人 / …）
取值 = 客户自己填（A 团队 / 华东 / 3C / …）
```

**⚠️ 维度类型必须由客户自定义**——见 `01` §3.2 修订和 §3.4 本节。

### 2.2 ② 列规则：每个字段看到什么（三种，不是两种）

**这是本机制里最容易被做漏的一块**。大多数人只会想到"给 / 不给"，但现实里最需要的是第三种：

| 规则 | 含义 | 例子 |
|---|---|---|
| **可见** | 原值 | 供应链岗位看到真实采购价 |
| **遮蔽** | 看不到，且**不确定性地知道"你看不到"** | 加价率对运营不可见 |
| **派生** ⭐ | **给一个"官方口径"的替代值** | 运营看到的"成本价" = **团队结算价**（= 采购价 × (1+加价率)），**真实值绝不进入 agent 上下文** |

**为什么"派生"是关键**：

- 只做"遮蔽"→ 业务做不下去（运营确实需要用一个成本口径来做备货/定价）
- 做"派生"→ **业务照常跑，机密不出门**。运营知道的"成本"**本来就是公司给他的官方口径**，这不是欺骗，是**企业对岗位的口径定义**

**派生的实现约束**：
- 派生公式**在数据出口层求值**，**不在 agent 侧**（否则 agent 得先拿到真值）
- 派生结果**不可反推**：公式里用到的参数（上文例子里的"加价率"）**必须同时对同一视窗遮蔽**
- 派生字段要**可区分**（标记为派生值）——审计和交付物上要能看出"这是个折算口径"

### 2.3 ③ 聚合规则：汇总值怎么给（最隐蔽）

**"总数"看起来无害，其实是最常见的泄露通道。**

| 给法 | 后果 |
|---|---|
| 直接给"全量总数" | 用"总数 − 自己"就能算出别人的量 |
| 给"自己范围内的总数" | ✅ 默认做法 |
| 给"跨范围的汇总"（如"盘面是否紧张"） | **必须在数据出口折算**，且**不返回可用于减法反推的精度** |

**我拍**：**默认只给"本视窗内"的聚合。** 需要跨范围的汇总视图时，走 `35` 的**跨边界可见授权**，且返回**档位化/折算后**的值，不返回精确数。

## 3. 数据视窗怎么组出来（三方叠，缺一不可）⭐

```
               岗位包声明（模板，跨客户复用）
                    声明：需要【某类归属维度】的【敏感级】
                            ∩
         数字员工实例配置（客户自己的配置）
              填：维度 = 货权团队；取值 = A 团队
                            ∩
              触发者身份（人）
              这个人本身的角色允许看到什么
                            ↓
                     数据视窗（策略引擎生成）
                            ↓
                在数据出口强制执行（连接器网关）
```

### 3.1 硬规则：只能收紧，不能放宽

| 规则 | 内容 |
|---|---|
| **交集语义** | 三方**求交**，不是求并。任何一方没给 = 没权限 |
| **单向收敛** | 下级只能更窄；要放宽必须**上级显式授予**（`26` §2.3） |
| **默认最窄** | 配置缺失时**不给**，不是"全给" |

### 3.2 岗位包禁止写死客户配置

**这是"岗位包能不能复用"的分水岭**（`03` §1.3）。

| 能写进岗位包 | 不能写进岗位包 |
|---|---|
| "我需要某类归属维度的本团队范围" | "我看 A 团队" |
| "我需要成本类字段（敏感级 L2）" | "成本价按 ×1.15 折算" |

**出现了客户特有的维度名或取值 → 这个包只能卖给这一家。**

### 3.3 维度类型是"客户可配置的类型系统"

**平台不预设维度清单**（不写死"仓/店/SKU 段"这类枚举）。

| 谁 | 做什么 |
|---|---|
| 平台 | 提供"**能新增维度类型**"的能力：定义维度名、维度取值枚举、维度与数据源的映射 |
| 客户技术团队 | 定义自己的维度（"货权团队：A 团队 / B 团队"），并把它映射到各数据源的字段上 |
| 数字员工实例 | 选取值 |

**⚠️ 连带必须定的一条：维度为空时的默认值（Day 4 自审补）**

**问题**：客户刚开户，一个维度类型建了但**取值为空** → 数字员工上岗后**查什么都返回 0 条**，看起来像"系统坏了"。

**我拍（默认值三档，由客户技术团队选一个）**：

| 默认策略 | 什么时候用 | 风险 |
|---|---|---|
| **自动建一个 `默认` 取值**（推荐） | 小客户、单团队客户 | **无风险**——它就是"全部"的显式表达 |
| **要求先填再上岗** | 大客户、多团队客户 | 上岗被卡住（但这是**有意的**：逼客户想清楚边界） |
| **兜底为"全部"** | ❌ **禁止** | **fail-open**，与 `34` §3.1"默认最窄"直接矛盾 |

> **硬规则：默认策略不许是"兜底全部"。** 空维度 = 看不见任何数据（fail-closed），**不是 = 看得见全部**。
> 这条与 §3.1"配置缺失时不给"是同一条原则，**只是换了个位置**（维度取值缺失）。

**验收判据（通用性）**：**客户新增一类维度、新增一个取值、改一次归属 → 平台零改动。**

### 3.4 ⚠️ 视窗必须覆盖"该员工能访问的全部数据源"

**这是本机制唯一可能失效的地方。**

一个数字员工往往不止碰一个数据源：主表、汇总表、明细、**调拨记录**、**在途单**、历史归档、知识库。

> **只要有一个数据源没带视窗，所有其他数据源上的隔离都白做**——从那个没设防的口子就能推出全部信息。

**我拍**：
1. 数据源**注册时**就声明它用哪些维度
2. **未声明维度的数据源，默认对该数字员工不可访问**（fail-closed，同 `06` 的默认拒绝）
3. 新增数据源时提示"**有 N 个数字员工需要重新核对视窗**"

### 3.5 ⭐ 视窗要按【环境】各配一份（Day 3 补）

**背景**：客户的连接器**大部分没有测试环境**（外采 ERP / Shopify / Amazon 只有生产），而联调又要尽量在测试环境做。
**所以同一个数据源，在不同环境里的数据范围可能不同**——预检环境是模拟/脱敏数据，客户生产环境是真实数据。

| 规则 | 内容 |
|---|---|
| **视窗按环境各配一份** | 环境是**连接器的属性**（`04` §2.1），所以视窗也按连接器的环境分别配置 |
| **两份都要有** | 不能"配了生产就不配测试"——**没有测试那份，联调就跑不了** |
| **差异必须可见** | 两份视窗指纹不同 → **在联调的双跑对比里显式列出**（`36` §4.2.3） |
| **探测逐个连接器做** | `data_view.probe` **必须每个连接器单独做**，不能合并成"整体通过"——测试通过 ≠ 生产通过 |

> ⚠️ **这条是个真陷阱**：如果只按"一个员工一份视窗"来配，那么**联调时用的是生产视窗**——
> 要么联调直接碰真实数据（有泄露与污染风险），要么联调做不了（`36` §4.2.5 ①）。

## 4. 组合推演泄露 ⭐（单字段控制一定漏，这是四个后门）

| # | 后门 | 怎么漏的 | 怎么堵 |
|---|---|---|---|
| 1 | **字段组合** | 看到"结算价 100"+"加价率 30%" → 反推真实成本 77 | **公式参数与被派生字段绑定遮蔽**（§2.2） |
| 2 | **聚合反推** | 给"全量 250" − 自己 100 → 别人 150 | **默认不给跨范围聚合**；必须给时档位化（§2.3） |
| 3 | **时序反推** | 今天自己 100、明天自己 70（卖 30），再看"全量"→ 差出别人销量 | **快照/盘点统一时点口径**；跨范围值**不带时间切片** |
| 4 | **跨实例串台** | A 查过一次全量 → 落进**工作区记忆**或**语义缓存** → B 召回时捞出来 | 记忆条目 + **缓存键带视窗指纹**（§6） |

**共同原因**：这四条都不是"某个字段没遮住"，而是**多个合法可见的值被组合出来了**。

**我拍**：**把"防推演"当成数据视窗的一部分实现，而不是靠后来打补丁。** 具体三条：
1. **敏感字段登记**：标记哪些字段是"组合后敏感的"
2. **聚合白名单**：跨范围聚合不是默认能力，要显式配
3. **与遮蔽同层**：防推演和遮蔽在**同一个出口组件**里做，不能分两处（分了就一定漏一处）

## 5. 生效点：一次取数的完整链路

```
数字员工发起取数（语义接口：sales.query / inventory.query / knowledge.search …）
      │
      ▼
① 策略引擎：由**四方交集**（触发者 ∩ 实例配置 ∩ 岗位包声明 ∩ 客户策略）
                算出【数据视窗】= 行 ∩ 列 ∩ 聚合（只能收紧）
      │
      ▼
② 连接器网关 · **入口阶段**：注入过滤条件 + 附加列规则 + 附加聚合规则
      │         （agent 的查询语句里没有权限信息，它也不需要知道）
      ▼
③ 真实数据源 / 数据层 / 知识库：执行
      │
      ▼
④ 连接器网关 · **出口阶段**：应用遮蔽与派生 + 防推演校验 → 返回
      │
      ▼
⑤ agent 拿到的是【已裁剪的结果】——它从未见过被遮蔽的值
      │
      ▼
⑥ 审计：记"谁、以什么视窗、查了什么、返回了几条"（**不抄业务数据**，`26` §3.2）
```

### 5.1 ⭐ "出口层"就是连接器网关的出口阶段（Day 7 定，解除施工阻塞）

**独立评审（施工队试读）指出**：本文 §5 的"④出口层"，`26` §2.2 说成"连接器网关"，`architecture` §6.3 把三件事全画在网关上——**四处不一致，而"出口层"在 `31` 的能力清单里根本不存在**。
**后果**：施工队"连 module 名字都定不下来"。

**我拍（定死，不再有歧义）**：

| 问 | 答 |
|---|---|
| "数据出口"是哪个组件？ | **连接器网关**。它是唯一出口（`04` §3、`architecture` §6.3） |
| "出口层"是什么？ | **网关内部的一个阶段**，不是独立组件。**不单独进能力清单** |
| 那为什么分成两步？ | 因为**入口阶段注入条件**（改查询）、**出口阶段处理结果**（改返回值）。**两段在同一个进程里，但不是同一段代码** |
| `architecture` §6.3 把三件事画在网关一个框里，对吗？ | **对，但太粗**——它应该画出"入口/出口两阶段"。**本文 §5 的图是权威** |

**为什么要强调"两阶段"而不是"一个网关"**：`34` §9（决策表）说"**防推演必须和遮蔽同层同组件**"——
**如果实现时把遮蔽放在出口、把防推演漏在别处，就一定漏一处**。**"出口阶段"这个划分就是为了让它们在同一段代码里。**

**连带修正**（Day 7）：
- `26` §2.2 的"生效点在数据出口（连接器网关）"——**保留，它是对的**（网关 = 出口）
- `architecture` §6.3 的图**加注"入口/出口两阶段"**
- `31` §1 的能力清单**不新增"出口层"**（它是网关的内部阶段，不是独立能力）

### 5.2 ⭐ 自动验证怎么读目标系统（Day 7 定，解除"永远停在预演态"的风险）

**施工队试读指出的最严重的一条**：

> `06` §2.3.6 要求"**比对目标系统实际状态**"，而 `06` §4 第 5 条纪律说受信执行器"**不读业务数据——它只写**"。
> **谁来读？没写。** 若由 agent 读回，它要过数据视窗，可能遮蔽它自己的写结果 → **验证永远失败 → 按 §2.3.7 永远降回预演态 → 该岗位永远上不了生产。**

**这是个真窟窿，我拍三条补上**：

| # | 规则 | 说明 |
|---|---|---|
| **① 新增一条独立通道：只读回执（Read Receipt）** | 它是**受信执行器的一部分**（同一信任域），**只读它刚刚写过的那条记录的状态字段**，不读任何其他业务数据 | 它回答的问题只有一个："**我写的那张单子，现在是什么状态**" |
| **② 回执不过数据视窗** | 因为回执读的是**执行器自己写的记录的元状态**（状态码/时间戳/成功标志），**不是业务数据**，所以不存在"被视窗遮蔽自己的写结果" | 这是它与 agent 读回的本质区别 |
| **③ "验证做不了"是可降级场景** | 若目标系统连"查状态"都不支持（老 ERP 常见），**不是"永远停在预演态"**，而是：**走 `06` §2.3.9 的未验证能力台账 + 客户签字确认**，然后**允许在"验证缺位"标记下继续** | 同 `36` §4.2 的"不可测 ⊘"处理方式 |

**修正 `06` §4 第 5 条纪律的措辞**（原文说"它只写"太绝对）：

> **原**：「**不读业务数据** | 它只写。防止它变成一个新的数据泄露点」
> **改为**：「**不读业务数据** | 它只写，**外加读回自己刚写的记录的元状态（只读回执）**。它绝不读任何其他业务数据，防止它变成一个新的数据泄露点」

**一句话**：**执行器读的只有"自己那张单子的状态"，不是客户的业务数据。** 这条界线划清，`06` §2.3.6 才落得下去。

**三条不可违反的设计约束**：

1. **权限不在 SQL 里，也不在提示词里**——agent 拼的查询**不含权限条件**，网关注入
2. **agent 侧不持有真实凭证**（`architecture` 铁律三），所以它**绕不过网关**
3. **禁止用提示词替代数据视窗**——"你别泄露 X"不是控制措施（`19` §3.4）

## 6. 与既有机制的接口（每一条都是必须做的补丁）

| 机制 | 冲突/风险 | 补丁 |
|---|---|---|
| **跨会话记忆**（`03` §1.1、`architecture` §5.3） | 工作区记忆是**跨岗位**的 → A 团队写的内容 B 团队能召回 | 记忆条目带**视窗指纹**，召回时按当前视窗重新裁剪；指纹不匹配的**不召回** |
| **语义缓存**（`30` §4） | 缓存命中会**跨权限复用**结果 | 缓存键**必须含视窗指纹**；且**前缀里不放视窗取值**（否则缓存全废，见 `30` §4 补充） |
| **审计**（`26` §3） | 审计要能追责 | 审计记**视窗摘要**（用了哪些维度、遮蔽了哪些字段），不记业务数据 |
| **知识检索**（`33` §6.1） | 检索也是取数 | 检索管线里插入视窗过滤，**在算相似度之前** |
| **子代理**（`22` §3、`19` §3.3） | 子代理可不可以有更宽的视窗？ | **不可**。子代理继承父级视窗，且**只能更窄**（能力单调不增） |
| **数据要求下沉计算**（`06` 受信执行器） | 有些计算**必须**用真值 | 真值计算**下沉到受信执行器**，只回结果不回真值（§7） |

---

## 7. 真值计算：如果业务真的需要真实值

**场景**：某个岗位的活**必须**用真实采购价才能算（真实毛利、真实成本分析）。

**不要让 agent 拿到真值。** 三个选项，按优先序：

| 方案 | 做法 | 适用 |
|---|---|---|
| **① 受信执行器算**（首选） | agent 请求"算这个 SKU 的真实毛利" → 执行器（有真值权限）算 → **只返回结果** | 计算结果本身就是交付物 |
| **② 派生兜底** | 给一个折算口径，业务用折算口径做决策 | 大部分经营分析 |
| **③ 授权看真值** | 走 `35` 的显式授权，**该数字员工被授权看真值** | 职责本身就是看真值（如财务/供应链） |

**① 的分界**：**agent 负责"决定要算什么"，执行器负责"算"**——这和 ADR-2"agent 不直写生产"是同一个思路：**敏感动作下沉到受信层**。

## 8. 验收标准

| # | 标准 |
|---|---|
| V1 | 同工作区、同岗位包的两个数字员工，**互相查不到对方范围内的行** |
| V2 | A 数字员工问"这个 SKU 还有多少货"，得到的是**自己范围内的数**，不是全量 |
| V3 | 运营类数字员工看到的成本字段是**派生值（官方口径）**，**真实值不出现在上下文、日志、交付物里** |
| V4 | 派生公式的参数（如加价率）**对同一视窗不可见**（反推不出来） |
| V5 | 跨范围聚合**默认不给**；必须给时**不返回可减法反推的精度** |
| V6 | A 查过的数据**不会通过工作区记忆或缓存**被 B 拿到 |
| V7 | **未声明维度的数据源默认不可访问**（fail-closed） |
| V8 | 客户**新增一类维度 / 新增一个取值 / 改一次归属 → 平台零改动**（通用性判据） |
| V9 | 岗位包里**不含任何客户特有的维度名与取值**（复用性判据） |
| V10 | 子代理**拿不到比父级更宽的视窗** |
| V11 | 需要真实值的计算**下沉到受信执行器**，agent 上下文里无真值 |
| V12 | 每一次取数的审计能回答"**以什么视窗、查了什么**"，且**不含业务数据** |

## 9. 这一步顺带拍掉的决策

| # | 问题 | 我拍 |
|---|---|---|
| 1 | 隔离该按客户、工作区还是数字员工切？ | **都切，且数字员工级是必须补上的一层**——客户内部的边界同样是边界 |
| 2 | 资源维度的种类谁来定？ | **客户技术团队自定义**（平台提供类型系统，不预设枚举） |
| 3 | 字段级只有"给/不给"两种吗？ | **三种：可见 / 遮蔽 / 派生**。派生是最需要的那一种 |
| 4 | 跨范围的总数能不能给？ | **默认不给**；要给走显式授权 + 档位化 |
| 5 | 防推演放哪一层？ | **和遮蔽同层、同组件**（放两处一定漏一处） |
| 6 | 真实值确实需要时怎么办？ | **受信执行器算，只回结果**（同 ADR-2 思路） |
| 7 | 岗位包能不能写数据范围？ | **只能声明"要什么"，不能写"是哪家"**——否则岗位包不可复用 |

## 10. 与 `35` 的分工（别做重）

| | **`34` 数据视窗** | **`35` 跨边界授权** |
|---|---|---|
| 管什么 | **看得见什么** | **能不能跨过去，以及怎么跨** |
| 默认 | 最窄 | 不可跨 |
| 关键动作 | 行/列/聚合裁剪 | 申请 → 审批 → 受信执行 |
| 一句话 | **"你看得到的东西，已经不是全部"** | **"你想动别人的东西，得有人同意"** |

**两者合起来，才是完整的"客户内部数据边界"。**
