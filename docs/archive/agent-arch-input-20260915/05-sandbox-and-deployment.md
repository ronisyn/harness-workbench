## ⚠️ 先分清：平台里有**两个**沙箱（Day 4 补）

**本文讲的是第一个。它们是两个不同的隔离边界，不能互相替代、也不能合并成一个实现。**

| | **① agent 的沙箱**（本文） | **② 插件的运行环境**（[`12`](./12-skills-and-plugins.md) §3、[`32`](./32-skill-plugin-store.md)） |
|---|---|---|
| 关的是谁 | **agent**（干活的工人） | **插件**（工人手里别人送来的工具） |
| 谁写的代码 | 我们（roni）或我们选的（DS harness / codex） | **第三方** |
| 危险程度 | 中——但它**必须能跑任意命令** | 高——**但只需要算个数** |
| 实现 | **gVisor（runsc）**，敏感客户升 microVM（ADR-3） | **WASM 优先，容器兜底** |
| 粒度 | 一次运行一个，百毫秒级启动 | 每次调用一个，微秒级启动，一个进程可装上千个 |
| 为什么不能用对方的方案 | **WASM 跑不了 agent**（它要 shell、文件系统、任意命令——WASM 都没有） | **gVisor 装插件太贵太重**（一小段计算逻辑配一整个虚拟内核） |

> **一句话**：**gVisor 关的是"干活的工人"，WASM 关的是"工人手里那把别人送来的工具"。**
> **换 agent 不动插件沙箱，换插件运行时也不动 agent 沙箱。**

## 0. 五条不变量

任何设计取舍都不能破坏这几条：

| # | 不变量 | 含义 |
|---|---|---|
| **S1** | **一个运行 = 一个沙箱 = 用完即毁** | 不复用跑过的沙箱。上一个人的残留不会泄给下一个人 |
| **S2** | **沙箱内没有长期凭据** | 凭证永远在沙箱外；沙箱里最多有分钟级的临时票据 |
| **S3** | **别的客户/工作区不是"不许看"，是"不存在"** | 不在 mount namespace 里、不在网络可达范围内 |
| **S4** | **沙箱内不能提权** | 也不能影响宿主、不能影响别的沙箱 |
| **S5** | **交付物是唯一出口** | 除了明确的交付物，其余一切随沙箱销毁 |

> **S3 的措辞很重要。** "不许看"是策略，可以被绕过；"不存在"是事实，绕不过去。设计的努力应该花在把前者变成后者上。

## 1. 沙箱规格：只声明语义，不绑定实现

ADR-3 要求"沙箱规格抽象必须与底层运行时解耦"。落地方式：

**规格（Profile）只声明语义**，由**实现层**去满足它：

```
规格（语义）                    实现（可替换）
─────────────                  ─────────────
网络：全断 / 白名单      ──►     gVisor（runsc）      ← 基线
文件：只读什么/可写什么  ──►     Kata / Firecracker   ← 敏感客户
持久化：要 / 不要        ──►     普通容器             ← 不推荐
资源：CPU/内存/时长
```

**为什么要这么分**：将来某个客户要求升到 microVM，或者某个场景要降级到轻量容器，**改的是实现层，不是每个岗位包**。

### 1.1 预定义规格（够用就好，不要一开始就做一堆）

| 规格 | 网络 | 文件 | 持久化 | 适用 |
|---|---|---|---|---|
| **纯计算** | 无出站 | 只读 + 临时目录 | 无 | 数据分析、报表生成 |
| **只读取数** | 白名单（只到连接器网关） | 只读 + 临时目录 | 无 | 计划类、分析类岗位 |
| **开发工作区** | 白名单（包仓库 / 代码托管） | 项目副本可写 | 会话内 | 代码类岗位 |
| **集成验证** | 白名单（测试环境） | 项目副本可写 | 会话内 | 部署验证类 |
| **特权** | — | — | — | **原则上不开放给 agent**，仅人在环 |

**关键**：规格是**少数几个固定的**，不是给每个岗位现配一个。岗位包引用规格名，不自己拼参数——否则每个岗位都会配出一个"刚好够用"的宽松环境，安全基线就散了。

### 1.2 ⭐ 规格还必须有"运行时"这一维（Day 6 补：之前漏了）

**上面那张表只声明了四样：网络 / 文件 / 持久化 / 资源。少了最关键的一样——沙箱里能用什么语言跑。**

**为什么这是缺口**：规格是岗位包引用的（`03` 第 7 块）。**规格里没有运行时维度，"这个岗位能不能写代码"就没法声明**——只能给个大而全的镜像，那就回到了我们一直避免的"每个岗位配一个刚好够用的宽松环境"。

**顺带影响成本**：镜像越大，冷启动越慢、拉取越贵（§9 认了这是结构性成本）。**"什么岗位配什么运行时"直接决定这块花多少钱。**

**补上这一维**：

| 运行时档 | 里面有什么 | 给谁 |
|---|---|---|
| **R0 · 无代码执行** | 只有 shell 基础命令 + 文件读写 | **只查数出报告的岗位**（大部分岗位） |
| **R1 · 数据脚本** | + **Python**（数据处理栈） | 数据分析、报表、备货计算类 |
| **R2 · 全栈脚本** | + **Python + Node/TS** | 需要跑工具链、调 API、做转换的岗位 |
| **R3 · 开发环境** | + 包管理器 + 构建工具链 | **代码类岗位**（`27` §6 里我们自己的项目，不是客户岗位） |

**三条使用纪律**：

1. **岗位包声明运行时档位，平台决定档位里装什么**——同"沙箱规格只声明语义、不绑定实现"（§1）的思路
2. **默认 R0**——大部分岗位不需要跑代码，**别默认给 Python**
3. **运行时档位与 `39` 的接入无关**：客户的外部系统是什么档，**不影响我们需要什么运行时**（别把两件事绑在一起）

> ⚠️ **R3 要特别说明**：它是给**我们自己开发平台/连接器**用的（`27` §6），**不是给客户数字员工的**。
> **客户数字员工原则上不超过 R2**——R3 意味着沙箱里挂着包仓库凭据，那是 `27` §6.5 明确要隔离的东西。

#### ⭐ 修正（Day 7）：发起人指定的第二个岗位包是"软件工程师"，所以"开发工作区"规格要重新评估

**原状态**：`11` Tier 2 #10 拍"**开发工作区规格第一批不做**"，理由是"先把只读取数跑稳"。

**发起人 Day 7 明确**：**第一个岗位包定两个——备货计划专员 + 软件工程师**（`40` R23）。

**所以这条要改**：

| 项 | 原 | 改 |
|---|---|---|
| "开发工作区"规格（`05` §1.1 第 3 行：白名单 + 项目副本可写 + 会话内） | 第一批不做 | **要做**——否则软件工程师岗位**无处运行** |
| `R3` 运行时档（包管理器 + 构建工具链） | 客户岗位不超过 R2 | ⚠️ **软件工程师岗位需要 `R3`**——**这是 `27` §6.5 那条隔离规则的唯一例外**，必须补护栏（见下） |

**`R3` 给客户岗位时必须补的三条护栏**（缺一不可）：

| # | 护栏 | 理由 |
|---|---|---|
| **1** | **只能挂客户自己的代码仓库** | 平台自己的仓库凭据**永不进沙箱**（`27` §6.5）——这是"两个世界互不碰"的底线 |
| **2** | **仓库凭据是"一次性只读克隆"** | 拉完即失效，**不在沙箱里留常驻凭据**（`01` S2"凭证永不进沙箱"的延伸：进的是分钟级临时票据） |
| **3** | **出口白名单只含客户自己的仓库域名** | 防止它把代码推到别处 |

**同时保留一条**：**`R3` 不做成"什么都装"的通用开发机**。它是**一组固定的镜像档**，不是"给个 apt 权限让它自己装"。**否则回到"每个岗位配一个刚好够用的宽松环境"**（§1 的原始禁令）。

> **一句话**：**软件工程师岗位要 `R3`，但 `R3` 是"客户自己的仓库 + 一次性凭据 + 窄出口"，不是"通用开发环境"。**

**与 `03` 第 7 块的衔接**：

```yaml
运行环境:
  规格: 只读取数            # 网络/文件/持久化/资源
  运行时: R1                # ⭐ 新增：能用什么语言
```

## 2. 能力调用怎么走（"凭证永不进沙箱"的落地）

这是整个沙箱设计里最需要说清楚的一环。

**agent 在沙箱里，连接器在沙箱外。agent 怎么用连接器？**

```
┌─────────────────── 沙箱内 ───────────────────┐
│  agent                                        │
│    │ 调用 inventory.query({仓库, SKU})         │
│    ▼                                          │
│  能力客户端（agent 运行时的一部分，固定实现）      │
│    │ 带上分钟级临时票据                         │
└────┼──────────────────────────────────────────┘
     │  ← 沙箱边界（唯一的出口）
     ▼
┌─────────────────── 沙箱外 ───────────────────┐
│  连接器网关                                    │
│    · 校验票据（签名/有效期/绑定本次运行/在权限内）│
│    · 从凭证代理处取真实凭据（agent 永不可见）     │
│    · 调用真实系统                               │
│    · 行级过滤 + 脱敏                            │
│    · 审计埋点                                   │
└───────────────────────────────────────────────┘
```

**三条要点：**

1. **沙箱内没有连接器凭证，连连接地址都不完整**——它只知道网关在哪
2. **临时票据绑定"本次运行"**，不是绑定数字员工。否则同一实例的两个并发会话可以互相冒用
3. **所有出口必须走代理**——哪怕将来加了一条白名单，也仍然过网关，这样才能保持审计链完整

## 3. 文件系统：三块，边界清楚

| 块 | 内容 | 生命周期 |
|---|---|---|
| **只读层** | 这次运行允许看到的物料（数据快照、对照表、模板） | 随沙箱销毁 |
| **可写层** | agent 干活的地方（overlay 上层 / 临时目录） | 随沙箱销毁 |
| **交付物区** | 产出物落在这里 | **存活，是唯一能出沙箱的东西** |

**"只读层"里放什么，由这次运行的权限决定**——这是 S3（"不存在"）的落地：不该看的工作区，它的卷**根本不会被挂载**。

> ⚠️ **给 agent 一个"能写出沙箱"的通用文件写入能力，等于把沙箱废掉。** 写能力只对交付物区开放，且交付物必须符合岗位包声明的结构（否则就是夹带）。

---

## 4. 网络：默认全断

- **默认拒绝所有出站**
- 白名单**由岗位包的连接器声明生成**（default-deny：没声明的一律拒绝）
- 所有出站**经过代理**（可审计、可限流、可做外泄检测）
- **禁止直连**任何真实业务系统——只能到连接器网关

**为什么必须默认全断**：agent 是可被提示词注入劫持的。只要给它一条能出去的通道，"把数据发到某个地址"就变成一个可执行的动作。**默认全断是把"能不能外泄"从模型的决定变成配置的决定。**

## 5. 生命周期

```
预热池 ──► 创建（挂载+注入票据）──► 运行 ──► 产出交付物 ──► 销毁
   ▲                                                      │
   └────────────── 回收，绝不复用 ─────────────────────────┘
```

- **可以复用的是"空壳"**：预先拉起的、什么都没跑过的沙箱模板。目的是缩短启动时间，**不是省钱到复用跑过的沙箱**
- **跑过的沙箱一律销毁**，哪怕它看起来很干净（S1）
- **销毁要确定**：进程、临时目录、内存中的票据、网络连接，全部清掉
- 异常终止（超时、崩溃、被杀）也要走销毁流程，不能留在池子里

## 6. 资源与预算

每次运行都要有硬上限，超限优雅中止并**保留已产出的部分结果**：

| 维度 | 为什么要 |
|---|---|
| CPU / 内存 | 防止一个运行拖垮节点上其他客户 |
| 墙钟时长 | 防止无限循环 |
| **成本上限** | agent 可能"努力过头"，烧钱没有天花板 |
| 磁盘写入量 | 防止写满节点 |
| 进程 / 线程数 | 防止 fork 炸弹 |
| 出站流量 | 防止通过小数据量反复外发绕过检测 |

> **"优雅中止并保留部分结果"很重要**：直接杀掉会让人白等一场；留下已完成的部分，人还能接着用。

## 7. 逃逸防护清单

| 措施 | 防什么 |
|---|---|
| 非 root 运行 + 禁止提权 | 权限提升 |
| 只读根文件系统 | 篡改运行时 |
| seccomp 白名单系统调用 | 利用内核漏洞 |
| 无宿主设备、无宿主 socket | 逃逸到宿主 |
| gVisor / microVM 的内核隔离 | 内核共享带来的逃逸面 |
| 每次运行独立命名空间 | 沙箱之间互相看见 |

**注意**：这些是**同一层的多重措施**，不是纵深防御的全部。真正的纵深来自"沙箱 + 网络 + 权限 + 检测"这四类是**不同技术栈**的机制（见 [`01-identity-and-isolation.md`](./01-identity-and-isolation.md) §5 的四道闸）。

## 8. 部署拓扑

```
┌─────────────────────────────────────────────┐
│ 控制面（无状态、多活、不接触业务数据）          │
│ 身份 / 岗位包 / 策略 / 计费 / 审计 / 连接器管理 │
└────────────────┬────────────────────────────┘
                 │ 下发策略、收集事件
┌────────────────▼────────────────────────────┐
│ 数据面（按客户分片）                          │
│  ┌──────────┬───────────┬────────────────┐  │
│  │ 沙箱池    │ 连接器网关 │ 凭证代理        │  │
│  │ (节点分池)│ (无状态)   │ (不接触数据)    │  │
│  └──────────┴───────────┴────────────────┘  │
└─────────────────────────────────────────────┘
```

- **节点分池**：不同客户默认不同池（尤其大客户独占）。同一池内的沙箱靠命名空间隔离
- **连接器网关无状态**，可水平扩展；**凭证代理不接触业务数据**，只发凭据
- **存储按工作区独立**：对象存储前缀独立、卷独立
- **控制面故障不该让正在跑的运行崩溃**——两者用事件流解耦

## 9. 成本：这是结构性的，要认下来

**每次运行独占资源**是隔离的代价。一个运行从拉起沙箱到跑完，内存和 CPU 基本是独占的，**跑一次可能就是几毛到几块钱**。

**必须承认：这部分成本降不到零，只能缓解。** 缓解方向：

| 手段 | 说明 |
|---|---|
| **池化预热** | 预热"空壳"缩短启动时间，不破坏 S1 |
| **规格分级** | 简单任务用轻量规格，别一律上大沙箱 |
| **闲时回收** | 长时间无活动的运行提前中止 |
| **模型分级** | 规划用强模型、抽取用便宜模型（这个是省得最多的） |

> ⚠️ **成本是靠架构省的，不是靠定价转嫁的。** 如果单位成本失控，把成本转嫁给客户只会让你更快失去客户。这一条在 [`architecture.md`](./architecture.md) §8 的计费设计里已经考虑进去（客户按"干的活"付费，内部才按成本核算）。

## 10. 待决问题

1. **沙箱规格由谁选？** 你按岗位包类型定默认（我倾向这个），还是客户能自己选？
   → **客户不该能选**，否则他们都会选最宽松的那个。规格应该由岗位包作者（你）定，客户只能选"用哪个规格的岗位"。

2. **"开发工作区"这类需要写权限的规格，第一批要不要做？**
   你的前四个优先级（供应链、运营、产品、IT）里，IT/研发是唯一需要它的。**我倾向第一批不做**——先做出只读取数这一类，把安全基线跑稳，再开写权限。

3. **沙箱内的"代码执行"能力给不给？**
   分析类岗位常常要跑一段计算。给 = 灵活但攻击面大；不给 = 很多分析做不了。
   **我倾向给，但限制在"纯计算规格"**（无网络、无持久化、临时目录可写）——这样即使被注入，也无处可去。

4. **连接器网关要不要按客户分实例？**
   共享（省成本，但一个客户的高流量会影响别人）vs 独立（隔离好，成本高）。我倾向**共享 + 按客户限流**，大客户升独立。
