# 47 · 平台自身的运营智能体（自运营）

> **由来**：发起人 Day 11 提出——**"我希望我们自己的这个平台也是个智能体自动化运营的平台"**，并给了四个场景。
>
> **它改变了什么**：原先把"运营这个平台"当成**发起人的活**（`45` §6.1 写"内部管理台第一版只有他一个人能用"）。
> **现在**：**平台自己养一组 agent 来运营自己**——推广、售前、售后、修复、架构师巡检。
>
> ⚠️ **与给客户的承诺直接相关**：`46` §3 原写"可用性尽力而为、不承诺修复时间"，
> **那是因为默认只有一个人**。**有了常驻巡检与修复 agent，"响应"才有了实体**（见 §6）。

---

## 0. 一句话

**平台对外卖"数字员工"；对内自己也用一组"数字员工"来运营自己。**

```
                    ┌── 我们自己的 agent 团队（本节）──┐
                    │  推广 · 售前 · 售后 · 修复 · 架构师  │
                    └───────────────┬─────────────────┘
                                    │  它们也是数字员工
                                    │  （同样的岗位包、同样的权限模型、同样的审计）
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
   【官网】                    【业务平台】                  【研发后台 + 服务器】
   推广 + 售前                 售后 + 修复                    架构师
```

**关键设计原则**：**它们不是"特制的内部脚本"，而是"跑在我们自己平台上的数字员工"**——
**用同一套岗位包、同一套权限、同一套审计**。
**这是最好的自证**：我们自己天天用它，它有什么毛病我们第一个知道。

## 1. 场景一 · 客户的数字员工出故障（售后 + 修复）

### 1.1 客户在业务平台上能看到什么（⭐ 要设计清楚）

**发起人问**："具体哪些原因客户可以看清楚，你来设计，包括修复、恢复等等"

**我拍：故障分四类，客户看到的"原因"和"能不能自己修"必须一一对应**——

| 类别 | 典型原因 | 客户能否自己解决 | 界面上给什么 |
|---|---|---|---|
| **A · 客户侧配置问题** | 凭据过期、账号被改密码、ERP 地址变了、数据范围调过 | ✅ **能** | 明确指路："ERP 那个账号的密码换了，请在这里重填" + **一键跳到配置页** |
| **B · 客户侧环境问题** | 数据面主机断电/磁盘满、网络不通、客户系统本身在维护 | ✅ **多半能** | "你的数据面主机磁盘用了 95%，请清理" + 操作步骤 |
| **C · 平台侧问题** | 我们的服务故障、调度卡住、模型厂商异常 | ❌ **不用他修** | "**是我们的问题，已自动上报，你不用做任何事**" + 进度可见 |
| **D · 岗位定义问题** | 提示词有歧义、验收标准过严、编排漏了一步 | ❌ **要我们改岗位包** | "**这个岗位的配置需要调整，已提交**" + 影响面（哪些任务受影响） |

> ⭐ **为什么这么分**：**客户最怕的是"报错了但不知道该找谁"**。
> **四类一分，客户立刻知道"这是我要做的"还是"这是你的事"**——**这一条本身就是产品体验**。
> **反过来，我们也少掉一堆"本可以自助解决"的沟通。**

**客户在界面上能做的三件事**：
1. **看原因**（上面四类，带原始错误摘要，不堆栈）
2. **点"要求修复"**（触发下面的链路）
3. **看修复进度与结果**（谁在处理、到哪一步、预计什么时候）

**恢复**：修好之后**不是自动恢复跑**，而是给客户三个选项——**立即重跑失败的任务 / 只恢复排程 / 先不动**（默认）

### 1.2 两个 agent：客服（诊断）与修复（执行）

**发起人的描述**：

> "业务平台有 2 个我们的 agent，一个是帮客户答疑，锁定问题，判断问题，如果问题是 agent 自己有能力解决的，就向研发后台提交问题，向另一个 agent 提交工单；另一个 agent 的职能就是修复已知问题，修复好之后反馈给客服 agent，客服 agent 告诉用户如何操作……如果客服 agent 判断这个问题只有人能解决，就会发一个工单给我"

**我把它落成三条职责边界**（这是这一节最要紧的部分）：

| | **客服 agent**（诊断） | **修复 agent**（执行） |
|---|---|---|
| **能做什么** | 答疑、定位、分类（A/B/C/D）、**给出自助步骤**、派工单 | **执行"已知配方"的修复**：重连数据源、重放失败运行、清磁盘、重启数据面、重新加载配置 |
| **不能做什么** | ❌ **不直接改任何东西**（它只诊断和建议） | ❌ **不发明新修复**——只做**已有配方**里的动作 |
| **它的"知识"** | 每个数字员工的**全部资料与示例**（来自研发后台） | **修复配方库**（每个配方：症状 → 动作 → 验证 → 回滚） |
| **越界了怎么办** | 判断"只有人能解决" → **发工单给发起人** | 遇到没有配方的 → **退回客服 agent，转人工** |

**⭐ 关键：修复 agent 的"配方"从哪来？——这是这套设计的命门**

```
研发后台（人 + 架构师 agent）造出修复配方
        ↓  进【配方库】（带版本、带验证）
修复 agent 只能执行配方库里的动作
        ↓  执行完 → 验证 → 报告
```

**为什么必须这样**：**修复是"改客户生产环境附近的东西"**（`06` 的写路径）。
**让 agent 现场发明修复动作 = 让它在客户环境里即兴发挥**——**这违反 ADR-2 的精神**。
**所以：agent 可以"选配方"，不能"发明配方"。**

### 1.3 工单去哪儿

| 工单类型 | 谁处理 | 时限 |
|---|---|---|
| **C 类（我们的问题）** | 修复 agent 自动处理 | 自动 |
| **D 类（岗位定义问题）** | **研发后台**（改岗位包 → 走质量门 → 发新版） | 按版本节奏 |
| **需要人判断的** | **发起人**（或将来的人工团队） | **24 小时内响应**（`46` §3） |
| **客户侧配置问题** | **客户自己**（客服 agent 给步骤） | 客户自行 |

## 2. 场景二 · 官网与推广、售前、售后（一条完整链路）

**发起人的描述很完整，我只补充设计上的关键点。**

```
① 推广 agent           ② 售前客服 agent          ③ 售后客服 agent
   官网 SEO/GEO 优化      介绍能力与价值             付费后一步步指引配置
   每天更新               引导注册与签约             知道每个岗位包的全部资料与示例
   接统计看流量           只管"值不值"               只管"怎么配"
        │                      │                        │
        └──── 引流 ────────────┴──── 注册 → 付费 ────────┘
```

### 2.1 ⭐ 售前与售后必须**分开两个岗位**（这是设计要点）

**发起人已经这么分了**，我说明为什么这样对：

| | 售前 agent | 售后 agent |
|---|---|---|
| 知识集 | **产品能力、价值、价格、案例** | **每个岗位包的配置步骤、所需资料、示例、常见问题** |
| 目标 | **让客户判断"值不值"** | **让客户把员工配起来** |
| 收入相关 | **能谈价、能引导签约** | **不碰价格**（已付费） |

**为什么必须分**：
1. **知识集不同**——售前知道价格但不需要知道配置细节；售后天天讲配置但**不该谈价**
2. **权限不同**——售前**不能碰客户的工作区**（还没付费）；售后**能碰**（要指引配置）
3. **被投毒的风险不同**——售前的知识是**公开的**（官网可见）；售后的知识是**客户的**（含示例数据）

> **一条硬规则**：**售后 agent 知道"配置步骤"，但看不到客户的业务数据**（`34` 数据视窗在它身上同样生效）。
> 它是"教你操作"，不是"替你操作"。

### 2.2 售后 agent 的"资料"从哪来（⭐ 与研发后台的接口）

**发起人原话**："**它知道每个数字员工需要的全部资料，包括示例。当然这些是我们在研发后台给一个岗位包开发好的**"

**所以这是一条明确的制品通道**：

```
研发后台：开发岗位包时，【同时产出】一份"配置指南"
   ├─ 这个岗位需要客户准备什么（清单）
   ├─ 每一步怎么做（带示例）
   ├─ 常见错误与怎么办
   └─ 一个"配好了长什么样"的样例
        ↓  随岗位包一起进【岗位库】
售后 agent 直接取用（只读）
```

**这条通道不新造**——它就是 `44` §4 的"装载清单"，**只是从"给人看的文档"变成"给 agent 用的知识"**。
**一份内容，两种用法**（人看指南、agent 读知识），**不写两遍**。

### 2.3 推广 agent（官网）

| 项 | 做什么 |
|---|---|
| **职责** | **SEO**（搜索引擎）+ **GEO**（生成式引擎优化）**每天更新**；接统计（百度统计等）看流量 |
| **产出** | 内容草稿 + 更新提案——⚠️ **不直接发官网**（官网是生产，走 `06` 的审批） |
| **能读** | 站点统计、搜索表现数据 |
| **不能做** | 不能改价格、不能承诺能力（那是售前和你的活） |

> ⚠️ **`GEO` 这个词要解释一下**：让内容更容易被**AI 搜索/AI 助手**引用和推荐。
> **它和 SEO 是两套逻辑**（SEO 讨好爬虫排序，GEO 讨好模型的理解与引用）——**架构上不需要新东西**，只是内容和投放策略不同。

### 2.4 官网与业务平台的关系

| | 官网 | 业务平台 |
|---|---|---|
| 谁用 | 潜在客户（**不认识我们**） | 已注册客户 |
| 入口 | 公开 | **官网右上角"申请注册"** |
| 注册后 | —— | 能看**业务模块 / 业务单元**（具体怎么设计，走原型确认） |

## 3. 场景三 · 架构师 agent（研发后台 + 服务器）

**发起人的描述**："负责不断的自我进化，每日巡检异常，优化服务器、性能等等，保障服务器稳定，包括你说的，备份、恢复等等，都由这个架构师 agent 来设计和实施"

### 3.1 ⭐ 巡检与处置必须分开（这是本节最重要的判断）

**发起人说"设计和实施"都归它**——**我建议分两级，理由是 `06` 的写路径规则**：

| 级别 | 做什么 | 要不要人批 |
|---|---|---|
| **① 巡检（只读）** | 每日体检：磁盘、内存、容器状态、队列积压、失败率、证书到期、备份是否成功 | **不用**，自动跑，出报告 |
| **② 低风险处置（白名单）** | 清日志、重启卡住的容器、拉新证书、重跑失败的备份 | **不用**，但**每次留痕 + 事后通知** |
| **③ 高风险处置（要批）** | 改配置、扩缩容、改备份策略、动网络、升级组件 | **要发起人批**（走 `06`） |
| **④ 设计（出方案）** | 备份策略、恢复演练方案、容量规划 | **出方案给人看**，批准后才实施 |

**判据一句话**：

> **"这个动作做错了，要不要人工介入才能恢复？"**
> 不要 → 白名单里可以自动做（如重启容器）。
> 要 → **必须人批**。

### 3.2 ⭐ 它顺便解决了 `46` §4 那个"我们为什么会挂"

**架构师 agent = 那三条制度性回答的技术底座**：

| 原来只能靠制度 | 现在有实体 |
|---|---|
| "有备份" | **它每天跑备份并验证备份可恢复**（不是"配了策略就算"） |
| "有恢复演练" | **它定期做恢复演练并出报告** |
| "运维手册" | **它的巡检报告就是手册的活文档** |
| "服务器稳定" | **它每日巡检 + 低风险自愈** |

> **对客户的说法变成**："我们的平台有一个常驻的架构师 agent，**每天体检、发现问题自己能修的立刻修，修不了的当天报给我们的人**。"——**这比"尽力而为"具体得多。**

### 3.3 与"自我进化"的关系

**发起人提到"不断自我进化"**——**这条要克制**：

| 可以自动 | 不可以自动 |
|---|---|
| 巡检 → 发现模式 → **提改进方案** | ⚠️ **不能自己改自己的代码或配置** |
| 优化建议进"待批池" | ⚠️ **不能自己发版** |
| 跑恢复演练、压测 | ⚠️ **不能自己动生产容量** |

**理由**：**"自我进化"如果没有边界，就是一个在有生产权限的环境里自己改自己的东西。**
**边界就是 `37` 那条**：**它只能"造制品 + 提提案"，制品要过质量门，提案要人批。**

## 4. 场景四 · 客户不付费了（冻结与数据处置）

**发起人说**："他不付费就行了，客户数据暂存在那里，我们可以约束一下，多久不用的冻结账户的数据如何处理，然后轻量级的保存这些数据即可"

**我拍一条时间线**（与 `46` §1⑤ 的"终止后 15 天"要接上，两者是不同场景，别混）：

| 阶段 | 时间 | 状态 | 数据 |
|---|---|---|---|
| **欠费** | 到期后 **7 天** | 服务**只读**（能看历史，不能派新活） | 全量保留 |
| **冻结** | 7 天 – **90 天** | 账号冻结（登录能进，只能看账单和导出） | **全量保留**，客户**可随时导出** |
| **轻量保存** | 90 天 – **1 年** | 只保留**元数据**（有哪些员工、交付物目录、账本） | ⚠️ **业务数据转为归档**：可导出，但**不保证随时可取**（要解冻流程） |
| **清理** | 1 年后 | 账号注销 | **删除并出删除确认**（`46` §1⑤） |

**三条纪律**：

| # | 规则 | 为什么 |
|---|---|---|
| **① 全程可导出** | 从欠费第一天起，**导出按钮一直在** | 客户不付费不等于**失去自己的数据**——这条是口碑 |
| **② 不删快、可恢复** | 冻结期**不做任何删除** | 客户可能只是忘了续费 |
| **③ 清理前通知** | 清理前 **30 天**发通知（邮件 + 站内） | 避免"突然没了" |

## 5. 这五个 agent 各归谁管（一张表说清）

| agent | 在哪 | 归谁 | 用的是不是同一套岗位包机制 |
|---|---|---|---|
| **推广** | 官网 | 业务平台 | ✅ 是（岗位包 + 知识集） |
| **售前客服** | 官网 | 业务平台 | ✅ 是 |
| **售后客服** | 业务平台 | 业务平台 | ✅ 是 |
| **修复** | 业务平台 | 业务平台 | ✅ 是（**+ 配方库**） |
| **架构师** | 研发后台 + 服务器 | 研发后台 | ✅ 是（**+ 白名单 + 分级审批**） |

> ⭐ **这张表的意义**：**我们自己就是第一个客户。**
> 我们不用它们的毛病，客户就会遇到；我们嫌它们笨的地方，客户也会嫌。
> **"自运营"是这套架构最好的自证，也是最便宜的验证。**

## 6. 对 `46`（对外承诺）的连带修正

| 原 | 改为 |
|---|---|
| "可用性：尽力而为，不承诺百分比" | **保留**（第一年仍不承诺数字），但**加上**："有常驻巡检与自动修复；发现平台侧问题会主动处理并通知" |
| "修复时间：不承诺" | **保留"不承诺修复时间"**，但**分级**：C 类（我们的问题）**自动处理**；需人判断的 **24 小时内响应** |
| "我们出状况怎么办" | **补第 4 条**：常驻架构师 agent 每日巡检 + 自动备份验证 + 定期恢复演练（`47` §3.2） |

## 7. 与既有文档的关系

| 文档 | 关系 |
|---|---|
| `36` | 这五个 agent **也是数字员工**，走同一套生命周期（上岗审核、契约、退出） |
| `06` | 修复动作与架构师的高风险处置**走同一套写路径与审批** |
| `44` §4 | 售后 agent 用的"配置指南"**就是装载清单**（一份内容，两种用法） |

| `34` | **售后 agent 看不到客户业务数据**——数据视窗在它身上同样生效 |
| `37` | 修复配方由研发后台产出，**进库、带版本、可回滚** |

## 8. 验收标准

| # | 标准 |
|---|---|
| G1 | 客户能看到故障的**四类归因**，且**每类都告诉他"该谁做"** |
| G2 | **客服 agent 不直接改任何东西**；**修复 agent 只执行配方库里的动作** |
| G3 | **修复配方带版本、带验证、带回滚**；无配方时**退回人工，不现场发明** |
| G4 | 售前与售后是**两个岗位**，知识集与权限**分离**；**售后看不到客户业务数据** |
| G5 | 售后用的"配置指南"**与装载清单同源**（不是两份文档） |
| G6 | 推广 agent **不直接发官网**（走审批）；不碰价格与能力承诺 |
| G7 | 架构师 agent **巡检自动、低风险自愈留痕、高风险处置要人批** |
| G8 | 架构师**不能自己改代码/配置/发版**；只能造制品与提提案 |
