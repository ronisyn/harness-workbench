### 12.8 ⭐ 为什么要单独出一份 `49`（agent 架构独立成册）

> **由来**：发起人要求——"**把只涉及到 agent 的架构单独打印给我，不要和任何平台混在一起**"。

**`49` 立了三条规矩**：

| # | 规矩 |
|---|---|
| ① | **只收"只属于 agent"的内容**。平台内容一律标注为「**接口**」——意思是"agent 只负责这里，那边归平台" |

### 12.9 ⭐ 工具策略：用围栏，不接管（推翻旧判据）

| # | 事项 | 结论 | 依据 |
|---|---|---|---|
| **196** | 外部引擎自带的工具，要不要接管？ | ⭐ **不接管，用围栏。** <br>**旧判据作废**：原文"外部引擎如果不能被接管工具，它自带的工具会绕过权限和审计"——**这个判断默认了"引擎自带工具不如我们的"，而该前提未经验证**。<br>**实证结论**：① 两家自带工具**都比自研的好**（为长任务、多轮迭代、真跑代码打磨）② **两家都提供从外部约束的机制** ③ **剥夺工具 = 拿确定的能力损失换一个已有替代方案的收益** | `50` §3 |
| **197** | 修正后的引擎选型判据是什么？ | 判据从"能不能被接管"改为"**能不能被围栏**"。选引擎时问四句：① 有没有沙箱模式 ② 沙箱拿不到时是否 **fail-closed** ③ 网络能不能**默认断** ④ **参数能不能白名单化**（封掉逃生门） | `50` §3.3 · `09` §3-b |
| **198** | 围栏必须围住哪几件事？ | **四件，缺一件等于没围**：① 写越界（引擎沙箱模式）② 危险命令（引擎执行策略 / 平台命令白名单）③ ⭐ **网络出口**（默认断网 + 白名单代理）④ ⭐ **逃生门**（参数白名单，禁止透传 `--yolo` 类开关） | `50` §5.1 |
| **199** | 逃生门怎么封？ | **在调用层用参数白名单**，不允许透传任意 flag —— **不是"约定不用"**。理由：`--dangerously-bypass-approvals-and-sandbox` 是**唯一能一次性废掉整个隔离设计的开关** | `50` §3.2.4 |

### 12.10 ⭐ 隔离：四层，不是二选一

| # | 事项 | 结论 | 依据 |
|---|---|---|---|
| **200** | gVisor 和 harness 自带沙箱是什么关系？ | ⭐ **不是竞争，是两个层级**。DS harness 自己的 README 就写明："这是**同世界隔离**：进程仍与宿主共享内核和文件系统；**需要隔离整个环境时，请使用容器、microVM 或远程执行器**"。Codex 官方同样建议"容器负责隔离、Codex 负责围栏"。<br>**四层**：① gVisor/microVM（平台侧，防逃逸与跨租户）② harness 沙箱（引擎侧，工作区围栏）③ 工具层围栏（fs 围栏 / 命令策略）④ 网络出口（平台侧） | `50` §5 |
| **201** | 四层里哪层最容易被漏？ | ⭐ **网络出口**。**gVisor 挡不住 `curl`**——没有这层，前面三层全白做 | `50` §5.1 |
| **202** | 围栏方案下，数据视窗怎么生效？ | ⭐ **出口在"喂进沙箱的数据"上**，不是"agent 看不看得到"。平台把**裁剪后的数据物化**成沙箱内的工作文件，agent 的原生工具只看得见这个文件——**它根本没有原始数据可读**。<br>**这把数据视窗从"君子协定"变成"物理隔离"**。推论：装载时数据面多一条职责——**把裁剪后的数据集物化进沙箱**，而不是让 agent 拿凭据去查原始库 | `50` §3.4 |
