# 细化 ⑨：技能库、插件库与连接器

> 父文档：[`architecture.md`](./architecture.md) §12 细化路线 第 ⑨ 项（同时覆盖目标①里的"技能/插件体系"）
> **命名已统一（Day 2）：不叫"市场"——叫「技能库 / 插件库 / 连接器」。** 发布与安装的完整流程见 [`32`](./32-skill-plugin-store.md)。
> 为什么重要：它们是**岗位包的能力来源**，也是"平台表达力"的另一半。ADR-4 说护城河 = 岗位包的表达力 × 连接器生态的广度——技能和插件就是往这个生态里放东西的方式。

---

## 0. 先把三样东西分清

> ⭐ **Day 3 补充：还有第四样——【岗位库】。**
> 技能库（怎么干一件事）、插件库（会算什么）、连接器（连什么）、**岗位库（一个完整岗位的定义）**。
> 四者都是平台方的可复用资产，**其中岗位库商业价值最高**（客户买的就是岗位）。
> "岗位包怎么造出来、怎么复用、怎么不腐烂"见 [`37-role-package-authoring.md`](./37-role-package-authoring.md)；**发布与版本治理沿用本文与 `32` 的同一套，不另造**。

这三样最容易被混成一团，混了之后治理手段就会用错：

| | 是什么 | 有没有代码 | 风险 |
|---|---|---|---|
| **连接器** | 接入一个外部系统（ERP、Shopify、Amazon） | 有（平台侧、受控） | 越权读写、数据外泄 |
| **插件 / 工具** | 一段**加工逻辑**（特殊计算、格式转换、自定义算法） | **有** | RCE、越权、供应链投毒 |
| **技能** | "**怎么干一件事**"的声明：流程、提示词、参考 | **没有** | 内容投毒、注入 |

**判据：**

> **连接器连外部，插件算东西，技能说怎么干。**
> **技能里出现的任何"逻辑"，要么是提示词，要么是参数——不能有可执行代码。有代码的就不是技能，是插件。**

---

## 1. 为什么技能和插件必须分开治理

因为它们的**风险模型完全不同**，所以治理手段也不同：

| | 技能 | 插件 |
|---|---|---|
| 出问题的方式 | 被人写进去一段坏内容，诱导 agent 干坏事 | 代码本身干了坏事 |
| 治理手段 | **内容审核 + 来源可信** | **签名 + 沙箱 + 能力声明 + 运行时强制** |
| 审核成本 | 低（读一遍就知道） | 高（要看代码、要测） |
| 迭代速度 | 快（改文字而已） | 慢（要重新签名发版） |

**这个区分决定了岗位包里哪些东西客户可以改、哪些必须受控**（[`03`](./03-role-package.md) §4.1 的三档判据）：

- **技能**在"表述性/取值性"那一档——客户业务用户自己就能改
- **插件**在"受控改"那一档——客户技术团队加，你把关
- **职责边界、交付物 schema、验收标准、权限声明**在"结构性"那一档——**客户改不了**（`03` §4.1）

---

## 2. 技能长什么样

一个技能包里应该有五样：

| 内容 | 说明 |
|---|---|
| **什么时候用它** | 触发条件。**这一条最常被漏**，导致 agent 不知道该用 |
| **步骤** | 干这件事的流程 |
| **提示词片段** | 具体的说法、口径、注意事项 |
| **参考资料** | 挂在技能上的小知识（不是整个知识库） |
| **输入输出约定** | 它吃什么、吐什么 |

外加：版本号、作者、来源。

> **"什么时候用它"这一条值得单独强调**：技能写得好不好，九成看这一句。没有触发条件的技能，等于没写——agent 不知道什么时候该想起来它。

## 3. 插件的运行时与能力声明

### 3.1 运行时选型（D4，已推迟，这里给倾向）

| 选项 | 优点 | 缺点 | 倾向 |
|---|---|---|---|
| **WASM** | 启动快、隔离好、无系统调用 | 生态受限、不好调外部库 | **优先** |
| 容器化子进程 | 兼容性好、什么都能跑 | 重、启动慢、攻击面大 | 兜底 |

**倾向 WASM 优先、容器兜底**。但这条**推迟到有第一个真实插件需求时再定**（Tier 3 #27）。

### 3.2 能力声明：不是文档，是策略

```yaml
capabilities:
  - data.read:workspace://current        # 只能读本工作区
  - net.egress:["api.internal.corp"]     # 白名单出口
  - fs.write:tmp                          # 只能写临时目录
denied_by_default: true                  # 未声明即拒绝
```

**关键理解**：这份声明**不是给人看的说明书，而是沙箱启动时生成策略的输入**。声明了才有开关，没声明的一律拒绝。

### 3.3 一个反直觉但很重要的判断

> **插件的安全性，主要不取决于代码审得好不好，而取决于"能力声明 + 运行时是否真的约束住了"。**

因为：**即使代码是恶意的，只要它声明不了网络能力，它就发不出去数据。**

所以供应链安全的优先级应该是：

```
运行时强制（能力约束）  >  签名与来源  >  代码审查
```

**代码审查是最弱的一环**——它靠人看，一定会漏。而"声明不了就调不到"是机器保证的。

这不是说前两个不重要，而是说**不要把安全性寄托在"我审过了"上**。

### 3.4 ⚠️ 插件的运行环境，不等于 agent 的沙箱（Day 4 补）

**这是两个独立的隔离边界，必须分开实现。**

| | **agent 的沙箱**（[`05`](./05-sandbox-and-deployment.md)） | **插件的运行环境**（本节） |
|---|---|---|
| 关的是谁 | agent（干活的工人） | 插件（工人手里别人送来的工具） |
| 谁写的代码 | 我们 / 我们选的 agent | **第三方** |
| 实现 | **gVisor（runsc）**，ADR-3 | **WASM 优先，容器兜底** |
| 粒度 | 一次运行一个 | **每次调用一个**（微秒级） |

**为什么插件优先用 WASM**（真正的理由不是"快"）：

| | **WASM 插件** | **容器插件** |
|---|---|---|
| 它能碰系统吗 | **不能**——它只能调用**宿主显式导入给它的函数**，没导进去的它连"看见"都做不到 | 能——它在真文件系统里，靠**挂载 + 网络策略 + seccomp** 限制 |
| 越权可能吗 | **物理上不可能**（没有那个入口） | **可能**，靠内核拦 |
| §3.2 的"能力声明"怎么落地 | 声明"要 `读SKU`" → **只导入 `读SKU`** | 声明 → 配挂载 + 策略 |

> **"声明即边界"在 WASM 上是物理成立的，在容器上只是策略挡着。** 这就是 WASM 优先的理由。
> **容器兜底**用于需要长驻、需要完整文件系统的插件——这类需求真实存在，但少。

**⚠️ 一条不可违反的设计约束**：

> **不要用 WASM 替掉 agent 的 gVisor，也不要用 gVisor 替掉插件的 WASM。**
> **WASM 跑不了 agent**（agent 要 shell / 文件系统 / 任意命令，WASM 都没有）；
> **gVisor 装插件太贵太重**（一小段计算逻辑配一整个虚拟内核）。
> **两者是并列的两个边界，不是同一件事的两个方案。**

## 4. 供应链安全的完整清单

| # | 措施 | 防什么 |
|---|---|---|
| 1 | **能力声明 + 运行时 default-deny** | 越权（**最可靠的一环**） |
| 2 | **签名与来源验证** | 冒名、篡改 |
| 3 | **清单审查**（它声明了什么，合不合理） | 声明过宽（一个"Excel 合并"要网络权限？） |
| 4 | **静态扫描** | 明显的恶意代码、已知漏洞 |
| 5 | **沙箱测试** | 跑起来的行为和声明不符 |
| 6 | **SBOM / 依赖清单** | 供应链投毒（尤其是容器化插件） |
| 7 | **可下架 + 可撤销** | 出事了能止血——**这条现在就要有** |

> **第 3 条是最实用的**：不需要读懂代码，只需要看"一个做格式转换的插件为什么要网络权限"。**声明与实际用途不匹配，就是最强的信号。**

## 5. 三层库，三种信任级别

| 层 | 谁提供 | 审核 | 谁能装 |
|---|---|---|---|
| **平台技能库 / 插件库** | 你 | 你自己负责 | 所有客户（按技能声明的"适用岗位"过滤） |
| **客户私有** | 客户技术团队 | 你把关（受控改档） | 只有这个客户 |
| **第三方**（将来） | 外部 | 完整审核流水线 | 视授权而定 |

**三层用同一套机制（签名、能力声明、版本、归属），只是审核强度不同。** 这样客户私有的东西将来要升到平台层，不用重做。

> **"第三方"这一层现在不做**——理由见 §7。

---

## 6. 版本与兼容

- 技能 / 插件有**独立版本号**
- 岗位包引用时带**版本约束**（`demand-forecast@^2.0`）
- **破坏性变更必须升大版本**——因为岗位包可能依赖它的输出格式

**一个具体问题**：客户装了 `@^2.0`，你发了 `3.0`（破坏性），客户不会自动升。**这是对的**——但也意味着你要维护多个版本。

**建议**：明确写出"支持几个版本"，比如"当前大版本 + 上一个大版本"，超期提前通知。

## 7. 关于开放：现在开哪一层

**"第三方"这一层现在不做。**

理由三条（第 3 条是别人的血泪教训）：
1. 前提是**两边都有人**（供给方 + 需求方）——你现在只有一个客户
2. 早期做 = 做一堆没人用的机制（评分、排行、结算、争议处理）
3. ⭐ **别在还没人写技能的时候就去设计市场**——[AutoScout24](https://tech.autoscout24.com/blog/posts/designing-a-coding-agent-skills-marketplace/) 的原话：
   > **"Start with exploration, then standardise.**
   > **如果我们在还没人写技能的时候就去设计市场，我们会在错误的方向上过度设计。"**
   （他们的市场是**草根长出来的**：先是工程师私下分享技能，需求自然浮现，治理团队才介入）

**但这里有个关键区分（很多人在这一步会做错）：**

| | "开放机制"（**可以晚做**） | "约束机制"（**现在必须做**） |
|---|---|---|
| 内容 | 评分、排行、分成、上架流程、争议处理、推广位 | **签名、版本、能力声明、归属、运行时强制、可下架** |
| 为什么 | 只在"有多方参与"时才有意义 | **它们是"插件怎么被约束住"的一部分**，跟开不开放无关 |

> **换句话说：你现在不需要开放第三方，但你现在的插件就必须是"签名 + 声明能力 + 有归属 + 能被下架"的。**

**推荐的推进顺序：**

1. **自己写**技能和插件（服务现有客户）——把机制跑通
2. **客户技术团队能加**（私有层）——把"受控改"的流程跑通
3. **出现复用需求时**（同一个东西第二个客户也要），再升到平台层 / 考虑开放第三方

第 3 步是自然发生的——**当你发现"这东西我要给第二个客户装一遍"的时候，就该往上提了。**

## 8. 贡献与治理机制（借 AutoScout24 实践）

AutoScout24 真的建了一个（他们叫 skills marketplace，**16 个插件、多团队贡献**），有**三个机制值得照搬**：

### 8.1 ⭐ "更新的自主权，新增的治理权"

> 原文：**"autonomy for updates, governance for additions"**

| 动作 | 谁说了算 | 摩擦 |
|---|---|---|
| **更新**已有的技能/插件 | **归属方自己**（改完发版） | 极低 |
| **新增**一个技能/插件 | **平台把关**（确保它解决的是共性问题） | 有评审 |

**为什么这样分**：更新是"把已有的做好"，新增是"决定要不要收进来"——**后者需要全局视角，前者不需要**。

### 8.2 归属制（每个东西有主）

每个技能/插件有**明确归属**（类似 GitHub 的 CODEOWNERS）：
- 归属方**负责 review 和维护**
- 但**不排他**——任何人都能提改进，归属方 review

**好处**：不会出现"没人管的孤儿技能"。

### 8.3 自动质量门（不靠人盯）

**用一个 linter 做成"必过检查"**，机械验证：结构规范、命名规范、版本号有没有升、归属有没有填、能力声明格式对不对。

AutoScout24 的原话：**"自动化无聊的守门"**——人容易漏看"命名是不是短横线格式"，机器不会。

**他们的关键洞察（对我们特别适用）**：
> 技能和插件**经常是 agent 自己写的**。在这种情况下，机械的结构检查（对人来说可能觉得吹毛求疵）**变得必不可少**——它是一层一致的强制，能抓到"写它的 agent"和"审它的人"**都不会注意**的问题。

**为什么对我们特别适用**：我们的技能很可能就是 **roni 自己产出的**（`29` 的经验沉淀）——**给自己写的检查，是刚需**。

### 8.4 什么该进平台库、什么不该（他们划得很清楚）

| ✅ 该进 | ❌ 不该进 |
|---|---|
| 跨岗位/跨客户的共同问题 | 单个客户的特有工作流 |
| 平台级的标准 | 单一项目的定制 |
| 跨技术栈通用的 | 某个行业特有的 |

**不该进的怎么办**：放进**客户私有层**（§5）。

## 9. 待决问题

1. **技能能不能带"参数"？**
   比如一个技能说"安全库存按 N 天算"，N 是参数。
   **我倾向能带**——否则每个客户的"同一个技能、不同参数"就得复制成两份技能，很快就乱了。但参数必须**在岗位包的覆盖层里改**，不能改技能本身。

2. **插件能不能读写"交付物"？**
   比如一个插件要给计划表加一列核对结果。
   **我倾向只读 + 只能附加字段，不能改已有字段**——否则插件的改动会绕过审批（[`06`](./06-approval-and-executor.md)）。

3. **技能/插件的"下架"做到什么程度？**
   下架 = 不能新装？还是连已装的也停用？
   **我倾向分两级**：软下架（不能新装，已装的继续跑，但提示客户）+ 硬下架（立即停用，用于安全事件）。

4. **要不要允许技能互相引用？**
   允许 = 能组合出复杂流程；不允许 = 简单、好审核。
   **我倾向不允许**——需要组合的时候，那是岗位包的职责，不是技能的。**技能应该是"一件事"，不是"一套框架"。**
