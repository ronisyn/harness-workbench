## 一、总体判断

1. **组织级/隔离级设计是可信的、可实施的**：`architecture` §1 四条铁律 + ADR-1/8/9、`01` 四道闸、`34` 数据视窗（行/列/派生/聚合）都给出了"机制 + 验收标准"，**不是口号**。R1/R3/R5/R6/R7/R14/R17 在我读到范围内可判"已解决"。
2. **但"分期交付"这条主线是断的**：R2（供应链→运营→产品→IT）在 44 份文档里**没有任何落点**，`architecture:L131`、`L652` 明确把里程碑定为"按能力成熟度，不按垂直场景"。平台被设计成一个**能力完备但交付顺序未定**的东西。
3. **被标为"一期"的三件事（三个 agent 可插拔、5 个里程碑、客户自持 Key）彼此不自洽**：ADR-5 说一期 3 个 agent（`architecture:L40`），`11:L110` 说子 agent 是一期核心，但 `architecture:L658` 的 M2 才出现"子 agent 适配"，M0/M1 的关键交付里**一个 agent 都没有**，`03:L289-291` 的 `engine.fallback: [codex, builtin]` 又是悬空字段。
4. **成本数值的来源是真的，且可核验**：`23:L79-88`、`L113-124` 标注"实读 harness 源码"并给出 `DEFAULTS` 原文，与 `40:L170` 客户质问"这些数值经过验证了吗"对得上。这一条比我预期的好。
5. **R12（脱离本机/移动端/服务器定时）只有一半**：服务器化与定时任务的身份模型都有（`16:L44`、`01:L285-295`），但**移动端在全部 44 份文档中只出现 1 次**（`16:L20`），且是"天然基础"的推测句；生产级调度被 `16:L61-76` 自己列为"未验证"。

## 三、缺口详述

### R2：岗位分期优先级——**只在"砍功能"时被用过一次，从未变成交付顺序**
- **现状（修正：不是零命中）**：全库唯一实际使用点是 `05-sandbox-and-deployment.md:L277-278`「**"开发工作区"这类需要写权限的规格，第一批要不要做？** / 你的前四个优先级（供应链、运营、产品、IT）里，**IT/研发是唯一需要它的。我倾向第一批不做**」，对应决策 `11:L94`"**不做**"。——即：**团队知道这条需求存在，只用它论证过一次"某个功能可以砍"，从未把它变成交付顺序**。`architecture` §11 里程碑 M0–M3 全部以"能力"命名（`L656-659`），无一条与业务岗位顺序挂钩；`11:L201` 甚至把"先做供应链还是代码工程师"列为**失效问题**。`40:L54` 亦自标注「⚠️ **尚未落进任何文档**」。
- **为什么不够**：里程碑不写岗位顺序 → 实施时**无法回答"第 1 个交付给客户的岗位是哪个"**。而 `40:L52` 的原话是"供应链的**所有岗位都要先做**""其他岗位靠后慢慢来"——这是**排产约束**，不是能力描述。另外 `11:L201` 的失效判定**逻辑错误**：客户说的是"平台领域无关，但交付要有优先级"，两件事不冲突，把优先级问题判为失效是**用 ADR-4 掩盖了一条真实需求**。
- **最小补法**：在 `architecture` §11 里程碑表右侧加一列"**该阶段必须完成的业务岗位链**"，M0=备货计划（含 Excel+数据层），M1=采购/发货/仓储/供应链管理者（`40:L52` 前四类），M2=运营四岗，M3=产品经理/IT；并在 `11` 里把 `L201` 那行改成"**领域无关（平台）≠ 交付无序（路线图）**"。

### R9：一期三个 agent——**宣称可插拔，但一期路线图上没有 agent**
- **现状**：ADR-5（`architecture:L40`）「一期 3 个」；`19:L106-116` 给了三个定位（roni 主推 / DS harness 当零件来源 / codex 后接）；`25:L10` 同口径。**但**：`architecture:L656-658` M0 关键交付=模型网关+参考岗位包+连接器网关+数据视窗+沙箱+审计+审批，**无 agent**；M1 无 agent；**M2 才出现"子 agent 适配"**。`09:L24-44` 只给了 `派活()/结论()` 的伪接口，**没有 `AgentAdapter` 的真正契约**（`architecture:L390-396` 的 TS 接口是 `spawn(task, ctx, budget, caps)`，与 `09` 的四字段结构不一致、无错误语义）。`03:L289-291` 的 `engine: {preferred, fallback}` **没有任何文档实现它**（谁按什么规则切、切了之后 roni 的记忆/上下文怎么办）。
- **为什么不够**：一期三个 agent 是**客户原话的硬要求**（`40:L98-99`），但路线图上它是 M2 的能力。按文档实施，一期只会交付 **roni 一个**，"三个可插拔"变成宣传语。另外 `09:L61-81` 自己指出致命的**工具接管问题**（外部 agent 自带工具会绕过网关），并承认"**很多引擎不完整支持**"——这条**没有结论**（"必须选一条"但没有选，也没有对 codex/DS 做过验证）。**并且：全库无路由规则、无能力差异对照表**（只有 `19:L110-112` 的定位句与 `19:L116` 的接入顺序），文档把"三个 agent 可能配不同模型"当作**设计前提**反复消费（`23:L135`、`23:L158`、`22:L176`），却从未把它变成交付项与验收项——**前提被消费了，交付没被定义**。
- **最小补法**：①把"三个 agent 都能被同一调度器驱动"提到 M0/M1，作为**验收项**（`22:L176` 已有这句话，只需入表）；②补一份 `AgentAdapter` 契约文档（统一 `09` 与 `architecture` 两处接口签名 + 失败语义 + 记忆归属）；③对 codex/DS 各写一行"工具接管 or 围栏"的**结论**，并把"工具可否被接管"列为选型一票否决项；④给 `engine.fallback` 写清切换语义（或先删字段，别留悬空）。

### R12：脱离本机 / 移动端 / 服务器定时——**移动端只有 1 处推测句；定时任务的复用依据经源码核对不成立**
- **现状**：定时：`16:L22`「`dsh-schedule`：**durable** after/at/fixed-rate」；`16:L44`「Host 部署到服务器、常驻运行（**这是"关了电脑任务还跑"的前提**）」；身份：`01:L285-295` 服务身份 + `architecture:L522`。身份模型是完整的，但"能不能跑在服务器上"**只有 `16:L44` 一句前提句**。移动端：全库命中仅 `16:L20`「浏览器界面 … **移动端的天然基础**（浏览器/小程序连同一套）」——**是一句推测，不是设计**；`10` 六种接入形态（`L45-52`）里**没有移动端/响应式/小程序**；`31:L14-41` 平台 22 项能力清单里**没有移动端**。
  > 本节的反向证据来自**对 harness 源码的实读**（子代理独立核验，路径：`C:\Users\颜文\AppData\Roaming\npm\node_modules\@deepseek-ai\dsh\node_modules\@deepseek-ai\dsh-schedule\README.md` 等），**不是 `docs/` 内的叙述**。
- **为什么不够（原判"未验证"应升级为"已有反向证据"）**：①**`16:L22` 对 `dsh-schedule` 的引用与源码语义不符**。实读 `@deepseek-ai/dsh-schedule\README.md`：它是「**Session-local durable reminders**」「the schedule_create / schedule_list / schedule_delete tools and **live-owner delivery**」，「**Reminders survive restarts, but delivery requires a live root agent: closed sessions keep reminders overdue until resumed**」「**Delivery never uses email, SMS, push, or browser notifications**」，且「**repeating reminders run on a fixed interval only**」（不支持"每月 1 号/15 号"这种日历式规则）。→ `16:L22` 只摘引了 "durable after / at / fixed-rate" 三个词，**省掉了全部限制条件**；`16:L63`「`dsh-schedule` 是 durable 的」是**只读摘要的局部引用**。②**`16:L44` 的"常驻运行"是前提句，不是机制句**：全库没有任何文档回答"定时任务由哪个组件/进程承载、跑在哪台机器"（`22` §2 只说"调度器是平台一等能力"，全文无"定时/cron/常驻"）。③`16:L21` 称 `dsh-headless` 是"direct core Agent/Session runner，无 Host/HTTP/浏览器层"，实读其 README 为「One-shot task mode … the process opens no ports and **leaves nothing running behind**」——**一次性任务模式，不是常驻载体**。④`16:L20` 的移动端推测句同样有反证：`dsh-web-app\README.md`「You can change the port and allow extra hosts, but **cannot bind all network interfaces**」——默认只能本机访问。⑤移动端连"做不做、做成什么形态"都没定，而客户原话要"**在手机、在任何电脑上都能随时操作和使用 agent**"，其中"**审批/复核**"是最刚需动作（`06` 的 L1–L4 全靠人在环），缺它则 L2/L3 写路径在移动场景直接断掉。
- **最小补法**：①**先决定定时任务的承载实现**（不要继续引用 `dsh-schedule`）：自研持久队列 + 幂等 + 重试 + 错过补偿 + 状态可见，写成 `16` §3 的验收清单并挂 M1；同时把 `16:L22`/`L63` 的引用改为"仅借鉴 durable 语义，实现自研"。②新增一节（可挂 `10` 或 `38`）回答三件事：移动端=响应式 Web 还是小程序/App、移动端身份怎么进、**移动端的复核与审批怎么走**。

### R19：多站点扩展——**有机制，验证链不全**
