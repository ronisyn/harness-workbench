## 0. 一句话

**岗位包是平台方的资产，不是客户的配置。**

**这一句决定了本文全部设计**：

| 如果岗位包是 | 那么重点在 | 交付杠杆 |
|---|---|---|
| 客户自己写 | 降低**客户填写门槛** | **没有杠杆**——每家从零来 |
| **平台方写**（已确认） | 建**岗位库**、做**模板继承**、卡**质量门** | ⭐ **第 N 个岗位的成本递减** |

**所以本文的核心不是"编辑器怎么做"，而是"资产怎么积累、怎么复用、怎么不腐烂"。**

## 1. 先分清三个东西（它们常被混成一锅）

| | 是什么 | 谁写 | 血缘 |
|---|---|---|---|
| **角色草稿** | 一次对话的产物——"这个岗位大概干什么" | AI 提议 + 人改 | 客户私有，随时可弃 |
| **岗位包** | **九块结构的模板**，不含任何客户配置 | **平台方/交付团队** | **跨客户复用（资产）** |
| **数字员工实例** | 岗位包 + 客户配置 | 客户技术团队 | 客户私有 |

**判据**：

> **岗位包是"模板"，不是"这个客户的这个员工"。**
> 一旦岗位包里出现团队名、店铺名、阈值取值 → **它就只能卖给这一家**。

**为什么必须分开**：**第 12 个岗位便宜的唯一来源，就是"第 1 个岗位留下的模板能复用"**。混在一起，每个岗位都得从零来。

## 2. 生成流程（六步）

```
① 一句话输入（谁提的：交付团队 / 预研 / 客户需求）
      ↓
② 澄清（AI 提问，不是 AI 猜）
      ↓
③ 生成【角色草稿】—— 九块都填上，但标注哪几块是"待决"
      ↓
④ 人在结构化编辑器里改（不是改一段提示词）
      ↓
⑤ 质量门（§4）
      ↓
⑥ 固化成【岗位包 v1】→ 发布到【岗位库】
```

### 2.1 澄清问什么：只问架构无法推导的

| 必须问 | 为什么 AI 推不出来 |
|---|---|
| **它产出什么？谁接？** | 交付物 schema + 下游 |
| **它绝对不能干什么？** | 职责边界——**这是发权限的依据**（`03` §1.2） |
| **错了谁复核？复核标准是什么？** | 复核人 + **验收标准**（§4 G5） |
| **什么时候跑？** | 触发方式（手动/定时/事件/接口） |
| **用什么数据？哪些不能看？** | 数据要求 + 敏感级 |

**不能问的**（AI 该自己定）：九块的结构、提示词措辞、沙箱规格名、模型分级路由、成本上限默认值。

> **判据**：**问"业务事实"，不问"技术选择"。** 这也正是架构讨论里那条规矩——**同一套逻辑用在产品里**。

### 2.2 结构化编辑器（不是聊天框里改一段提示词）

**为什么必须是结构化的**：改一段提示词，人看不出"这一改让权限变大了没有"。
**按九块分区编辑，每块的改动都能显示影响**：

```
[1 身份]   岗位名 / 职责描述 / ★不管什么
[2 能力]   需要的连接器能力 / 技能 / 知识集要求
[3 权限]   ★数据要求（维度类型 + 敏感级）  写权限默认 L0-L1
[4 交付物] 结构 schema / 复核人 / ★验收标准 / 要不要解释
[5 编排]   子代理结构（并行/串行）+ 汇总方式
[6 触发]   手动 / 定时 / 事件 / 接口 / 批量
[7 环境]   ★引用平台的沙箱规格名（不许自己拼参数）
[8 模型]   分级路由（规划用强 / 抽数用便宜）
[9 交互]   对话式 / 列表式 / 在哪确认

右侧实时显示：本岗位会拿到哪些能力、哪些数据要求、哪些写权限
```

## 3. ⭐ 生成边界：AI 的手伸到哪里

**这条决定生成出来的东西能不能用。**

| 九块 | AI 生成？ | 说明 |
|---|---|---|
| 1 身份 | ✅ 生成 | 名字 + 职责描述；**"不管什么"要人确认** |
| 2 能力 | ✅ **从需求反推** | "要查销量" → 需要 `sales.query` 能力 |
| 3 权限 | ⚠️ **只给默认最窄** | 数据要求声明 + 写权限默认 L0/L1 |
| 4 交付物 | ✅ **生成 schema 草稿** | 字段从需求反推；**复核人与验收标准必须人填** |
| 5 任务编排 | ✅ 生成 | "查销量+查库存+查物流+验证→汇总"这类结构是稳定的 |
| 6 触发 | ⚠️ 给人选 | 不猜 |
| 7 运行环境 | ❌ **引用平台规格** | 岗位包**不许自己拼参数**（`architecture` §6.2：否则每个岗位都配出一个"刚好够用"的宽松环境） |
| 8 模型策略 | ✅ 给默认分级 | 强模型规划 / 便宜模型抽数 |
| 9 交互形态 | ✅ 给默认 | 人可覆盖 |

**三条硬规则**：

1. **AI 只生成"岗位包"（模板层），绝不生成"客户配置层"**
   数据视窗取值、连接器指向、阈值数字——**必须由人在实例化时填**（`03` §1.3）
2. **安全相关的默认值一律取最窄**（写权限、数据范围、批量上限）——**AI 不许"贴心地"放宽**
3. **AI 生成的东西一律是"草稿"**——`03`/`29`/`33` 都是"agent 提议 → 人确认"，**同一个模式第四次用**

## 4. 质量门：生成的岗位包凭什么算合格

`36` §4 的上岗审核管"**配齐了、联通了**"（实例层）。
**本节的 G1–G8 更早——管"这份岗位包本身写得对不对"（模板层）。**

| # | 标准 | 不合格的表现 |
|---|---|---|
| **G1** | **九块完整** | 漏了第 5 块（任务编排）→ 每次让模型现场想"派谁" |
| **G2** | **职责边界是"可执行"的，不是礼貌用语** | 写"我会认真负责"→ 策略引擎无法据此发凭证（`03` §1.2） |
| **G3** | **能力最小集** | 要 3 个连接器却声明了 10 个 → 权限面过大 |
| **G4** | **交付物 schema 可校验**（字段、类型、必填） | 产出无法自动验证 |
| **G5** ⭐ | **交付物带"验收标准"** | 见 §4.1 |
| **G6** | **无客户特有名词**（维度名、取值、系统名） | **不可复用**（`03` §1.3） |
| **G7** | **不引用具体工具名/接口地址** | 换连接器实现就崩（`04` §1 的判据） |
| **G8** | **用平台的语义能力名，不用底层通道** | 出现 `db.query(sql)` → 权限没法收敛（`04` §3） |

### 4.1 ⭐ G5：交付物要带"验收标准"（本轮补的重要缺口）

**我们早先定了"交付物要人复核"，但一直没定"复核的标准从哪来"。**

**它应该写在岗位包里**——因为它是**这个岗位的业务定义**，不是平台的通用规则。

```yaml
deliverables:
  - id: replenishment-plan
    结构: replenishment-plan.v2
    复核: required
    验收标准:                          # ★ 新增
      - 每个 SKU 的备货量都附了计算依据
      - 未突破库龄滞销线
      - 缺数据的项必须显式标注，不能留空
    解释: required
```

**为什么这条重要**：

| 没有验收标准 | 有验收标准 |
|---|---|
| 复核人各凭感觉 → **学习闭环的数据是脏的**（`28` §3 靠"人改了什么"学，标准不一就学不到规律） | 复核有一致口径 → 经验可沉淀 |
| 出纠纷时说不清"什么叫没做好" | 验收标准就是**交付质量的定义** |
| 客户觉得"这东西靠运气" | 客户能看见"这个岗位按什么标准验收" |

> **这条同时把 `28`（交付物流程）、`29`（经验从哪来）、`36`（上岗审核）三处断掉的地方接上了。**

## 5. ⭐ 三层模板：第 N 个岗位便宜的机制

**"交付杠杆"不能靠"AI 每次重新生成"，要靠"模板能继承"。**

```
① 骨架模板（平台级）          ← 跨所有客户：九块结构 + 通用提示词框架 + 最小权限原则
      ↓ 继承 + 特化
② 行业模板（平台级，可选）     ← 跨同行业客户：如"电商运营""供应链计划"的常见块
      ↓ 继承 + 特化
③ 客户岗位包（可私有）         ← 这家的具体岗位：不含客户配置，但含这家的业务特点
      ↓ 实例化（客户技术团队做）
④ 数字员工
```

### 5.1 ⚠️ 模板不是代码，是"可复用的骨架 + 预置块 + 示例集"

| 允许 | 不允许 |
|---|---|
| 预填九块的内容 | 模板里写分支逻辑（`if 客户是A则…`）——**那是代码** |
| 预置任务编排结构 | 模板里硬编码数据范围 |
| 预置交付物 schema 与验收标准 | 模板里写具体连接器地址 |

> **一旦模板里出现"分支逻辑"，它就从"配置"退化成"代码"**——ADR-4"岗位是配置不是代码"当场破。

### 5.2 ⭐ 生成时先查库（这条最省钱）

```
新需求进来
   ↓
① 先在【岗位库】里找相似的 ──► 命中 → 以它为基底特化（几分钟）
   ↓ 未命中
② 从行业模板特化 ──► 半自动
   ↓ 未命中
③ 从骨架全量生成 ──► 最贵，但产出会进库，下次就不用从头来
```

**这就是"第 12 个比第 1 个便宜"的实现**——**每一次新建都在给库添砖**。

**查库不是"文本相似度"，按四个维度匹配**：

| 维度 | 匹配什么 |
|---|---|
| **产出物类型** | 都是"计划单"？还是"分析报告"？ |
| **数据依赖** | 都依赖"销量 + 库存 + 物流"？ |
| **编排结构** | 都是"多路取数 → 汇总 → 验证"？ |
| **写权限需求** | 都只读？都要写？ |

**给交付团队的界面**：不是"从零开始"，而是"**这里已有 7 个相似岗位，你要基于哪个改？**"

### 5.3 ⚠️ 特化之后要不要跟基底升级（Day 3 补：不定义库会变成一堆分叉）

**"以它为基底特化"之后产生的是一个独立包。** 那基底升级了，派生包跟不跟？

| 场景 | 我拍 |
|---|---|
| **派生包 = 纯特化**（只填了取值/措辞，没改结构） | **跟随基底**，自动合并（冲突时人工裁决） |
| **派生包 = 已分叉**（改了结构性内容） | **不自动跟随**，标记"**已分叉，基底有 N 项更新待评估**"，由交付团队逐项决定 |
| **基底废弃** | 派生包**不受影响**（它自己是一份完整的包），但血缘里标注"基底已归档" |

**为什么要定**：不定义的话，**基底升级时没人知道哪些派生包需要动**——结果就是**库越长越乱，查库命中率越来越低**，交付杠杆反而失效。

**血缘是这条的实现基础**（§6.3）。

## 6. 岗位库：第三个可复用资产

**平台到目前有两个可复用资产**：技能库（`12`）、插件库（`12`/`32`）。
**岗位包是第三个，也是商业价值最高的一个**——**因为客户买的就是岗位**。

| | 技能库 | 插件库 | **岗位库** ⭐ |
|---|---|---|---|
| 是什么 | 怎么干一件事 | 会算什么 | **一个完整岗位的定义** |
| 客户感知 | 间接 | 间接 | **直接（这就是产品）** |
| 可售卖 | 是 | 是 | **是（核心资产）** |

**发布与治理沿用 `32` 的同一套**（不另造）：

| 项 | 沿用 |
|---|---|
| 谁能发布 | **平台方/交付团队**（不是客户） |
| 客户能做什么 | **引用 + 实例化配置**；覆盖边界见 `03` §4.1 三档——**结构性内容一律不可改**，表述性/取值性可以（改了不是新包，是覆盖层） |
| 上下架 | 软下架 / 硬下架（`32` §7 #28 同规则） |
| 版本语义 | patch / minor / major（`32` §5 同规则） |
| 签名与来源 | 同插件（`12` §3） |

### 6.1 ⭐ 发布治理：审批 + 签名 + 血缘（Day 3 补：缺了这三样，平台说不清自己卖的是什么）

平台方写包，等于**包是自己的产品**。**那内部就必须有发布纪律**（`32` 对技能/插件有，岗位包不能没有）。

| 项 | 我拍 |
|---|---|
| **发布审批** | 岗位包发布必须**内部审核通过**（不是谁都能发）——建议**双人**：业务负责人（内容对不对）+ 平台负责人（安全边界对不对） |
| **签名** | 每个发布版本带**签名与来源**（谁发的、什么时候、基于哪版） |
| **血缘** ⭐ | 记录 `包 X 基于 骨架 S + 行业模板 I + 是否分叉` |
| **可见范围** ⭐ | 每个包声明**能卖给哪些客户**（骨架=全部；行业模板=指定行业；客户私有=只有这家） |
| **生成审计** ⭐ | 记录：谁生成、AI 还是人手改、改了几轮、用了哪个模板、质量门哪几项第一次没过 |

**血缘的实际用途**：某个骨架写错了，要能查出**所有受影响的包与实例**。
**没有血缘，只能一个个翻**——而库越大越翻不动。

**可见范围的用途**：行业模板是**资产**，不该所有客户都看得到（那等于把行业 know-how 免费送出）。

### 6.2 ⭐ 资源画像（Day 3 补：`03` 第 7 块只说"引用规格名"，没说怎么表达负担）

**问题**：`03` 第 7 块说岗位包"引用平台的沙箱规格名，不许自己拼参数"（对）。**但没说岗位包怎么表达"我这个岗位的活大概多重"。**

**影响**：`22` 的批量编排要按这个做并发规划（"1000 个 SKU 一次跑"，机器从哪来）。

**我拍：岗位包声明【资源画像】——不是具体参数，是档位。**

| 声明项 | 取值示例 | 谁用 |
|---|---|---|
| **典型运行时长** | 秒级 / 分钟级 / 十分级 | 调度器选超时阈值 |
| **并行度** | 单路 / 多路（N 路） | 批量编排排并发 |
| **数据量级** | 小（千行）/ 中（十万行）/ 大（百万行） | 提示数据面准备 |
| **建议沙箱规格档位** | 纯计算 / 只读取数 / 开发工作区 | 映射到 `05` 的规格名 |

**注意**：这只是**画像**，**不是参数**——真正的参数仍由平台规格决定（否则回到"每个岗位都配出一个刚好够用的宽松环境"，`architecture` §6.2）。

## 7. ⭐ 岗位包版本 ≠ 契约版本（最易出事的一处）

| | 岗位包版本 | 权责契约版本（`36` §5） |
|---|---|---|
| 是什么 | **模板**的版本 | **实例**的授权版本 |
| 谁改 | 平台/交付团队 | 客户技术团队 |
| 改了会影响谁 | **只是候选**，不影响在岗员工 | **立即影响那个员工** |

**硬规则**：

> **岗位包升级 ≠ 已在岗员工自动升级。**
> 升级是一条**提案**：平台发布新版 → 客户看到 **diff** → 客户决定是否应用 → 应用了才生成新的契约版本。

**为什么**：`32` §5 已定技能"不一刀切自动升级"（输出格式一变，下游可能接不上）。
**岗位包影响面更大**——它连**交付物 schema** 都可能变。所以**必须客户点头**。

**升级呈现给客户的样子**：

```
岗位包【备货计划专员】v2 → v3（minor：加了"在途库存"能力）

影响范围：
  · 交付物 schema：无变化
  · 需要的新数据：在途库存（需客户配数据视窗）
  · 需要的新连接器能力：logistics.in_transit（需客户授权）
  · 已在岗员工：3 个（应用后各生成新契约版本）

[ 应用到全部 ]  [ 逐个选择 ]  [ 稍后 ]  [ 钉在 v2 不再接收更新 ]
```

**"钉在 vX"是必须的**：大客户升级窗口不由我们决定，**必须能选择不跟**。

## 8. 岗位包也会腐烂（防腐沿用 `29` 的逻辑）

**岗位包会被写坏**——需求变了、连接器能力变了、发现编排漏了一步。**所以它也需要 Anti-Rot。**

| 腐坏 | 怎么发现 | 怎么处理 |
|---|---|---|
| **能力失效** | 它引用的连接器能力被下架改了 | 标记**需修订**，通知使用它的客户 |
| **验收标准过时** | 客户反馈"这条现在不适用了" | 提议修订 → 人确认 |
| **同类岗位重复** ⭐ | 岗位库里出现两个高度相似的包 | 提示**合并**（否则库越用越乱，查库命中率下降） |
| **长期无人用** | 某个包 6 个月零实例 | 提示**归档**（不删，保留血缘） |
| **经验反哺** ⭐ | 某个岗位做久了，稳定下来的做法 | **可以提升为模板的一部分**——这是库自己长大的通道 |

> ⭐ **最后一条是"越用越值钱"在岗位库上的体现**：客户 A 用出来的好做法，**可以变成下一个客户拿到的模板**。
> **但必须脱敏 + 人确认**（不能把客户 A 的业务特点带进通用模板，`03` §4 的"结构性 vs 表述性"）。

**补充两条 Day 3 的处置规则**：

| 腐坏 | 处置 |
|---|---|
| **一包多实例的升级中间态** ⭐ | 一次升级应用到 N 个实例时，**逐个原子生效**（不出现"半新半旧"），且**账本要能回答"升级期间这个岗位是什么状态"** |
| **归档之后** | 归档**不删**（保留血缘与历史）；已引用它的实例**继续用**，只是不再接收更新；**删除**只发生在整租户销毁时（`01` §6.4） |

## 9. ⭐ 发布、灰度、回滚、紧急下架（Day 3 补：缺了这套，大客户不敢用新版本）

### 9.1 灰度（`architecture` §3 说岗位包"可灰度"，这里落实）

```
新版本发布
   ↓
① 先在【内部参考实例】上跑（参考工人，`architecture` §1）
   ↓
② 灰度：选定 1–2 个客户实例切到新版，与旧版【并行对比】
   ↓
③ 对比指标天然来自交付物（`03` §5 的原则）：
     · 人工修改率（人改得多 = 这版不好）
     · 验收失败率
     · 平均运行成本与时长
   ↓
④ 指标达标 → 全量；不达标 → 回滚
```

**"并行对比"是灰度的关键**：同一岗位上跑两个版本，**用交付物质量说话，不靠感觉**（`03` §5 已定这条判据）。

### 9.1.1 ⭐ 金标冒烟：roni 已有能力，升格为平台级回归机制（Day 4 第 2 轮自审补）

`17` §1 记录 roni 有"**金标冒烟**"。**这是新架构一度漏掉的一环**——它回答的是一个必然会被问到的问题：

> **"改了提示词 / 换了模型版本 / 发了一版岗位包之后，我怎么知道原来能干的事现在还能干？"**

**没有它，任何改动都是盲改。** 对交付团队尤其致命——"这个包卖给了 5 个客户，我改一句提示词，凭什么知道没改坏？"

#### 两个层次（一层对内，一层对客户）

| | **① 平台级金标**（对交付团队） | **② 实例回归样本**（对客户） |
|---|---|---|
| 是什么 | 参考工人 + 每个岗位包配一套**标准任务集** | 这个数字员工历史上**做过的代表性任务** |
| 判什么 | 结构对不对、必填字段齐不齐、关键结论口径一致不一致 | **它的行为有没有漂移** |
| 什么时候跑 | **每次改动前必跑**：改提示词 / 换模型 / 发新版包 / 改连接器 | 定期 + 重大变更后 |
| 谁看 | 交付团队 | 客户技术团队 + 平台 |

#### 三条规则

1. **金标样本必须是"已验收过"的**——用历史上**人批过**的交付物当基准（客户 A 用出来的好做法，`37` §8 的"经验反哺"是同一个来源）
2. **样本要脱敏**（客户 A 的样本进平台级金标时，`03` §4 的结构性/表述性判据同样适用）
3. **判据分层**：`结构类`可自动判 → **不过就是不过**；`结论类`（口径、量级）→ **报警 + 人工确认**，不自动判失败（避免"业务上合理的变化"被误判为回归）

> **和 `36` §4.2 联调的关系**：**联调是"上岗前的一次性检查"，金标冒烟是"每次改动后的回归检查"。**
> 前者回答"它现在能不能干"，后者回答"**它是不是变差了**"。
> **两者都可复用同一套"用例声明"结构**（`36` §4.2.1），只是触发时机与判据不同——**不做两套**。

#### 对现有文档的连带

| 文档 | 连带 |
|---|---|
| `36` §4.2 | 联调用例与金标冒烟**共用用例声明**，只是时机不同 |
| `30` | 换模型版本/改路由 → **触发金标冒烟**（模型是行为变量之一） |
| `02` | 金标样本涉及客户数据 → **脱敏后**才能进平台级金标 |

### 9.2 回滚（⚠️ 不是"撤销"，是"发一个回到旧行为的版本"）

**为什么不能"撤销"**：`36` §5 定了"能力增删是事件、生成新契约版本"。
**撤销 = 抹掉历史 = 账本断裂**。所以回滚的正确形态是：

```
发现问题版本 v3
   ↓
① 【紧急下架】v3：不能再被新实例引用（`32` #28 的硬下架）
   ↓
② 【回滚】给已应用 v3 的实例，发一个 v4，其内容 = v2 的行为
   —— 而不是"把 v3 撤掉"
   ↓
③ v3 期间产出的交付物：**标记"产出时使用了已回滚的版本"**，
   不删除、不改写、但要让人在复核时看见
   ↓
④ 账本记录：谁在什么时候、因为什么回滚
```

**第 ③ 条最容易被省掉**：不回滚历史交付物（那是审计凭证），但**必须标记**——否则事后没人知道"那批东西是用一个后来被否掉的版本做的"。

### 9.3 紧急下架的触发与权限

| 项 | 规则 |
|---|---|
| **谁能硬下架** | **平台方**（不需要客户同意，但**必须通知**）——安全事件不能等客户排期 |
| **通知时限** | 立即通知所有使用该包版本的客户 |
| **已产出交付物** | 冻结复核？不。**照常复核，但界面显式提示**风险来源 |
| **根因与修复** | 下架与修复是两件事：**先止血（下架），再修复（发新版）** |

## 10. 验收标准

| # | 标准 |
|---|---|
| P1 | **一句话输入 → 生成九块齐全的角色草稿**，且每块标注"AI 生成/待人确认" |
| P2 | **澄清只问业务事实**（产出什么/不管什么/谁复核/何时跑/用什么数据），不问技术选择 |
| P3 | 质量门 **G1–G8 全部通过**才能固化成岗位包；**G5 验收标准缺失则不许发布** |
| P4 | **生成的岗位包里不含任何客户特有名词与取值**（可复用性判据） |
| P5 | AI **只生成模板层**，客户配置层（视窗取值/连接器/阈值）**一律留空待人填** |
| P6 | 安全相关默认值**一律最窄**（写权限 L0/L1、数据范围最小、批量上限 1） |
| P7 | **新建岗位时先查库**：命中则提示"基于哪个已有岗位特化" |
| P8 | 三层模板可继承，且**模板内不含分支逻辑**（不是代码） |
| P9 | 岗位包**版本与契约版本独立**；升级是**提案**，客户可 diff、可拒绝、可**钉在旧版** |
| P10 | 交付团队的编辑界面**能实时显示**"本岗位会拿到哪些能力/数据要求/写权限" |
| P11 | 岗位库里**高度相似的包会被提示合并**；长期无人用的会被提示归档 |
| P12 | **经验反哺模板时必须脱敏 + 人确认**，不得把某客户的业务特点带进通用模板 |
| P13 | **换一个客户、换一个数据源，只加连接器 + 配实例，不改岗位包**（ADR-4 的量化验收） |
| P14 | **覆盖边界三档生效**：结构性内容（职责边界/schema/验收标准/权限声明）**客户改不了**；表述性与取值性可以 |
| P15 | **覆盖项记录"基于哪个包版本"**；升级时**冲突逐项让人选**，合并结果生成新的实例配置版本 |
| P16 | **发布要过内部审批（业务 + 平台双人）+ 签名**；血缘可查 |
| P17 | **交付物按产出时的验收标准快照判定**，不按最新版（`28`） |
| P18 | 灰度期**同一岗位两版并行**，用**人工修改率 / 验收失败率 / 成本**对比决定去留 |
| P19 | **回滚是"发一个回到旧行为的新版本"，不是撤销**；回滚期间产出的交付物**标记来源版本**，不删除不改写 |
| P20 | **硬下架只有平台方能做，且必须立即通知**；止血与修复分开 |
| P21 | **一包多实例升级逐个原子生效**，账本可回答"升级期间这个岗位是什么状态" |
| P22 | **派生包标注是否已分叉**；基底升级时"未分叉"自动合并、"已分叉"逐项评估 |
| P23 | **每个包含可见范围**（骨架/行业/客户私有），**行业模板不对全部客户可见** |
| P24 | **资源画像已声明**（典型时长 / 并行度 / 数据量级 / 建议规格档位），供 `22` 编排与 `05` 选规格 |
| P25 | **生成过程可审计**（谁生成、用哪个模板、AI 与人各改了几轮、质量门首次未过项） |

## 11. 这一步顺带拍掉的决策

| # | 问题 | 我拍 |
|---|---|---|
| 1 | 岗位包谁来写？ | **平台方/交付团队**（已确认）。所以它是**平台资产**，不是客户配置 |
| 2 | AI 生成到什么程度？ | **生成模板层全部九块；客户配置层一律留空** |
| 3 | 生成的安全默认值怎么取？ | **一律最窄**。AI 不许"贴心地"放宽 |
| 4 | 交付物要不要带验收标准？ | **要**（G5）。**没有它，"复核"没有口径，学习闭环的数据是脏的** |
| 5 | 岗位包能不能写分支逻辑？ | **不能**。一旦有分支就从"配置"退化成"代码"，ADR-4 当场破 |
| 6 | 怎么保证第 N 个岗位更便宜？ | **三层模板 + 生成前先查库**；每次新建都在给库添砖 |

| 9 | 岗位包能当商品卖吗？ | **能，而且这是核心资产**——客户买的就是岗位 |
| 10 | **客户能不能改包本体？** | **结构性内容不能**（职责边界/schema/验收标准/权限声明）；**表述性与取值性能**（三档见 `03` §4.1） |
| 11 | 客户覆盖与升级冲突怎么合？ | **覆盖项记"基于哪个版本"**；升级时逐项让人选，生成新的实例配置版本 |
| 12 | 特化出来的包要不要跟基底升级？ | **未分叉自动跟随、已分叉逐项评估**（否则库变成一堆分叉） |
| 13 | 岗位包要不要内部发布审批？ | **要**（业务 + 平台双人 + 签名 + 血缘）——**否则平台说不清自己卖的是什么** |
| 14 | 行业模板谁能用？ | **声明可见范围**，不对全部客户可见（那是免费送行业 know-how） |
| 15 | 岗位包升级出事怎么办？ | **硬下架（平台方单方，立即通知）+ 回滚（发一个回到旧行为的新版本，不是撤销）** |
| 16 | 回滚期间产出的交付物怎么办？ | **标记来源版本，不删不改**——否则事后没人知道那批东西的出身 |
| 17 | 岗位包怎么表达"活有多重"？ | **资源画像**（时长/并行度/数据量级/建议规格档位），不是具体参数 |
| 18 | 一包多实例升级怎么算一致？ | **逐个原子生效**，账本可回答升级期间的状态 |
| 19 | 交付物按哪版验收标准判？ | **产出时的快照**，不按最新版（`28`） |
| 20 | 生成过程要不要审计？ | **要**（谁生成、用哪个模板、AI 与人各改几轮、质量门首次未过项） |

