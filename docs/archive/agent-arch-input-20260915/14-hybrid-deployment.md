# 细化 ⑪：混合部署（现在就要做）

> 父文档：[`architecture.md`](./architecture.md) §12 细化路线 第 ⑪ 项
> 状态：**已定（Day 2）——现在就要做。**

---

## 0. 这份文档现在**是**什么

**Day 2 更新：混合部署从"未来可能"升级为"现在就要做"。**
原因：客户的数据中台是独立项目、跑在客户自己的服务器上。要装"手脚"（数据面）上去就地读数据，就必须混合部署——**数据不搬出客户内网**。

**核心澄清（之前理解有误）**：数据哪儿都不去，一直留在客户数据中台里。混合部署解决的是"**agent 在哪里读数据**"，不是"数据存哪"。

```
数据留在客户数据中台（不动）
   ↑ 在客户内网就地读取
数据面（agent 运行时 + 连接器 + 沙箱）装在客户服务器
   ↑ 只和你的控制面通信（下发岗位包/策略，回传审计/计量）
控制面（管理/计费/岗位包/策略）留在服务商
```

下面六条本来是"为了将来能拆开、今天必须做对"的保险条款，**现在升级成"现在就必须做对"的约束**——尤其第一条"控制面不碰业务数据"。

> **保险的定义就是：平时不花钱，出事时救命。**

---

## 1. 先分清两个面

| | 控制面 | 数据面 |
|---|---|---|
| 管什么 | 配置、人、钱、策略、岗位包 | **跑 agent、连外部系统、读业务数据** |
| 碰业务数据吗 | **不碰** | 碰 |
| 在哪 | 你这里（统一升级、统一计费） | 默认也在你这里；混合部署时搬到客户那边 |

**混合部署 = 控制面留在你这儿，数据面放进客户的内网（数据不出他的网）。**

---

## 2. 今天必须做对的六件事

### ① 控制面绝不能碰业务数据

这条今天遵守了，将来才能把控制面拿走。

**反例**：为了"方便"，让计费服务去查了一下客户的订单明细来算钱。

> **判据：控制面的任何服务，如果要读业务数据才能工作，就是设计错了。**

### ② 标识里要能表达"在哪"

每个实体（客户、工作区、数字员工、运行、交付物）的标识，要能看出它属于哪个部署位置。

这就是决策清单 Tier 2 的 **#23（`<region>` 要不要进 URI）**——它不只是"区域"，也是"**这个数据面在哪**"。

### ③ 两个面之间只通过"契约"通信

不能有共享数据库、不能有共享文件系统、不能有直接的方法调用。**只能通过明确定义的接口 + 事件流。**

> **判据：如果数据面和控制面连的是同一个数据库，那它们从来就不是两个东西。**

### ④ 数据面要能独立启动、独立运行、独立恢复

- 数据面本地要有**足够的元数据副本**（岗位包、权限配置），断连了也能继续跑
- 断连期间的审计事件要**能缓存，恢复后补传**
- **不能"控制面一挂，所有正在跑的活全停"**

### ⑤ 策略要能"离线执行"

权限判定发生在**数据面**（因为要快、要在边界上执行）。控制面只负责**下发策略**，不负责**每次判定都参与**。

> **判据：如果每一次工具调用都要回控制面问一次"行不行"，这个架构就是耦合的。**

### ⑥ 计费与审计要能"事后归集"

数据面产生事件 → 控制面归集 → 计费。**不能反过来**（控制面实时要求数据面报告）。

---

## 3. 关键：这六条的成本几乎为零

因为它们**不是"为混合部署额外做的事"，它们本身就是好设计。**

| 条款 | 即使永远不混合部署，它也是 |
|---|---|
| ① 控制面不碰数据 | **安全要求**——它是 [`01`](./01-identity-and-isolation.md) 里"平台运营方"这个最大风险点的缓解手段 |
| ② 标识带位置 | 多区域、多环境的前提 |
| ③ 只走契约 | 控制面 / 数据面各自独立扩容的前提 |
| ④ 独立运行 | **可用性要求**——控制面故障不该让在跑的活崩溃（[`architecture`](./architecture.md) §2 已写） |
| ⑤ 策略离线执行 | **性能要求**——每次调用回中心问一次，延迟受不了 |
| ⑥ 事件事后归集 | **吞吐要求**——同步报告会把两边一起拖死 |

> **所以这不是"要不要为未来买单"，而是"要不要现在就把该做对的做对"。**

---

## 4. 什么时候**才该**真做混合部署

触发信号（任一即可）：

- 客户要求"**数据不出我的内网**"
- 客户要求"**部署在我的机房**"
- 出现受监管行业客户（金融、政企）
- 数据出境成为合规问题

**在那之前，别做。** 但因为上面六条今天做对了，真到那天你要做的是"**把数据面打包搬走**"，而不是"**重新设计**"。

## 5. 待决问题

1. ~~**① 要不要提升成一条正式决策（ADR-8）？**~~
   **✅ Day 3 已定：升为 ADR-8**（已入 `architecture` §0.5 的 ADR 表）。理由："控制面不碰业务数据"是一条会被日常开发不知不觉违反的约束——"就查一下订单算个钱"听起来很合理。**写成 ADR，才能在被违反的时候指着它说话。**
   **连带的第二条**：`34`/`35` 那轮又拍出 **ADR-9（隔离是默认，跨边界要显式授权）**——它和本文第 ① 条是同一个思路的另一面（**数据面在客户侧、控制面只拿元数据；客户内部边界默认隔离、跨越要授权**）。

2. **数据面离线时能跑多久？**
   取决于本地元数据副本的有效期。太长 = 策略更新不到（安全风险）；太短 = 网络一抖就停。
   **我倾向：策略离线有效期按"小时"级（比如 24 小时），超时后降级为只读 + 提示。** 但这取决于你将来客户的实际网络情况。

3. **两个面之间的契约，用同步接口还是只用事件？**
   只用事件 = 彻底解耦，但实现复杂、调试难。
   混合 = 控制→数据用事件下发，数据→控制用事件上报，**少数管理操作走同步接口**。
   **我倾向混合**，全异步在这个规模上没必要。
