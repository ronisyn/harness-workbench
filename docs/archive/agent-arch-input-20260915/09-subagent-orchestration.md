# 细化 ⑧：子 agent 适配

> 父文档：[`architecture.md`](./architecture.md) §12 细化路线 第 ⑧ 项
> 前置：[`07-engine-shell-boundary.md`](./07-engine-shell-boundary.md)（agent 内部：引擎与运行时的边界）、[`08-context-engineering.md`](./08-context-engineering.md)（上下文与预算）
> 对应你原始设想的第 2 点：**自研一个 agent，可以集成 Codex、Claude 作为子 agent**。

---

## 0. 先说清楚：子 agent 的价值是"上下文隔离"，不是"能力增强"

**这一点如果搞反，会白白烧掉很多钱。**

| 该用子 agent | 不该用 |
|---|---|
| 任务能并行（多个独立调查） | 简单任务（拆了反而更贵） |
| 需要大量试错的脏活，但只要一个干净结论 | 需要共享大量上下文的（拆了要反复传，传的就是钱） |
| 需要一个"不同性格"的执行者（例如专门挑错的审查者） | 单线程的线性任务 |
| 上下文会爆炸，必须隔开 | —— |

**判据**：子 agent 解决的是"**这一大堆中间过程不该污染主上下文**"，不是"**多个人干活更快**"。每一次派活都有传递成本，收益必须来自"隔离掉的上下文"，否则就是纯亏。

---

## 1. 统一接口：平台看到的是同一个东西

不管底下是 Codex、Claude Code、harness，还是将来自研的，**平台看到的一律是同一个接口**：

```
派活(
  任务说明,
  上下文切片,        ← 只给它需要的那部分
  预算额度,          ← 切分出来的，不是共用
  权限子集           ← 父级的真子集
)
  ↓
结论(
  结构化结果,        ← 符合声明的结构
  消耗了多少,
  用了哪些能力,      ← 审计
  结束原因
)
```

**这是 ADR-5 的第二次考验**：换引擎不该改业务资产，换子 agent 引擎同样不该。

---

## 2. 四条硬约束（铁律二的落地）

| # | 约束 | 说明 |
|---|---|---|
| **1** | **权限 ≤ 父级** | 子 agent 永远不能拿到父级没有的权限。通常是**严格小于**——只给它这个任务需要的 |
| **2** | **预算切分，不共享** | 子 agent 拿到的是**额度**，不是"共同账户"。它超支不能拖垮父级 |
| **3** | **深度限制** | 子 agent 不能再无限递归派生。**建议上限 2 层** |
| **4** | **结果收敛** | 只回传结构化结论，**不回传原始上下文** |

第 4 条的两个理由：**防上下文爆炸**（把子 agent 的整个上下文倒回来，等于没隔离）、**防污染**（子 agent 读到的外部内容不该流进主上下文）。

## 3. ⚠️ 外部引擎自带工具 —— **Day 12 已修正：结论反了**

> ⚠️ **本节结论已推翻，原文保留在下面以示可追溯。**
> **原结论**："接管优先——外部引擎如果不能被接管工具，就只能走围栏，而围栏更粗。"
> **错在哪**：这个判断**建立在一个没验证的前提上**——"引擎自带的工具不如我们的"。
> **实证后（[`50`](./50-agent-tech-architecture.md) §3，本机源码 + 官方文档）**：
> 两家引擎（DS harness、Codex）自带工具**都比我们自研的好**（都是为"长任务、多轮迭代、真跑代码"打磨的），
> **而且两家都提供了从外部约束的机制**。**剥夺它们的工具，是拿确定的能力损失，去换一个我们已经有替代方案的收益。**
>
> **✅ 新结论：用围栏，不接管。** 详见 §3-b。

### 3-a 原文（已作废，保留可追溯）

Codex、Claude Code 这类引擎**自带一批工具**：读写文件、执行命令、访问网络。如果你直接把它们当子 agent 跑起来，**它们会用自己的工具，绕过你的连接器网关、权限和审计。**

```
你以为的：  Codex ──► 你的连接器网关 ──► 审计 ✓
实际发生的：Codex ──► 它自己的文件/shell/网络工具 ──► 审计 ✗  权限 ✗  脱敏 ✗
```

~~两条处理路线，必须选一条~~（**已改为"围栏为主线"**）：

| 路线 | 做法 | 结论 |
|---|---|---|
| ~~接管~~ | 禁用它的原生工具，只注入你提供的工具清单 | ❌ **不作为主路线**：能力损失大，且很多引擎不完整支持 |
| **围栏** | 让它的原生工具在**沙箱里**跑，受沙箱、网络白名单、执行策略约束 | ✅ **主线** |

---

## 3-b ✅ 围栏方案（现行结论）

### 为什么围栏可行：两家引擎都提供了外部约束点

| 引擎 | 约束点（来源） |
|---|---|
| **DS harness** | 沙箱做成**契约 + provider 注册表**（`ctx.sandbox` + `SandboxProvider`）；`dsh-fs-sandbox` **在工具层强制**，且"文件与 shell 两个能力族**绝不会约束到不同根目录**"；模式拿不到时 **fail-closed**（`SANDBOX_UNAVAILABLE`）（实读本机源码） |
| **Codex** | 三档沙箱（`read-only` / `workspace-write` / `danger-full-access`）；**`workspace-write` 下默认断网**；**execution policies**（Starlark `prefix_rule`，`allow`/`prompt`/`forbidden`，**在沙箱之前评估**）；越界与联网要人批（核实官方文档） |

### 但围栏必须围住四件事，缺一件等于没围

| # | 围什么 | 怎么围 |
|---|---|---|
| 1 | **写越界** | 引擎自己的沙箱模式（`workspace-write`） |
| 2 | **危险命令** | 引擎的执行策略（`forbidden` 规则）或平台侧命令白名单 |
| 3 | **网络出口** | ⭐ **默认断网 + 白名单代理**。**gVisor 挡不住 `curl`**，这层必须单独做 |
| 4 | **逃生门** | ⭐ **参数白名单**：`--dangerously-bypass-approvals-and-sandbox` / `--yolo` 这类开关**不允许透传**（不是"约定不用"） |

### ⭐ 围栏方案带来的一个必须重新设计的点

**agent 的原生工具不经过我们的连接器网关，那数据视窗怎么生效？**

❌ "在提示词里告诉它别读那些字段"——**这不是控制措施**（`19` §3.4 已定死）。

✅ **数据视窗的出口在"喂进沙箱的数据"上**：平台把裁剪后的数据**物化**成沙箱内的工作文件，
agent 的原生工具只看得见这个文件，**它根本没有原始数据可读**。

**这把数据视窗从"agent 看不看得到"变成"沙箱里有没有"——是物理隔离，不是君子协定。**
详见 [`50`](./50-agent-tech-architecture.md) §3.4。

### 修正后的引擎选型判据

> 判据**不是**"能不能被接管工具"，而是——**能不能被围栏**。选引擎时问四句：
> ① 有没有沙箱模式 ② 沙箱拿不到时是否 **fail-closed** ③ 网络能不能**默认断** ④ **参数能不能白名单化**（封掉逃生门）

## 4. 预算怎么切

| 规则 | 为什么 |
|---|---|
| **切出去的是额度，不是共享池** | 一个子 agent 失控不能烧掉整个任务的预算 |
| **父级必须留一部分给自己** | 全分出去的话，父级最后没有余额做汇总和交付 |
| **子 agent 没花完的，显式回收** | 不自动回流——否则并发时会出现"两个子 agent 都以为还有余额" |
| **分配依据是任务复杂度，不是平均分** | 平均分会让简单任务浪费、复杂任务不够 |

**"父级必须留一部分"是实操里最容易漏的**：不预留的话，所有子 agent 跑完，父级发现自己没钱把结果汇成交付物了。

---

## 5. 结果收敛：子 agent 的自述不可信

**子 agent 说"我做完了"不算数。** 它可能：
- 只做了一部分，但报告说完成了
- 拿到了它不该拿的数据
- 用了一个你不认识的能力

所以回传的东西必须能验证：

| 回传 | 用来验证什么 |
|---|---|
| **结构化结果**（符合声明结构） | 结构不对 = 直接拒收 |
| **用了哪些能力、各调用了几次** | 对得上你的网关日志吗 |
| **消耗明细** | 对得上你的计量吗 |
| **结束原因**（完成 / 超预算 / 放弃 / 出错） | 区分"真的做完了"和"我不干了" |

> **"结束原因"必须由平台裁决**（[`07`](./07-engine-shell-boundary.md) 第三条边界）：
> 引擎说"完成"，平台要能验证结果符合结构、能力调用在权限内——**否则"完成"只是它的一面之词**。

---

## 6. 失败了怎么说清楚

和连接器的失败分类一样（[`04`](./04-connectors.md) §4.1），**不能糊成一个 `error`**：

| 失败类型 | 父级该怎么做 |
|---|---|
| **任务做不了**（能力不足 / 信息不够） | 换个思路，或降级交付 |
| **无权限** | **停下来**，不要重试、不要绕路 |
| **超预算** | 收下部分结果，自己收尾 |
| **系统故障** | 可重试 |
| **结果不合结构** | 拒收，要么重派要么自己补 |

**"无权限"和"系统故障"绝不能混**——混了以后父级会不停重派，**在审计上看起来就像在试探越权**。

---

## 7. 和主 agent 的边界

一个容易糊涂的地方：**子 agent 产出的东西，算不算交付物？**

我的主张：**不算。** 子 agent 的产出是**中间材料**，只有主 agent 的产出才是交付物，才走 §2.2 的状态机和审批。

理由：**审批的对象必须是"一个明确的责任主体产出的东西"**。如果子 agent 的产出直接进审批，那就没人能解释"为什么是这个结果"了（`explain` 要求的是主 agent 的依据）。

---

## 8. 待决问题

1. **第一批要不要做子 agent？**
   **✅ 已改（Day 2）：第一批就要做。** 之前的"先不做"是错的——备货任务的核心就是并行派异构子代理查多个数据源（销量/库存/物流/验证），不是"锦上添花"。相关新概念见 [`19`](./19-platform-vs-agent-boundary.md) 与岗位包的"任务编排"块。

2. **深度上限 2 层够不够？**
   够的话好办。如果某个场景真的要 3 层，那说明任务分解方式可能有问题——**先看是不是岗位包该拆成两个岗位，而不是靠递归解决。**

3. **要不要支持"异构子 agent"（同一个任务派给两个不同引擎比对）？**
   好处：能对比哪家做得好，也能互相纠错。代价：双倍成本。
   **我倾向先留接口不做实现**，等主 agent 稳定了再说。

4. **子 agent 的记忆怎么算？**
   它有没有自己的数字员工记忆？我倾向**没有长期记忆**——子 agent 是"用完即走"的，记忆留在主 agent 那一层。否则记忆的所有权会变得很乱。**且它的数据视窗只能比父级更窄、不能更宽**（[`34`](./34-data-view.md) §6）。
