# 细化 ④-B：上下文工程

> 父文档：[`architecture.md`](./architecture.md) §12 细化路线 第 ④ 项
> 边界依据：[`19-platform-vs-agent-boundary.md`](./19-platform-vs-agent-boundary.md) §3.4 —— **上下文"组装机制"归 agent，"准入规则"归平台**。
> ⚠️ **本文只讲原则**；**具体数值与实现**见 [`23`](./23-rw-port-parts-detail.md)（spill/修剪/压缩）与 [`24`](./24-on-demand-recall.md)（按需召回）——**避免两处各说一套**。
> 为什么重要：**它是成本的主要来源，也是提示词注入的第一现场。** 你实测自研比成熟框架贵 2–3 倍——差距大概率就在这里。

---

## 0. 一条总原则

> **上下文是花出去的钱，不是"信息越多越好"。**

每一段塞进上下文的东西都在付两种费：**token 的钱**，和**注意力被稀释的代价**（东西越多，模型越抓不住重点）。

**判据：这一段不进上下文，agent 会不会做错？不会，就别放。**

这条判据要贯穿下面所有设计。

---

## 1. 上下文分五层，按"稳定度"排序

**这是整份文档里最值钱的一张表**，因为它同时决定了缓存和成本。

| 层 | 内容 | 什么时候变 | 能不能复用 | 放哪 |
|---|---|---|---|---|
| **系统层** | 岗位包生成的身份、职责、边界 | 只有岗位包换版本才变 | **最稳定** | **最前** |
| **工具层** | 工具 / 能力清单（**已按权限过滤**） | 只有权限变才变 | 稳定 | 紧接系统层 |
| **知识层** | 检索到的知识、技能 | 每次不同 | 不稳 | 中段 |
| **任务层** | 本次任务、目标、交付物结构 | 每次不同 | 半稳定 | 中段 |
| **结果层** | 工具返回 | 每次都变 | 最不稳 | **最后** |

### 为什么这个顺序重要

成熟框架之所以便宜，很大一部分原因就是**它把最稳定的那几段做成可以复用的**——同样的前缀重复出现时，不用重新算一遍。**如果你的自研每次都把上下文重新拼一遍，前缀就永远命中不了，那部分钱就白花了。**

> ⚠️ **这是推断，不是结论。** 但它和你观察到的事实一致（同模型、差 2–3 倍），而且是最容易验证的一条：**先去看你的每次调用，前缀部分是不是稳定的**。如果每次开头都不一样，这就是主因。

### 落地的三条纪律

1. **最稳定的放最前面，最易变的放最后面**——顺序本身就是钱
2. **不要为了让提示词"看起来更完整"而加东西**——加进系统层的东西会让缓存失效
3. **每次运行的系统层 + 工具层应该逐字节一致**（同一版本岗位包 + 同一权限）——不一致就是漏了

## 2. 工具结果是膨胀的主因

绝大多数自研 agent 的成本失控，出在"把工具返回原样塞回去"。

**四条纪律：**

| # | 纪律 | 说明 |
|---|---|---|
| 1 | **结构化，不要倾倒** | 连接器返回的是结构，不是一大段文本 |
| 2 | **有大小上限** | 超过就截断，并明确标记"被截断" |
| 3 | **大结果落盘，上下文只留摘要 + 引用** | agent 需要细节时再去取 |
| 4 | **保留什么由岗位包声明** | 不是引擎临场决定 |

**第 3 条最被低估。** 一次查询返回 5000 行，正确做法不是"截前 100 行"（agent 会以为只有 100 行），而是：

```
上下文里：  "查到 5000 行，摘要：……；完整结果在 result://run-123/inventory-1，
            需要时用 fetch 取回指定范围"
```

这样既没撑爆上下文，也没丢信息，而且**agent 知道自己不知道什么**——这比给它一个残缺的数据强得多。

> **具体数值与实现见 [`23`](./23-rw-port-parts-detail.md) §2/§3**（spill 阈值 32768 字节、预览头尾对半；修剪 8192/4096/1024）。**本文只讲原则，不重复数值。**

## 3. 提示词注入的防御在这里做

这是"**上下文准入归平台**"（[`19`](./19-platform-vs-agent-boundary.md) §3.4）这条边界最要紧的理由。

### 三层防御

| 层 | 做什么 |
|---|---|
| **来源标注** | 每一段进来都标清楚它从哪来：用户输入 / 检索文档 / 工具返回 / 外部网页 |
| **信任分级** | 不同来源的信任等级不同。**来自外部的内容不能改写系统指令** |
| **结构隔离** | 外部内容用明确的边界包起来，在结构上就区分于指令 |

**核心思路**：不要指望"在提示词里告诉它别听外面的话"——**要让外部内容在结构上就没有资格当指令。**

### 和 §1 的关系

系统层和工具层是**平台生成、可信的**；知识层和结果层是**外来的、不可信的**。

**所以顺序不只是为了缓存，也是信任边界**：可信的在前、不可信的在后，中间有明确分界。

> ⚠️ **一个具体风险**：如果让 agent 把"上一次工具返回的内容"写进系统层或知识层，可信区就被污染了。**这条要在平台侧堵死，不能靠 agent 自觉。**

## 4. 权限过滤在进上下文之前

和 [`07`](./07-engine-shell-boundary.md) §2 呼应：**agent 拿到的工具清单是过滤后的。**

所以上下文里**根本不存在越权的目标**。这比"调用时再拦"强——拦的那道可能被绕过，看不见的没有绕法。

## 5. 压缩：什么时候压、压什么、什么绝对不能压

| 问题 | 答案 |
|---|---|
| **什么时候压** | 接近上限时。不要等满了才压 |
| **压什么** | 先压最老的、最不相关的（工具返回里的原始细节优先） |
| **绝对不能压** | **交付物的依据**（`explain` 要求的那部分）、审计需要的信息 |
| **压完怎么留痕** | 两份都留：**压缩摘要**进上下文，**原始轨迹**入审计 |

> **"绝对不能压交付物的依据"是个具体的坑**：如果压缩时把"为什么算出来是这个数"的来源删了，人复核时就看不到解释，`explain: required` 就成了空话，审计链也断了。

> **触发条件与比例见 [`23`](./23-rw-port-parts-detail.md) §4**（比例制：模型窗口的 **80%** 触发、保留 **16%**）。**本文只讲"什么绝对不能压"这条原则。**

## 6. 预算控制（**平台**裁决）

[`07`](./07-engine-shell-boundary.md) §3 的第三条边界：**结束与预算由"平台运行时"裁决**（旧称"壳"，术语见 [`19`](./19-platform-vs-agent-boundary.md) §1——按 `19` §3.3/§3.4 的拆法，**预算与准入归平台**），agent 说"我还想继续"不算数。

四种预算同时管：

| 预算 | 超了怎么办 |
|---|---|
| token | 见下面的降级策略 |
| **钱** | 同上——这是最硬的一条 |
| 步数 | 强制收敛：要求给出当前最优结果 |
| 墙钟时长 | 优雅中止，**保留已产出的部分结果** |

### 6.1 接近预算时怎么"软着陆"

硬停会让人白等一场。**更好的做法是逐级降级：**

```
消耗到 70%  →  提示 agent 收敛（减少探索、少做检索）
消耗到 85%  →  换便宜模型收尾（规划已经做完了，收尾不需要强模型）
消耗到 100% →  优雅中止，交付已完成的部分 + 说明还差什么
```

**"换便宜模型收尾"是个实用技巧**：一个任务里，最贵的往往是最初的规划和最后的润色，中间的执行可以便宜。全用同一个模型，是成本高的常见原因之一。

### 6.2 省钱的顺序（按性价比）

1. **上下文组装**（§1、§2）——省得最多，且是一次性的架构工作
2. **模型分级**——规划用强模型，抽取 / 格式化 / 收尾用便宜模型
3. **缓存命中**——稳定前缀
4. **减少步数**——把"确定的规则"固化成配置，不要让模型每次现场推理（**这正好是岗位包存在的意义**）

> **第 4 条值得单独记住**：**"用更少的步骤干完同一件事"才是自研真正的理由。** 你比通用框架懂这家客户的业务，你知道该看哪几张表、哪几个字段——通用框架只能靠模型现场摸索，**摸索就是烧钱**。

## 7. 待决问题

1. **缓存的具体做法由谁决定？**
   不同厂商的缓存机制不同（有的自动、有的要显式标记）。**我倾向：平台提供"稳定的前缀"这个事实，具体怎么标记交给适配器。**

2. **工具结果落盘的引用机制，做到什么程度？**
   简单版：只给摘要 + 一个句柄。复杂版：支持 agent 按范围取回、按条件再查。
   **我倾向先做简单版**，因为更好的做法常常是"让它重新用连接器查一次"，而不是"把大结果存着"。

3. **压缩由平台还是引擎做？**
   [`07`](./07-engine-shell-boundary.md) 说部分接管。我的具体倾向：**"压什么"由平台定（哪些不能压是业务决策），"怎么压"交给引擎**（它是引擎的强项）。

4. **来源标注要做到多细？**
   粗：只标"外部 / 内部"。细：标到具体连接器、具体文档、具体行号。
   **我倾向细**——因为复核的人需要知道"依据是哪来的"，这直接关系到交付物的可信度。
