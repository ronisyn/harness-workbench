# 22 · 任务编排与子代理调度

> 状态：方案，技术决策由我拍。
> 前置：`09`（子代理）、`19`（归属修订）、`03`（岗位包九块第 5 块）
> 这是三层结构的**交汇点**：岗位包声明（模板）→ 平台执行（调度）→ agent 提供（子代理机制）。

---

## 0. 一句话 + 三层拆分

一个岗位的活，被拆成几个子代理并行干，平台调度、回收、汇总。

```
岗位包：声明「备货 = 销量子代理 + 库存子代理 + 物流子代理 + 验证子代理 → 汇总」
平台：  拆解 + 权限收缩 + 预算切分 + 并发调度 + 回收 + 汇总 + 审计
agent： 提供「跑一个子代理」的能力（引擎 + 工具）
```

---

## 1. 任务编排模板（岗位包第 5 块）——长什么样

**我拍：模板是"声明"，不是代码。**

**理由**：岗位的活是**稳定的业务结构**，声明式够用，而且能审计、能由客户在覆盖层改。如果模板变成代码，就回到"每个岗位写代码"的老路。

**结果**（模板的样子）：

```yaml
编排:
  备货计划:                          # 这个岗位的一个任务类型
    子代理:
      - 角色: 销量分析
        用: [sales.query]             # 只给它这些连接器能力
        产出: 销量趋势
      - 角色: 库存分析
        用: [inventory.query]
        产出: 库存与库龄
      - 角色: 物流方案
        用: [logistics.query]
        产出: 路线/时效/成本
      - 角色: 提报核验
        用: [report.query]
        产出: 提报与实际差异
    关系: 并行                        # 并行 | 串行 | 混合
    汇总: 
      方式: 智能                       # 规则（确定性合并）| 智能（主 agent 综合）
      交付物: 备货计划单
```

客户能看、能改（在覆盖层加一个子代理、调连接器），不用写代码。

---

## 2. 调度器（平台执行）——怎么跑

**我拍：调度器是平台的一等能力，所有 agent 共用。**

**理由**：三个 agent 都要能跑"备货"这个编排，调度逻辑不能长在某个 agent 里，否则换个 agent 就得重做调度。

**执行步骤**：
1. **拆解**：按模板创建 N 个子代理任务
2. **权限收缩**：每个子代理只给"它声明要用的连接器"（见 §3）
3. **预算切分**：父任务预算分给子代理（见 §4）
4. **并发调度**：按"关系"并行/串行跑
5. **回收**：每个子代理返回结构化结果
6. **汇总**：按模板声明的汇总方式（见 §5）
7. **审计**：全程记（谁派了谁、各用了什么、花了多少）

**结果**：调度逻辑写一次，roni / DS / codex 都能被它驱动。

---

## 3. 子代理的权限收缩

> **原则的权威在 [`09`](./09-subagent-orchestration.md) §2**（四条硬约束）；**本节只讲"编排时怎么落地"，不重复原则**。

**我拍：子代理的权限 = 岗位包能力 ∩ 它声明要用的能力；工具清单过滤后下发。**

**理由**：铁律二（能力单调不增）。查库存的子代理不该看到"物流"连接器，更不该看到"写"权限。

**结果**：
- 查库存的子代理，它的工具清单里**只有** `inventory.query`——物流、写库、外发都不出现（不是"出现了但被拦"，是"根本不出现"）
- 子代理之间互相看不见对方在查什么
- 即使某个子代理被注入劫持，它能碰到的也只是"查库存"这一个动作

---

## 4. 预算切分

**我拍（沿用 `09` 已定的四条，这里落地）：**
1. 切出去的是**额度**，不是共享池
2. **父级必须留一部分给自己**（否则跑完没钱做汇总）
3. 没花完的**显式回收**，不自动回流
4. 按**复杂度**分，不平均分

**结果**：一个子代理失控（陷入循环烧钱），烧掉的只是它自己的额度，拖不垮整个任务。

---

## 5. 结果回收与汇总（两种汇总）

**我拍：汇总分两种——规则汇总（确定性）+ 智能汇总（主 agent 综合）。模板声明用哪种。**

**理由**：有些汇总能确定（把几个表按字段合并），有些必须判断（备货量要综合销量+库存+物流+提报一起算）。

| 汇总方式 | 谁做 | 适用 |
|---|---|---|
| **规则** | 平台（确定性代码） | 字段合并、差异清单、去重——不需要判断 |
| **智能** | 主 agent 的引擎 | 备货量、补货节奏——需要综合判断 |

**结果**（以备货为例）：
- 4 个子代理各自返回结构化结果
- "提报核验"的差异 → 规则汇总成"差异清单"（确定性）
- "备货量" → 主 agent 引擎读 4 个结果，综合算出，并生成"为什么是这个数"（`explain`）

---

## 6. 失败处理

**我拍：一个子代理失败 → 标注"这块数据缺失"，其余继续跑，不整体崩。**

**理由**：数据缺失比整体失败好。备货计划可以"库存数据未取得"地交付，让复核的人一眼看到；而不是因为库存没查到，整个备货计划都不出了。

**结果**：
- 失败的子代理 → 汇总时那块标注"未取得 + 原因"（超预算 / 无权限 / 系统故障）
- 关键子代理失败（比如销量都没查到）→ 可选重试一次；仍失败则降级交付，明确标注
- 复核的人看到交付物就知道"哪块是空的"

---

## 7. 批量并发（模板 × N 份）

**我拍：批量 = 一次触发，把同一个模板跑 N 份（16 平台 = 16 份"备货计划"），并发上限由平台统一管。**

**理由**：16 平台备货是"同一个活 × 16 份"，不是 16 个不同的活。而并发上限是**成本闸门**（`10` 里说过：并发任务数是唯一能主动控制的成本杠杆，因为每个任务吃一个沙箱）。

**结果**：
- 触发一次"批量备货"，平台拆成 16 个"备货计划"模板实例，受并发上限约束（比如同时最多 4 个在跑，其余排队）
- 16 份交付物各自独立（16 个平台各一份备货计划），不合成一份
- 每个实例内部，又各自派自己的 4 个子代理

**层级关系**：`批量 → 任务实例 → 子代理`。批量是"×N 份"，任务实例是"1 次编排"，子代理是"编排里的一个分支"。

## 8. 与"脚本化 workflow"的边界（为什么它后置）

| | 任务编排模板（现在做） | 脚本化 workflow（后置） |
|---|---|---|
| 谁定义 | 岗位包声明，客户能改 | 开发者写 JS |
| 结构 | 固定（备货永远是那 4 个子代理） | 任意、异构、分阶段 |
| 门槛 | 配置 | 编程 |
| 服务对象 | 业务岗位 | 一次性复杂任务 / 平台侧高级编排 |

**我拍：声明式模板覆盖"岗位的稳定结构"，够第一批用；脚本化留给"一次性复杂任务"，后置——但接口上留位置，将来插一个"脚本式编排器"即可，不用重构。**

---

## 9. 待决（都是可后置的技术细节，我先给了默认值）

| 项 | 我的默认 |
|---|---|
| 批量并发默认上限 | 同时 4 个（可配置），保护沙箱池和成本 |
| 子代理超时 | 每个子代理独立预算 + 时长上限；超时=失败，走 §6 标注缺失 |
| 汇总的"智能"步骤用哪个引擎 | 用主 agent 当前配的引擎（降级链同岗位包） |
| 子代理能否再派生子代理 | 否，深度上限 1（`09` 已定 max depth 2，这里收严到"任务编排内只一层"） |

---

## 10. 结果总览（做完后是什么样）

- 备货岗位 = 一个模板：4 个子代理并行查数 → 主 agent 综合算备货量 → 出"带依据、带缺失标注"的备货计划单
- 16 个平台 = 一次批量触发，16 份并行（受并发上限保护）
- 任何一个子代理、任何一份都**权限窄化、预算独立、全程审计**
- 三个 agent（roni/DS/codex）都能被同一个调度器驱动，换 agent 不重写编排
