# 33 · 知识层（知识库 / 数据层 / 与经验的边界）

> 状态：方案，技术决策由我拍。平台侧补充议题 ①（复盘发现的最大空白）。
> 前置：`24`（按需召回）· `29`（经验管理）· `04`（连接器）
> 由来：复盘发现——**"知识库"只在 5 份文档里泛泛出现，没有专门设计**。而它是"数字员工越用越聪明"的另一半。

## 0. 一句话

**知识层回答"数字员工知道什么"，经验层（`29`）回答"它学到了什么"。两者缺一不可。**

**现状**：经验层已有设计（`29`），**知识层是空白**——它不定，`29` 和 `24` 都悬空。

---

## 1. 知识层包含三块（不同类型，不同处理）

**核心原则（沿用）：能精确查的，别让模型记。**

| 块 | 装什么 | 怎么用 | 谁来 |
|---|---|---|---|
| **① 数据层** | **结构化数据**：历史备货表、库存记录、SKU 对照表 | **精确查询**（走连接器，不进上下文、不进向量库） | 连接器（`04`）读，本层存 |
| **② 知识库** | **非结构化文档**：SOP、政策、合同、历史邮件 | **按需检索**（全文打底、向量留位） | 本层 |
| **③ 经验库** | agent **自生**的判断 | 按需召回 | `29` |

**这三块的分界一句话**：

> **需要精确数字的 → 数据层；需要读懂意思的 → 知识库；数字员工自己悟出来的 → 经验库。**

---

## 2. ⭐ 知识 vs 经验的边界（最容易混，这里定死）

| | **知识**（本层） | **经验**（`29`） |
|---|---|---|
| 来源 | **外来**——人给的、系统里抓的 | **自生**——干出来的 |
| 谁写 | **人**（技术团队/业务用户上传） | **agent**（+ 人确认归类） |
| 例子 | "美西仓安全库存按 30 天算"（写好的 SOP） | "这家的采购员习惯多留 3 天"（改出来的） |
| 什么时候变 | **源变了**才变 | **持续积累** |
| 有无有效期 | 有（源文件更新就过期） | 有（`29` 的防腐） |
| 管理方式 | **摄入 → 更新 → 失效** | **五维沉淀 → 防腐** |

**判据**：

> **"这句话是我告诉它的" → 知识；"这条判断是它自己攒的" → 经验。**

**一个边界例子**：客户发来一份新的《备货 SOP》→ 进**知识库**。
执行三个月后，agent 发现"SOP 里说 30 天，但美东实际要 35 天"→ 这条**观察**进**经验库**（策略维），并**提示人来更新 SOP**。

**→ 这就是知识和经验的双向流动**：知识指导经验形成，经验反过来推动知识更新。

## 3. 知识怎么进来（摄入管线）

```
来源                识别类型             去处
─────────────────────────────────────────────────
文件上传（Excel/PDF/Word）
连接器抓取（ERP/中台）  →  结构化？  →  ① 数据层（精确查询）
IM 消息（钉钉/飞书）             ↓
手工录入              →  非结构化？ →  ② 知识库（分块 + 索引）
```

**关键设计（我拍）**：

| 项 | 决定 |
|---|---|
| **类型识别** | **不让模型猜**——按来源和格式定（Excel 且带字段 → 结构化；PDF/Word → 非结构化） |
| **分块** | 非结构化文档分块时**保留出处**（哪个文件、哪一页）——用于引用和追溯 |
| **幂等** | 同一份文件重复摄入**不产生重复知识**（按内容哈希去重） |
| **归属** | 每一条知识**必须挂到** `客户 → 工作区`（`26` 的归属链） |

**为什么"保留出处"重要**：`24` 说召回要"带来源"——复核的人得知道**这条依据从哪来**。

### 3.1 多模态：入库 ≠ 能检索（Day 3 补）

**上面那张管线图有个漏洞**：它假设进来的东西"本来就能读"。但现实里大量的知识是**扫描件、截图、PPT、Excel 里的图表**——**存进去了，却检索不到**。

| 形态 | 处理 | 做不到会怎样 |
|---|---|---|
| 文本 PDF / Word / 邮件 | 直接抽取 | —— |
| **扫描版 PDF / 拍照件** | **必须过 OCR**，否则只能当附件存着 | 客户传了合同，agent 说"我查不到" |
| Excel / CSV | 表格→**数据层**；单元格文字→知识库 | 装进知识库就变成"读不懂的一大块" |
| PPT / 图片 | 抽取文字 + **保留图本身**（有些信息在图里） | 图里的流程说明彻底丢失 |
| 音视频 | **本版不做**，只登记"有这个源、需要时人工转写" | 别假装支持 |

**两条纪律**：
1. **解析失败要显式报错，不能静默入库**——"入库成功但检索不到"比"入库失败"更糟，因为没人会去查
2. **原件永远保留**（`§3` 的幂等按原件哈希）；解析结果只是**派生视图**，可重解析（OCR 引擎升级后能重跑）

### 3.2 ⭐ 对话产生的知识：必须人确认，永不自动入库（Day 3 补）

**风险**：客户在对话里随口说了一句"我们华东仓一般留 45 天"，agent 把这句话当知识存进库——**下次它就拿这句随口话当规则用了**。而且这句话可能是错的、过期的、或者是**别的客户**说的。

**我拍（硬规则）**：

```
对话里产生的内容
   │
   ├─ 属于「承诺/待办」（"周二给你"）  → 进记忆（`29`），不进知识库
   ├─ 属于「本次任务的事实」           → 进会话/运行上下文，用完即散
   ├─ 属于「外部事实」（第三方信息）    → 不可信，进上下文但不入库
   └─ 属于「可复用知识」（规则/口径/SOP）
          ↓
       ① agent 提议："这句话看起来是一条可复用的规则，要入库吗？"
          ↓
       ② 人确认（要说明**归属到哪一层、哪个知识集**）
          ↓
       ③ 入库，并记「来源 = 对话 + 谁说的 + 什么时候」
```

**为什么必须人确认（三条理由，任何一条都够）**：
1. **对话是低质量信道**——口语省略、半句话、说错又改口
2. **说话的人不一定有权限**——一个业务用户随口定的规则，不该变成全公司的知识
3. **入口是投毒面**——知识会进 agent 的上下文，**入库就是"让外部内容持续影响模型行为"**，这是攻击面（同 `08` §3 的可信度分层）

**归属默认值（减少人的负担）**：默认挂到**说话人所在的工作区**，**不挂到数字员工**（一个人说的不该只给一个员工用）。要挂更高层（客户级）必须**客户技术团队**确认。

> 与 `29` 的一致：经验是 **agent 提议 → 人确认**（`29` §3）；知识是 **agent 提议 → 人确认**。**同一个三段式，别做两套。**

### 3.3 一份源文件可能同时进三层（Day 3 定）

**你的合同/价格单场景**：一份合同里有**结构化的价格表**、**非结构化的条款**，还带**版本**。

**我拍：允许"一份源文件 → 多层落点"，但共用同一个"文档身份"。**

```
一份《2026 年度采购合同.pdf》
   ├─ 价格表/账期/生效日期  → ① 数据层（结构化，精确查询）
   ├─ 条款正文              → ② 知识库（分块 + 索引）
   └─ 版本号/生效区间        → 挂在【文档身份】上，三层共用
```

**关键：`文档身份`（document id）是一等对象**，三层记录都指回它。这样才能回答"**这条数据的出处是哪份文件**""**这份合同改版后，哪些知识过期了**"。

**为什么不强行放一处**：三层要的处理方式完全不同（精确查询 / 检索 / 生命周期），硬放一处必然有一头做不好——**这正是"一份文件只属于一层"这个简单规则会翻车的地方**。

## 4. 知识怎么存（隔离与新鲜度）

### 4.1 隔离（我拍：与治理层一致）

| 层 | 隔离 |
|---|---|
| **客户** | 独立存储空间（物理隔离前缀） |
| **工作区** | 独立命名空间 |

**一条硬规则**：**检索时先按归属过滤，再算相似度**——绝不能"先检索全库、再过滤"（那意味着别的客户的内容进过内存）。

### 4.2 每条知识带三样元数据（我拍）

| 元数据 | 用途 |
|---|---|
| **出处** | 哪个文件/哪个系统、哪一页——用于引用与追溯 |
| **摄入时间** | 判断新旧 |
| **来源的更新时间** | 判断源是不是已经变了 |

### 4.3 ⭐ 分层归属（Day 3 补：知识归谁、谁能用、谁能改）

**上面 §3 只写了"必须挂到 客户 → 工作区"，不够用**——平台自己也要有知识，而且知识该按**可见范围**分级。

| 层 | 装什么 | 谁能改 | 谁用得上 |
|---|---|---|---|
| **平台级**（跨客户） | 平台自带的**通用知识**：行业通识、平台功能说明、内置模板 | ⚠️ **见下方修正：不能只有平台运营方** | 所有客户（**只读**） |
| **客户级** | 这家客户的**公司级口径**：财务制度、公司政策、通用合同模板 | 客户技术团队 | 该客户下所有工作区 |
| **工作区级** ⭐ | 这块业务的知识：SOP、历史邮件、**岗位相关文档** | 客户技术团队 + 该工作区业务用户 | 该工作区 |
| **数字员工级** | 只跟这一个员工有关的：它的专属作业指引 | 该员工的管理人 | **该员工自己** |

> ⚠️ **修正（Day 7，P0-1 的一半）**：原文"**平台级知识只有运营方写、客户只读**"——**这等于运营方能往客户数字员工的脑子里塞东西**。
> 对抗性评审把它列为 P0：平台方**同时掌握配置下发权和知识写入权**，而知识会进数字员工的上下文，**影响它的每一次判断**。
>
> **改为**：
> | 谁 | 能做什么 |
> |---|---|
> | 平台运营方 | 可以**提供**平台级知识（起草、放到"可选用"池） |
> | **客户技术团队** | **决定采纳哪些**——采纳了才对该客户的数字员工生效。**不采纳就不进上下文** |
> | 客户业务用户 | 不能碰平台级知识 |
>
> **一句话**：**平台方可以给，不能单方面"推送生效"。** 同 `06` §0.1 第 ④ 条。
>
> **连带**：技能（`12`）与插件（`32`）的"平台发布 → 客户生效"也要走同一条——**发布 ≠ 生效，客户采纳才生效**（`32` §5 的升级策略已经这么写了，这里明确它同样适用于知识）。

**三条定死的规则**：

1. **默认挂工作区**——这是最常见、也最安全的默认值（`03` §1.3 的同一思路：能窄就别宽）
2. **往上挂要更高权限**：挂到客户级要客户技术团队确认；**挂到平台级只有平台能操作**
3. **可见范围 = 层 × 知识集**：数字员工**不是"能看到该层全部知识"**，而是**只看它被授权的知识集**（`03` 第 2 块的"知识集"声明）。**归属决定"存在哪"，知识集决定"谁能取"。**

> **为什么必须区分"归属层"和"知识集"**：
> 客户级有 200 份文档，但"备货专员"只需要其中 5 份。如果只按层可见，它的检索空间里塞了 195 份无关内容——**召回质量下降、上下文被污染、还可能命中不该看的**。
> **归属是存储维度，知识集是权限维度**，两个都不能省。

### 4.4 ⭐ 数据层的版本化（Day 3 补：价格单、合同这类）

**你的场景**：供应商合同和价格单**会改版**，而且**新版本不能污染历史**——查"3 月份那批货的成本"必须用**当时生效的价格**，不能用今天的价。

| 项 | 我拍 |
|---|---|
| **数据层对象有身份 + 版本** | 同一份价格单的每次改版是一个**新版本**，不覆盖（同 `28` §2 交付物的版本规则） |
| **每版带生效区间** | `生效起 / 生效止`（或"至下一次改版"） |
| **查询必须带时间口径** | 查历史一律用**业务发生时间**匹配生效区间；**不允许"用最新版算历史"** |
| **改版的发现** | ① 连接器发现源变了 → 自动拉新版；② 人手动上传新版 |
| **改版的影响面** | 新版本入库时提示："有 N 条历史记录引用了旧版"——**不自动重算**（重算历史是业务决定，要人点头） |
| **未生效版本** | 可以提前录入（"下月起执行"），但**不进当前生效集** |
| **追溯** | 任一历史数字都能回答"当时用的是哪一版、哪一行" |

**为什么这条重要**：**价格/成本类数据的版本错误，是会直接算错钱的那类错误**——而且错得不明显（数字看着都合理，只是用了错的口径）。

## 5. 知识怎么更新与失效（借 `29` 的防腐思路）

**知识会腐烂**（SOP 改了、政策过期了），和 `29` 的经验一样需要治理：

| 腐坏 | 怎么发现 | 怎么处理 |
|---|---|---|
| **源更新了** | 连接器发现源变了 / 人重新上传 | **重新摄入**（幂等，替换旧版） |
| **源消失了** | 连接器报"取不到" | 标记**可疑**，提示人确认 |
| **政策到期** | 知识带**有效期** | 到期**不再参与检索**，提示复核 |
| **互相矛盾** | 新知识与旧知识冲突 | **入库时提示裁决**（同 `29` §4.2） |

**谁裁决**：人（同 `29`——涉及业务判断，系统只发现和提示）。

## 6. 知识怎么被用（接 `24`）

**按需召回，不预先注入**（`24` §2.2 已定）：

```
数字员工干活
   ↓ 需要知识时
查知识（工具调用）
   ↓ 先按归属过滤 → 再检索（全文打底，向量留位）
带出处的片段 → 进上下文
```

**三条纪律**：
1. **按需**——不用知识的轮次，一条都不带（`24` 验收标准 C1）
2. **带出处**——每段都标"来自哪个文件哪一页"
3. **可信度分层**——检索到的内容是**外来的、不可信的**，不能改写指令（`08` §3 + `19` §3.4）

### 6.1 ⭐ 检索要过数据视窗（Day 3 补：本文最大的漏洞）

**原文只写了"先按归属过滤再算相似度"——那只挡住了跨客户，挡不住"同一个客户内、不同数字员工之间"。**

**问题场景**：同一个工作区里有 A、B 两个数字员工，知识库里有一份《A 团队 8 月盘点表》。
B 的员工问一句相关的话，**按原文的规则（同客户 + 同工作区）它是可以检索到的**——**泄露就发生在客户内部**。

**定死：检索是"取数"的一种，必须过数据视窗（[`34`](./34-data-view.md)）。**

```
检索请求
  ↓
① 知识集过滤（这个员工被授权看哪些知识集）      ← `03` 第 2 块
  ↓
② 归属过滤（客户 → 工作区）                      ← §4.3
  ↓
③ 数据视窗过滤（行级：这份文档属于哪个团队/区域）  ← `34`，**新增的一层**
  ↓
④ 算相似度（在① ② ③ 都过滤完之后）              ← §4.1 的顺序原则不变
  ↓
带出处的片段
```

**顺序不能变**：**先过滤、后算相似度**（`§4.1` 已定）。"先检索全库再过滤"意味着**别的客户/别的团队的内容进过内存**——那已经算泄露了。

**召回结果回来之后还有一次机会**：如果某条知识的**值**是敏感的（成本、价格），召回时要按视窗**遮蔽或派生**（`34` §3-④）。

### 6.2 知识的容量与保留（Day 3 补）

**知识也会涨**（连接器每天抓、人每天传）。三条：

| 项 | 我拍 |
|---|---|
| **去重** | 按原件哈希幂等（§3）；**改版算新版本不算新知识**（§4.4） |
| **失效不等于删除** | 过期/被替代的知识**移出检索候选集**，内容保留（可查、可追溯）——同 `29` §4.4 的"下架 ≠ 删除" |
| **真删的两类** | ① 明确作废且人要求删；② 客户退出（随 `01` §6.4 密码学销毁） |

> **为什么"失效 ≠ 删除"对知识尤其重要**：知识是**依据**。三年前的一笔决策依据哪份 SOP，将来出纠纷是要能翻出来的。**检索不到 ≠ 不存在**——这是两个不同的动作，必须分开实现。

## 7. 谁维护

### 7.1 按身份分工

| 身份 | 能做什么 |
|---|---|
| **平台运营方** | 提供摄入管线与检索引擎；不碰客户知识内容（**唯一例外：平台级知识**，§4.3） |
| **客户技术团队** | 接知识源（连接器）、批量导入、配归属与知识集 |
| **客户业务用户** | 上传/更新自己岗位用得上的知识（如新的 SOP） |

**知识内容的修改门槛比技能还低**——它就是"内容"，不是逻辑。

### 7.2 ⭐ "必须遵守"的东西，不是知识（Day 3 补：最容易混的一处）

**这是本文最重要的边界，比"知识 ≠ 经验"还容易搞错。**

原文 §1 把所有知识都当成"**按需检索、可信度低的外来内容**"。但现实里有一类东西**不能只靠检索**：

| | **参考**（知识） | **必须遵守**（规则） |
|---|---|---|
| 例子 | "美西仓安全库存按 30 天算"（SOP 里写的） | "合同必须盖章才能发出" / "备货量不能突破滞销线" |
| agent 能不能不照做 | 能（它有裁量） | **不能** |
| 该放哪 | **知识库**（可检索、可引用） | **验证规则 / 岗位包 / 策略**（`28`/`03`/`26`） |
| 怎么生效 | 检索到 → 进上下文 → 影响判断 | **系统强制**：策略引擎拦、验证规则挡 |
| 违反了会怎样 | 结果可能不准 | **动作被拒/交付物被判不合格** |

**判据一句话**：

> **"它看到就会照做" → 知识；"它必须照做、不照做要拦住" → 规则。**
> **不能把"必须"寄托在模型的自觉上。**

**落地形态（拿你的合同场景）**：

| 内容 | 落在哪 |
|---|---|
| 合同条款正文、模板文字 | **知识库**（agent 写合同时检索、引用） |
| "必须走法务审批" | **策略/审批规则**（`06`：没审批就不放行） |
| "金额 > X 要两人批" | **策略**（规则算，不让模型感觉） |
| "合同要素要齐（甲乙方/金额/期限）" | **验证规则**（`28`/`29`：交付物被判不合格） |
| "我们的标准付款账期是 30 天" | **知识库**（是口径，不是强制） |

**反过来，"必须遵守"也有约束**：不能什么都在知识库里写一句"必须"就以为生效了。**凡是被当成"必须"的，必须有一个非模型的执行点在后面兜着**——要么策略引擎、要么验证规则、要么审批。

**编辑位置一览（回答"我去哪儿改"）**：

| 想改什么 | 去哪改 | 谁有权限 |
|---|---|---|
| 知识内容（SOP、文档、口径） | 知识库 | 客户技术团队 / 业务用户 |
| 结构化数据（价格、库存口径） | 数据层（走连接器或上传） | 客户技术团队 |
| 可复用的"怎么做" | 技能库（`12`） | 客户技术团队 |
| "必须遵守"的规则 | 策略 / 验证规则 / 岗位包 | 客户技术团队（**更高的门槛**） |
| agent 自己攒的判断 | 经验库（走人确认） | 人确认 |

## 8. 验收标准

| # | 标准 |
|---|---|
| K1 | 上传一份 SOP → 能被检索到，且**带出处**（哪个文件哪一页） |
| K2 | 上传一份历史备货 Excel → 进**数据层**，能被**精确查询**（按 SKU/时间），**不进向量库** |
| K3 | 同一份文件重复上传 → **不产生重复条目**（幂等） |
| K4 | 检索时**先按归属过滤**，跨客户内容**从不进内存** |
| K5 | 源文件更新后 → 知识能**重新摄入**；源消失 → 标记**可疑** |
| K6 | 知识带有效期，**到期不再参与检索** |
| K7 | 不用知识的轮次，上下文里**一条知识都没有** |
| K8 | 知识和经验**不混**：人给的内容进知识库，agent 攒的判断进经验库 |
| K9 | **一份扫描版 PDF** 上传后能被检索到（OCR 生效）；**解析失败会显式报错**，不静默入库 |
| K10 | **对话里说的内容不会自动进知识库**；agent 只能**提议**，人确认后才入库 |
| K11 | 平台级 / 客户级 / 工作区级 / 数字员工级四层知识**各自可见范围正确**；数字员工**只看被授权的知识集** |
| K12 | 价格单改版后：**查历史用当时生效的版本**；新版本入库时提示"N 条历史引用了旧版" |
| K13 | 同一工作区内，B 数字员工**检索不到** A 团队的知识（**数据视窗生效**，不只是跨客户隔离） |
| K14 | **"必须遵守"的规则被违反时会被拦**（策略/验证），而不是"检索到了但模型没照做" |
| K15 | 一份合同同时进数据层与知识库时，**共用同一个文档身份**，能互相追溯 |
| K16 | 失效知识**移出检索候选集但内容仍在**（可查、可追溯） |
