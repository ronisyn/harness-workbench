## 0. 一句话

**数字员工是"一堆授权的载体"。**

```
数字员工 = 岗位包（模板，全局不变）
         + 实例配置（数据视窗取值、连接器、触发方式、上限）
         + 一份「权责契约」（授权集合） ⭐
```

**所以它的生命周期，本质是「权责契约」的生命周期**——**契约签立、契约修订、契约中止、契约清算**。

**这一句决定了后面所有设计**：员工本身**不该"变"**（变的是契约），所以：

| 常见做法 | 为什么错 |
|---|---|
| 直接改数字员工的权限配置 | **改完就说不清"上个月它到底能干什么"**——审计和追责全断 |
| 员工要换职责时改它的配置 | 同上；且**历史交付物对不上它的权责** |
| **修订契约，生成新版本** ⭐ | 任一历史时刻都能回答"它当时能干什么" |

## 1. 先补上第五种寿命（`13` 只定义了四种）

`13` §0 定义了：交付物（月/年）、会话（天/周）、运行（分钟/小时）、沙箱（分钟级）。**这四种都在"一个数字员工之下"。**

**本文补上第五种，也是最长的两种之一**：

| 概念 | 寿命 | 归属 | 本文管什么 |
|---|---|---|---|
| **岗位包** | **全局**（跨客户、版本化发布） | 平台 | 只在"入职"时被引用 |
| **数字员工** ⭐ | **长**（月～数年），**身份终生不可迁移** | 工作区 | **本文** |
| **权责契约** ⭐ | **中**（随修订换版） | 数字员工 | **本文**（最容易漏的一层） |
| 交付物 / 会话 / 运行 / 沙箱 | 见 `13` | 见 `13` | 本文只管"退出时怎么处置" |

**关键推论**：

> **"数字员工活了多久"和"它能干什么"是两个问题。**
> 前者是一条身份线，后者是一串契约版本。**混在一起，退出时必然算不清账。**

## 2. 状态机（五个状态 + 两条不可逆边）

```
                        ┌──────────────┐
   ① 建  ──►  草稿 ──►  │   ② 在岗      │ ◄──┐
              (未上岗)   └──────┬───────┘    │
                               │            │ 复职（同一工作区，回归原有资产）
                        ┌──────▼───────┐    │
                        │   ③ 停用      ├────┘
                        │ (可恢复)      │
                        └──────┬───────┘
                               │ 退出（不可逆）★
                        ┌──────▼───────┐
                        │   ④ 已退出    │   身份与账本永久保留（tombstone）
                        │ (不可恢复)    │   资产按 §5 清算
                        └──────┬───────┘
                               │ 销毁（仅客户退出/合规要求时）
                        ┌──────▼───────┐
                        │   ⑤ 已销毁    │   密码学不可恢复（`01` §6.4）
                        └──────────────┘
```

| 状态 | 语义 | 可逆吗 |
|---|---|---|
| **草稿** | 配好了但没上岗。**不派活、不给数据视窗、不发凭证** | 可改可删 |
| **在岗** | 正常接活 | 可停用 |
| **停用** | **挂起**：不接新活，**已有资产与契约全部保留** | **可复职** |
| **已退出** | **离职**：契约终止、授权全部收回、资产清算。**身份永久保留** | **不可逆** |
| **已销毁** | 记录也删（仅客户退出或合规要求） | 不可逆 |

**两条不可逆边**（要显式确认，不能误触）：

1. **在岗/停用 → 已退出**：契约终止
2. **已退出 → 已销毁**：连身份记录都不留

> ⚠️ **"退出"与"销毁"必须是两件事**（沿用 `26` §1.1 租户生命周期的同一条原则）：
> **退出 = 停止工作 + 清算资产；销毁 = 连痕迹都不留。**
> 把两者合成一个动作，客户就只剩两个选择——要么不敢退出，要么一退全没了。

## 3. 入职：一条"一句话 → 上岗"的链（`37` 展开，这里只定接口）

```
一句话需求
   │
   ▼
① 生成【角色草稿】—— agent 提案：这个岗位干什么、不干什么、要什么数据、产出什么
   │
   ▼
② 人确认（三段式：agent 提议 → 人改 → 人确认，同 `29` §3）
   │
   ▼
③ 落成【岗位包】—— 领域无关的模板，**不含任何客户特有配置**（`03` §1.3）
   │  ⚠️ 第 ①–③ 步由【平台方/交付团队】完成，**不是客户做的**（`37` §0）——
   │     而且第 ③ 步之前要过【质量门 G1–G8】（`37` §4）
   │
   ▼  ────────── 以下是客户侧（实例层）──────────
④ 实例化【数字员工】—— 绑工作区、配数据视窗取值、配连接器、配触发方式、配上限
   │
   ▼
⑤ **上岗审核**（§4）—— 不通过不许上岗
   │
   ▼
⑥ 上岗 → 签发首版权责契约（v1）
```

**这套和现有的三段式完全一致**（`29` §3 经验、`33` §3.2 知识都是"agent 提议 → 人确认"）。**同一个模式用三次，不做三套。**

> ⚠️ **链上跨了两个责任主体**（Day 3 明确）：
> **第 ①–③ 步是平台方/交付团队的活**（造资产），**第 ④–⑥ 步是客户的活**（配实例）。
> **不要把它当成一条"客户自助流程"**——那会让岗位包失去资产属性（`37` §0）。

### 3.1 八步操作流程（每步产出什么）

> **上图的 ④–⑥ 在客户侧展开为八步**（本文 §3 与 §4.2、`37` 的关系）：
> `37` 管第 ①–③ 步（造包 + 质量门）；**本文管第 ④–⑧ 步（配实例 + 上岗）**。

| # | 步骤 | 谁做 | 状态 | 产出 |
|---|---|---|---|---|
| ① | 创建（选岗位库里的包或从零） | 客户技术团队 | 草稿 | 实例记录 |
| ② | 引导录入（一句话 → 角色草稿 → 人改 → 确认） | 交付团队协助 | 草稿 | 角色草稿（`37` 展开） |
| ③ | 配数据（数据视窗取值、接连接器、选知识集） | 客户技术团队 | 草稿 | 数据视窗 + 连接器清单 |
| ④ | 定权责（写权限、上限、复核人、下游） | 客户技术团队 | 草稿 | 权责清单 |
| ⑤ | 联调测试（§4.2） | 平台/客户 | 草稿 | 检查报告（按连接器分） |
| ⑥ | 生成上岗清单 + 人签字 | 客户技术团队 | 草稿 | 上岗验收报告 |
| ⑦ | 上岗：签发契约 v1 + 发服务身份与 Key + 挂触发 | 平台 | **在岗** | 契约 v1 + 凭据清单 |
| ⑧ | 通知相关人 | 平台 | 在岗 | 通知记录 |

**每一步都必须落数据，不能只是"做完了"。** 因为第 ⑦ 步之后这些数据就是**契约的内容**，第 ⑧ 步之后它们就是**审计的证据**。

## 4. ⭐ 上岗审核：没有它，"数字员工"只是一个聊天窗口

**这是本文最重要的新增机制。**

**问题**：客户建一个数字员工，如果不做任何检查就让它上岗，会出现：
- 它**能碰什么数据没定** → 要么什么都看不到，要么（更糟）什么都看得到
- 它**产出什么没定** → 产出没人接得住
- 它**错了谁负责没定** → 没人复核
- 它**能花多少钱没定** → 跑飞了才发现

**我拍：上岗前必须过一关，五项全绿才放行。**

| # | 检查项 | 不通过的后果 |
|---|---|---|
| **1** | **岗位包的职责边界已正确继承到本实例**（不是"有没有写"——那在 `37` 质量门 G2 查过了） | 它会越界 |
| **2** | **数据视窗已配全**（所有它能访问的数据源都声明了维度，`34` §3.4） | **漏一个就是后门** |
| **3** | **交付物与复核人已定**（谁接、谁复核、要不要解释） | 产出没人接 |
| **4** | **上限已定**（成本 / 时长 / 频次 / 并发，`30` §8） | 跑飞 |
| **5** | **触发方式已定**（手动 / 定时 / 事件 / 接口，`03` 第 6 块） | 不知道什么时候跑 |

> ⭐ **与 `37` 质量门的分工（Day 3 明确，避免同一件事查两遍）**：
>
> | | `37` 质量门 G1–G8 | `36` 上岗审核五项 |
> |---|---|---|
> | 查什么 | **这份岗位包（模板）写得对不对** | **这个实例（配置）配齐了没有** |
> | 谁查 | 平台方/交付团队 | 客户技术团队 + 平台 |
> | 时机 | 发布岗位包之前 | 上岗之前 |
> | 例子 | "职责边界是**可执行的**吗"（G2） | "职责边界**继承到这个实例了吗**"（第 1 项） |
>
> **一句话**：**`37` 管模板，`36` 管实例。** 两边都查，但**查的不是同一件事**。

**为什么这条值得单列**：

> **它把"配好了"从主观判断变成可检查的清单。**
> 而且它顺手解决一个销售问题——**客户能看见自己买的东西"配齐了"**。

**审核不通过的员工停在"草稿"态**：能被改、能被删，但**不派活、不给数据视窗、不发凭证**。

### 4.2 ⭐ 联调测试：环境是"连接器级"属性，不是"客户级"

**我上一轮把"环境"当成了客户的属性，这是错的。** 现实是：

> **同一家公司里，自研数据中台有测试环境，外采 ERP / Shopify / Amazon 只有生产。**

**所以环境标记下沉一层，挂在连接器（甚至能力）上**：

| 客户 | 连接器 | 有测试环境？ | 能做什么 |
|---|---|---|---|
| 同一家 | 数据中台（自研） | ✅ | **双跑对比**（含写操作在测试环境真跑） |
| 同一家 | ERP（外采 SaaS） | ❌ | **生产只读探测**；写操作**不可测** |
| 同一家 | Shopify / Amazon | ❌ | 同上，且写操作**直接影响生意** |

**可测性还是"能力级"的，不是"连接器级"的**——同一个 ERP，**读**可能能探，**写**没有测试环境：

| 能力 | 有测试环境 | 生产可只读探 | 结论 |
|---|---|---|---|
| 数据中台·读 | ✅ | ✅ | 双跑对比 |
| 数据中台·写 | ✅ | —— | 测试环境 dry-run |
| ERP·读 | ❌ | ✅ | **生产只读探测（唯一证据）** |
| ERP·写 | ❌ | ❌（不可逆） | **不可测 → 走 `06` §2.3 首跑护栏** |

> **一句话**：**"能测"不是客户的一个属性，是一张"哪些能力在哪儿能测"的矩阵。**

#### 4.2.1 用例声明（一套定义，多处运行）

```
检查项（用例）：平台定义，与环境无关       ← 只有一套
       ×
环境：参数不同，但可重复执行              ← 一次运行只针对一个环境
       ↓
执行报告（同一结构，带环境指纹 + 视窗指纹）
```

**硬判据**：

> **同一个检查项，在测试环境跑和在客户环境跑，用的是同一份定义。**
> **一旦为"预检"和"客户验收"写两套用例，两边迟早不一致**——那预检就失去意义了。

**检查项清单**：

| id | 检查什么 | 判定 |
|---|---|---|
| `conn.probe` | 连接器连通 + 凭据有效 | 能取到数据 |
| **`data_view.probe`** ⭐ | **用它自己的身份发一次探测查询** | **返回值确实是裁剪过的** |
| `deliverable.produce` | 交付物能生成、能导出、复核人能收到 | 端到端通 |
| `trigger.fire` | 手动/定时/事件能真跑 | 一次真实触发 |
| `cost.estimate` | 跑一次的实际消耗 vs 上限 | 不超上限 |
| **`reverse.reachable`** ⭐ | **反向通路**：客户系统 → 平台（对外接口 / Webhook 回调） | 回调能到达 |
| `write.dryrun` | 写操作走草稿链路（`06` L2） | **只在允许写测试的环境做** |

> ⭐ **`reverse.reachable` 容易漏**：`10` 定义了六种接入方式，**联调不能只测"我们连客户"，还要测"客户连我们"**。
> ⭐ **`data_view.probe` 是最值钱的一项**：视窗是"声明"，**只有真发一次查询才知道它生效了没有**——而且它**必须逐个连接器做**，不能合并成"整体通过"（测试连接器通过 ≠ 生产连接器通过，`34`）。

**四种结果状态**（不能只有"通过/失败"）：

| 状态 | 含义 |
|---|---|
| **通过** | ✅ |
| **失败** | ❌ |
| **跳过** | 有条件但这次没做（客户不想做 / 时间不够） |
| **不可测** ⊘ | **该连接器根本没有可测环境**——不是"没测"，是"测得不了" |

> ⚠️ **"不可测"必须在视觉上和"通过"完全不同**。否则报告会给人"全绿"的错觉，**而风险恰恰藏在 ⊘ 里**。

#### 4.2.2 报告按【连接器 × 能力】聚合

```
检查报告
├─ 数据中台   [测试] ✅6/6   [生产] ✅6/6   → 双跑，无差异
├─ ERP        [不可测] ——    [生产] ⚠️2/6
│     · conn.probe ✅   · data_view.probe ✅ ★   · write.dryrun ⊘
│     · reverse.reachable ✅   · trigger.fire ✅   · cost.estimate ✅
└─ Shopify    [不可测] ——    [生产] ⚠️3/6
      · data_view.probe ✅   · 写操作（上架/改价）⊘ ← 高风险
```

**指标口径要和 `30` 一致**：**清单 + 报告**，不含业务数据。

#### 4.2.3 双跑对比（"两种情况都会发生"的正解）

既然两边都会跑，**就不是"选一个跑"，而是"允许跑两次，然后把两份报告对比"**：

```
预检环境跑一次 → 报告 A（环境指纹 = 预检）
客户环境跑一次 → 报告 B（环境指纹 = 客户）
                      ↓
                自动对比，列出差异 ★
```

| 差异类型 | 说明什么 |
|---|---|
| **A 通过、B 失败** | **典型陷阱：预检通过 ≠ 客户环境能跑**（数据范围/网络/凭据/数据源版本都可能不同） |
| **视窗指纹不同** | 两个环境的裁剪规则不一致——**最该被看见的差异** |
| 某项跳过 | 客户侧缺条件 |

> **预检的价值不是"证明能跑"，而是"证明在我这儿能跑"。** 它**不能替代**客户环境验收，只能**减少**在客户现场卡住的概率。

#### 4.2.4 联调模式由"连接器矩阵"自动推导（客户不用选）

```
这次上岗要接的连接器里：
  有 full 的     →  这一部分走【双跑对比】
  有 readonly 的  →  这一部分走【生产只读探测】
  有 none 的     →  这一部分进【不可测台账】
  三者都有       →  三种同时生效（同一个员工、不同连接器）

最终签字：客户在【生产环境报告】上签一次
```

**所以模式不是三选一，而是"同一个数字员工身上三种都可能有"。**

**签字规则**：

| 概念 | 规则 |
|---|---|
| **报告** | 每个环境一份，都可留档（至少一份、至多三份） |
| **上岗批准** ⭐ | **只有一次**，且**必须由客户在"生产环境"的报告上签字** |
| **预检报告** | **不能作为上岗依据**，只能作为参考附件 |
| **对比报告** | 两份都在时自动生成，附件形式 |

#### 4.2.5 三条边界（不做清楚会出事）

**① 联调必须用专用测试数据，不能碰生产**
客户环境里那个生产员工，联调时会读**真实数据**。风险：污染、泄露、误判。
→ 用**专用测试数据集**或明确的**只读探测查询**，完成后再放行到真实范围。
→ 兜底：客户说"没有测试数据"→ 允许用真实数据做**只读探测**，但**必须留审计**，且**禁止写操作测试**。

**② 写操作联调：默认不在客户生产做**
`write.dryrun` 走 `06` 的 L2——**它仍然在客户系统里建了一张单子**。
→ **默认只在测试环境做**；要在生产做，必须**客户显式同意** + **专用测试单据 + 事后作废**。

**③ 网络隔离时用离线自检工具** ⭐
如果客户环境**不能从平台侧发起**（只能单向出网或完全内网）：

```
数据面自带自检脚本 → 在客户内网就地跑那七项 → 产出报告（带环境指纹 + 签名）
                    → 通过既有通道回传（或人工导出带回）
```

**好处**：**同一套检查项、同一个报告结构**，只是执行者从"平台"变成"客户内网的组件"。**架构不用改，只多一个执行位置。**

#### 4.2.6 条件上岗（不通过怎么办）

| 情形 | 处置 |
|---|---|
| 全部通过 | 正常上岗 |
| **非关键项跳过**（如 `write.dryrun`） | **可上岗**，报告标注跳过项 + 风险等级 + **定期重试计划** |
| **关键项失败**（`conn.probe` / **`data_view.probe`** / `trigger.fire`） | **不许上岗** |
| **视窗探测失败但客户坚持** | **不许上岗**——⭐ **唯一没有例外的一项** |

> **为什么 `data_view.probe` 没有例外**：其他项失败是"干不了活"，**这项失败是"能看到不该看的"**。风险量级不一样。

#### 4.2.7 不可测能力的补偿措施

选了"允许不可逆写"（A 方案）之后，**这块必须写清楚**：**没有测试环境，不等于没法控制风险**。

| 操作类型 | 处置 |
|---|---|
| **只读** | **照测**——生产只读探测就是唯一且充分的证据 |
| **可逆写** | **专用测试单 + 事后作废**，必须客户显式同意 + 留审计 |
| **不可逆写** | **走 `06` §2.3 的首跑护栏**（预演态 + 自动验证 + 成熟度阶梯 + 未验证台账） |

→ 完整设计见 [`06`](./06-approval-and-executor.md) §2.3。**`36` 与 `06` 的分工：`36` 管"上岗时怎么测"，`06` 管"以后每次真写怎么护栏"。**

## 5. 在岗：契约修订（"能力增删"是事件，不是改配置）

**员工在岗期间，能力一定会变**（接一个新系统、开一个写权限、加一个技能、收一个权限）。

**我拍：每一次变化都生成一版新契约，旧版永久保留。**

```
权责契约 v1  数据视窗: [团队=A]  连接器: [ERP只读]      写权限: 无
      │
      ├─ 事件：接入物流系统（客户技术团队，附理由）
      ▼
权责契约 v2  数据视窗: [团队=A]  连接器: [ERP只读, 物流只读]  写权限: 无
```

| 规则 | 内容 |
|---|---|
| **每次变更 = 一个新版本** | 不覆盖（同 `28` §2 交付物的版本规则） |
| **变更是一条事件** | 谁改的、何时、加/减了什么、为什么 |
| **能力可以增，也可以减** | **减**同样是事件——"上个月它还能写，这个月收回了"必须能查到 |
| **收紧立即生效** | 收回权限不需要等，**立刻生效** |
| **放宽要走授权** | 放宽是**正向授权**（`35` §2 的档位），**必须有授权记录** |
| **历史可回放** | "3 月 15 日它能不能读物流数据"→ 查 v1 契约，答案确定 |

**契约里还有一个会变、但特别容易被漏掉的字段：每个不可逆能力的「成熟度」**（`06` §2.3.7）。

```
权责契约 v3
  数据视窗: [团队=A]  连接器: [ERP读写, 物流只读]
  写权限:   submit_purchase_order  L3  成熟度=收敛中(2/5)  批量上限=5
```

> **为什么成熟度必须进契约**：它决定"这个操作要不要每次预演、批量能到多少"。
> **如果它只是一个运行时变量，审计时就会变成"上个月它到底是在预演态还是稳定期"说不清**——而这一点在出事后是第一个被问的。
> **改成熟度 = 换契约版本 = 留痕**（这正是把"放行"变成可追溯动作的办法）。

> **为什么"收紧立即、放宽留痕"**：安全上，**收回权限必须即时**（否则被收权的人还能干一会儿）；
> 而放宽是**风险增加**的方向，必须留下"谁批的"。**这一条与 `26` §2.3"只能收紧不能放宽"是同一条规则的落地。**

## 6. 停用：挂起，不是休假

**停用的语义要精确，否则退出时会算不清账。**

| 停用时**保留** | 停用时**停止** |
|---|---|
| 权责契约（原样冻结） | 接新任务 |
| 数据视窗（**冻结**，不扩大不缩小） | **数据访问**（连读也不给） |
| 记忆与经验（原样保留） | 会话（已有会话**进入只读**） |
| 交付物与账本 | 对外接口（Key 进入停用态） |
| 席位（**是否占席位按计费规则**，见 `30`） | 定时/事件触发 |

**两条容易做错的**：

1. **停用期间不该能读数据**——"不干活了但还能查数"是典型的越权残留。**冻结视窗 ≠ 保留访问。**
2. **停用不该自动恢复**——复职必须**人显式操作**，且要**重新过一遍上岗审核的第 2 项**（数据视窗是否还配得全，因为期间数据源可能变了）。

**复职（停用 → 在岗）**：

| 项 | 规则 |
|---|---|
| 资产 | **全部回归原样**（记忆、经验、契约、交付物都在） |
| 契约 | 沿用停用时的版本；若期间策略变了，**以更严的一方为准**（只能收紧，`26` §2.3） |
| 审核 | **重跑第 2 项**（数据源可能变了） |
| 账本 | 记一条"复职"事件，**不新建身份** |

## 7. ⭐ 退出：一次有序的清算（十一项处置）

**退出不是"删掉一个配置"，是一次资产清算。** 十一项，一项都不能漏：

| # | 处置项 | 怎么处置 | 为什么 |
|---|---|---|---|
| **1** | **权责契约** | **终止**（不是删除）——最后一版永久保留 | 事后要能回答"它当年能干什么" |
| **2** | **数据视窗** | **立即失效** | 权限是活着的授权，人走了不能留 |
| **3** | **跨边界授权**（`35`） | **全部立即失效**（尤其"可执行"档位） | `35` §10 已定 |
| **4** | **身份与凭证** | 服务身份**吊销**；对外 Key **立即吊销 + 宽限期** | 宽限期给外部集成留切换时间，**但不放行新请求** |
| **5** | **进行中的运行** | **跑完当前运行**（不中途杀），之后不再接新活 | `32` §6 已定的同一条原则："当前运行结束后才生效" |
| **6** | **等待中的人工确认** | **转交**给接任者；**无接任者 → 超时按 `06` 的"默认拒绝"关闭** | 不能挂在那里等一个不存在的人 |
| **7** | **未完成的任务** | **退回工作区任务池**（变回未分配） | 活是工作区的，不是员工私有的 |
| **8** | **数据层 / 连接器凭据** | **销毁**（凭据是实例级的，不转移） | 新员工用新凭据 |
| **9** | **记忆** | **留在原归属**（工作区级留工作区、员工级转归档只读） | 见下方"三条争议点" |
| **10** | **经验** | **留在原归属**；被污染的**必须显式销毁** | 同上 |
| **11** | **交付物** | **完全不受影响**，留在交付物账本与归属链上 | **员工离职不能让历史交付物失效** |

### 7.1 三条最容易做错的

**① 交付物绝不能跟着员工走。**

员工 3 月做的备货计划，**离职后仍然要能查、能追溯、能被下游引用**。交付物**属于工作区**（`28` §1）。

> 代价：**"已退出"的数字员工身份记录必须永久保留**（tombstone），否则交付物账本里那一栏会指向一个不存在的东西——**审计链断裂**。
> 这正是 §2 把"退出"和"销毁"分开的原因。

**② 记忆和经验的归属，取决于它"是谁的"。**

| 这条内容是 | 归属 | 退出时 |
|---|---|---|
| 业务事实（"这个 SKU 退货率 30%"） | **工作区** | 留在工作区，接任者能用 |
| 岗位经验（"这家供应商交期不准"） | **数字员工** | 转**归档只读**；接任者**不能直接继承** |
| 原始运行记录 | 工作区（`13`） | 按 `26` §3.4 保留策略 |

**③ 被污染的资产必须显式销毁——退出流程要有"投毒开关"。**

**场景**：客户因为**合规原因**（这个员工被越权用过、被注入攻击过）要退出它。
那么**它的全部记忆与经验都可能带毒**，转移给接任者 = **把污染扩散下去**。

| 退出类型 | 记忆与经验 |
|---|---|
| **正常退出**（业务调整） | 留在原归属，成为机构资产 |
| **异常退出**（合规/安全，显式标记） | **全部销毁**，不转移、不复用 |

> ⚠️ **这个开关必须有**。否则遇到"这个 agent 被人投毒过"的情况，客户唯一的选项是**整个工作区重来**——那代价太大了。

### 7.2 退出的执行者与不可自动性

| 项 | 规则 |
|---|---|
| **谁能退出** | **客户技术团队**（不是业务用户，也不是数字员工自己） |
| **数字员工能否自己退出** | **绝对不能** |
| **AI 能否建议退出** | **可以建议**（如"这个岗位三个月没接过活"），但**只有人能执行** |
| **退出前必须提示** | 还有未完成的任务 / 待确认的交付物 / **依赖它对外接口的外部系统** |
| **退出是异步的** | 有进行中运行时**排队等它跑完**，不是立即完成 |
| **审计** | 退出本身是一条**不可篡改**事件（谁、何时、为什么） |

### 7.3 ⭐ 资产复核：人在**哪**看、看**什么**、点**什么**（Day 3 补：上一版只写了"人来判断"，没给界面）

**上一版（§7.1 ③、§9）说了"人要判断哪些资产可信、哪些要销毁"，但没说人在哪判断。没有这个界面，那条流程根本执行不了。**

#### 7.3.1 位置：数字员工详情页 → **资产**

每个数字员工一个**主页**，五个页签。这是"管理一个数字员工"的唯一入口：

```
数字员工 [备货专员A]
├─ 资料    身份 / 职责边界 / 不管什么
├─ 契约    历史版本 v1 v2 v3…（当前版高亮，可 diff）
├─ 数据    数据视窗（行/列/遮蔽/派生）、连接器、数据源清单
├─ 资产 ★  知识集 / 记忆 / 经验 / 技能 / 验证规则   ← 复核在这里
└─ 账本    就业事件流（上岗/修订/停用/复职/退出）
```

**关键设计：资产页默认筛出"需要你决定的东西"，不是把全部资产倒给用户。**

```
资产复核（3 项待裁决 / 共 412 项）

[待裁决] 经验·策略   "华东仓安全库存按 45 天算"
         来源：对话（业务用户-张三，3/15）   被召回 2 次   未经验收
         [ 采纳 ] [ 归档只读 ] [ 隔离待判 ] [ 销毁 ] [ 导出 ]

[待裁决] 经验·记忆   "3/15 把 SKU-123 备货量 320 → 400"
         来源：复核修改（复核人-李四）       状态：可疑（验收失败触发）

[待裁决] 记忆        任务#8821 中间结论："供应商 X 交期 7 天"
         来源：运行 #8821                   与经验库冲突（另有"14 天"）
```

#### 7.3.2 每条资产要能看到什么（数据字段）

| 字段 | 为什么必须有 |
|---|---|
| **类型** | 记忆 / 经验（五维中哪一维）/ 知识引用 / 技能 / 验证规则 |
| **内容摘要** | 一眼能判断 |
| **来源** ⭐ | **谁给它的**——人教的？对话里说的？agent 自己攒的？**这决定可信度** |
| **形成时间 / 来源时间** | 判断新旧 |
| **被召回次数 / 最后召回时间** | 没被用过的优先处理 |
| **是否触发过验收失败** | `29` §4.2 的"可疑"标记 |
| **冲突项** | 和哪一条冲突（能对比着看） |
| **信任级别** | 见 §7.3.3 |

#### 7.3.3 ⭐ 五级信任 + 五个动作

**先纠正上一版的含糊**：`36` 上一版只说"留 / 转 / 销"三种。**不够**——中间缺了"**没想好怎么办**"这一档。

| 动作 | 含义 | 能被召回吗 | 可逆吗 |
|---|---|---|---|
| **保留** | 正常资产 | ✅ | 可 |
| **归档只读** | 留档、可查、**不参与召回** | ❌ | 可 |
| **隔离待判** ⭐ | **不确定，先不让它影响行为**，等人判断 | ❌ | 可 |
| **销毁** | 内容删除，**只留一条哈希记录** | ❌ | **不可逆** |
| **导出留档** | 先导出到指定位置，再决定销毁 | —— | —— |

> ⭐ **"隔离待判"是必须的一档**。否则人在"没想好"时只有两个选择：**留着（可能带毒）**或**删掉（可能是冤枉的）**。
> **而且它必须真的停止召回**——"标记了但还是被用"是最糟的状态。**这一条要写进验收（L21）。**

#### 7.3.4 怎么查（三个入口，覆盖三种场景）

| 入口 | 场景 | 查法 |
|---|---|---|
| **① 按状态筛** | 常规复核 | 筛"可疑 / 隔离 / 从未被召回 / 已过期" |
| **② 按来源筛** ⭐ | 追责 / 投毒 | 筛"来源 = 某次对话 / 某个运行 / 某个人"——**污染往往有共同来源** |
| **③ 从任务/交付物倒查** ⭐ | 具体一件事出问题了 | 打开任务 → 看这个员工为它用了哪些资产 → 逐条看 |

**第三个入口最关键**：**人不会凭空复核，一定是"某件事出问题了"才来查。** 所以资产必须能从任务和交付物**反查**回来。

#### 7.3.5 溯源能追到多深（三级下钻）

```
概况（这里有什么、多少条、哪些可疑）
   ↓ 点一条
条目（内容 + 来源 + 召回历史 + 冲突项）
   ↓ 再点
原始现场（哪次会话、哪次运行、哪个工具返回、谁说的那句话）
```

**"隔离待判"的判定依据就在第三级**——人得能看见"这句话当时是怎么冒出来的"。

#### 7.3.6 量大的时候怎么办（否则没人会用）

| 机制 | 做法 |
|---|---|
| **默认只给人看"要决定的"** | 全量资产不铺开（412 项里只有 3 项需要裁决） |
| **批量处理** | 按来源 / 按类型 / 按时间批量采纳或批量归档 |
| **销毁不能批量** ⭐ | 必须逐条确认，或走"我已逐条复核"的显式签认 |
| **复核本身留痕** | 谁在什么时候把哪条资产判成了什么——**这也是一条审计事件** |

#### 7.3.7 在岗员工的"定期资产复核"（反向投毒场景的入口）

| 触发 | 做什么 |
|---|---|
| **定时** | 每季度提示复核"从未被召回"和"可疑"的资产 |
| **事件驱动** | 召回质量下降 / 验收失败率上升 → 上升为复核任务 |
| **与 Anti-Rot 的分工** | `29` §4 防腐解决**自动可判**的（过期、冲突、失败标记）；**资产复核解决需要人判断的** |

**`36` §9 的"先停用再判断"就从这里进**：停用后，资产复核页顶上加一个"**本次为安全审查**"的标记，默认筛选切到"按来源"，并把导出/销毁的权限提高一档（需要更高级别的人确认）。

### 7.4 ⭐ 四类操作的"数据 / 流程 / 交付"对照（Day 3 补）

**总纲**：

> **每一次操作都必须产出一份"验收报告"，不是一次后台动作。**
> 这是把"数字员工"当**产品**而不是当**配置**的分水岭——客户看得见自己买到了什么、改了什么、退了什么。

#### 7.4.1 上岗

**① 平台要落的数据**

| 类 | 数据 |
|---|---|
| 身份 | 名称、工作区、岗位包版本、描述 |
| 职责 | 干什么 / **不干什么**（`03` §1.2，这是发权限的依据） |
| 知识 | 被授权的**知识集**清单（`33` §4.3） |
| 权限 | 数据视窗（每数据源的维度 + 行/列/派生规则）、连接器与能力清单、写权限级别（L0–L4） |
| 运行 | 沙箱规格、模型策略、成本/时长/并发上限 |
| 节奏 | 触发方式 |
| 交付 | 交付物 schema、复核人、`explain` 要求、下游岗位 |
| **成熟度** ⭐ | 每个不可逆能力的成熟度档位（`06` §2.3.7，**是契约的字段**） |
| 审计 | 创建人 / 批准人 / 时间 / 依据 |

**② 流程**：见 §3.1 八步。

**③ 交付包（给客户的东西）**

| 交付物 | 内容 |
|---|---|
| **数字员工档案** | 身份 + 职责边界 + 知识集 + 数据视窗 + 上限（**可导出、可给客户合规部门**） |
| **权责契约 v1** | 完整授权清单（含成熟度） |
| **上岗验收报告** | 五项审核（§4）+ 联调七项（§4.2）逐项结果 |
| **数据视窗清单** | 每数据源 × 每字段的可见性（**客户最关心这张**） |
| **未验证能力台账** | 哪些能力 ⊘ 无测试环境（`06` §2.3.9）——**客户必须签字确认知情** |
| **凭据清单** | 对外 Key、服务身份、有效期、吊销方式 |
| **接入信息** | 触发方式、接口地址、示例调用 |
| **相关人名单** | 谁复核、谁接活、谁被通知 |

#### 7.4.2 迭代版本（在岗期间能力增删）

**① 数据**

| 类 | 数据 |
|---|---|
| 变更内容 | 加/减了什么（连接器能力、数据范围字段、写权限、知识集、技能、上限阈值、**成熟度**） |
| **变更理由** | **必填**（同 `06` §5、`28` §3 的"记原因"） |
| **影响面** ⭐ | 会影响哪些**历史交付物**、哪些**在途任务**、哪些**外部集成** |
| **授权链** | 收紧立即生效；**放宽必须有批准人** |
| 新契约 | 生成 v(n+1)，旧版永久保留 |

**② 流程**

```
① 发起变更（谁、改什么、为什么）
② 影响面自动分析 ★ → "本次变更有 3 个在途任务、1 个外部集成依赖旧权限"
③ 分方向处置：收紧 → 立即生效（不等）｜放宽 → 走 `35` 授权档位（记批准人）
④ 生成契约 v(n+1) + 变更单
⑤ 【可选】重跑联调（改了连接器/视窗就必跑）
⑥ 通知受影响方（在途任务负责人、外部集成联系人）
⑦ 记账本
```

**③ 交付包**

**变更单** · **新契约 + 与旧版的 diff** ⭐ · **影响面报告** · **重跑联调报告**（如需要） · **通知记录**

> ⭐ **契约 diff 是给客户看的东西**。客户技术团队要能一眼看出"这个月这个员工的权限变了哪几处"——**这也是审计和合规最容易问的问题**。

#### 7.4.3 停用（挂起）

**① 数据**

| 类 | 数据 |
|---|---|
| 停用信息 | 原因、发起人、时间、**是否预计复职** |
| **冻结快照** ⭐ | 停用当刻的**契约版本号 + 数据视窗完整快照**——复职时要拿它对照 |
| 在途处置 | 有哪些未完成任务、待确认项 → 各自去向 |
| 对外影响 | 哪些外部集成在调它 → 已通知谁 |
| 席位状态 | 计费上的席位是否释放（`30` §7.2） |

**② 流程**：见 §6 与 §7（停用与退出共用大部分清算动作）。

**③ 交付包**

**停用处理单**（逐项结果） · **在途清单与去向** · **冻结快照**（复职要用） · **外部集成通知记录** · **席位变化说明**

#### 7.4.4 退出与销毁

| | 退出 | 销毁 |
|---|---|---|
| 多做的事 | **十一项清算**（§7）+ **资产复核**（§7.3） | 删除就业账本与身份记录 |
| 交付包 | **退出清算报告**（十一项逐项去向 + 资产复核结论）· 对外接口终止确认 · 资产去向清单 | **销毁证明**（哈希 + 时间戳） |
| 谁能做 | 客户技术团队 | 客户技术团队 + **平台参与**（要动 KMS） |

#### 7.4.5 四类操作共用的东西（别做四套）

| 共用件 | 说明 |
|---|---|
| **同一个详情页的五个页签** | 资料 / 契约 / 数据 / 资产 / 账本——四类操作都从这里进 |
| **同一套"清单 + 报告"格式** | 上岗清单、变更单、停用单、清算报告**结构一致**（逐项 + 结论 + 签字） |
| **同一本就业账本** | 四类操作都只往里**追加事件**，从不改历史 |
| **同一个联调模块** | 上岗跑全量，迭代跑增量，停用不用跑 |
| **同一条审批链** | 复用 `06`，不另造 |

## 8. 退出之后：复职与重建（两个都行，但代价不同）

**客户可能会后悔。** 所以两种路都要留，且要**让人看见代价**：

| | **复职**（已退出 → 停用/在岗） | **重建**（新建一个数字员工） |
|---|---|---|
| 身份 | **同一个**（账本连续） | 新的 |
| 契约 | 从最后一版起（需重新过审核） | 从岗位包重新配 |
| 交付物 | 归属链连续 | **归属链断开**（历史交付物仍指向旧员工） |
| 记忆 / 经验 | 按退出时的处置结果：**未销毁的可恢复** | **不继承**（除非显式复制，且要记录） |
| 审计 | 完整连续 | 两段，需人工关联 |
| 适用 | 同一工作区内的业务调整 | **换工作区**、原员工被污染、想干净重来 |

> **⚠️ "迁移到另一个工作区"不是一条路**——数字员工**绑定单一工作区、终生不可迁移**（`architecture` §3）。
> 要换工作区只能**重建**：可以**复制岗位包与配置**（含数据视窗取值，但要**重新确认**），**记忆与历史留在原处**。
> 这条限制是有意的：**允许迁移就等于允许把数据带过隔离边界**（`35`）。

**复职的时间窗**：**不设硬性期限**，但复职时**必须重过上岗审核**——因为数据源、策略、上游系统都可能变了。

### 8.1 ⭐ 新建的数字员工：资产从零开始（Day 4 自审补）

**上一版只说了"重建不继承记忆"——那是从 `重建者` 的角度说的。还没说清 `新员工` 的角度。**

| 资产 | 新建时 |
|---|---|
| **记忆** | **空**。它没干过活，没有"上次这家供应商交期不准" |
| **经验** | **空**（新员工没有个人经验；`29` 的经验要等它干出活、人确认后才产生） |
| **知识** | **不是空的**——按**知识集授权**（`33` §4.3）拿到**工作区的存量知识**。⭐ **这正是新员工能立刻干活的原因** |
| **交付物** | 无历史产出 |
| **契约** | v1（首版） |
| **数据视窗** | 上岗时配（`36` §4），与前任无关 |

**一条容易误会的推论**：

> **"新员工什么都不知道"是错的。**
> **它知道的是"人告诉它的东西"（知识），不知道的是"干出来的东西"（经验/记忆）。**
> 所以**接任者能立刻接手**——因为岗位的知识（SOP、口径、政策）本来就挂在工作区，不属于个人。

**但反过来有一条硬规则**：

> **前任的"岗位经验"（`29` 五维里属于数字员工级的那些）不会自动转移给接任者。**
> 接任者要重新攒。**这是有意的**——经验带着"当时的语境"，直接继承会让接任者犯**别人的错**（`36` §7.1 ②）。

## 9. 一个不能漏的场景：人走了，但资产被污染过（反向也要防）

上面讲的是"**员工退出时资产可能带毒**"。**反过来同样成立**：

> **资产已经带毒了，但员工还在岗。**

`29` §4 的防腐已经在处理一部分（经验冲突、验收失败标可疑），但**"整个数字员工被判定为不可信"这个级别的事件**（比如它的 Key 泄露过、它的沙箱逃逸过）**没有对应的处置动作**。

**我拍：加一个"隔离态"的过渡动作**（不新增状态，用"停用 + 强制复检"表达）：

```
发现员工不可信
   ↓
① 立即停用（收回全部授权，保留资产原样 = 保留证据）
   ↓
② 人审查：哪些资产可信、哪些要销毁（走 §7.1 ③ 的投毒开关）
   ↓
③ 结论三分支：复职 / 带清算的复职 / 退出
```

**关键**：**先停用再判断，不要直接退出**——**退出会清算资产，而清算前你需要那些资产当证据。**

## 10. 就业账本（Employment Ledger）⭐

**员工这一生，是一条可回放的记录：**

```
实例化（引用岗位包 vN + 实例配置 + 数据视窗）
  → 上岗审核通过
  → 上岗（契约 v1 签发）
  → 契约修订 v2（接入物流）      ← 能力增删是事件
  → 契约修订 v3（收回写权限）
  → 停用（原因）
  → 复职
  → 退出（原因）
  → 资产清算记录（各项去向）
  → [可选] 销毁
```

| 性质 | 内容 |
|---|---|
| **不可篡改** | 同 `26` §3.3 |
| **不可删除** | 直到整租户销毁（`01` §6.4） |
| **可回放** | 任一时点"它当时能干什么、谁批的"都能答 |
| **挂归属链** | `客户 → 工作区 → 数字员工`（`26` §1.2） |

**这份账本同时满足三件事**：
1. **审计**——谁在什么时候给了它什么权限
2. **审计链完整**（§7.1 ①）——交付物不会指向一个不存在的员工
3. **产品**——客户能看见"这个员工的历史"，**这是能卖给客户的东西**

## 11. 与既有设计的接口

| 机制 | 怎么接 |
|---|---|
| **岗位包**（`03`） | 模板，**入职时引用一次**；后续契约修订不回头改岗位包（岗位包是全局资产） |
| **归属链**（`26` §1.2） | 员工挂链上；**退出后仍挂**（tombstone） |
| **数据视窗**（`34`） | 是**契约的一部分**；退出立即失效；修订即换版本 |
| **跨边界授权**（`35`） | 退出时**全部立即失效**；进行中的申请**撤回** |
| **交付物**（`28`） | **不受影响**；跨岗位流转照常（下游不需要知道上游员工在不在） |
| **经验**（`29`） | 退出时**留在原归属**；"下架 ≠ 删除"（`29` §4.4）在这里第二次用到 |
| **会话/运行**（`13`） | 员工退出**不销毁历史会话**（会话属于工作区） |
| **计费**（`30`） | 停用/退出时**席位如何释放**要定义（`30` §7.2 的席位口径） |
| **技能拔插**（`32` §6） | 同一条原则复用：**"当前运行结束后才生效"** |

## 12. 验收标准

| # | 标准 |
|---|---|
| L1 | 数字员工的五个状态**可显式流转**；两条不可逆边**需二次确认**，不能误触 |
| L2 | **未过上岗审核的草稿态员工：不派活、不给数据视窗、不发凭证** |
| L3 | **能力增删生成新契约版本**，旧版可查；任一时点能回答"它当时能干什么" |
| L4 | **收回权限立即生效；放宽权限必须有授权记录** |
| L5 | 停用期间**读数据也被拒绝**（冻结视窗 ≠ 保留访问） |
| L6 | 复职**回归原有资产**、**不新建身份**，且**重过数据视窗检查** |
| L7 | 退出时**跑完当前运行**再停止接活（不中途杀） |
| L8 | 退出后**历史交付物完全不受影响**，且**归属链仍能指回该员工**（tombstone） |
| L9 | 退出后**对外 Key 立即吊销**（宽限期不放行新请求）；数据视窗与跨边界授权**全部失效** |
| L10 | 退出时**未完成任务退回工作区任务池**；待确认项**转交或按超时拒绝关闭** |
| L11 | **退出 ≠ 销毁**：退出后身份记录仍在，销毁是独立动作 |
| L12 | **异常退出可显式标记"资产带毒" → 记忆与经验全部销毁、不转移** |
| L13 | 数字员工**不能让自己退出**；**AI 只能建议，人才能执行** |
| L14 | **"迁移到另一个工作区"不被支持**；换工作区只能重建，**记忆不随之迁移** |
| L15 | 就业账本**不可篡改、可回放**，且记录包含每次授权的批准人 |
| L16 | 客户**新增/调整一个数字员工的全过程，平台零改动**（通用性判据） |
| L17 | **环境标记挂在连接器（能力）上，且必须由客户技术团队显式签字**；待确认时**一律按"生产 + 最严格"处理** |
| L18 | 同一公司内**有测试环境的连接器走双跑、没有的走生产只读探测**，**三种模式在同一员工身上可并存** |
| L19 | 报告**按【连接器 × 能力】聚合**，且 **"不可测"（⊘）与"通过"在视觉上完全不同** |
| L20 | **两次报告（预检 / 客户环境）能自动对比**，并列出差异（含**视窗指纹差异**） |
| L21 | **"隔离待判"的资产真的停止召回**——不是"标记了但还在被用" |
| L22 | 资产复核的**销毁不能批量**（逐条确认或显式签认），且**复核本身留痕** |
| L23 | 资产能**从任务/交付物反查**（三级下钻到原始会话/运行） |
| L24 | **`data_view.probe` 失败一律不许上岗**，无例外；其他关键项失败同样不许 |
| L25 | 非关键项跳过/不可测 → **可上岗**，但报告标注 + **未验证能力台账在客户界面可见且客户确认** |
| L26 | 每个**不可逆能力**上岗时处于**预演态**；升级由**数据**决定（连续成功 + 零失败 + 零驳回 + 时间），不由模型决定 |
| L27 | 自动验证失败 → **自动降回预演态**（降级是自动的、立即的） |
| L28 | **批量上限永远存在**，成熟度再高也不能超；超限走**单独更高一级审批** |
| L29 | **L4 类操作不因成熟度降级**（改权限/改阈值永远双人 + 时间窗 + 可回滚） |
| L30 | 每次 L3 执行后**自动验证**（不需人参与），结果进账本与经验库；失败则相关经验标"可疑" |
| L31 | 无测试环境的连接器，**预演单必须含"反向动作提案"**；真不可逆的必须显式标记 |
| L32 | 网络隔离客户可用**离线自检工具**跑同一套检查项，产出**同一结构的报告** |

## 13. 这一步顺带拍掉的决策

| # | 问题 | 我拍 |

| 1 | 数字员工的生命周期有哪几个状态？ | **草稿 / 在岗 / 停用 / 已退出 / 已销毁**五个，两条不可逆边 |

| 14 | 要不要就业账本？ | **要**。它同时满足审计、审计链完整、以及"能卖给客户"三件事 |

### Day 3 第二轮追加（联调 / 资产复核 / 四类操作）

| # | 问题 | 我拍 |
|---|---|---|
| 15 | 环境是客户级属性还是连接器级属性？ | **连接器级，甚至能力级**。同一家公司里，自研中台有测试环境、外采 ERP / Shopify / Amazon 只有生产 |
| 16 | 客户两套环境都有，联调在哪跑？ | **都跑，然后自动对比**（预检报告不能作为上岗依据，只作参考附件） |
| 17 | 联调模式要不要让客户选？ | **不用选**，由"连接器矩阵"自动推导；同一员工身上三种模式可并存 |
| 18 | 环境标记谁来定？ | **客户技术团队签字 + 平台复核**；**判错的后果是所有保护措施一起失效**，所以待确认一律按"生产 + 最严格" |
| 19 | "不可测"和"通过"能一样显示吗？ | **绝对不能**。否则报告给人"全绿"错觉，**风险恰恰藏在 ⊘ 里** |
| 20 | 视窗探测必须逐个连接器做吗？ | **必须**。测试连接器通过 ≠ 生产连接器通过（数据范围/权限/字段都可能不同） |
| 21 | 客户坚持要上岗但视窗探测没过？ | **不许上岗**——**唯一没有例外的一项**（其他项失败是"干不了活"，这项是"能看到不该看的"） |
| 22 | 人在哪复核资产？ | **数字员工详情页 → 资产页签**，默认只筛出"需要你决定的" |
| 23 | 资产处置只有"留/销"吗？ | **不够**。五档：保留 / 归档只读 / **隔离待判** / 销毁 / 导出 |
| 24 | "隔离待判"要不要真的停止召回？ | **要**。"标记了但还是被用"是最糟的状态 |
| 25 | 复核怎么查？ | 三个入口：按状态 / **按来源（追投毒）** / **从任务与交付物倒查** |
| 26 | 溯源追到多深？ | **三级**：概况 → 条目 → **原始现场**（哪次会话/运行/谁说的） |
| 27 | 销毁能批量吗？ | **不能**（人最容易被批量点的动作，必须逐条或显式签认） |
| 28 | 每次操作要交付什么？ | **一份验收报告**，不是后台动作——上岗/迭代/停用/退出**四类结构一致**（逐项 + 结论 + 签字） |
| 29 | 没有测试环境的连接器，怎么写操作？ | **允许（A 方案）**，但必须走 `06` §2.3 的首跑护栏：预演态 + 自动验证 + 成熟度阶梯 + 未验证台账 |
| 30 | "预演"和技术 dry-run 是一回事吗？ | **不是**。没有测试环境时，**唯一能做的是"把动作完整渲染给人看"**，而不是发假请求 |
| 31 | 成熟度谁来定？ | **数据定**（连续成功 + 零失败 + 零驳回 + 时间），**不是模型判断**；且**成熟度是契约的字段**（改它 = 换版本 = 留痕） |
| 32 | 成熟度高了能放开批量吗？ | **不能无限放**。**批量上限永远存在**，超限走单独更高一级审批；**L4 永远不降级** |
| 33 | 出错时怎么降级？ | **自动且立即**（人工申请太慢，出错时需要的是护栏不是流程） |
| 34 | "首次人工监督"够吗？ | **不够**。必须配**自动验证**（执行后比对目标系统实际状态）——这才是"没有测试环境"的补偿 |
| 35 | 网络隔离客户怎么联调？ | **离线自检工具**（随数据面部署，就地跑同一套检查项，产出同一结构报告） |
