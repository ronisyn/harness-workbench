# 28 · 交付物流程（平台侧）

> 状态：方案，技术决策由我拍。平台侧第 2 步。
> 前置：`03`（岗位包，交付物的 schema 定义在那）· `06`（审批与受信执行器）· `26`（治理层的归属维度）
> **为什么单独做**：交付物的**流程管理**（状态/版本/复核/审批/归档/流转）是**平台的职责**，但之前写在 `03`（agent 侧的岗位包文档）里，**放错位置了**。

---

## 0. 一句话

**交付物 = agent 产出的东西（内容）+ 平台管的东西（流程）。**

**分界**：
| 谁 | 管什么 |
|---|---|
| **岗位包**（agent 侧） | 交付物**长什么样**——字段 schema、导出格式、要不要复核、要不要解释、**送给谁（`38`）** |
| **平台**（本文） | 交付物**怎么流转**——状态、版本、复核、审批、归档、跨岗位传递 |
| **平台**（[`38`](./38-deliverable-delivery.md)） | 交付物**怎么送到人手上**——界面底座 / 飞书 / 邮件 / 对话。**送达状态与本文的状态机分开**（`38` §6） |

---

## 1. 交付物对象模型

一个交付物不是"一个文件"，是**一个有身份、有版本、有流转记录的对象**：

| 字段 | 说明 |
|---|---|
| **归属链** | `客户 → 工作区 → 数字员工 → 运行`（治理层定的公共维度，见 `26` §1.2） |
| **类型** | schema 名（如"备货计划单 v2"），来自岗位包 |
| **内容** | **结构化数据（内核）**——不是 Excel |
| **状态** | 草稿 / 复核中 / 已确认 / 已交付 / 作废 |
| **版本历史** | 每次改动 = 一个新版本（谁改的、何时、改了什么） |
| **外观** | 导出的 Excel / PDF（**只是渲染结果**，随时可重生成） |
| **依据** | `explain` 要求的"为什么是这个结果"（岗位包声明 `explain: required` 时） |
| **验收标准快照** ⭐ | 产出时所用的**验收标准**（来自当时的岗位包版本，`37` §4.1）——**判定一律按这一版，不按最新版** |
| **流转记录** | 谁看过、谁批过、交给了谁 |
| **送达记录** ⭐ | 送过给谁、哪个版本、哪个渠道、回执如何（[`38`](./38-deliverable-delivery.md) §8）——**与上面的状态机分开，送达失败不回写状态** |

> **核心原则（重复一遍，因为它最容易被做错）**：**人看到的是 Excel，系统里存的是数据。**
> 内部结构化 → 岗位之间能自动传、能对比历史、将来接 ERP 不用重做。

---

## 2. 状态机（含版本规则）

```
草稿 ──▶ 复核中 ──▶ 已确认 ──▶ 已交付 ──▶ 归档
  ▲        │
  └────────┘  被退回（带意见）
       │
       └──▶ 作废
```

**版本规则（我拍）**：
- **每次内容改动 = 一个新版本**（不覆盖）
- **每次状态变更 = 一条事件**（谁、何时、从什么状态到什么状态）

**为什么必须留版本**：两个理由——
1. **学习闭环**：要能对比"**agent 原始的** vs **人改后的**"（见 §4）
2. **审计**：要能追溯"这个数是谁改的、什么时候改的"

> ⚠️ **"覆盖式修改"是这套系统最容易犯的错**——一旦覆盖，学习闭环断了、审计也断了。

---

## 3. 复核：不只是把关，更是学习闭环的数据源

**复核界面必须记录**：

| 记什么 | 用途 |
|---|---|
| agent 原始值 vs 人改后的值 | 知道 agent 哪里不准 |
| 人填的改动原因 | 知道**为什么**不准（这是最有价值的） |
| 谁改的、改了多久 | 质量与效率指标 |

**这些数据的两个去向**：
1. **归集到岗位/知识** → 让 agent 变准（`24` 的按需召回会把它们捞出来用）
2. **进"人工修改率"看板** → 客户看到价值、你评估岗位包质量（`architecture` §8.3）

**平台负责收集和保存，agent 负责消费。**

> ⚠️ **Day 3 修正**："归集到岗位/知识"这句话太粗。权威归属是 [`29`](./29-experience-management.md) §1：
> 人的修改先形成**经验**，再按**五维**路由——技能维进技能库、工作流维进岗位包、验证规则维进策略、记忆/策略维进经验库。
> **不是笼统地"归集到知识"**（知识和经验是两回事，见 [`33`](./33-knowledge-layer.md) §2）。

## 4. 与审批/执行器的衔接（`06`）

交付物流程和 `06` 的"写操作五级"是**接在一起的**：

```
agent 产出        →  L1（交付物本身，不算写生产）
人复核确认        →  交付物状态 = 已确认
   │
   └─ 如果需要写外部系统（进 ERP、下采购单）
        → 触发 `06` 的 L2（草稿态写）或 L3（生效写）
        → 受信执行器代做
```

**关键**：**交付物的"已确认"是写操作的授权前置**——`06` 里说的"人点提交"就是这一步。**两个流程在这里咬合，不要各做一套。**

---

## 5. 跨岗位流转（供应链那条链）

你之前描述过：备货计划 → 采购 → 发货 → 仓储。**交付物就是这条链上的交接物。**

**我拍：交付物"交给下一个岗位"时，是同一个对象在流转，不是复制。**

```
备货计划专员 → 产出"备货计划单" → 确认 → 交付
                                        │
                                        ▼
                              采购专员的"待办"里出现它
                                        │
                                        ▼
                              采购据此产出"采购计划"
```

**实现**：岗位包的任务编排里声明"下游"（谁接这个交付物），平台负责把它挂到下游岗位的待办。

> ⚠️ **跨边界流转要过授权**（Day 3 补）：如果下游岗位落在**另一个数据边界**内（另一个团队/区域，见 [`34`](./34-data-view.md)），
> 那么"交付"这个动作**不只是挂个待办**——它可能意味着**数据归属或处置权的变化**，必须走 [`35`](./35-cross-boundary-authorization.md) 的申请-审批-执行。
> **交付物能传，不等于对方有权收。**

**为什么是"同一对象"而不是"复制"**：
- 复制会产生 N 个版本，对不上账
- 同一对象流转，**审计链完整**（这个数从哪来、经过谁的手）

> 这也回答了一个隐含问题：**岗位之间的接口是什么？** 答案是**交付物**——它的 schema 就是岗位之间的契约。

## 6. 归档与检索（顺带回答你那个"历史存档"问题）

**我拍：结构化存储 + 精确查询，不是向量检索。**

| 项 | 决定 |
|---|---|
| **存储** | 结构化（按 schema 存字段），按归属链分区 |
| **检索** | **精确查询**：按 SKU / 时间 / 平台 / 岗位查——**这正是你之前问的"备货表历史存档怎么放"的正解** |
| **外观** | Excel 随时可从结构化数据重生成 |
| **保留** | 热数据 + 归档（与审计同周期，见 `26` §3.4） |

**为什么不用向量检索**：历史备货表是**结构化数据**，能精确查就别让模型"检索猜"——这是 `24` 定的原则。

## 7. 验收标准

| # | 标准 |
|---|---|
| D1 | 一次人工修改后，**agent 原始版本仍可查**（没被覆盖） |
| D2 | 任一交付物能**倒推出**"哪个客户/工作区/岗位/运行产出的" |
| D3 | 交付物能**从结构化数据重新导出 Excel**，且与当初一致 |
| D4 | 交付物交付给下游岗位后，**是同一个对象**（不是副本），审计链完整 |
| D5 | "agent 原始值 vs 人改后值 + 原因"**被完整记录**，可用于让 agent 变准 |
| D6 | 交付物"已确认"能**正确触发** `06` 的写流程（L2/L3） |
| D7 | 查历史备货量：按 **SKU + 时间 + 平台** 精确查到，**不走向量检索** |
