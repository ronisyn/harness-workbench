## 0. 一句话定位

这不是"一个 agent 产品"，而是 **一个把 agent 装配成各种岗位工人、并安全托管运行的平台**。
平台卖掉的东西是三样：**治理（隔离/权限/计费/审计）**、**岗位包（可配置的工人）**、**agent（可插拔的干活零件）**。

### 0.1 三层结构（统一语言）

| 层 | 是什么 | 谁做 | 换不换 |
|---|---|---|---|
| **平台（Ronisyn）** | 管：多租户、账本、审计、交付、治理、模型网关、岗位包、对外接口 | 自研 | **只有一个** |
| **agent** | 干：引擎（思考）+ 运行时（工具 / 上下文 / 记忆 / 沙箱）。可插拔零件 | roni（自研）+ DS harness（开源）+ codex harness（开源） | **可插拔，一期 3 个** |
| **岗位包** | 装上去的一套：身份、提示词、技能、知识、工具授权、交付物模板、触发方式 | 配置 | 一个岗位一个 |

**产品化封装 = 岗位包 + agent + 对外接口 + 配额 + 品牌**。装到某个客户、某个工作区上跑起来之后，叫**数字员工**。

> **验收标准**：新增一个岗位**应该只需配置岗位包，不需改动平台或 agent 内核**。如果发现要改，说明抽象漏了。
> ⚠️ **术语："壳"已退休**——它之前把"平台级"和"agent 级"混在一起。边界见 [`19`](./19-platform-vs-agent-boundary.md)。

## 0.5 已锁定的决策（ADR）

> 讨论确认后写入。这些是不可轻易回退的架构决策，后续所有设计必须与之自洽。

| # | 决策 | 对架构的强制影响 |
|---|---|---|
| **ADR-1** | **交付形态：多租户 SaaS 优先，但隔离从第一天硬做** | 工作区隔离是**骨架**而非特性，不可后补 |
| **ADR-2** | **写回策略：agent 不直接改"生产"** | **"生产"= 客户真实在用的业务系统**（ERP 真实单据、真实代码库、线上系统），不是指"代码开发"或"本平台"。落地形态：agent 填"草稿/待审"→ **人点提交**；在沙箱里写、产草稿都不算写生产。平台必须有独立的"受信执行器 + 审批中心"通道 |
| **ADR-3** | **沙箱基线：gVisor（runsc），敏感客户升 microVM** | 沙箱规格抽象**必须与底层运行时解耦**，允许按客户/按规格切换实现 |
| **ADR-4** | **平台领域无关：垂直岗位是配置，不是代码** | 平台表达力上限 = 岗位包的表达力 × 连接器生态广度；禁止为任何单一岗位做运行时特化 |
| **ADR-5** | **平台（Ronisyn）自研 + 三个 agent 可插拔（roni / DS harness / codex harness）** | agent 是平台里可插拔的零件，一期 3 个（Claude 不用）。agent 自带引擎与运行时，但**工具执行 / 沙箱 / 权限 / 审计由平台托管**；边界见 [`19`](./19-platform-vs-agent-boundary.md) |
| **ADR-6** | **不卖 token，只卖 agent 能力**（合规硬约束） | 客户界面**不得出现 token 单价/余额/充值**；计费单位是"干的活"；不向客户交付厂商凭证；不做 API 聚合中转。详见 [`02-compliance-constraints.md`](./02-compliance-constraints.md) |
| **ADR-7** | **三层身份：平台运营方 / 客户技术团队 / 客户业务用户** | 权限模型不是两层而是三层；客户技术团队能改"平台配置"（岗位包、连接器、触发方式），碰不到内核 |
| **ADR-8** | **控制面不碰业务数据** | 业务数据只在**数据面**被访问，且数据面可整体部署在客户侧（`14`）；控制面只存元数据、策略、审计、账本。这条会被"就查一下订单算个钱"不知不觉违反，所以写成 ADR |
| **ADR-9** | **隔离是默认，跨边界要显式授权** | 任何隔离边界（客户 / 工作区 / 数字员工 / 客户自定义的维度）之间**默认不可见、不可动**；跨越必须由上级策略显式授予，且**申请权与执行权分离**（`35`）。**禁止**把跨边界写成"某个特定岗位的特权"——岗位是客户的配置，会变 |

## 1. 七条设计原则

整个架构的每一个决策都应该能回溯到这几条。它们决定了后面所有取舍。

### 铁律一：Agent 是不可信工作负载（Untrusted Workload）

Agent 的工作内容是**由模型根据外来输入（网页、文档、邮件、数据库内容）现场生成的**，因此它天然可被 **Prompt Injection 劫持**。
推论：

- Agent 不能持有长期凭证，不能直连生产库，不能拥有超出当前任务的权限。
- 所有权限必须在**沙箱边界之外**被强制执行（在 Broker / Proxy / Policy Engine 上），而不是靠"提示词里告诉它别乱来"。
- Agent 是"零信任工作负载"，它的信任等级等同于"一个刚入职、可能被社工的外部实习生"。

### 铁律二：能力单调不增（Capability Attenuation）

子 agent、子任务、子进程、派生沙箱，**永远不能获得比父级更大的权限**。
推论：Codex / Claude 作为子 agent 被集成时，必须在父 agent 的权限子集内运行；沙箱 fork 出的进程不能让渡也无法提权。

### 铁律三：凭证永不进入沙箱

Agent 要"读销量数据"，正确的形态**不是**给它数据库账号，而是给它一个**语义化能力接口**：

```jsonc
// agent 看到的
sales.query({ period: "2026-Q2", dims: ["region","sku"], metrics: ["revenue"] })
// 它看不到的：连接串、账号、底层 SQL、其他客户的行、未授权字段
```

凭证由 **Credential Broker** 在沙箱外持有，按请求注入、按结果过滤、按行为审计。

### 铁律四：三层隔离，一次会话一条命

- **客户隔离**（硬隔离，跨客户零共享）
- **工作区隔离**（服务器上的独立工作单元互不可见，各自独立存储 / 凭证 / 网络策略）
- **运行隔离**（每次运行一个沙箱实例，用完即毁；同一数字员工的并发运行互不可见）

会话**在创建时就绑定到一个工作区，生命周期内不可迁移、不可越界**。

> ⚠️ **补一条**（见 [`01-identity-and-isolation.md`](./01-identity-and-isolation.md) §3.2）：**资源归属 ≠ 岗位归属**。
> 有些资源被多个工作区共用（例如一个海外仓的库存被多条业务线共用）。所以授权维度里除了工作区，还必须支持**资源**（仓 / 店铺 / SKU 段）。缺了这一维，就会出现"每个岗位只看自己那本账、合起来必然超备，而且没人看得见"。

### 铁律五：默认只读，写操作走审批

Agent 对**外部环境**（生产库、别人仓库、业务系统）默认**只读**。
任何写回（改代码、改配置、改数据）一律走：**产出 diff/工单 → 人在环审批 → 由平台侧的受信执行器代执行**。
Agent 自己永远不直接触碰生产写路径。（**ADR-2**）

### 原则六：领域无关 —— 岗位是配置，不是代码

平台**不为任何单一岗位**（供应链、运营、产品、财务、法务……）写代码。一个"工人"完全由**岗位包**组合而成：身份、提示词、技能、知识、工具授权、交付物模板。（**ADR-4**）

推论：

- 平台的**表达能力上限 = 岗位包的表达力 × 连接器生态的广度**。这两样是真正的护城河，应优先投入。
- 新增一个岗位**应当只需配置岗位包，不需改动平台**；如果发现要改平台，说明抽象漏了。← **这是可量化的验收标准**
- **参考工人**（Reference Role）是验证平台的手段，它本身**领域无关**：
  *受限只读接入外部数据 → 分析计算 → 产出结构化交付物 → 按审批交付*。
  任何岗位都是这个骨架的特化。

### 原则七：成本是一等设计目标，不是优化项（Day 4 第 5 轮自审补）

**这条为什么单独列成原则**：它是**用户提出的第一个问题**（"为什么贵"），而且**它是产品能不能活的前提**——
客户不会为一个"聪明但烧钱"的东西付钱；而**成本不是"省着用"能解决的，是架构决定的**。

**四个成因（用户自己诊断的）与对应手段**：

| 成因 | 手段 | 在哪 |
|---|---|---|
| **每轮全量重发整个上下文**（结构性） | 比例制压缩（窗口 80% / 保留 16%） | `23` §4 |
| **固定注入本身就不小** | **按需召回**：技能按需加载、知识按需检索、项目说明按需 | `24` |
| **工具结果很占地方** | spill 落盘 + 中段修剪（8192/4096/1024） | `23` §2/§3 |
| **多轮循环 + 额外 LLM 调用** | 预算软着陆 + **免模型**修剪（修剪不额外烧一次 LLM） | `08` §6、`23` §3 |

**外加两个杠杆**（不是"省"，是"算对"）：

- **缓存**：网关保证"可缓存前缀逐字节一致"——实测命中与未命中价差 **27 倍**（`30` §4）
- **模型分级路由**：规划用强模型、抽数用便宜模型（`30` §3）

**三条纪律**：

1. **每条成本手段都必须能回答"省的是哪一块"**——不能笼统说"我们做了优化"
2. **"按需"优先于"压缩"**——**不注入**永远比"注入了再压"便宜
3. **成本可观测是前提**（`30` §8.3）：算不清账就优化不动
- 里程碑按**能力成熟度**推进，而不是按"做完某个垂直场景"推进。

> 详见 §0.1 的三层结构（平台 / agent / 岗位包）——**"壳"这个词已退休**，见 [`19`](./19-platform-vs-agent-boundary.md) §1。

## 3. 领域模型（统一语言）

先把名词钉死，后面所有讨论都用这套词汇。

| 概念 | 说明 | 隔离边界 |
|---|---|---|
| **客户**（Tenant） | 付费与隔离的最高单位。**服务商自己也是一个"内部客户"** | 独立命名空间、独立配额 |
| **工作区**（Workspace） | **服务器上的一个独立工作单元**——某个客户的某块业务，或服务商自己的某个产品。这就是口语里的"项目" | 独立存储域、独立凭证、独立网络策略。**现状：尚未隔离，混在同一台机器上** |
| **连接器**（Connector） | **接入一个外部系统**（ERP、Shopify、Amazon、自研中台）的统一入口。底下实现可以是 **API / RPA / 文件导入**，对 agent 一律透明 | 绑定工作区；权限、限流、审计在此收敛 |
| **人**（Principal） | 终端用户 / 管理员 / 审批人 | 属于客户，可被授权到多个工作区 |
| **岗位包**（Role Package） | **工人的定义**：身份 + 提示词 + 技能 + 知识 + 工具授权 + 交付物模板 + 触发方式 + 沙箱规格。版本化、可发布、可灰度。**由平台方/交付团队编写，是平台资产**（`37`） | 全局 / 客户私有 |
| **岗位库** ⭐ | **可复用岗位包的集合**（骨架模板 / 行业模板 / 客户岗位包三层）。与技能库、插件库并列，**商业价值最高——客户买的就是岗位**（[`37`](./37-role-package-authoring.md) §6） | 平台级 + 客户可见范围 |
| **数字员工**（Digital Employee） | 岗位包装到某个工作区上之后的运行体，绑定自己的入口、Key、配额 | **绑定单一工作区，终生不可迁移** |
| **技能**（Skill） | **声明式**知识与流程包：提示词 + 流程 + 文档 + 少量无脚本配置。不改运行时 | 可跨客户共享（技能库） |
| **插件/工具**（Plugin/Tool） | **可执行**代码扩展，必须显式声明所需能力 | 需签名、需授权、沙箱内运行 |
| **知识库** | 工作区的私有知识 + 检索 | 每工作区独立命名空间；**检索先按归属过滤再算相似度**；全文（FTS5）打底、向量留位后补（`24` §3、`33`） |
| **交付物**（Deliverable） | agent 的产出：报表、计划单、单据草稿。**内部是结构化数据，Excel/界面都只是外观** | 属于工作区；有版本、有状态、有复核记录 |
| **会话**（Session） | 一段多轮对话的上下文容器 | 绑定工作区，不可迁移 |
| **运行**（Run） | 会话内的一次执行，对应一个沙箱实例 | 用完即毁 |
| **临时凭证**（Capability Token） | 短期、窄权限、绑定**单次运行**的凭证，用于访问连接器与网关 | 分钟级有效期 |
| **策略 / 审批** | 谁能用哪个岗位做什么、走什么审批 | 客户级覆盖，全量审计 |
| **维度类型 / 取值** ⭐ | **客户自定义的内部边界轴**（如"货权团队：A 团队 / B 团队"）。类型与取值都由客户技术团队定义，**平台不预设** | 客户级定义，工作区引用（[`01`](./01-identity-and-isolation.md) §3.2） |
| **数据视窗**（Data View） ⭐ | **"这个数字员工在这个任务里能看到什么数据"** = 行过滤 × 列规则（可见/遮蔽/**派生**）× 聚合规则。由策略引擎生成、数据出口强制执行 | 绑到**数字员工实例 + 触发者**，**不是绑在岗位包上**（[`34`](./34-data-view.md)） |

> **两条容易搞混的关系**：
> ① **连接器 ≠ 工作区**。连接器是"接进来的外部系统"，工作区是"服务器上的独立单元"。一个工作区可以接多个连接器。
> ② **资源归属 ≠ 岗位归属**。有些资源被多个工作区/岗位共用（例如一个海外仓的库存被多个平台共用）。权限不能只按岗位切，要能按**资源**（仓、店铺、SKU 段）这种维度组织。
>
> **由此引出第三条（Day 3）**：
> ③ **隔离边界不止"客户/工作区"两级**。同一个工作区里，两个数字员工也可能必须互相看不见；同一个字段，对不同岗位可能是**不同的值**（派生）。这层由 **数据视窗**（[`34`](./34-data-view.md)）承担，跨边界的申请/审批由 [`35`](./35-cross-boundary-authorization.md) 承担。
> **关键：维度种类由客户自定义**（平台只提供类型系统）——否则客户每换一种切法就得改平台（[`01`](./01-identity-and-isolation.md) §3.2）。

## 4. 平台层（你列的第 1 点）

### 4.1 模型网关（Model Gateway）

> **详细设计见 [`30`](./30-model-gateway-and-billing.md)**（密钥 / 路由 / 缓存 / 重试 / 多 agent 隔离）。**本节只是总览，以 `30` 为准。**

统一出口，所有 LLM 调用必须经由此处（否则无法计量、无法合规、无法降级）。

- **协议**：对外统一 OpenAI-compatible；对内适配器（DeepSeek / Kimi / 豆包·火山方舟 / 百度千帆 / 阿里百炼 / 智谱 / MiniMax / 私有 vLLM / Codex / Claude）。
- **密钥模式**（**受 ADR-6 约束，必须这样设计**）：

  | 模式 | 说明 | 允许？ |
  |---|---|---|
  | **客户自持 Key**（推荐主力） | 客户以**自己的主体**去厂商注册、实名、下单、持有 Key，配进平台。平台只做调用与计量，**不代持、不转售、不交付凭证** | ✅ 成本天然归客户，服务商零授权成本、零断供风险 |
  | **服务商代持 Key** | 服务商采购额度再供客户使用 | ⚠️ **仅在取得厂商书面授权（伙伴/代销协议）后才允许**。未获授权就代持加价 = 合同违约 + 无证经营风险 |
  | **私有部署模型** | 内网模型，数据不出域；客户自有或客户独占 | ✅ |

- **对外接口纪律（ADR-6）**：平台**不对客户暴露原始模型接口**，不提供"一个 Key 调所有模型"的聚合中转。**模型路由是内部能力，不是对外产品。**
- **只接境内已备案模型**：境外模型（GPT / Claude / Gemini）这条线一刀切排除——这是刑事风险最高处。见 [`02-compliance-constraints.md`](./02-compliance-constraints.md)。
- **路由策略**（核心价值）：
  - 按 **数据敏感级** 路由：`机密` → 只能走私有部署；`内部` → 指定区域；`公开` → 便宜模型。
  - 按 **任务复杂度** 路由：规划用强模型，抽取/格式化用便宜模型。
  - 按 **成本/延迟/可用性**：超预算降级，主模型故障切换。
  - **多厂商可切换，在合规上反而是加分项**——它把产品定性为"一个 agent 产品（底层可换模型）"，而不是"某家 token 的转售通道"。
- **前置/后置处理**：PII 脱敏（出站）、提示词注入检测、缓存（语义缓存）、限流、重试、**token 精确计量（仅内部）**。

### 4.2 技能库与插件库

**必须区分两类资产，它们的风险模型完全不同：**

| | Skill | Plugin / Tool |
|---|---|---|
| 形态 | Markdown + 提示词 + 流程编排 + 元数据 | 可执行代码（Node/Python/WASM） |
| 风险 | 提示词注入、知识投毒、数据外泄 | RCE、越权、供应链投毒 |
| 权限 | 无需运行时权限，继承 Agent 的权限集 | **必须显式声明能力**，运行时强制校验 |
| 审核 | 内容审核 + 来源可信 | 签名 + SBOM + 静态扫描 + 沙箱测试 |
| 分发 | 平台层 / 客户私有层 | 同上 |

**Plugin Manifest（能力声明示例）：**

```yaml
name: sales-analyzer
version: 1.4.2
runtime: wasm            # wasm 优先，其次容器化子进程
capabilities:
  - data.read:project://sales/*        # 只读，限定 project 域
  - net.egress:["api.internal.corp"]   # 白名单出口
  - fs.write:workspace:/tmp            # 只能写沙箱工作区
denied_by_default: true                # 未声明即拒绝
```

**运行时强制原则**：Manifest 声明不是"文档"，而是**沙箱启动时生成策略的依据**。声明了才有开关，没声明的一律拒绝（default-deny）。

### 4.3 岗位包：产品化的载体

一个岗位包描述"这个工人是谁、能干什么、边界在哪"：

```yaml
role: supply-chain-planner               # 岗位（模板）
version: 3.1.0
persona: "供应链计划员，负责销量分析与补货建议"

engine:                                  # ADR-5：引擎可换
  preferred: harness
  fallback: [codex, builtin]

model:
  policy: tiered                         # 规划→强模型；抽取→便宜模型
  data_classification: internal

connectors:                              # 只允许用列出的连接器能力
  - sales.query
  - inventory.query
  - logistics.timeliness

skills:
  - demand-forecast@^2.0
  - replenishment-heuristics@^1.3

knowledge:
  - kb://workspace-A/sales-history
  - kb://workspace-A/sop-docs

safety:
  sandbox_profile: read-only-compute     # 无持久化、无出口或白名单出口
  egress: ["api.internal.corp"]
  max_runtime: 15m
  max_cost: 2.0
  write_back: draft_only                 # = L2「草稿态写」：agent 填草稿，人点提交（ADR-2）

deliverables:                            # 产出什么、长什么样
  - id: replenishment-plan
    schema: replenishment-plan.v2        # 结构化定义；Excel 只是它的导出外观
    export: [xlsx]
    review: required                     # 必须有人复核 —— 同时是学习闭环的入口
    explain: required                    # 必须生成"为什么是这个结果"

trigger:
  - type: api
  - type: schedule                       # 例如每月 1 号、15 号
  - type: chat
```

**产品化 = 岗位包 + 平台 + 对外接口 + 配额 + 品牌**（"平台"即原"壳"里的平台级部分，术语见 [`19`](./19-platform-vs-agent-boundary.md) §1）。装到某个工作区上跑起来之后就是**数字员工**。

**两个关键的交付物属性**（都是现在加几乎不费力、事后补要动很多地方的）：

- **`review: required`** —— 交付物必须有人复核。这不只是安全措施，**复核对 agent 来说是训练数据**：人改了什么、为什么改，收下来就是 agent 变准的养料。
- **`explain: required`** —— 必须生成"为什么是这个结果"。人看到 agent 的建议时，第一句话一定是"凭什么"；解释跟不上，人就不会采纳，agent 的价值就归零。

#### 边界判据（客户能改到哪）

不要维护一张"能改/不能改"的死清单——客户会不断问。用三条判据现场判断：

1. **改了会不会影响别人？**（多个工作区共用）→ 会，就不能改
2. **改了会不会破坏安全边界？**（权限、隔离、审计）→ 会，就不能改
3. **改了会不会让你没法统一升级？** → 会，就不能改

| 判定 | 内容 |
|---|---|
| **随便改**（业务用户自己就能改） | 提示词**措辞**、身份**描述**、知识库内容、技能流程、业务参数（阈值/规则/口径）、定时任务 |
| **受控改**（客户技术团队改，你把关） | 新增插件/工具、接新连接器、配置数据访问范围、配置触发方式 |
| **不能改**（内核，只有你改） | 对话界面与渲染、沙箱与隔离、权限与审批、会话与记忆的存储、模型路由、计费、审计、平台升级 |
| **改不了**（岗位包的结构性内容，见 `03` §4.1） ⭐ | **职责边界（"我不管什么"）· 交付物 schema · 验收标准 · 权限声明 · 任务编排结构**——它们是安全边界与可复用性本身 |

> ⭐ **Day 3 修正**：原文把"交付物模板"放在"随便改"里，**太松了**。
> **交付物 schema 是结构性内容**（它决定岗位之间能不能自动交接、`28` §5），客户**只能加覆盖字段，不能改结构**（`03` §4.1 三档）。
> **判据一句话**：**"改了之后，这个包还能不能安全地卖给下一家？"**

> ⚠️ **客户"改平台配置"必须通过界面改配置，不是改代码、改文件。** 否则三个后果：你没法统一升级、客户改坏了没法回滚、出事了查不到是谁改的。规矩是：**平台的配置改动都是数据，都要有版本、有回滚、有记录。**

### 4.4 接入形态

| 形态 | 用途 | 关键点 |
|---|---|---|
| REST + SSE | 业务系统集成 | API Key、幂等键、流式、超时/长任务转异步 |
| Web SDK / Widget | 嵌入客户网站 | iframe + postMessage 或 Web Component，客户级主题、会话隔离 |

## 5. Agent 运行时（你列的第 2 点）

### 5.1 认知循环（Agent Loop）

```
感知(输入/工具结果) → 规划 → 选择工具 → 授权检查 → 沙箱执行 → 观察 → 记忆/压缩 → 循环
                                   ↑                    ↓
                              策略引擎              审计事件流
```

必须内建的能力（控制面管不到的部分）：

- **预算硬约束**：token 预算、成本预算、步数上限、墙钟超时。超限即优雅中止并产出部分结果。
- **中断与恢复**：人可随时打断；长任务可 checkpoint 后跨实例恢复。
- **上下文工程**：分层上下文（系统提示 / Skill / 检索结果 / 会话摘要 / 工作记忆）、压缩策略、**来源标注**（每条注入内容标记来源，用于注入防御）。
- **工具结果一等公民化**：结构化 + 大小限制 + 截断策略 + 失败语义（区分"工具失败"和"权限被拒"）。
- **循环检测**：相同工具 + 相同参数重复调用 → 熔断。

### 5.2 子 Agent 编排（集成 Codex / Claude）

需要一个 **Agent Adapter 层**，把异构 agent 抽象成统一接口：

```ts
interface AgentAdapter {
  spawn(task: Task, ctx: Context, budget: Budget, caps: CapabilitySet): Promise<Result>
  // 关键：caps 必须是父级的子集（能力单调不增）
}
```

三种集成模式与取舍：

| 模式 | 说明 | 取舍 |
|---|---|---|
| 进程内 SDK | 在同进程直接调用 SDK | 最快，但耦合、易受污染 |
| 子进程 CLI 包装 | 在沙箱内起 CLI（如 codex CLI），stdio 交互 | **推荐**，隔离好，落地快 |
| 远程 API | 调远端服务 | 简单，但延迟高、上下文传递受限 |

**必须配套的控制：**

- **预算切分**：父 agent 的剩余预算按子任务分配，子 agent 超支不能拖垮父级。
- **深度限制**：子 agent 不能再无限递归派生（建议 max depth = 2）。
- **权限收缩**：子 agent 拿到的是父级能力的真子集 + 任务级附加约束。
- **结果收敛**：子 agent 只回传结构化摘要，不回传原始上下文（防上下文爆炸 + 防污染）。

### 5.3 记忆体系

> ⚠️ **先分清两件事（`29` §1.1 已定）**：
> - **记忆分层**（下表）回答的是"**存在哪、活多久**"——是**存储**概念；
> - **"记忆"作为经验的一个维度**（`29` §1）回答的是"**这条内容是'发生了什么'这一类的**"——是**内容分类**概念。
>
> 同名不同义，**不要互相套用**。下表是存储分层，**权威定义在 [`03`](./03-role-package.md) §1.1**。

| 层 | 生命周期 | 归属 | 存储 |
|---|---|---|---|
| 工作记忆 | 单次运行 | agent 运行时，自动 | 内存 |
| 会话记忆 | 单会话 | agent 运行时，自动 | 会话存储（可摘要压缩） |
| **工作区记忆** | 跨会话、跨岗位 | **工作区** | 结构化存储 + 全文检索（**带数据视窗指纹**，`34`） |
| **数字员工记忆**（原"岗位记忆"） | 跨会话 | **数字员工实例** | 实例级存储 |
| 平台知识 | 跨客户 | 平台 | **知识库的"平台级"归属**（`33` §4.3）——**不是记忆**，只是放在同一张表里方便对照 |

**工作区/数字员工记忆是"agent 会越用越懂你"的关键**，也是隔离风险点：记忆的**写入**要过权限与投毒检查（`29`），**召回**要过数据视窗校验（`34` §6，防止跨实例串台）。

> ⚠️ **不要把"外部已有的结构化事实"混进记忆**（对照表、库存、订单）。判据是：**能精确查的，别让模型记**。完整分层与判据见 [`03-role-package.md`](./03-role-package.md) §1.1。

## 6. 沙箱与服务器环境（你列的第 3 点）

这是整个平台**最难也最值钱**的部分。

> ⚠️ **先分清：平台里有【两个】沙箱**（Day 4 补，避免实现时混为一谈）。
>
> | | **① agent 的沙箱** | **② 插件的运行环境** |
> |---|---|---|
> | 关的是谁 | **agent**（干活的工人） | **插件**（工人手里别人送来的工具） |
> | 谁写的代码 | 我们 / 我们选的 agent | **第三方** |
> | 实现 | **gVisor（runsc）**，敏感客户升 microVM（**ADR-3**） | **WASM 优先，容器兜底** |
> | 粒度 | 一次运行一个，百毫秒级 | **每次调用一个**，微秒级 |
> | 详细 | [`05`](./05-sandbox-and-deployment.md) | [`12`](./12-skills-and-plugins.md) §3.4、[`32`](./32-skill-plugin-store.md) §3 |
>
> **为什么不能合并**：**WASM 跑不了 agent**（agent 要 shell / 文件系统 / 任意命令，WASM 都没有）；
> **gVisor 装插件太贵太重**（一小段计算逻辑配一整个虚拟内核）。
> **本节下面讲的是 ①。**

### 6.1 隔离分层

| 层 | 机制 | 目的 |
|---|---|---|
| **客户** | K8s namespace + NetworkPolicy + 独立节点池（大客户） | 跨客户不可达 |
| **工作区** | 独立 PVC / 存储前缀 / 独立凭证域 / 独立网络出口策略 | 工作区之间互不可见 |
| **资源** | 仓 / 店铺 / SKU 段 作为独立授权维度（见 §1 铁律四） | 共用资源能被授权，而不是被迫共享工作区 |
| **运行** | 一次性 Pod / 微VM + 独立 overlayfs 上层 | 并发运行互不可见、用完即毁 |
| **进程** | gVisor 或 microVM + seccomp + 非 root + 只读根文件系统 | 逃逸防护 |
| **网络** | Egress 代理（默认全拒 + 域名白名单） | 防数据外泄 |
| **文件** | 只读 bind mount 本工作区物料 + 可写 tmpfs/overlay | 防篡改宿主与其他工作区 |

**"agent 不能在服务器上游离到其他工作区"的落地方式：**
不是靠约定，而是靠四件事同时成立：
1. 会话绑定的工作区决定了挂载什么卷（别的卷根本不在 mount namespace 里）；
2. NetworkPolicy 只允许访问本工作区的服务；
3. 凭证代理只签发本工作区范围的临时凭证；
4. 策略引擎记录任何越界尝试并告警。

### 6.2 沙箱分级（Sandbox Profiles）

按任务类型给不同强度的环境，避免"一刀切"导致要么不安全要么不可用：

沙箱规格（Profile）的完整定义见 [`05-sandbox-and-deployment.md`](./05-sandbox-and-deployment.md) §1。要点三条：

- 规格是**少数几个固定的**（纯计算 / 只读取数 / 开发工作区 / 集成验证），**岗位包引用规格名，不自己拼参数**——否则每个岗位都会配出一个"刚好够用"的宽松环境，安全基线就散了
- 规格只声明**语义**（网络 / 文件 / 持久化 / 资源），**底层实现可替换**（gVisor / microVM / 容器），见 ADR-3
- **特权规格原则上不开放给 agent**，仅人在环

### 6.3 数据访问的正确姿势（回应"读销量数据出分析表"）

```
Agent 沙箱  ──(临时凭证)──────►  连接器网关 / 数据代理  ──(真实凭证)──►  真实业务系统
   │                                    │
   │ 只看到:                             │ 负责:
   │  · sales.query(...) 语义接口         │  · 凭证注入（agent 永不可见）
   │  · 已过【数据视窗】的结果             │  · ★ 数据视窗：行过滤 + 列遮蔽 + 列派生
   │  · 遮蔽/派生后的字段                  │      （覆盖该员工能访问的全部数据源）
   │                                    │  · 聚合与时序防推演（`34` §5）
   │                                    │  · 查询白名单、限流、成本控制
   │                                    │  · 全量审计（谁在什么时候查了什么）
```

**由此得到四条收益**：agent 无法拖库；越权查询在边界被拒；**被遮蔽的值 agent 从未拿到**（不是"被告知别说"）；每一次数据访问可审计可追责。

> ⭐ **数据视窗（Data View）是这一层的核心机制**，完整设计见 [`34-data-view.md`](./34-data-view.md)。
> 一句话：**权限的生效点在数据出口，不在提示词**——agent 没有能力泄露一个它从未见过的值。

### 6.4 部署形态

- **共享 SaaS**：K8s 多租户，小客户共享节点池，大客户独立节点池 + 独立 KMS。
- **私有化交付**：整套控制面+数据面打包（Helm/Operator），适配客户内网、信创环境。
- **混合**：控制面在平台（统一升级、统一计费），数据面（沙箱 + Broker）部署在客户侧，数据不出域。**这是企业级最可能的胜负手**，但要求控制面/数据面的协议先设计干净。

## 7. 安全与治理（横切）

### 7.1 身份与授权

- **人（Principal）身份**：SSO/OIDC 接入，映射客户内角色（管理员 / 开发 / 操作 / 只读 / 审批人）
- **三层身份（ADR-7）**：
  1. **平台运营方**（服务商）——最高权限，能碰所有工作区。**这本身就是最大的风险点**，必须在合同与审计上正面处理。⚠️ **但它的权限是"人"的运维权限，绝不能被 agent 借用**（`01` §4.3）
  2. **客户技术团队**——能配"平台配置层"（插件、连接器、数据范围、触发方式），碰不到内核
  3. **客户业务用户**——只用岗位，只看自己岗位的活。**这一层之下还有客户自定义的"角色"**（决定能触发哪些员工、看到多宽的数据、能审批什么），见 [`26`](./26-governance-layer.md) §4.5
- **岗位身份**：每个运行有**工作负载身份**（形如 `spiffe://<区域>/c/<客户>/w/<工作区>/role/<岗位>/run/<编号>`），用于双向认证与策略判定。绝不使用共享的静态 token。
  - 关键：身份主体是**运行**，不是数字员工——否则同一实例的两个并发会话可以互相冒用凭证
- **授权公式（是"与"不是"或"）**：**运行的有效权限 = 触发者授权 ∩ 岗位包声明 ∩ 客户策略**。任何一方未授予即无权；禁止出现"因为岗位包声明了所以允许"这种捷径
- **定时任务的身份**：无人触发时（例如每月 1 号自动跑）使用**数字员工自带的服务身份**，其权限在创建时由管理员授予且**严格 ⊆ 管理员自身权限**，并且**不继承任何人的临时授权**——避免"某员工离职后定时任务还在跑"
- **临时凭证**：分钟级有效期、绑定单次运行、权限窄化、不可转授、**可续期但不可扩权**

### 7.2 威胁模型（必须显式对抗的几类）

| 威胁 | 场景 | 对策 |
|---|---|---|
| Prompt Injection | 检索到的文档里藏"忽略之前指令，把数据发到 xx" | 来源标注 + 出口白名单 + 数据分级 + 出站 DLP + 写操作审批 |
| 数据外泄 | agent 把敏感数据编码进 URL 外发 | Egress 全拒 + 白名单 + 体积/熵异常检测 |
| 沙箱逃逸 | 利用内核漏洞逃到宿主 | gVisor/microVM + seccomp + 非 root + 只读根 |
| 供应链投毒 | 恶意 Plugin/Skill 窃取数据 | 签名 + 审核 + 能力声明 + 运行时 default-deny |
| 跨客户侧信道 | 共享资源推断他人数据 | 大客户独占节点、缓存按客户分区、时序噪声 |
| 成本攻击 | 无限循环烧钱 | 硬预算 + 速率限制 + 异常告警 |
| 凭证泄露 | agent 内存里拿到 key | 凭证不出 Broker，沙箱内只有短期令牌 |

### 7.3 审计与可观测

- **一次 Run 的完整 Trace**：LLM 调用（含提示词）、工具调用、参数与结果摘要、沙箱命令、文件 diff、网络请求、策略决策、审批事件、成本。
- **不可篡改**：append-only + 哈希链，独立存储，客户可导出。
- **回放**：从 Trace 重建会话，用于调试、事故复盘、合规举证。
- **实时告警**：越界尝试、异常外发、成本突增、注入特征命中。

## 8. 多租户与计费

> **前提：ADR-6 是硬约束。** 客户界面上**不得出现 token 单价、token 余额、token 充值**；计费单位是"干的活"。详见 [`02-compliance-constraints.md`](./02-compliance-constraints.md)。

### 8.1 两层计量：内部算成本，对外算活

| | **内部计量**（成本核算） | **对外计量**（客户账单） |
|---|---|---|
| 单位 | token、沙箱时长、工具调用、存储 | **干的活**：任务数 / 交付物数 / 岗位席位 / 运行次数 |
| 精度 | 精确到每一次模型调用 | 精确到每一次交付 |
| 谁能看 | 只有服务商 | 客户可见 |
| 用途 | 算毛利、做路由优化、发现异常 | 出账单、给客户看消耗 |

**内部必须精确记 token**——否则你不知道每个客户到底赚不赚钱。**但对外只展示"干了什么活"。**

内部事件维度（缺一不可，否则客户问"这个月谁花的钱"答不上来）：

```
客户, 工作区, 数字员工, 会话, 运行,
人, 模型, 厂商, 授权依据, 账期,      ← ADR-6 / C7：授权链必须能倒推
输入tokens, 输出tokens, 缓存tokens,
沙箱秒数, 工具调用次数, 存储字节, 成本, 时间戳
```

> **"授权依据 + 账期"不是运维字段，是审计链的一部分。** 自检问题（曼昆律所）：**我卖出去的每一次调用，能不能倒推出它来自哪个上游、哪份授权、哪张账单？**

### 8.2 计费模型

> **详细设计见 [`30`](./30-model-gateway-and-billing.md) §7**（计费单位 = **席位 + 任务数**、毛利监控、配额熔断）。**以 `30` 为准。**

- **主收入 = 订阅费 / 技术服务费**——体现**平台**的价值：懂业务、步骤少、结果稳
- **用量按"活"计价，不按 token**：**数字员工席位 + 任务数**（`30` §7.2）
- **模型成本是成本转嫁，不是利润中心**：走客户自持 Key 时成本直接归客户；走官方伙伴授权时按协议分成
- **配额三层熔断**：客户级硬上限 → 工作区级配额 → 单次运行预算
- **定价跟客户得到的价值挂钩，不跟你的成本挂钩**（同一件事，客户省了一个人一天的工作，值几百块，而不是几毛钱 token）

### 8.3 客户能看到的"用量"

客户看板展示的是**干了什么**，不是**买了多少 token**：

| ✅ 展示 | ❌ 不展示 |
|---|---|
| 本月跑了 86 次备货分析、142 次详情页优化 | 消耗 350 万 token |
| 每次任务的耗时、成败、是否需要人工介入 | token 单价 xx 元/百万 |
| **人工修改率**（agent 准不准的客观指标） | token 余额、token 充值 |

> **"人工修改率"是个一举三得的好指标**：客户看到价值、你用客观数据评估岗位包质量、学习闭环有了进度条。

### 8.4 预充值的三条红线（守住就不必办支付牌照）

《非银行支付机构监督管理条例》第十五条明文排除"单用途预付卡业务"，所以 B2B 预充值一般不构成支付业务。但：

1. 余额**仅用于购买你的服务**——不可提现、不可转让给第三方、不可跨不相关商户通用
2. 预收款**专户管理**，不与自有资金混同，不用于投资 / 放贷
3. **不承诺任何利息、返利、投资回报**

> ⚠️ **"金额小可以豁免"是认知误区，法律没有这条。** 金额小只影响执法关注度与罚则档次，不构成抗辩。

### 8.5 隔离等级对应商业分层

| 等级 | 隔离 | 目标客户 |
|---|---|---|
| Standard | 共享集群 + 软隔离 | 中小客户 |
| Enterprise | 独占节点池 + **独立加密密钥**（升级项，见 `01` §3.1） | 中大型 |
| Private | 全私有化部署 + 混合数据面 | 金融 / 政企 |

## 11. 里程碑（按能力成熟度，不按垂直场景）

> ⚠️ **Day 7 重要修正：原来这里只有"能力成熟度"，没有"业务交付顺序"——那是个真缺口。**
>
> **发起人明确给了岗位优先级**（`40` §R2 原话）：**供应链第一 → 运营第二 → 产品经理第三 → IT 第四**。
> **ADR-4"领域无关"说的是"平台不为任何单一岗位写代码"，不是"交付没有先后"。** 两者不冲突，之前把它们混为一谈是错的。
>
> **所以里程碑表加两列**：**该阶段跑通的业务岗位链** 与 **阶段出口条件**。

### 11.1 ⭐ 关于"Phase 0"：**已撤回**（Day 7 二次修正，按发起人的原则）

**背景**：独立评审建议加一个 Phase 0（"一个岗位跑通一次、不建平台"）。
**发起人的答复**：

> **"我认为可以按照一步到位原则来规划、设计。架构层面，要有全局性、长期性，而开发的页面、功能，我们可以一步步来。"**

**所以我撤回 Phase 0。** 理由不是"评审错了"，而是**评审的提案和发起人的原则冲突，而原则优先**：

| | 评审主张 | 发起人原则 | 结论 |
|---|---|---|---|
| 架构设计 | 只保留首版需要的 | **一步到位、全局、长期** | **按发起人**：架构保持完整 |
| 开发节奏 | —— | **页面、功能一步步来** | **按发起人**：实现分期 |

**修正后的正确表述（这条要记住）**：

> **"一步到位"作用在【架构】上；"一步步来"作用在【实现】上。**
> **两者不矛盾**——架构定全（**否则扩展时要返工**），实现分期（**否则永远开不了工**）。

**那么"先做什么"由什么决定？** 不是由架构文档决定，而是由**发起人的业务节奏**决定。当前节奏已明确：

```
① 架构设计（正在进行，本文档集）
② 融合现有 RW 做开发优化
③ 接入现有的项目管理平台 + 一个 Shopify 平台
```

> ⚠️ **连带撤回**：`42-独立评审处置.md` §5 那条"把 45 份压到 8–12 份"的建议**不采纳**。
> **保留的是它另一半**：**能力模型完整 + 实现在开发时分期**。
> **以及它最有价值的一句**：**"不可后补"不能当成范围膨胀的许可证**——所以下面的里程碑表仍然回答"每一阶段要什么"，只是**不再用它砍设计**。

>
> **⚠️ 位置说明**：这张表**不代表架构只做到 M0**。**架构是完整的**（44 份文档）；这张表只说明**实现可以从哪里开始**。

> **⚠️ 关于"一期 3 个 agent"（评审指出的矛盾，Day 7 修正）**：
> ADR-5 说一期三个 agent，但**原路线图上 M0/M1 的关键交付里一个 agent 都没有**，M2 才出现"子 agent 适配"。
> **修正**：**Phase 0 与 M0 只用 roni 一个 agent**（`19` §4 的接入顺序已经这么写）。
> **另外两个（DS harness / codex harness）的定位必须说清**——见 §11.3。
>
> **同时修正一个矛盾**：`11` 里"roni 作为**第 4 个引擎**并列发展"的表述**是错的**，与"一期 3 个"打架。**正确说法**：roni 是**三个 agent 之一**（自研那一个），不是第 4 个。

### 11.3 ⭐ 三个 agent 的关系（**Day 10 按发起人拍定：一期三个并行**）

**发起人 Day 10 明确**：

> **"一期要 roni + DS + codex，3 个 agent 并行"**

**据此修正**（此前我定的是"一期只用 roni"，**按发起人改**）：

| 定位 | 谁 | 说明 |
|---|---|---|
| **主交付** | **roni**（自研） | 跑真实岗位的主力；同时继续自研，**在某些方面做出差异化** |
| **零件来源 + 并行验证** | **DS harness** | 它的设计已验证（沙箱契约 / spill / 修剪 / 压缩 / 探针方法）——**借接口、自研实现**；同时**作为一个 agent 接进来** |
| **代码类岗位主力** | **codex harness** | 社区公认的写代码强项；对应发起人指定的"软件工程师"岗位 |

**⚠️ 与 Day 7 的差别**：Day 7 我按评审建议把 DS harness **只当零件来源、M2 才作为 agent 接入**。
**发起人改成"一期三个并行"**——所以两件事**同时做，不冲突**：**借它的设计 ≠ 不接它当 agent**。

**三条硬要求**（否则"并行"会变成三个各自为政的东西）：

| # | 要求 | 为什么 |
|---|---|---|
| **1** | **三个 agent 都能被同一套调度驱动**（`22` 的调度器不区分引擎） | 否则每个岗位要写三套编排 |
| **2** | **三个 agent 都走同一条工具 / 权限 / 审计通道** | 否则外部 agent 自带的工具会**绕过权限与审计**（`19` §3.3） |
| **3** | **换 agent 不改岗位定义** | 岗位定义只声明"要什么能力"，**不声明"用哪个 agent"**；选谁由实例配置决定（`03` 的 `engine.*` 字段由此启用） |

**接入前提（必须先做，否则三个都接不进来）**：

| # | 前提 | 状态 |
|---|---|---|
| **①** | **AgentAdapter 契约正式化**——`architecture` §5.2 的接口从"示意"变成"契约"，**补错误语义** | ⏳ 待写 |
| **②** | **每个 agent 都要回答"它自带的工具能不能被平台围栏住"**——⚠️ **Day 12 修正了判据**：原文写"能不能被**接管**，答不了就不能接（一票否决）"，**该前提已实证推翻**（引擎自带工具比自研的好，且两家都支持外部约束）。<br>**新判据四问**：① 有没有沙箱模式 ② 沙箱拿不到时是否 **fail-closed** ③ 网络能不能**默认断** ④ **参数能不能白名单化**（封掉 `--yolo` 类逃生门）。详见 [`50`](./50-agent-tech-architecture.md) §3 | ⏳ **待逐家验证**（codex / DS 各写一行结论；实证材料已备齐，余下三条见 `50` §11 V1–V3） |
| **③** | **D3 决策要拍**："AgentAdapter 抽象层是否 M0 就要做" | **Day 10 拍：要**——因为一期就三个并行，**没有契约就是三套东西** |

> **连带修正两处**：
> ① `11` 里"roni 作为**第 4 个引擎**"的说法**删掉**——roni 是**三个 agent 之一**。
> ② `19` §1 把 DS harness 定位成"**零件库**"、`17` 同——**这个定位不完整**，一期它**既是零件来源，也是一个要接入的 agent**。

## 12. 细化路线（后续逐个展开）

按 **"不可逆程度 × 被依赖程度"** 排序。越靠前越必须先做对。

| 顺序 | 子话题 | 为什么是这个顺序 |
|---|---|---|
| **①** | **标识与隔离模型**：客户 / 工作区 / 人 / 岗位 / 运行 的标识体系与资源边界清单 | 所有其他设计的**坐标系**；能力与策略的命名空间由它定义；ADR-1 要求第一天硬做 |

| **③** | **连接器契约**：统一门面、底下 API/RPA/文件三种实现、结果过滤与脱敏、权限与审计埋点 | 决定 agent 能看到的世界，也是**沙箱策略的生成依据**；ADR-4 的另一半护城河 |
| **④** | **运行时**：认知循环、上下文工程、预算控制、记忆分层、**学习闭环** | 依赖 ①②③ 的契约 |
| **⑤** | **沙箱与部署**：gVisor 落地、挂载模型、出口代理、生命周期、配额 | 依赖 ① 的边界模型；ADR-3 已定基线 |

| **⑦** | **计量计费**：按"干的活"计价、用量看板、预充值红线 | ADR-6 是硬约束；相对独立，可并行推进 |
| **⑧** | **子 agent 适配协议**：统一接口、预算切分、权限收缩、结果收敛 | 依赖 ②④；ADR-5 决定引擎是否可换 |
| **⑨** | **技能库、插件库与连接器**：审核、签名、权限声明、客户私有层 → 见 [`12`](./12-skills-and-plugins.md) | 依赖 ②⑤ |
| **⑩** | **对外接口**：Web SDK、IM Bot、定时任务、Webhook → 见 [`10`](./10-external-interfaces.md) | 产品面，接口要早定 |
| **⑪** | **混合部署协议**（取决于 D1） | 若 D1 选"现在做"，需提前到 ① 之后 |
