# 细化 ④-C：会话与运行的生命周期

> 父文档：[`architecture.md`](./architecture.md) §12 细化路线 第 ④ 项
> 前置：[`07`](./07-engine-shell-boundary.md)（agent 内部：引擎与运行时）、[`08`](./08-context-engineering.md)（上下文与预算）、[`10`](./10-external-interfaces.md)（接口里的长活）
> 为什么单独做：**这套系统的常态是"长活 + 等人复核"**，而"中断后怎么恢复""等人时资源怎么办"没有任何别的文档覆盖。

---

## 0. 先把四个概念的寿命分清

**不同寿命的东西绑在一起，是这类系统最常见的架构错误。**

> ⚠️ **本文的四种寿命都在"一个数字员工之下"**。**数字员工本身是第五种寿命**（月～数年），它有自己的完整生命周期——
> 入职 / 上岗 / 契约修订 / 停用 / 复职 / **退出清算**，见 [`36-digital-employee-lifecycle.md`](./36-digital-employee-lifecycle.md)。
> **分界**：本文管"**一次干活的寿命**"，`36` 管"**一个员工的寿命**"。

| 概念 | 寿命 | 说明 |
|---|---|---|
| **交付物** | 长期（月/年） | 产出的东西，有版本、有状态、有复核记录 |
| **会话** | 天 / 周 | 人机交互的容器，可跨天 |
| **运行** | 分钟 / 小时 | 一次执行 |
| **沙箱** | **分钟级** | **用完即毁**（[`05`](./05-sandbox-and-deployment.md) 不变量 S1） |

**关键推论**：运行可以等几个小时（等人复核），但**沙箱不能等**。这两件事必须解耦。

---

## 1. 两种触发，结构不同

| | 有人触发 | 无人触发（定时 / 事件） |
|---|---|---|
| 有会话吗 | **有**——人机交互 | **没有**——就是一个独立运行 |
| 身份 | 触发者授权 + 岗位包声明 + 客户策略 | **数字员工的服务身份** |
| 特点 | 可以多轮、可以追问 | 一次跑完就结束 |

**别硬把定时任务塞进一个"会话"里**——它没有对话，塞进去只会让会话状态机变得难以理解。

---

## 2. 运行的状态机（注意"等待人工"）

```
排队 ──► 启动中 ──► 执行中 ──┬──► 已完成
                              ├──► 等待人工确认 ──┬──► 已确认 ──► 已交付
                              │                    └──► 被退回 ──► 执行中
                              ├──► 预算耗尽 ──► 已中止（保留部分结果）
                              └──► 失败
```

> ⚠️ **"等待人工确认"是一个独立状态，不是"还在跑"。**
> 对外接口（[`10`](./10-external-interfaces.md)）如果把这两者混了，客户的集成会一直等不到结果。
> 对内也一样：**监控、计费、超时策略对这两个状态的处理完全不同。**

---

## 3. 中断与恢复（最缺的一块）

三种中断，恢复方式不同：

| 中断原因 | 能不能继续 | 怎么继续 |
|---|---|---|
| **人主动打断** | ✅ | 接着跑，上下文还在 |
| **预算耗尽** | ✅ **但需要追加预算** | 追加后才能继续——**不能自动续，否则预算就是纸糊的** |
| **系统故障** | ✅ | **从检查点重建** |
| **策略拒绝 / 越界** | ❌ | 不恢复，等人工处理（这可能是安全事件） |

### 3.1 检查点存什么、不存什么

| 存 | 不存 |
|---|---|
| 上下文摘要 | **沙箱状态** |
| 已完成到哪一步 | 沙箱里的临时文件 |
| 已产出的交付物（已经独立存在） | 内存里的凭据 |
| 剩余预算 | —— |

**核心：恢复 = 重建一个干净沙箱 + 重放上下文摘要。** 不是"把沙箱恢复回来"——沙箱是一次性的（S1），指望它活着本身就是设计错误。

> ⭐ **Day 4 自审补：这一节就是 roni 的"任务现场"**
> `17` §1 记录 roni 有"记忆四层"，其中"**任务现场**"不是记忆——**它就是本节说的检查点**（`03` §1.1 的对账表）。
> **归属定死**：检查点**既不是**工作区记忆**也不是**数字员工记忆，它是**运行的附属物**——寿命跟着运行走（`13` §0 的第三种寿命）。
> **推论**：运行结束/被终止后，检查点按 `26` §3.4 的审计周期保留，**但不进任何"记忆召回"的候选集**。

#### 3.2 ⭐ 验收钩子：roni 已有能力，正式接进平台（Day 4 自审补）

`17` §1 记录 roni 有"**任务契约 + 无人值守驱动器（验收钩子）**"。**新架构一度只在 `28` 讲了"人复核"，没接住这个机制。**

**它是一个独立的触发点，和"人复核"是两件事**：

| | **验收钩子**（自动） | **人复核**（`28` §3） |
|---|---|---|
| 谁做 | **系统** | 人 |
| 什么时候 | 运行产出后**立刻** | 排在人的待办里，可能几小时后 |
| 判什么 | **机器可判的**：结构对不对、必填字段有没有、有没有突破硬阈值（`37` §4.1 的验收标准里**可自动判的那几条**） | **业务判断**：这个数合不合理、要不要改 |
| 结果 | 通过 → 进人复核队列；不通过 → **当场打回给 agent 重试**（省掉人白看一遍） | 改 / 批 / 驳 |

**三条规则**：

1. **钩子只判"机器可判"的部分**，判不了的一律交给人（**不许用模型冒充业务判断**）
2. **钩子不通过 → 先让 agent 自己修**（可配重试次数，`06` §5 的重试机制）
3. **钩子结果进账本 + 进 `29` 经验**——它是"机器判定"那一支的**前置**（`06` §2.3.6 的自动验证是同一条思路用在写操作上）

> **一句话**：**钩子管"格式和硬线"，人管"业务判断"。** 两者串起来，人才不会把时间浪费在"连必填字段都缺"的产出上。

> 这条也顺带解释了为什么**交付物必须独立于运行存在**：如果交付物只活在沙箱里，沙箱一销毁就没了。

## 4. ⚠️ 等人复核时，沙箱必须销毁（成本关键）

这是整份文档最实际的一条。

```
agent 产出草稿 → 运行进入"等待人工确认"
                        │
                        ├─ ❌ 错误做法：沙箱挂着等
                        │     → 一个等待复核的任务占着一个沙箱几小时
                        │     → 如果有 50 个单子同时在等人，你就有 50 个沙箱在空转
                        │
                        └─ ✅ 正确做法：**沙箱立即销毁**
                              人复核完 → 重建沙箱继续
```

**为什么这条重要**：沙箱成本是这套系统的主要成本之一（[`05`](./05-sandbox-and-deployment.md) §9）。而"等人"这件事**天然是慢的**——人可能半小时后才看，也可能第二天才看。

**如果沙箱跟着等，你的成本曲线会被"人的响应速度"决定，那是最糟糕的一种成本结构。**

## 5. 会话的归属、过期与并发

### 5.1 归属

会话**属于工作区**，不属于平台，也不属于人。
（同一个人可能在不同工作区有不同会话；同一个工作区的会话也可能被多个人看到，取决于权限。）

### 5.2 过期

| 什么时候清 | 清什么 |
|---|---|
| 会话过期 | **对话历史** |
| **交付物不清** | 交付物有自己的寿命和归档策略 |
| 记忆不清 | 记忆是跨会话的资产（[`03`](./03-role-package.md) §1.1） |

**"会话过期 ≠ 交付物过期 ≠ 记忆过期"**——这三个寿命不同，要分别管。

### 5.3 并发：同一会话串行

**同一会话同一时间只允许一个运行。**

理由：两个运行同时在同一个会话里跑，会同时改同一份交付物——**而交付物是有状态机的**（[`06`](./06-approval-and-executor.md)），并发修改会让状态机的语义直接崩掉。

不同会话之间当然可以并行。

---

## 6. 一个容易忽略的细节：谁的时钟

超时（等人工超时、运行超时、会话过期）用**谁的时钟**？

- 运行超时 → 平台时钟（技术问题）
- **等人工超时 → 客户的业务时区**（"24 小时"对客户意味着他的工作日，不是 UTC 24 小时）

**这条不注意，会出现"周六提交的单子周一早上就被自动拒绝了"。** 而 [`06`](./06-approval-and-executor.md) 定的是**超时默认拒绝**——所以时钟错了，后果是实实在在的。

## 7. 待决问题

1. **"等待人工确认"要不要占用并发配额？**
   占（保守，防止客户提一堆单子不处理）vs 不占（合理，因为没在消耗资源）。
   **我倾向不占执行并发，但单独设一个"待处理队列上限"**——两件事分开管。

2. **会话能不能"移交"给另一个人？**
   比如专员休假了，交给同事接着处理。
   **我倾向能，但要留痕**（谁在什么时候接管了），因为它会影响权限判定（新的人有不同的权限）。

3. **同一会话能不能有多个交付物？**
   比如一轮对话里既出了计划表，又出了分析报告。
   **我倾向能**，但要能明确区分——不能混在一个交付物里。

4. **运行失败后自动重试几次？**
   涉及钱的失败（预算耗尽）**绝不自动重试**。技术性失败（系统故障）可以重试，但要设上限（建议 1–2 次）。
   **"自动重试"在 agent 场景里比普通系统危险**——重试意味着重新烧一次钱，还可能重新改一次东西。
