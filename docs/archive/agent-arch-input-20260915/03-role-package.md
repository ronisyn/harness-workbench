## 0. 一句话

**岗位包 = 一个岗位的完整定义，全部是配置，一行代码都没有。**

它是模板；装到某个客户、某个工作区上跑起来之后叫**数字员工**。对外卖的"产品"，就是 *岗位包 + 平台 + 对外接口 + 配额 + 品牌*（"平台"= 原"壳"的平台级部分，术语见 [`19`](./19-platform-vs-agent-boundary.md) §1）。

**验收标准（可量化）**：新增一个岗位，需要动的只有——
① 写一份岗位包配置 ② 补它需要的连接器（如果没有）③ 定交付物结构 ④ 试跑调提示词 ⑤ 发布。

**如果这五步里出现了"改平台的代码"，说明抽象漏了。** 这条要一直拿来卡自己。

## 1. 岗位包里装什么（九块）

> **本节定义"装什么"；"怎么造出来、怎么复用、怎么不腐烂"见 [`37`](./37-role-package-authoring.md)。**
> **岗位包是平台方的资产**（不是客户的配置）——这决定了它必须**不含任何客户特有内容**（§1.3）。

按人的角度想："要交给一个新人一个岗位，你得告诉他什么？"——岗位包就是这份交接说明。

| # | 块 | 回答的问题 | 关键内容 |
|---|---|---|---|
| **1** | **身份** | 我是谁 | 岗位名、职责描述、说话方式（**表述性，客户可覆盖**）、**明确的职责边界**（我不管什么 → **结构性，客户不可改**，见 §4.1） |
| **2** | **能力** | 我能用什么 | 允许使用的连接器能力清单、技能、**知识集**（看哪些知识，见 `33` §4.3）、**工具分档**（见 §1.4） |
| **3** | **权限** | 我能碰到什么 | **数据要求**（需要哪类归属维度的哪个敏感级，见 §1.3）、能不能写、能不能外发 |
| **4** | **交付物** | 我产出什么 | 结构定义、状态流转、谁复核、要不要解释 |
| **5** | **任务编排** | 我怎么把活拆开干 | **这个岗位的活，拆成哪几个子代理、并行还是串行、结果怎么汇总**。例如"备货 = 销量子代理 + 库存子代理 + 物流子代理 + 验证子代理 → 汇总" |
| **6** | **触发** | 什么时候干 | 手动 / 定时 / 事件 / 接口 / **批量**（同模板 × N 份并行） |
| **7** | **运行环境** | 在哪干 | 沙箱规格、时长上限、成本上限、出口白名单 |
| **8** | **模型策略** | 用什么脑子 | 分级路由（规划用强模型、抽数用便宜模型）、数据敏感级、备用模型 |
| **9** | **交互形态** | 人怎么跟我打交道 | 对话式 / 列表式；显示什么；在哪确认 |

> **第 9 块（交互形态）的边界要划清**：**平台**提供"有哪些交互形态可用"（对话、列表、文件导出、审批），**岗位包**只声明"这个岗位用哪一种"。所以换交互形态算配置，改交互形态的实现才算动平台。

> **第 5 块（任务编排）是新加的**：它是"能确定的规则要固化、别让模型现场悟"这条原则的直接落地——备货的"查销量+查库存+查物流+验证→汇总"是稳定结构，写进岗位包，比每次让模型现场想"派谁"更稳、更省、更不漏。详见 [`09`](./09-subagent-orchestration.md)。

### 1.4 ⭐ 工具分档：roni 已有能力，正式纳入岗位包（Day 4 自审补）

**这一条是从 roni 现状里"捞回来"的**（`17` §1：roni 的 64 个工具分三档，**可裁剪、可拦截**，高危工具弹审批卡）。

**新架构一度只保留了"连接器能力清单 + 沙箱规格"，把"工具分档"这个成熟能力丢了。** 现补回，并和 `26` 的权限两维对齐：

| 档 | 是什么 | 例子 | 默认给谁 |
|---|---|---|---|
| **基础档** | 所有岗位都要用的通用能力 | 读写文件、计算、格式化 | **所有岗位默认带** |
| **专业档** | 按岗位职责授予的领域能力 | 供应链分析、详情页优化、BOM 处理 | **岗位包显式声明才给** |
| **高危档** | 一用就可能造成不可逆影响的能力 | 对外发送、批量写、删除、发布 | **默认一律不给**；要给必须走高阶授权 + 强制审批卡 |

**三条规则**：

1. **档位是"岗位包声明 + 平台规格"的交集**——岗位包声明"我需要专业档的 X、Y"，**平台政策决定"这个档位在这个沙箱规格里能不能用"**（同 `26` §2.2 的四方交集）
2. **高危档永远伴随审批卡**（不是"配了就用"）——这与 `06` 的 L3/L4 是同一套；`06` §2.3 的**首跑护栏**就是高危档的落地形态
3. **裁剪链沿用 roni 已有的**（`23` §1：会话档位 ∩ 平台档位 ± 强制开关）——**"工具的来源"从静态数组变成声明，裁剪逻辑本身不动**

> **为什么这条必须补回来**：它是"**能力最小集**"（`37` 质量门 G3）在工具层的实现。
> **没有分档，岗位包的"能力清单"就只能是一份平铺列表**——审的人看不出哪些是高危的，系统也没法对高危的自动加护栏。

### 1.1 记忆放哪？（最容易漏的一块）

记忆的**实现**属于 agent 运行时（所有岗位共用一套机制），但"这个岗位要用哪几类记忆"属于岗位包的**声明**。分四类：

| 类型 | 是什么 | 归属 |
|---|---|---|
| **工作记忆** | 单次运行内的临时上下文 | agent 运行时，自动 |
| **会话记忆** | 一段对话的上下文 | agent 运行时，自动 |
| **工作区记忆** | 这个工作区积累的经验（跨会话、跨岗位） | **工作区**，不是岗位包 |
| **数字员工记忆**（原"岗位记忆"） | 这个数字员工自己的经验（例如"上次这家供应商交期不准"） | **数字员工实例** |

> ⚠️ **两条消歧（Day 3 补）**：
> ① **"记忆"有两个意思**：上表是**存储分层**（存在哪、活多久）；`29` §1 的"记忆"是**经验的内容分类**（"这条内容是'发生了什么'"）。**不要互相套用**，见 `29` §1 和 `architecture` §5.3。
> ② **记忆要过数据视窗**（`34` §6）：跨岗位的工作区记忆**可能串数据权限**——A 团队的数字员工写进工作区记忆的内容，B 团队召回时不能捞出来。记忆条目带**视窗指纹**，召回时校验。

#### ⭐ 与 roni 现有"记忆四层"的对账（Day 4 第 2 轮自审补）

`17` §1 记录 roni 现在是**四层**：会话 / 长期 / 方法 / 任务现场。**新的四类必须和它对上账，否则移植时各说各话**：

| roni 现在叫 | 对应本文哪一类 | 处置 |
|---|---|---|
| **会话** | **会话记忆** | 一一对应，直接沿用 |
| **长期** | **工作区记忆 + 数字员工记忆** | ⚠️ **要拆成两个**——roni 的"长期"混着"工作区的"和"这个岗位自己的"，而它们的**归属与退出处置不同**（`36` §7.1 ②） |
| **方法** | **不是记忆** → 归 `29` 的技能/策略维，或 `12` 的技能库 | roni 的"方法"本质是**可复用的做法**，属于经验/技能，**不该按"记忆"管**（`29` §1 已定"五维是归类去向"） |
| **任务现场** | **不是记忆层** → 是 `13` §3.1 的**检查点** | 它解的是"运行中断后怎么接着跑"，**寿命跟着运行**，与跨会话记忆不是一回事 |

> **一句话**：**roni 的四层里，只有"会话"和"长期"是记忆；"方法"要归经验/技能，"任务现场"要归检查点。**
> **不拆的后果**：把"方法"当记忆去召回（污染上下文），或把"任务现场"当长期资产保留（沙箱都毁了还留着现场）。

> **⚠️ 一处需要你给事实**：roni 的"**长期记忆**"里，**工作区级和岗位级各占多少、能不能分开**？
> 这决定迁移时是"直接拆"还是"要先做一次数据归集"。
> **你不确定也行**：我按"可拆"设计，迁移时用 `29` §3 的三段式（agent 提议 → 人确认）逐条归位——**这本来就是经验入库的标准流程**。

另外还有一类**不属于记忆、却最常被混进来**的东西：**外部已有的结构化事实**（对照表、库存、价格、明细）。

> **判据：能精确查的，别让模型记。**
> 对照表、库存、订单这类东西走**连接器查询**，不要塞进上下文让模型"记"或"悟"——几万条数据塞不进上下文，让模型去猜又贵又容易错。
> **记忆**只留给"agent 自己的经历"；**知识库**留给"说不清、要理解的东西"（政策、SOP、历史邮件）；**技能**留给"怎么干一件事"。

### 1.2 职责边界必须显式写（第 1 块）
这一条最容易被忽略，但它决定 agent 会不会越界。

举例（抽象的，不涉及具体业务）：一个"分析型"岗位的边界要写明"**我只产出建议，不下单、不改数据、不直接联系外部**"。这句话不是写给模型看的礼貌用语——**它是生成运行权限的依据**。写进岗位包，策略引擎就按它发凭证；不写，模型就可能自己"顺手"把事情做了。

### 1.3 数据权限：岗位包只许"声明"，不许"写死"（Day 3 新增）⭐

**这是"岗位包能不能复用"的分水岭。**

一个岗位包要能卖给客户 B，前提是它**不含客户 A 的任何配置**。所以：

| 谁 | 定什么 | 例子 |
|---|---|---|
| **岗位包**（模板，跨客户复用） | **声明要求**：需要哪类**归属维度**的哪个敏感级 | "需要【某类归属维度】的**本团队**范围，敏感级 L2" |
| **数字员工实例**（客户自己的配置） | **填取值**：具体是哪一类维度、哪个取值 | "维度=货权团队；取值=A 团队" |
| **触发者**（人） | 再往上叠一层：这个人的角色允许看到什么 | 同实例下，主管与专员可见范围可不同 |

**⚠️ 岗位包禁止出现**：具体团队名、店铺名、仓库名、区域名——**出现一个，这个包就只能卖给这一家客户**。

**机制**：三方叠出来的结果就是**数据视窗**（[`34`](./34-data-view.md)），由策略引擎生成、在数据出口强制执行。**跨边界的申请/审批/执行**另有一套（[`35`](./35-cross-boundary-authorization.md)）。

**为什么维度种类也不能写死在平台里**：见 [`01`](./01-identity-and-isolation.md) §3.2 的修订——**维度类型由客户自定义**，平台只提供"可新增维度"的能力。

## 2. 交付物：整个架构里最该认真设计的一块

前面几轮的结论（ADR-2 永不直写、学习闭环、必须解释）**全部落在这一块上**。

### 2.1 结构

```yaml
deliverables:
  - id: replenishment-plan
    名称: 备货计划
    结构: replenishment-plan.v2        # 字段定义 —— 这才是内核
    导出: [xlsx]                       # Excel 只是外观
    状态机: 草稿 → 复核中 → 已确认 → 已交付
    可见: [岗位本人, 复核人, 下游岗位]   # ⚠️ 这是"权限"，不是"送达"（见下方 ⚠️）
    复核: required                     # 必须有人复核
    验收标准:                          # ★ 复核时按什么判合格（`37` §4.1 新增）
      - 每个 SKU 的备货量都附了计算依据
      - 未突破库龄滞销线
      - 缺数据的项必须显式标注，不能留空
    解释: required                     # 必须生成"为什么是这个结果"

    # ── 送达（Day 5 新增，定义见 `38` §4）──
    申请:                              # 岗位周围的第①种人：谁能提需求
      谁能提: [客户角色: 运营/采购]      # ⚠️ 角色，不是具体人
      入口: [界面, IM, 接口]
    送达:
      底座: 界面                       # 不可关（`38` §3）
      推送:                            # 全部可选
        - 渠道类: [IM, 邮件]
          对象类: [复核人, 申请人]      # ⚠️ 角色，不是具体地址
          时机: [待复核, 已确认]
          附件: [xlsx]
```

> ⚠️ **`可见` 和 `送达` 必须分开配（Day 5 补）**：
> **"能看"不等于"会被通知"。** `可见` 是权限（谁能查）、`送达` 是通知（推给谁、走哪个渠道）。
> 只配了 `可见` 会出现"有权限但没人知道计划出来了"；只配了 `送达` 会出现"推给了一个没权限看的人"。
> **完整设计见 [`38-deliverable-delivery.md`](./38-deliverable-delivery.md)。**
>
> **两条纪律**：① **岗位包里不许出现具体邮箱、群名、人名**（否则包不可复用，§4.1）；
> ② **"谁能申请"之前完全漏了**——客户的原话是"计划专员做，**其他人只是申请或者审核**"，这两个角色都必须有落点。

> ⭐ **`验收标准` 是 Day 3 补的**：早先定了"交付物要人复核"，**但没定"复核的标准从哪来"**。
> 它属于**这个岗位的业务定义**（不是平台的通用规则），所以**写在岗位包里**。
> **没有它，"复核"没有口径——`28` §3 的学习闭环拿到的就是脏数据**（人各凭感觉改，学不到规律）。

**核心原则（重复一遍，因为它太容易做错）**：

> **人看到的是 Excel，系统里存的是数据。**

字段定义是内核，Excel 是导出物。这样岗位之间能自动传、能对比历史、将来要接进 ERP 或做成界面都不用重做。

### 2.2 状态机 —— "永不直写"就落在这里

```
草稿 ──► 复核中 ──► 已确认 ──► 已交付
  ▲        │
  └────────┘  （被退回，带修改意见）
```

- **草稿**：agent 产出，还没人看过
- **复核中**：人打开了、可能正在改
- **已确认**：人点了确认——**这一步是人的授权动作**，不是 agent 的
- **已交付**：传给下游（下一个岗位 / 进 ERP 的草稿 / 发出去）

**对外部系统的写，一律发生在"已确认"之后，而且由平台侧的受信执行器代做**（ADR-2）。agent 自己够不着写路径。
→ 五级写操作的完整定义见 [`06-approval-and-executor.md`](./06-approval-and-executor.md)。

### 2.3 每一次人工修改都要记（学习闭环）

上面那条状态机还藏着一件更重要的事：**人在"复核中"改了什么，必须逐条记下来。**

```
agent 建议备货 320
人改成 400
原因：（他填的一行字，或者只是改了数）
```

三个月后，这些记录就是让 agent 变准的唯一燃料。

**为什么这条是自研的核心价值**：Codex、Claude Code、百炼都不知道你客户的专员为什么把那 80 补上。它们没有这条通道，你有。

> ⚠️ 设计上有两个坑：
> ① **别让"改"变麻烦。** 如果复核界面比他自己做还费劲，他就不改、或者敷衍地改，你的数据就废了。
> ② **别让"取代"提前显性化。** 如果专员觉得自己在被训练成一个即将被裁的岗位，他不会真心配合。第一阶段要让他因为"用了省力"而配合。

### 2.4 解释（`解释: required`）

人看到 agent 的建议，第一句话一定是"凭什么"。解释跟不上，人就不敢点确认，agent 的价值直接归零。

**解释不是可选的礼貌，是交付物的一部分**——它要落进结构里，跟着单据走，而不是只在对话里说一遍就没了。

## 3. 岗位包怎么长出来：派生，而不是复制

你有 16 个平台、每个平台一个运营。**如果每个都从头写一份包，就是维护地狱。**

所以必须定一条规则，判断"这是同一个岗位的不同配置"还是"两个不同的岗位"：

| 差异在哪 | 怎么办 |
|---|---|
| **参数和知识**（用哪个连接器、平台特有规则、专属知识库） | **同一个岗位包 + 多份实例配置** |
| **流程和交付物**（干活的步骤不一样、产出的东西不一样） | **另做一个岗位包** |

按这条规则：

- **Amazon 运营 / Shopify 运营 / Temu 运营** → 大概率是**一个"平台运营"岗位包 + 十几份实例配置**（因为它们产出的东西是同一类，差别在平台规则和数据源）
- **备货计划 / 采购 / 发货 / 仓储** → **四个不同的岗位包**（因为它们产出的单据不同、上下游交接物不同）

**这条规则的价值**：它把"16 个平台"的成本从乘法变成加法，而且它可测——如果某两个平台运营非要写两份包，你就要问一句"是我的包设计得不够通用，还是它们真的是两个岗位"。

## 4. 包与实例：客户改的是覆盖层，不是包本身

这是设计上必须现在定死的一件事，否则将来没法统一升级。

```
岗位包（你发布，版本化，不可变）
      ↑
      │ 客户只能在这里加覆盖
      │
数字员工（装到客户的工作区）
      └── 覆盖层：提示词调整、业务参数、专属知识、数据范围
```

**规矩三条：**

1. **包是不可变的版本**——你要改，发新版本，不能就地改
2. **客户的定制全部落在覆盖层**——所以升级新版本时，定制不会丢
3. **客户的覆盖有边界** —— ⭐ **Day 3 收紧为三档**（见 §4.1）

**升级时的呈现**：新包版本 + 客户的覆盖层 = 客户看到的。系统要能**明确告诉客户"新版改了什么、你的覆盖跟新版有没有冲突"**，否则没人敢升级。

### 4.1 ⭐ 覆盖的三档边界（Day 3 定：修正"随便改"这个含糊说法）

**原文第 3 条写"改提示词、知识、参数、模板 → 随便改"，太松了。**
问题在于：**"模板"里既有措辞，也有安全边界**——职责边界、交付物 schema、验收标准都算"模板"，但它们**不是客户能随便改的**。

**定死三档**：

| 档 | 内容 | 客户能改吗 | 为什么 |
|---|---|---|---|
| **结构性** | **职责边界**（"我不管什么"）· **交付物 schema** · **验收标准** · **权限声明**（要哪类数据、什么敏感级）· 任务编排结构 | ❌ **绝对不能** | ① 它们是**安全边界**（职责边界是发凭证的依据，§1.2）② 它们是**可复用性本身**（改了包只能卖给这一家）③ 它们是**契约的一部分** |
| **表述性** | 提示词措辞 · 身份描述 · 说话方式 | ✅ **在覆盖层改** | 不影响安全，且客户最需要调这个 |
| **取值性** | 数据要求的具体取值 · 业务参数与阈值 · 专属知识 · 挂哪些技能/连接器 | ✅ **在实例配置里填**（本来就是空的，§1.3） | 本来就是客户配置层 |

**判据一句话**：

> **"改了之后，这个包还能不能安全地卖给下一家？"**
> 能 → 表述性或取值性，客户可以改。
> **不能 → 结构性，客户不能改**（要改就找交付团队发新版本）。

**为什么这条要这么严**：`37` 定"岗位包是平台方的资产"。**资产的安全边界如果客户能随手改，那它就不是资产了**——每个客户手里都是一个私自分叉的版本，**平台再也说不清"我卖出去的岗位到底是什么"**。

### 4.2 ⭐ 覆盖层与岗位包升级怎么合（Day 3 补：最可能首发就出事故的一处）

**场景**：客户在覆盖层改过提示词 → 岗位包 v3 也改了同一段 → 冲突。

**我拍：覆盖层必须"可重放"。**

```
① 每个覆盖项记录【基于哪个包版本改的】⭐
      —— 否则 v3 上来时无法判断"这段覆盖还有效吗"

② 升级时的合并规则：
   · 客户没覆盖的部分      → 直接采纳新版
   · 客户覆盖过的部分      → 【冲突，让人选】
         [ 保留我的覆盖 ]  [ 采用新版写法 ]  [ 并排看 ]
   · 客户覆盖项是结构性的  → 不可能出现（§4.1 已禁止）；
                             若历史数据里存在 → 【强制标记 + 要求整改】

③ 合并结果生成新的【实例配置版本】，不改包本体
```

**为什么"记录基于哪个版本"是关键**：包从 v2 升到 v3，中间可能隔了 v2.1、v2.2。
**不记录基线，就无法判断"客户当年改的那段，在新版里是不是已经被平台改掉了"**——人只能盲选。

## 5. 版本与灰度

- 岗位包有版本号，可**灰度**：同一岗位上跑两个版本，对比交付物质量
- **跑过的历史可追溯**：某一单是哪一版包产出的，必须能查
- **对比数据天然来自交付物**：人改得多 = 这版包不好，人改得少 = 这版包好。**这是评估岗位包质量的客观指标，不靠感觉**

> ⭐ **Day 3 收口：灰度、回滚、紧急下架、发布审批的完整设计见 [`37`](./37-role-package-authoring.md) §6.1 与 §9**，本节只保留"为什么这么判"的原则。
> **本节的三条原则仍然权威**（灰度对比用交付物质量说话）；**操作流程以 `37` 为准**。
