# 26 · 治理层（多租户 + 策略引擎 + 审计）

> 状态：方案，技术决策由我拍。平台侧第一个议题。
> 前置：`01`（标识与隔离）、`02`（合规）、`19`（平台 vs agent 边界）
> **为什么三者合并设计**：它们本质是**一件事的三面**——"**谁能做什么**（多租户+策略）→ **做了什么**（审计）→ **算谁的**（归属）"。分开设计必然重复。

---

## 0. 一句话

**治理层 = 平台的"管"里最基础的一层：定权限、记行为、归责任。**

平台的其它能力（交付物流程、计费、模型网关）**都靠它提供维度**——所以它必须最先做。

---

## 1. 多租户：补"生命周期"和"归属链"

`01` 已经解决了**隔离**（标识体系、资源边界、越界防御四道闸）。平台侧还缺两块：

### 1.1 租户生命周期（我拍）

```
开户 → 配置 → 运行 → 停用 → 删除
```

| 阶段 | 要做什么 | 备注 |
|---|---|---|
| **开户** | 建客户、分配配额、建默认工作区 | 小客户自动建一个 `default`，把概念藏起来 |
| **配置** | 配策略、密钥、连接器、岗位包 | 走三层身份里的"客户技术团队" |
| **运行** | 正常使用 | —— |
| **停用** | 挂起（保留数据、停跑任务、可恢复） | 与"删除"区分 |
| **删除** | **密码学销毁**（销毁 KMS key） | `01` §6.4 已定 |

### 1.2 归属链（我拍：这是审计和计费的公共维度）

每个**事件、消耗、交付物**都必须能回答：

```
属于哪个客户 → 哪个工作区 → 哪个数字员工 → 哪次运行
```

**为什么单独强调**：客户问"这个月谁花的钱"、"这条数据谁改的"时，答案就靠这条链。**它现在散在 `01`/`architecture` §8 里，这里定死为治理层的公共维度。**

## 2. 策略引擎：权限拆成两个正交维度
### 2.1 ⭐ 改进 roni 的权限模型（借 harness 实查）

| | roni 现在 | harness 实际 | 判断 |
|---|---|---|---|
| 模型 | **四档一维**：只读/读写/需审批/完全 | **两个正交旋钮**：沙箱模式（`read-only`/`workspace-write`/`danger-full-access`）× 审批策略（`ask`/`never`） | **harness 更对** |

**为什么 harness 更对**：**"需审批"根本不是权限档位，它是正交的审批策略。** 混成一维会丢掉组合：

| 沙箱模式 × 审批策略 | 含义 |
|---|---|
| 只读 + 免审批 | 随便查，不用问 |
| **只读 + 需审批** | ← **roni 的四档表达不了这个组合** |
| 工作区可写 + 需审批 | 能写，但每次要人点头 |
| 工作区可写 + 免审批 | 放手干 |

**我拍：roni 的四档改造为两个正交维度。** 结果：策略表达力翻倍，而且每个维度可以独立调。

### 2.2 有效权限 = 四方交集（沿用 `01`，Day 3 扩为四方）

```
有效权限 = 触发者授权 ∩ 数字员工实例配置 ∩ 岗位包声明 ∩ 客户策略
```

**是"与"不是"或"**——任何一方没给就是没权限。禁止"因为岗位包声明了所以允许"。

> ⭐ **Day 3 新增第三方**：**数字员工实例配置**。
> **为什么必须补**：岗位包是**模板**，它只能声明"我需要某类归属维度的某个敏感级"（`03` §1.3）；
> **具体是哪一类维度、取值是哪个**，属于**这个实例**的配置。
> **不补这一方的后果**：同工作区内两个数字员工（同岗位包）会拿到**完全相同的数据权限**——**客户内部的数据边界无法表达**（`34`）。

**⭐ 这四方叠出来之后，落成什么**：四方交集的结果**不是一个布尔值**（能不能），而是一个**结构化的裁剪规则**——即**数据视窗**：

```
行过滤 × 列规则（可见 / 遮蔽 / 派生） × 聚合规则
```

**生效点在数据出口**（连接器网关），**不在提示词、不在 agent 的查询语句里**。

→ 完整设计见 [`34-data-view.md`](./34-data-view.md)。本文只定它的**位置**：**它是策略引擎的输出、治理层的一部分。**

### 2.3 策略的层级与覆盖（我拍：只能收紧，不能放宽）

```
客户级策略  →  工作区级策略  →  数字员工级策略  →  触发者角色
   （宽）          （更窄）          （最窄）          （只减不增）
```

**硬规则：下级只能收紧、不能放宽**，除非**上级显式授予"可放宽"**。

**为什么**：否则一个客户技术团队的成员，可以通过"改岗位配置"绕过客户级的安全策略——**权限的层级必须单向收敛**。

#### ⭐ Day 3 补充：正向那一半（"显式授权"）

上面这条只说了**负向**（只能收紧）。但**隔离不能是绝对的墙**——业务上确实存在"这次需要看一眼/动一下别人的东西"。

**我拍：放宽只有一条合法路径——上级显式授权，且授权本身是一个受审计的动作。**

| 项 | 规则 |
|---|---|
| **谁能放开** | 只有**上级**（客户策略层），不能自己给自己放开 |
| **放开什么** | 三档：**可见 / 可申请 / 可执行**（`35` §2），**不是"全开"** |
| **放开给谁** | **不指定具体岗位**——平台里不写死"某个岗位能跨边界"；由客户策略决定谁拿到档位 |
| **有没有期限** | **有**。默认带有效期，到期自动收回 |
| **留不留痕** | **留**。"谁在什么时候给谁开了什么"本身就是一条审计事件 |

→ 完整设计见 [`35-cross-boundary-authorization.md`](./35-cross-boundary-authorization.md)。

**一句话对比**：
> **收紧是默认行为，放宽是显式事件。**

## 3. 审计：记什么、怎么脱敏、怎么不可篡改

### 3.1 事件五要素（我拍）

| 要素 | 内容 |
|---|---|
| **谁** | 身份（人 / 数字员工的服务身份 / 平台运营方） |
| **何时** | 时间戳（绝对时间，带时区） |
| **对什么** | 资源（连接器、交付物、工作区、单据） |
| **做了什么** | 动作 + **参数摘要** |
| **结果** | 成功 / 拒绝 / 需审批 / 失败（**失败要分类**，见 `04` §4.1） |

### 3.2 ⭐ 脱敏：审计要能追责，但不该抄一份业务数据（借 harness 实查）

harness 的遥测有 **`redaction`（脱敏）** 这一步。**我拍：照搬这个原则。**

**判据：审计要能证明"谁在什么时候对什么做了什么"，但不该把业务数据抄一份。**

具体：参数摘要进审计，**原始业务数据不进**（尤其敏感的销量、价格、客户信息）。需要追细节时，靠"事件 → 运行 → 交付物"的引用链去找，而不是把数据存在审计里。

**为什么重要**：审计库如果存了业务数据，它自己就成了一个**新的泄露点**，而且合规上"留存了什么"也要交代。

### 3.3 不可篡改（沿用已定的）

**append-only + 哈希链**，独立存储，客户可导出。

### 3.4 保留策略（我拍）

| 层 | 保留 |
|---|---|
| **热** | **90 天**（沿用 roni 现有的归档周期） |
| **归档** | 更久（按客户合规要求定） |
| **删除时** | 审计记录**保留"操作事实"**，但清掉内容（合规通常要求保留操作事实） |

## 4. 三者怎么咬合（一次动作的完整链路）

```
① 策略判定      谁能做？→ 允许 / 拒绝 / 需审批
                      （**四方交集** + 层级收敛 → 落成**数据视窗**，`34`）
② 执行          agent 干活 / 平台代执行
③ 产生事件      由**执行方**产生（agent 或平台）
④ 审计          由**平台**记录 + 脱敏 + 不可篡改
⑤ 归集          挂到「客户 → 工作区 → 数字员工 → 运行」维度
```

**关键一条**：**③ 和 ④ 必须分开**——事件由执行方产生，审计由平台记录。**审计不能被被审计对象自己记**（否则被劫持的 agent 能洗掉痕迹）——这是 `19` §3.1 定的，这里落到机制上。

## 4.5 ⭐ 用户与角色：客户内部的"谁能干什么"（Day 4 第 4 轮自审补）

**这是一个被跳过的东西。** 我们定了**三层身份**（ADR-7：平台运营方 / 客户技术团队 / 客户业务用户），但**没有定"客户内部的用户账号与角色体系"**——而这是客户**开户第一天就要用**的功能。

**问题**：客户的"张三"和"李四"都是"客户业务用户"，**但他们能看的东西不一样**（`34` 的四方交集里，第四方"触发者授权"就是它）。**没有用户与角色体系，这一方是空的。**

### 4.5.1 与现实的关系（和 roni 的对照）

roni 有完整的账号体系（登录、用户、角色）。**新架构不能丢这块** —— 详见 `31` §6.1 的板块归位表（"设置"要按三层身份拆权限）。

### 4.5.2 我拍：三层身份之下，客户自己有"角色"

```
平台运营方            ← 服务商内部（ADR-7 第一层）
     │
客户技术团队          ← 客户方的开发/运维（能配平台配置）
     │
客户业务用户 ──┬── 角色 A（例：运营专员）   ← ⭐ 这一层是本次补的
              ├── 角色 B（例：运营主管）
              └── 角色 C（例：供应链协调）
```

**关键**：**角色名和角色权限由客户自己定，平台不预设**——同 `34` §3.3 的"维度类型由客户自定义"，**同一个思路**。

### 4.5.3 角色决定什么（三样，且都是"上限"）

| 角色决定 | 具体 |
|---|---|
| **能触发哪些数字员工** | 不是所有人都能用所有员工（`32` §2 的适用范围） |
| **触发时拿到的数据视窗宽窄** | 四方交集的第四方（`34` §3）——**同员工、不同人、看到的不一样** |
| **能审批什么** | 审批路由按角色走（`06` §5 的"需要角色"）——**这就是"审批方是配置不是代码"的落点**（`35` §2） |

### 4.5.4 四条必须定的规则

| 规则 | 内容 | 为什么 |
|---|---|---|
| **① 角色只减不增** | 角色的权限是**上限**，最终有效权限仍走四方交集；**角色不能"放宽"数字员工的数据视窗** | 同 `26` §2.3"只能收紧" |
| **①-b 角色不自动继承自组织架构** ⭐ | 飞书里的头衔（例："供应链主管"）**不等于**平台里的角色。**角色必须单独分配** | **Day 8 补**：否则**客户在飞书里改个部门就能提权**（见 [`44`](./44-loading-standard.md) §1.7.2） |
| **② 人员离职有单独动作** | `01` §6.6 已有（撤销其临时授权、服务身份不继承人的临时授权）；**另需：他正在跑的运行怎么办、他待审批的项转给谁**。**飞书同步到离职状态时自动触发这套动作** | 同 `36` §7 的员工退出清算，**只是对象是人不是 agent** |
| **③ 跨工作区授权** | 同一个人可被授权到多个工作区（`architecture` §3"人"一行），但**授权记录要能查**。**一个人也可以属于多个组织**（`44` §1.7.4） | 审计 |
| **④ 账号与认证：访客与员工【区别对待】** ⭐ | ⚠️ **Day 8 修正**：原文"平台不自建客户的账号体系去认证终端用户"——**这条对【客户网站的访客】仍成立，对【客户的员工】不成立**（员工要复核审批，必须有账号）。<br>· **访客** → 只判权限，不做认证（[`10`](./10-external-interfaces.md) §3）<br>· **员工** → 建账号；**优先走飞书认证（我们不存密码）**；客户不用飞书时才自建密码体系（**那种情况下合规责任由我们承担**，是明知的取舍）<br>详见 [`44`](./44-loading-standard.md) §1.7 | 一刀切会做错 |
| **④-b 本地账号的密码找回走【短信】** ⭐ | **Day 10 补**（发起人明确"短信也要加"）。**但短信做成"连接器能力"，不写死在平台里**：<br>· **优先用客户自己的短信通道**（客户若已有短信服务，配进来 → 凭据归客户，符合 `44` §1.6.3 的"凭据不入平台"）<br>· 客户没有 → 用平台代持的短信通道。**⚠️ 这是全平台唯一一处我们代持第三方凭据的场景**，要单独标注并写进条款<br>· **走飞书的用户不需要短信**（飞书自己管找回）——**短信只在"客户不用飞书"时启用** | 单人不该为"找回密码"建一整套短信基础设施；**做成可插拔的，客户自带最好** |

### 4.5.5 ⚠️ 与 `36` 的边界（别做重）

| | **本文（人）** | **`36`（数字员工）** |
|---|---|---|
| 对象 | **人**的账号、角色、权限 | **数字员工**的状态、契约、资产 |
| 退出叫什么 | **人员离职**（`01` §6.6） | **数字员工退出**（`36` §7） |
| 共同点 | **都要"清算 + 转交 + 留痕"** | 同左 |

> **一句话**：**"人离职"和"数字员工退出"是两条线，但清算的逻辑是同一套。** 实现时可以共用机制，**但不要混在一个状态机里**。

## 5. 验收标准

| # | 标准 |
|---|---|
| G1 | 任一消耗/事件/交付物，都能**倒推出"客户→工作区→数字员工→运行"**四层归属 |
| G2 | 权限能表达"**只读 + 需审批**"这个组合（现 roni 的四档表达不了） |
| G3 | 工作区级策略**无法放宽**客户级策略（除非显式授权） |
| G4 | 审计事件里**没有原始业务数据**，但有"谁/何时/对什么/做了什么/结果" |
| G5 | 审计事件**不可篡改**（改任一事件，哈希链断裂可检测） |
| G6 | 删除租户后，数据**密码学不可恢复**（KMS key 已销毁） |
| G7 | 同工作区、同岗位包的两个数字员工，**数据权限可以不同**（第四方"实例配置"生效） |
| G8 | 数据视窗由策略引擎生成，**在数据出口强制生效**；agent 的查询语句里**不含权限条件** |
| G9 | **放宽权限必须有显式授权记录**（谁在什么时候给谁开了什么档位），且**带有效期** |
| G10 | 平台里**不出现任何具体岗位名/团队名/审批角色名**（通用性判据） |
| G11 | 客户**新增一类边界维度、新增取值、改一次归属 → 平台零改动** |
| G12 | 岗位包**不含客户特有的维度名与取值**（复用性判据） |
| G13 | **角色由客户自定义**，且角色**只能收紧不能放宽**数据视窗；同员工、不同人、**看到的数据不同** |
| G14 | **不存在"以平台运营方身份运行的 agent"**；运维通道与 agent 通道分离，都留痕 |
| G15 | **人离职**能撤销其授权、转交其待审批项、处置其在跑的运行 |
