## 1. 今天走了一条什么路（脉络）

今天的讨论**不是按计划走的，是被三次调研拽着走的**，但结果是好的——它把一个错误的商业模式纠正了，并顺手把架构的地基打了下来。

```
你的初始设想
  平台 + agent + 服务器环境；多租户；每个租户配 Key、单独计费；
  沙箱隔离；技能库/插件库；封装成产品带 API
        │
        ├─ 我先给了一版总览架构（三块：平台 / Agent / 服务器）
        │
        ├─ 你纠正了三件事：
        │    · 垂直岗位只是举例 → 平台必须领域无关
        │    · "项目"指的是服务器上的独立工作单元（不是租户内工作域）
        │    · 你已经有客户，不是还在找场景
        │
        ├─ 关键转折：你说想靠"token 中转站"赚钱（加价 15%）
        │   → 我派了三路调研：①厂商条款 ②境内监管 ③逐家条款
        │   → 结论一致：这条路的形态违规，且上游随时断供
        │   → 但四家厂商都留了同一个口子：卖"产品/Agent"可以
        │
        ├─ 于是商业模式被逼清楚：**不卖 token，卖壳**
        │
        ├─ 你提出关键业务事实：计划类走 Excel、执行类走 ERP
        │   → 这自动划出了 agent 的边界：agent 待在"计划侧"，天然停在 ERP 门口
        │
        ├─ 你坦率承认：agent 最终会取代备货专员，第一阶段需要他复核
        │   → 复核 = 训练数据 = 学习闭环，这条成了架构的一等公民
        │
        └─ 你叫停了我往业务细节里钻，要求回到架构层
            → 我们统一了三层语言：引擎 / 壳 / 岗位包
            → 建了目标，按"设计文档"推进
```

## 2. 已锁定的 7 条决策（ADR）

写在 [`architecture.md`](./architecture.md) §0.5，**除非明确推翻，后续设计必须与之自洽**。

| # | 决策 | 一句话 |
|---|---|---|
| **ADR-1** | 多租户 SaaS 优先，**隔离从第一天硬做** | 这是骨架不是特性，后补不可能 |
| **ADR-2** | **agent 不直接改"生产"** | 落地形态 = agent 填"草稿/待审" → 人点提交。"生产"= 客户真实业务系统，不是代码开发、不是本平台 |
| **ADR-3** | 沙箱基线 **gVisor**，敏感客户升 microVM | 沙箱规格必须与底层实现解耦 |
| **ADR-4** | **平台领域无关**：岗位是配置，不是代码 | 验收标准：新增岗位只需配岗位包，不改壳 |
| **ADR-5** | **平台（Ronisyn）自研 + 三个 agent 可插拔**（roni / DS harness / codex harness） | agent 是平台里可插拔零件；工具执行/沙箱/权限/审计由平台托管 |
| **ADR-6** | **不卖 token，只卖 agent 能力** | 合规硬约束，客户界面不得出现 token 单价/余额/充值 |
| **ADR-7** | **三层身份**：平台运营方 / 客户技术团队 / 客户业务用户 | 不是两层 |

## 3. 今天达成的重要共识（这部分最容易忘，刻意用口语记）

### 3.1 战略层面

- **"引擎不值钱，懂业务的壳才值钱。"**
  能跑工具循环的 agent 框架已经快变成免费零件（Codex、Claude Code、harness）。自研一个"能跑的 agent"不构成优势。

- **你第二次失败（成本比别人高 2–3 倍）不是路走不通，是几个可修的点。**
  同一个模型、成本差 2–3 倍，说明**差距全在"你怎么把东西喂给模型"上**。通常是这几条：缓存没用起来、上下文膨胀、一个模型干所有活、步子太多、没有沉淀。
  → **"用更少的步骤干完同一件事"才是自研真正的理由。**

- **真正的护城河是这四样**，而且**它们不依赖任何厂商的授权**——厂商换谁，它们都还在：
  1. 懂这家客户的业务
  2. 把 19 个连接器接进来
  3. 把十几个岗位的活儿配出来
  4. 把人改动 agent 产出的反馈沉淀下来

- **"先窄"窄的是客户，不是岗位。** 你有一个客户，但这家客户有 19 个系统、十几类岗位。所以目标是：**一套底子，能长出十几个岗位，且第 12 个的开发成本远低于第 1 个。**

### 3.2 业务规则层面

- **计划在 Excel，执行在 ERP。** 这不是巧合——"计划"是人在脑子里想清楚的事，"单据"是系统里的既成事实。**agent 待在计划侧，想写也够不着写路径。**
- **Excel 只能是外观，不能是内核。** 内部必须是结构化数据，Excel 是导出物。否则岗位之间没法自动传、没法比历史、将来没法升级。
- **"能精确查的，别让模型记。"** 对照表、库存、订单走连接器查询；记忆只留给 agent 自己的经历；知识库留给说不清要理解的东西；技能留给怎么干一件事。
- **每个岗位只干到自己的节点**，产出交给下一个岗位；等稳定了、信任高了、不出错了，再"一步做到底"。**信任是靠不出错挣来的，不是靠权限设计给的。**

### 3.3 交互设计层面

- **运营用对话界面，备货专员用列表界面**——同一份单子的两种视角，**不是一个界面**。
  （"偶尔来一次要结果" → 对话式；"每天处理一堆单子要效率" → 列表式）
- **agent 最值钱的不是那个数，是"为什么是这个数"。** 解释跟不上，人不敢点确认，价值直接归零。
- **"一步做到底"的技术形态 = 填草稿，人点提交**，不是直接过账。

### 3.4 合规层面（最快最确定的一条）

- **最现实的不是罚款，是断供。** 阿里云百炼 §4.6、智谱 §6.2 都明文禁止转售。你一放量就被封，比监管来得快。
- **边界很清楚**：卖"token"违规，卖"集成进自己产品的 agent 能力"四家都允许。
- **"金额小可以豁免"是认知误区**，法律没有这条。金额小只影响执法关注度和罚则档次。
- **路径 A（客户自持 Key）其实就是你原方案 1.1 和 1.2 的形态**——被拿掉的只有 token 溢价和 1.3。**你的收费结构本来就有三分之二是对的。**

## 6. 你可能还没意识到的事（明天值得单独聊）

1. **连接器的长期运维工作量，很可能大于 agent 本身。**
   19 个外部系统，每个都可能在某天悄悄改点什么。这个成本要在方案阶段就认下来。

2. **多平台共享海外仓 → 权限不能只按岗位切。**
   一个仓的库存被多条业务线共用。如果每个岗位只看自己那本账，合起来必然超备——**而且没有任何一个人能看见这个超备**。资源（仓/店铺/SKU 段）必须是独立于岗位的授权维度。

3. **备货专员知道自己的岗位最终会被取代——这会打断你的学习闭环。**
   第一阶段最需要的正是他的复核和修改。所以：**别让"取代"提前显性化**，让他因为"用了省力"而配合。

4. **现状风险：服务器上多个工作区还没隔离，混在同一台机器上。**
   客户 A 和客户 B 的东西放在一起，一旦串了是合同层面的事。这不是"以后记得做"。

5. **"客户接受你能看数据"是个会变的条件。**
   小客户接受；等客户变成上市公司、有了合规部门，就不会接受。所以加密隔离设计要**留着升级余地**，别做成将来改不了的样子。

6. **WorkBuddy 归错类了**——它是腾讯的订阅产品（席位+积分），不是大模型额度供应商，和其他 7 家不是一个物种。

## 8. 一句话记住今天

> **不卖 token，卖壳。**
> 引擎用现成的，壳自己造；
> 岗位全靠配置，agent 停在 ERP 门口；
> 人改 agent 产出的每一次，都是它变准的燃料。
