# 27 · 服务器资源治理

> 状态：方案，技术决策由我拍。
> 由来：用户的真实场景——**一台阿里云服务器上有多个项目**（我们的平台、官网、以后别的项目），而这些项目**可能由不同的 agent 工具部署**（dsh harness、Claude Code），**互相不知道对方存在**。
> 前置：`05`（沙箱与部署）、`01`（隔离）、`14`（混合部署）

---

## 0. 一句话

**隔离靠"盒子"，不靠"知道"。**

不能指望新项目的 agent 先查清服务器现状——它不会知道，也不该指望它知道。**正确的目标不是"让它知道"，而是"让它即使不知道，也打不起来"。**

---

## 1. 问题：一台服务器上多个项目，会怎么打架

| 冲突类型 | 具体表现 |
|---|---|
| **端口** | 官网装了 nginx 占 80 → **平台起不来** |
| **资源** | 某个项目内存泄漏 → **平台的服务被系统 OOM 杀掉** |
| **文件** | 两个项目写同一个目录 → 互相覆盖 |
| **依赖** | 一个项目升级了系统库 → **另一个项目的依赖坏了** |
| **进程** | 一个项目重启机器 / 杀进程 → 殃及别人 |

**根因**：这些项目由不同 agent 部署，**互不知情**。

---

## 2. 核心原则

> **① 让它"不知情也不会冲突"；② 唯一必须共享的东西（对外端口）由人守住。**

推论：
- **不能靠"约定"**（指望 Claude Code 遵守你的规范，不可靠）
- **要靠"结构"**（盒子把冲突的可能性物理消除掉）
- 剩下守不住的（80/443），**由人把关**

---

## 3. 三层机制

### 第 1 层 · 盒子（解决 90% 的冲突）

**我拍：每个项目一个容器。**

**理由**：容器是 Linux 上最轻的"盒子"——独立端口、独立目录、独立依赖、独立进程空间，阿里云现成支持，没有额外成本。

```
服务器
├─ 盒子A：Ronisyn 平台     → 内部端口 8080
├─ 盒子B：官网             → 内部端口 8081
└─ 盒子C：以后的项目        → 内部端口 8082
```

**盒子里它随便折腾，出不了盒子。** Claude Code 不知道平台存在也没关系——它在 B 盒子里装什么，都碰不到 A。

**怎么让 agent 用盒子**：提供**项目模板**（一个 `Dockerfile` / `docker-compose.yml`），部署时把模板给它，让它照着来。**人验收时检查它是否用了模板。**

### 第 2 层 · 入口层（守住唯一必须共享的东西）

**对外只有 80 / 443 这两个端口是必须共享的。** 用一个**反向代理**独占总口，按域名分流：

```
平台.你的域名     →  盒子A（8080）
www.客户域名      →  盒子B（8081）
```

**我拍：用 Caddy**（比 Nginx 省事——自动申请和续期 HTTPS 证书）。

**硬规则：80/443 被反向代理独占，任何项目都不许直接绑。** 这条是**唯一必须由人反复叮嘱的规范**——因为它是唯一一个"不遵守就会出事"的点。

### 第 3 层 · 登记表 + 资源上限

**（a）登记表：记录每个项目占了什么**

| 项目名 | 盒子名 | 内部端口 | 对外域名 | 目录 | CPU/内存/磁盘上限 |
|---|---|---|---|---|---|
| Ronisyn 平台 | ronisyn | 8080 | 平台.xxx.com | /srv/ronisyn | 4核 / 8G / 100G |
| 官网 | website | 8081 | www.xxx.com | /srv/website | 2核 / 2G / 20G |

**这张表是给你（人）看的，不是给 agent 自动读的**——因为**只有你知道全局**（你有服务器账号）。新项目部署前，你看一眼"还剩什么"，告诉它用多少。

**（b）资源上限：防止一个项目拖垮全服务器**

**我拍：每个盒子设 CPU / 内存 / 磁盘上限**（容器原生支持）。

**理由**：即使某个项目跑飞（内存泄漏、死循环、被挖矿），**也拖不垮其他项目**。
**结果**：一个项目的故障不会升级成全服务器的故障。

## 4. 隔离的三层关系（容易绕晕，这里理清）

服务器上其实有**三层"盒子"**，从大到小套着：

```
① 项目盒子（服务器级）       ← 本文：一个项目一个容器
    └─ ② 工作区（平台内）    ← `01`：一个客户的一块业务
         └─ ③ 运行沙箱       ← `05`：一次 agent 运行（gVisor）
```

| 层 | 是什么 | 谁管 | 隔离对象 |
|---|---|---|---|
| **① 项目盒子** | 一个项目（平台本身、官网、其他系统） | **你（人）** | 项目之间 |
| **② 工作区** | 平台内，一个客户的一块业务 | **平台（Ronisyn）** | 客户/业务之间 |
| **③ 运行沙箱** | 一次 agent 运行 | **平台** | 单次运行之间 |

**关键**：**Ronisyn 平台本身就是"①项目盒子"里的一个**；它在自己盒子里，再往下分"②工作区"。

**混合部署也是这个模型**：客户的"数据面"装进客户内网，就是**客户内网里的一个盒子**——同一个概念，不同位置。

> ⭐ **Day 3 补充：测试/预演环境也是"盒子"**
> `36` §4.2 要跑联调时，**测试环境同样应该是一个独立盒子**（独立数据、独立凭据、独立配额），而不是"和生产环境共用一套、靠配置切换"——
> 后者一旦配错，就会出现"**以为在测试、实际写进生产**"（`04` §2.1 已警告过这个后果）。
> **盒子在这里的作用不只是防冲突，更是防误判。**

---

## 5. 部署规范（给每个 agent 的一句话规则）

**每次让任何 agent 部署东西时，告诉它这几条**：

1. **用容器**，一个项目一个容器，别直接装到宿主机
2. **别碰 80 / 443**——那是反向代理的，你用自己的内部端口（8081、8082…）
3. **设资源上限**：CPU / 内存 / 磁盘（照我给你的数字）
4. **目录只在 `/srv/<项目名>` 下**，别往系统目录写
5. **改完告诉我**：用了哪个端口、哪个目录、多少资源 → **我登记进表**

> ⚠️ **诚实说明**：这套规范的执行，**最终靠人把关**。因为：
> - 你无法强制 Claude Code 遵守
> - 你能做的是：**把 80/443 占住**（结构上守住），**部署后检查**（人工验收）
> 所以规范要短、要好检查——上面五条就是照着"好检查"设计的。

## 6. ⭐ 代码层：同一台服务器上的多个项目，代码也必须互不干扰（Day 6 补）

**上面 1–5 节解决的是"跑起来不打架"，没解决"代码层面不打架"。** 客户明确指出了这个场景：

> **"同一台服务器上有多个项目——Ronisyn 平台自己是一个，还有官网、还有给客户定制开发的项目。
> 这些代码提交的时候，项目和项目之间都不可以受干扰，应该是干净的、独立的。"**

### 6.1 两个项目隔离的判据（都要满足，缺一不可）

| # | 判据 | 怎么做到 |
|---|---|---|
| **1** | **代码互不可见** | **一个项目 = 一个独立仓库 + 独立工作目录**（`/srv/<项目名>`）。**不做 monorepo**——多项目共用仓库就必然共享分支、共享 CI、共享权限 |
| **2** | **提交互不影响** | **一个项目一套 CI/CD**，各自独立触发。A 项目提交**不触发** B 项目任何流水线 |
| **3** | **发布互不影响** | **一个项目 = 一个盒子**（§3 第 1 层）。发布 B 不动 A 的容器 |
| **4** | **依赖互不污染** | 依赖装**容器镜像里**，不装宿主机（§5 第 1 条）。**这是"一个项目升级库，另一个项目坏了"的根治办法** |
| **5** | **凭据互不通用** | 每个项目的部署凭据、仓库凭据、密钥**独立**（同 `01` 的凭证域分离思路，只是这里是服务器级） |

> **一句话**：**"一个项目"的完整定义 = 一个仓库 + 一套 CI + 一个盒子 + 一套凭据 + 一行登记表。**
> 五个要素齐了，项目之间才是干净的。

### 6.2 登记表要加一列

§3 第 3 层的项目登记表**少了代码这一维**，补上：

| 项目名 | 盒子名 | 内部端口 | 对外域名 | **代码仓库** ⭐ | **工作目录** | CPU/内存/磁盘上限 |
|---|---|---|---|---|---|---|
| Ronisyn 平台 | ronisyn | 8080 | 平台.xxx.com | **`<私有仓库>/ronisyn`** | /srv/ronisyn | 4核 / 8G / 100G |
| 官网 | website | 8081 | www.xxx.com | `<仓库>/website` | /srv/website | 2核 / 2G / 20G |

### 6.3 平台自己的扩展件，是**同一个项目**的不同目录（不是新项目）

客户的话：**"给平台内开发的有关代码的东西，比如 MCP、插件、更新工具之类的，那都属于咱们平台/agent 项目的优化、迭代开发。"**

**所以定死**：

```
Ronisyn 平台（一个项目、一个仓库）
├─ 控制面
├─ 数据面
├─ agent 运行时
├─ 连接器          ← 新增站点在这里（`39` §3）
├─ 插件 / MCP 服务  ← 扩展件在这里
└─ 工具
```

| 规则 | 内容 |
|---|---|
| **扩展件不新开项目** | MCP / 插件 / 工具都是**平台项目的目录**，共用同一套仓库、CI、凭据 |
| **但可以单独发布** ⭐ | 平台整体发布 vs 单个连接器/插件独立发版——**两者不矛盾**：同一仓库，**制品可以分开** |
| **边界** | 只有当某个扩展件**技术上必须独立部署**（独立进程/独立域名/独立生命周期）时，才考虑拆成独立项目——**并要在登记表里说明理由** |

> ⚠️ **为什么"可单独发布"这条必须写**：`37` §7 定了"岗位包升级 ≠ 在岗员工自动升级"，`32` §5 定了技能升级策略。
> **如果连接器的发布必须跟着平台整体发版，那"新增一个站点"就变成了"全平台发一次"**——`39` 的可扩展性承诺当场失效。
> **所以：同一仓库、独立制品、独立灰度。**

### 6.4 三种项目形态（都要能共存）

| 形态 | 例子 | 特点 |
|---|---|---|
| **平台项目** | Ronisyn（控制面 + 数据面 + agent + 连接器 + 扩展件） | **最大、最活跃、持续迭代** |
| **独立产品/站点** | 官网、其他自研系统 | 与平台无关，各自独立 |
| **客户定制开发** | 给某个客户做的独立系统 | ⚠️ **与"客户在平台上建的岗位包"完全无关**——那是交付物，这是代码项目 |

> **最后一条要划清**：**"给客户定制开发一个系统"**和**"在平台上给客户配一个数字员工"**是两件事。
> 前者是一个代码项目（走本文的盒子隔离），后者是平台内的配置（走 `36` 的生命周期）。
> **别把两者混在同一套流程里**——这是很容易发生的混淆。

### 6.5 与 agent 的关系（关键：谁来提交代码）

| 场景 | 谁写代码 | 走什么 |
|---|---|---|
| 平台自身的迭代 | 我们（可能用 agent 辅助） | **本文的代码项目隔离** |
| 新增连接器/插件 | 我们 | 同上 |
| **客户在平台上干活** | **数字员工** | **不走代码仓库**——它产出交付物（`28`），走审批（`06`） |

> ⭐ **一句必须写死的话**：
> **数字员工的沙箱里不会有"平台代码仓库"的凭据，也不会碰平台的源码。**
> 它干的是**业务活**（查数据、出计划），产出的是**交付物**——**和平台自己的源代码是两个完全隔离的世界**。
> 这条把 `14`（ADR-8 控制面不碰业务数据）反过来也堵上了：**业务侧也碰不到平台侧**。

## 7. 验收标准

| # | 标准 |
|---|---|
| S1 | **新项目部署时，不需要知道其他项目，也不会端口冲突**（各自内部端口） |
| S2 | **一个项目跑飞（内存/CPU 打满），其他项目不受影响**（资源上限生效） |
| S3 | **对外只有 80/443，且归反向代理独占**；新服务只加一条路由规则 |
| S4 | **新增项目时，人能在登记表里查到"还剩多少资源"** |
| S5 | **一个项目升级依赖，不影响其他项目**（容器内独立依赖） |
| **S6** | 一个项目 = **一个仓库 + 一套 CI + 一个盒子 + 一套凭据 + 一行登记表**；五个要素齐了，项目之间才是干净的 |
| **S7** | **A 项目提交代码，不触发 B 项目任何流水线**；A 发布不动 B 的容器 |
| **S8** | 登记表里**有代码仓库与工作目录**两列，新人能一眼看出"哪个项目占着哪块" |
| **S9** | **平台的扩展件（连接器 / 插件 / MCP / 工具）不新开项目**，但**可以独立发版与灰度** |
| **S10** | **数字员工的沙箱里没有平台代码仓库的凭据，也不碰平台源码**——业务侧与平台侧互相碰不到 |

## 8. 和平台的关系（一个可能的产品机会）

**现状**：这套治理在**服务器层**，靠人把关。平台管不了平台外的项目。

**将来可能的演进**：把"部署一个项目"做成**平台的一个能力**——任何项目（官网、其他系统）都通过平台部署，平台负责分配端口/目录/资源、自动登记、自动加路由。

**好处**：平台成为服务器的"唯一管家"，登记表自动化，不再靠人记。

**但前提**：所有部署都走平台。**只要有 agent 绕开平台直接部署，这套就不成立**——所以这是"长期目标"，不是现在的方案。

**现在**：服务器层三层机制 + 人工把关。**够用，且可靠。**
