# 45 · 架构能力清单（脱开业务的检验）

> **这份文档解决什么**：发起人要求——
> > "**把属于架构层面的活，单独抽离出来，架构就是架构，不和任何业务挂钩，架构能支持什么样的业务、支持什么样的场景描述一下**"
>
> **它同时是一次检验**：本平台的核心决策之一是"**领域无关**"（ADR-4）。
> **如果架构真的领域无关，它就应该能全部脱开业务讲。**
> **所以本文有一条自查纪律**：**任何一条能力里出现具体业务名词（行业、岗位、系统名、单据名），就说明那条没抽象干净，必须重写。**
>
> **读法**：先看"能力"（架构提供了什么），再看"能支持什么"（因此能承接哪些场景）。**"能支持"不是承诺实现，而是"架构上不会挡住"。**

---

# 第一部分 · 平台架构

## P1 身份与组织

**能力**：三层身份（**服务提供方** / 客户技术团队 / 客户业务用户）；客户内部可自定义角色；支持第三方身份源登录与组织架构同步（只读、单向、可撤销）；也支持本地账号；两者可共存。

**能支持什么**：
1. 客户已有企业 IM/统一身份，员工**一键登录**，自动落到正确组织，不需要手工分配
2. 客户没有统一身份，用**手机号 + 邀请链接**自助激活
3. 客户中途换 IM，员工**不会因此进不来**
4. 一个人属于**多个组织**，在其中是不同的角色
5. 人员离职 → **自动停用 + 转交待办**，但记录保留

## P2 数据权限

**能力**：按"**客户自定义的归属维度**"做行级过滤；列级三档（可见 / 遮蔽 / **派生**）；聚合防反推；默认隔离、按需显式授权；跨边界需申请-审批-执行。

**能支持什么**：
1. 同岗位、不同团队，**互相看不到对方的行**
2. **同一个字段，对不同人给不同的值**（如"对外口径"与"内部口径"）
3. **汇总数不给**（防止用总数减自己反推出别人）
4. "能看见但动不了"——要动必须走审批
5. 客户新增一类归属维度（团队 / 区域 / 品类 / 渠道…）→ **平台零改动**

> ⚠️ **本文的自查点**：这条能力里没有任何"团队/区域/品类"是**写死的**——它们全是**客户自己定义的类型**。这是它抽象干净的证据。

## P3 运行隔离

**能力**：一次运行一个一次性沙箱，用完即毁；沙箱规格只声明语义（网络/文件/持久化/资源）并能按档选择运行时；**同一个平台里有两个独立沙箱**（跑"干活的"和跑"别人送来的扩展件"）。

**能支持什么**：
1. 跑的东西**碰不到宿主、碰不到别人的运行、碰不到别的客户**
2. 沙箱**不能提权**
3. 有的活只需要算数（不给网络、不给持久化），有的活需要读文件、跑脚本——**规格可选，安全基线不散**
4. 扩展件（第三方代码）**只能调用显式导入给它的能力**，没导入的连入口都没有

## P4 写路径与审批

**能力**：系统永远不直接改外部系统的数据；产出草稿 → 人确认 → 由**唯一受信执行器**执行；写操作分级；无测试环境时的首跑护栏（预演 / 自动验证 / 成熟度阶梯）。

**能支持什么**：
1. 任何"会改变别人系统"的动作，**都必须经过人**
2. **写进生产系统的东西是可查、可撤、可冲销的**
3. 目标系统**没有测试环境**时，也能安全上线：先出"如果执行会是什么样"的方案给人看
4. **首次执行小范围、双人批、有人在线**；跑稳了再放开
5. 执行失败**自动降回保守模式**，不需要人工发现

## P5 模型接入（多厂商 + 路由）

**能力**：**接入多个模型厂商**（每个厂商可挂多个模型）；所有调用经**唯一出口**；密钥客户自持或平台代持；按成本/延迟/可用性**分级路由**；缓存分区；重试退避；只接合规范围内的模型。

**能支持什么**：
1. **一个客户可以只用一家，也可以多家并存**；客户换厂商**不动上层**
2. **同一个活，规划用好模型、抽数用便宜模型**——省钱的直接手段
3. 客户自持密钥时，**成本天然归客户**；没有密钥时平台代持、按用量对账
4. 模型故障自动重试与降级，**不丢任务**
5. **客户之间不共享缓存**（防止串数据）
6. **模型清单与路由策略是平台能力，不是写死在岗位里**——加一家厂商，所有岗位都能用上

## P6 外部系统接入

**能力**：所有外部系统经**连接器**接入，实现形态可换（接口 / 界面自动化 / 文件 / 协议）；对外只给**语义化能力**，不给通道；统一返回"带出处和时效的数据"；接入标准由平台发布。

**能支持什么**：
1. 接一个**有接口**的系统 → 直接接
2. 接一个**没接口但能导出文件/开只读账号**的系统 → 一样能接（且成本接近）
3. 接一个**只有界面**的系统 → 用界面自动化兜底
4. 接一个**什么都没有**的系统 → **明确拒绝**，而不是硬接
5. 对外系统改版 → **连接器吸收，上层不动**
6. **同一类系统（一组平台）实现同一套语义契约** → 新增一个成员时，**上层零改动**

## P7 交付与流转

**能力**：产出是**结构化的**（外观可渲染）；有验收标准；可被复核、流转、送达（界面为底座，外加可选推送渠道）；送达按收件人权限裁剪。

**能支持什么**：
1. 人看到的是熟悉的表格，**系统里存的是数据**（所以能自动传给下一个环节、能对比历史、能接回业务系统）
2. **复核有明确口径**（不是凭感觉）
3. 产出能自动流转给下一个岗位
4. 结果能到人手上：**界面看 + 导出**、或推送到企业 IM / 邮件
5. **同一个交付物，不同人看到不同口径**

## P8 知识与学习

**能力**：数据层（精确查询）/ 知识库（检索）/ 经验库（自生）三分；分层归属 + 知识集授权；经验从"人的修改"和"验收结果"里沉淀并防腐。

**能支持什么**：
1. **能精确查的绝不塞进上下文**（这是成本的根本）
2. 文档类知识**按需检索、带出处**
3. **"必须遵守"的东西不放在知识库里**——它是规则，由系统强制执行
4. 人改过的每一次，都能变成下次更准的依据
5. 过时/冲突/失效的知识与经验**会被清理**，不会越用越乱

## P9 可复用资产

**能力**：技能（声明式）/ 插件（可执行）/ 岗位定义 三层库；版本、签名、血缘、灰度、回滚、下架。

**能支持什么**：
1. 一种"干法"能被**多个岗位共享**
2. 一个"岗位定义"能**跨客户复用**（前提：不含任何客户特有内容）
3. 升级是**提案**，客户可拒绝、可钉在旧版
4. 发版出事能**硬下架 + 回滚**，且**历史产出标记来源版本**

## P10 生命周期

**能力**：一个"数字员工"有完整寿命——生成 → 配置 → 上岗 → 迭代 → 停用 → 复职 → **退出清算**；能力变化生成**版本化的权责契约**；有不可篡改的**就业账本**。

**能支持什么**：
1. 任一时点能回答"**它当时能干什么、谁批的**"
2. **退出 ≠ 删除**：退出是停止 + 清算资产；连痕迹都不留是另一个动作
3. 退出时**产出不受影响**（归属链仍能指回它）
4. 发现它不可信时，**先停用保留证据**，再决定
5. **人不能凭空消失、资产不能凭空蒸发**

## P11 装载与交付

**能力**：一份统一的装载标准，按客户环境分三种形态（云端 / 数据面 / 桥接）；客户拿"装载清单"；有**客户可执行的自检工具**，报告可签收。

**能支持什么**：
1. 客户用 SaaS → **客户什么都不装**
2. 客户数据不出内网 → 客户装**一个容器**（一条命令）
3. 客户有自己的系统 → **只调接口**，不改我们的东西
4. 客户能**自己证明装好了**（不是靠我们口头说）
5. **每个数字员工在客户系统里有一个专用账号**，不用任何员工的个人账号

## P12 多租户与治理

**能力**：客户 → 工作区 → 数字员工 → 运行的归属链；配额与熔断；全量脱敏审计；合规约束内建。

**能支持什么**：
1. 两个客户**互不可见**，账单**可出**
2. 任一事件、消耗、产出**都能倒推四层归属**
3. 一个客户跑飞**不影响其他客户**
4. 审计**不抄业务数据**（避免自己变成泄露点）
5. 客户退出时数据**密码学不可恢复**

## P13 部署与运行

**能力**：控制面与数据面分离；数据面可装在客户侧；服务器上多项目互不干扰（部署与**代码**两层）；数据面可独立运行。

**能支持什么**：
1. **数据不出客户内网**（数据面装进客户侧，就地读）
2. 控制面**不碰业务数据**（这是能被客户安全评审指着看的约束）
3. 同一台服务器上多个项目**端口、资源、依赖、代码都不打架**
4. **拔掉控制面，客户侧仍能继续跑**

## P14 可观测与运维

**能力**：运行状态、成功率、人工修改率、成本、告警（分级）。

**能支持什么**：
1. 客户看得到"**今天干了什么活**"（跑了几个、成了几个、待处理几个）
2. 服务提供方看得到"**哪个客户/哪个岗位在烧钱或在报错**"
3. **"人工改得多"= 这个岗位定义有问题**——这是可量化的质量信号
4. 异常**主动告警**，不用人去翻

## P15 扩展机制

**能力**：扩展分四层——**新成员（同类系统）/ 新系统 / 新岗位 / 新机制**；前三层**不需要改平台**。

**能支持什么**：
1. 客户多接一个同类系统 → **写一个连接器实现，岗位定义零改动**
2. 客户多接一个自有系统 → 写一个连接器，岗位定义只声明"要哪类能力"
3. 客户多要一个岗位 → **写一份岗位定义，不写代码**
4. **判据**：每次扩展问一句"**这次平台动了没有**"——动了且不是真机制升级，就是抽象漏了

## P16 ⭐ 资产库（技能 / 插件 / 工具 / 岗位 / 连接器）

**能力**：五类可复用资产各有**注册、签名、能力声明、版本、血缘、分发**；谁能装按身份分层；客户只能"引用 + 实例化配置"。

| 库 | 装的是什么 | 客户能改什么 |
|---|---|---|
| **技能库** | 一种"干法"（声明式，无代码）：流程 + 提示词 + 参考文档 | 客户业务用户可改表述与取值 |
| **插件库** | 会"算东西"的可执行代码 | 需签名 + 能力声明；客户技术团队装 |
| **工具库** | 被调用的动作清单（含内置工具与外部工具） | 按档分配；客户不可自定义 |
| **岗位库** | 一个岗位的完整定义（可跨客户复用） | 客户只做实例化配置 |
| **连接器库** | 接一个外部系统的实现 | 客户按受控模板配置 |

**能支持什么**：
1. **平台研发出一个能力，能被多个岗位复用**（不是每个岗位各做一份）
2. 客户**自助装卸**技能/插件（按层级限制）
3. 每个扩展件**声明它要什么能力**，运行时按声明**强制**
4. 升级是**提案**（通知 / 手动确认 / 强制补丁分级），客户可拒绝、可钉旧版
5. 卸载时检查依赖；**当前运行结束后才生效**（不中途拔）
6. 每个扩展件有**来源与签名**——能回答"这个是谁发布的"

## P17 ⭐ 扩展件的运行时管控

**能力**：插件与工具**不是"装上就能用"**——它们运行在**另一个独立沙箱**里，能力按声明注入。

**能支持什么**：
1. **没声明网络能力的插件，物理上发不出去数据**（不是靠"我们审过了"）
2. 高危工具**默认不给**；要给必须走高阶授权 + 强制审批卡
3. 同一个平台上，**跑"干活的"和跑"别人送来的扩展件"用两个不同的隔离边界**
4. 扩展件**只能看见显式导入给它的那点东西**

## P18 ⭐ Agent 的注册与接入

**能力**：agent 是**平台里注册的零件**；平台定义统一接入契约（怎么派活、怎么收结果、失败怎么分类、能力怎么收缩）；支持多 agent 并列。

**能支持什么**：
1. **接入一个新 agent，不改上层装配**（岗位定义、调度、权限都不动）
2. 每个 agent 声明**它能做什么、需要什么能力**，平台据此裁剪
3. **外部 agent 自带的工具必须走平台通道**——否则它的权限与审计全失效
4. 多 agent 可**并存**，按岗位配置选用

## P19 ⭐ 会话与运行编排

**能力**：一个"活"的生命周期管理——触发、状态机、排队、并发、中断恢复、超时、取消、事件流。

**能支持什么**：
1. 一次活**跨小时跨天**，中间等人的时候**不占计算资源**
2. 系统故障后**从检查点重建**，不丢进度
3. **多个活并发**，各自有配额，互不拖累
4. 人能看见"**跑到哪一步了**"（而不是黑盒等）
5. 长活有**明确的中间状态**（"等人复核"不等于"还在跑"）

## P20 ⭐ 对外接口契约

**能力**：把"派一个岗位干活 / 取结果 / 看状态"暴露成稳定接口；三种接入形态（直接调用 / 内嵌 / 桥接）；身份传递与幂等约定。

**能支持什么**：
1. 客户的系统能**以编程方式派活并取结果**（不是只能人工点）
2. 长活**异步 + 回调 + 状态查询**
3. 客户重试**不会重复干活**
4. 客户能把我们的能力**嵌进自己的界面**
5. **接口暴露的是"活"和"结果"，不是模型和 token**（对应"不卖 token"的定位）

## P21 ⭐ 会话（人机交互的容器）

**能力**：会话有归属、有寿命、有并发规则、可移交；会话与"一次运行"是两个概念。

**能支持什么**：
1. 人和数字员工**反复来回**（不是一问一答就结束）
2. **同一个人和同一个员工，昨天的对话今天能接着**
3. 同一个会话**串行执行**（不会两个人同时用同一个会话打架）
4. 会话**可以移交给另一个人**（接管要留痕）
5. **会话过期 ≠ 产出过期 ≠ 记忆过期**——三者寿命不同，分别管

## P22 ⭐ 人机交互面（复核 / 审批 / 看板）

**能力**：把"人要做的动作"变成界面——看结果、改结果、批或不批、看进度、导出。

**能支持什么**：
1. 人**看到"改了什么、为什么改、影响多大、有没有风险"**（不是给个"同意/拒绝"按钮）
2. 复核像改自己的文件，**不像签一份文件**（轻，人才会认真改）
3. 一键回滚 / 一键退回
4. 人能看到"**我有几件待办、卡在谁那儿**"
5. **同一份产出，不同角色看到不同的面**（复核人看细节、管理者看概览）

## P23 账与钱

**能力**：内部算成本、对外算"干的活"；归属到客户/工作区/岗位；毛利监控。

**能支持什么**：
1. 客户看得到"**我用了多少、花了多少**"（按"活"计，不是按 token）
2. 服务方看得到"**哪个客户在亏钱**"
3. 成本能**归因到某个岗位、某次运行**
4. **客户界面不出现 token 单价与余额**（这是定位，也是合规约束）

## P24 ⭐ 岗位包与库的【创作】（**设计侧专属**）

**能力**：网页工作台——从一句话到岗位制品的全流程：起草 → 结构化编辑 → 质量门 → 签名 → 发布到库；库的版本、血缘、灰度、回滚、下架。

**能支持什么**：
1. **一句话 → 生成一份结构完整的岗位定义草稿**，且标注哪几块是 AI 给的、哪几块待人确认
2. **人在结构化编辑器里改**（不是改一段提示词）——右侧实时显示"这个岗位会拿到哪些能力、哪些数据要求、哪些写权限"
3. **不合格不发**：九块齐、职责边界可执行、能力最小集、交付物可校验且带验收标准、**无客户特有名词**
4. **做包前先查库**：已有相似的 → 以它为基底特化，而不是从零来
5. **一个包能跨客户复用**；客户只做实例化配置
6. 升级是**提案**：客户可 diff、可拒绝、**可钉在旧版**；发版出事能**硬下架 + 回滚**

## P25 ⭐ 质量与回归（**设计侧专属**）

**能力**：金标冒烟——一组"已验收过"的标准任务集；改提示词 / 换模型 / 发新版包 **前必跑**。

**能支持什么**：
1. **改一句话不会悄悄改坏**——回归会告诉你哪一项变了
2. **结构类**问题自动判（不过就是不过）；**结论类**报警 + 人工确认（避免业务上合理的变化被误判）
3. **同一套用例可以两处跑**：设计侧（改之前）和客户环境（装之后），**两份报告能自动对比**
4. **客户环境失败而设计侧通过 → 说明环境差异**，这是最容易被忽略的一类问题

# 第二部分 · Agent 架构

## A1 可插拔与统一接入

**能力**：agent 是平台里**可插拔的零件**；平台定义统一的接入契约；一期多个 agent 并列；**换 agent 不动平台**。

**能支持什么**：
1. 用自研的、用开源的、将来再接别的——**同一套调度与权限**
2. 接入顺序与定位可以不同（先交付一个，其余按需接）
3. **换引擎不改上层装配**

## A2 引擎与运行时的边界

**能力**：思考循环归 agent；工具执行、沙箱、权限、审计归平台托管；两者接口清晰。

**能支持什么**：
1. 不同 agent 有不同"想法"，但**都必须走同一条工具与权限通道**
2. **外部 agent 自带的工具不能绕过平台**（否则它的权限与审计全失效）

## A3 工具（**agent 侧：怎么用**）

> ⚠️ **与 P16/P17 的分工**（Day 9 澄清，原清单把这层写偏了）：
> **平台管"工具/插件这个资产本身"**（注册、签名、装卸、能力强制、版本）→ **P16 / P17**
> **agent 管"这一次活里怎么挑、怎么调"**（选择、参数、编排、裁剪链）→ **本节**

**能力**：按档选用工具（通用 / 专业 / 高危）；裁剪链（会话档 ∩ 平台档 ± 强制开关）；高危必带审批；工具清单**按需**装配。

**能支持什么**：
1. 同一个 agent，**不同任务拿到不同工具集**
2. 高危动作**永远有人卡着**
3. **不用某类工具的轮次，它的清单和说明一条都不带**（同 A5 的按需原则）
4. 加一个工具（平台侧）→ **agent 内核不动**

## A4 会话与运行

**能力**：两种触发（有人 / 无人）结构不同；运行有状态机（含"等待人工"）；可中断可恢复；沙箱用完即毁。

**能支持什么**：
1. 一次活能跨小时、跨天，**中间等人不影响资源占用**
2. 系统故障后**从检查点重建**（不是把旧沙箱救回来）
3. **无人值守也能跑**（定时/事件）

## A5 上下文

**能力**：分层上下文（稳定的在前、变化的在后）；按需召回（技能、知识、数据）；大结果落盘 + 中段修剪 + 比例压缩；**可信度分层**（系统层可信、外部内容不可信）。

**能支持什么**：
1. **不用某样东西的轮次，那样东西一条都不带**（这是成本的根本）
2. 上下文塞不下时**自动压**，且**被省略的部分有明确声明**
3. 外来的内容**不能改写指令**（防注入）

## A6 记忆

**能力**：分层记忆（运行内 / 会话 / 工作区 / 数字员工）；跨会话保留；写入过权限与投毒检查，召回过数据视窗校验。

**能支持什么**：
1. 同一个员工**下次记得上次的事**
2. 记忆**不跨权限串**（A 团队写的不会被 B 团队召回）
3. **"能精确查的"不进记忆**（对照表、明细之类走查询）

## A7 子代理编排

**能力**：按模板并行/串行派子代理，结果结构回收；子代理**权限只能更窄**；预算隔离；深度限制。

**能支持什么**：
1. 一次活拆成多路并行取数再汇总
2. 一路失败**不拖垮整体**（标注该块未取得）
3. 一个子代理烧钱失控**只烧它自己的额度**
4. **子代理拿不到比父级更大的权限**

## A8 成本控制（agent 侧）

**能力**：预算硬约束（token / 成本 / 步数 / 时长）；超限优雅中止并产出部分结果；免模型的修剪不额外调用；缓存友好排布。

**能支持什么**：
1. 跑飞之前**先停**，而不是事后才发现
2. **停下来也有产出**（不是白跑）
3. 省的手段**每一笔都能说出省的是哪一块**

# 第三部分 · 架构【不】支持什么（同样重要）

**明确说"不做"，比含糊说"支持"更有价值。**

| 做不到 / 不做 | 为什么 |
|---|---|
| **让机器自己决定改客户的生产系统** | 任何写生产都必须经人（ADR-2）。**这是产品定位，不是能力不足** |
| **接一个"什么都没有"的外部系统** | 没有接口、不能导出、不能开只读账号、也不让人操作 → **拒绝接入** |
| **客户之间共享模型缓存或记忆** | 会把跨客户复用写进设计（P5） |
| **员工在手机上走完审批** | 移动端当前不做（发起人已拍）。**通知能到手机，审批要回桌面** |
| **平台替客户做业务判断** | 平台给数据、给建议、给草稿；**判断与授权归客户的人** |
| **把"必须遵守"当成知识去检索** | 那不是知识，是规则，必须由系统强制执行 |
| **一次运行跨越多个客户** | 归属链第一位是客户，不可跨 |

# 第五部分 · 三个平台（官网 / 业务工作台 / 研发后台）

> **由来**：发起人提出——"**把平台分成两个部分，一个为业务服务（多租户、开账号、制作岗位包/数字员工），一个为我们的 agent 服务**（管理与设计 agent）"。
>
> **这个分法解决了一个之前写得很别扭的地方**：原来"平台提供沙箱接口、agent 自带沙箱实现"读起来别扭，
> 因为它把两件事混在一句话里——**研发 agent 时需要"能跑命令的地方"（研发侧）；客户跑任务时需要"受限的执行环境"（业务侧）**。
>
> ⚠️ **Day 12 修正：从"两个"改成"三个"**（决策 172/173/193）。
> 原表述漏了**官网**（对外讲清楚卖什么的地方），且旧名「设计平台」**把造 agent 和看客户线上状态捏成了一块**。
> 现在统一为：**① 官网 · ② 业务工作台 · ③ 研发后台**。

## 5.0 ⭐ 三个平台先分清（一句话各自是什么）

| | **① 官网** | **② 业务工作台** | **③ 研发后台** |
|---|---|---|---|
| **一句话** | 讲清楚我们卖什么 | **客户干活的地方** | **我们造与调 agent 的地方** |
| **内容源** | [`48`](./48-product-and-services.md) | 本文 §5.1 A 列 | 本文 §5.1 B 列 |

## 5.1 ⭐ 业务工作台 / 研发后台是什么

| | **A · 业务工作台**（对外） | **B · 研发后台**（对内） |
|---|---|---|
| **一句话** | 客户用它的地方 | **你造东西的地方** |
| **给谁用** | 客户的人（技术团队 + 业务用户） | **只有你**（将来是交付团队） |
| **在管什么** | 客户、工作区、人员角色、数字员工、交付物 | 岗位包、技能、插件、工具、连接器、Agent 接入、**CRM** |
| **核心动作** | 派活、复核、审批、看结果、看账单 | 起草、质量门、签名、发布、灰度、**调教与评测** |
| **形态** | **多实例**（每客户一个实例） | **一个实例**（网页工作台） |
| **多租户** | 必需 | **不需要**（一个内部单位就够） |
| **计费** | 必需 | 不需要 |
| **默认权限** | **只读**（`06` L0–L2，写要审批） | **读写**（要写代码、写配置） |
| **有没有客户业务数据** | **有**（敏感） | **没有**（只有测试样本；要看客户现场走代运营通道，以客户身份进、以服务商身份留痕） |
| **改动频率** | 低（稳） | **高（天天改）** |
| **出事影响** | **客户的生产** | 只是我们自己的研发 |

**最后三行是关键**：**默认权限相反**（只读 vs 读写）· **改动频率差一个量级** · **出事影响面完全不同**。
**这三点决定了它们不该混在一个安全边界里。**

## 5.2 ⭐ 不是两套东西，是【一份架构 + 两个实例】

**为什么不拆成两套代码**——两边要重复一大堆，而且会漂移：

| 两边都需要的 | 拆成两套的代价 |
|---|---|
| 登录与组织同步 | 写两遍，且两套认证会不一致 |
| 五类资产库 | 写两遍，**而且两边会漂移** |
| 审计与归属链 | 写两遍 |
| 会话与运行编排 | 写两遍 |
| 数据权限 | 写两遍 |

```
一份架构  →  两个实例

【B · 研发后台】网页工作台（1 个实例，只有你能进）
  起草岗位包 → 结构化编辑 → 质量门 → 签名 → 发布到【库】
  金标冒烟跑回归；用开发工作区规格（能写代码）
        │
        │  ⭐ 唯一的通道：制品进【库】（带版本与签名）
        ▼
【库】技能库 / 插件库 / 工具库 / 岗位库 / 连接器库
        │
        │  客户"采纳"才生效（不是自动同步）
        ▼
【A · 业务平台】（N 个实例，客户用）
  派活 → 复核 → 审批 → 拿结果 → 看账单
  只读取数规格；写操作走审批
```

**两个实例之间只有一条通道：制品库。** 这条通道**同时就是质量门、签名、版本、灰度的位置**。

## 5.3 ⭐ 五条不可混的规则

| # | 规则 | 为什么 |
|---|---|---|
| **① 客户永远进不了研发后台** | 那是"我们的工作台"，不是"客户的后台" | 一旦客户能进，他就能看/改我们给别家做的包 |
| **② 研发后台永远没有客户的生产凭据** | 它不需要连客户的系统 | 它是"**造工具的地方**"，不是"用工具的地方" |
| **③ 生成与执行分离** ⭐ | 岗位定义（人设、提示词、工具授权）在**研发后台产出**；业务平台**只按岗位包调用，不现场生成** | 这是"**同一个岗位卖给多家**"能成立的前提 |
| **④ 两边共用同一套身份、权限、审计模型** | 同一份架构，只是实例与配置不同 | 避免两套东西各长各的 |
| **⑤ 唯一的通道是制品库** | 任何"从 B 直接推到 A"的形式都不允许 | 否则会**绕过质量门** |

> ⭐ **第 ③ 条顺便回答了发起人最开始的那个问题**——"**我开发好一个岗位包，怎么装进客户系统**"：
> **产出物是"制品"（进库），装载是"制品到客户实例"**。
> **这不是两个独立问题，是一条链**：`研发后台造 → 库 → 客户采纳 → 业务平台装载`（`44` §6）。

## 5.4 能力域的归属一览

| 归属 | 能力域 |
|---|---|
| **共用**（一份设计，两个实例都跑） | P1 身份 · P2 数据权限 · P3 运行隔离 · P4 写路径审批 · P5 模型接入 · P6 外部系统接入 · P7 交付流转 · P8 知识学习 · P9 可复用资产 · P10 生命周期 · P11 装载 · P12 多租户 · P13 部署 · P14 可观测 · P15 扩展机制 · P16 资产库 · P17 扩展件管控 · P18 Agent 注册 · P19 会话与运行编排 · P20 对外接口 · P21 会话 · P22 人机交互面 · P23 账与钱 |
| **业务侧为主**（设计侧也有，但用途不同） | P10 生命周期（客户侧的员工）· P11 装载 · P12 多租户 · P23 账与钱 |
| **设计侧专属** ⭐ | **P24 岗位包与库的创作** · **P25 质量与回归** |
| **agent 侧** | A1–A8 |

> **说明**：多数能力"共用"是因为**两个平台用的是同一套底座**——
> 但**实例不同、配置不同、能看到的数据不同**。
> **这不是"没分开"，而是"分开的是实例与数据，不是代码"。**

# 第六部分 · 怎么用这份文档

| 谁 | 怎么用 |
|---|---|
| **发起人** | 逐条看"能支持什么"——**如果发现某条其实做不到，或者你还要的场景这里没有，就是架构缺了** |

| **客户/评审** | 看"能力"判断够不够；看"不支持什么"判断边界清不清楚 |
