# 20 · 移植 DS harness 零件（借鉴设计，在 roni 里实现）

> 状态：方案，**技术决策由我拍，用户只看结果**。
> 前置：`18`（抽边界）、`19`（平台/agent 边界）、`15`（harness 映射）
> 核心决定：**移植的是"设计"，不是"代码"**。harness 的价值在它的抽象接口思想，不在它的实现。

---

## 0. 总原则

> **借接口，不借代码。** 学 harness 的"抽象层怎么切"，在 roni 自己的 Node 架构里实现。

理由：harness 是 TS + Cordis 插件框架，直接拷代码会带进 Cordis 依赖，把 roni 变成"另一个 harness"。学设计则让这些能力变成 **roni 自己的资产**。

**做完的总体结果**：roni 从"进程裸跑的单体"变成"命令在受控沙箱里跑、大结果落盘、工具可装卸、压缩可替换"的独立 agent——具备入驻客户环境的硬条件。

## 1. 逐零件：借什么、怎么落地、结果是什么

### 1.1 沙箱（第一优先，最硬）

> ⚠️ **Day 4 第 3 轮自审修正：harness 的沙箱"不是"我们要的那种沙箱——这条必须写清楚，否则会误导实施。**
>
> **实读本机 dsh 0.1.5-rc.2 的证据**：
> - `dsh-sandbox` = "**Abstract process-sandbox seam**（同世界约束词汇表 + SandboxProvider 契约）"
> - `dsh-sandbox-local` = "**bwrap / landlock-run / macOS Seatbelt / Windows ACL restricted-token** 后端"——原话是 **same-world confinement**，且 **functionally probed, fail-closed**
> - 整个 README **没有出现** gVisor / runsc / microVM / kata / firecracker
>
> **结论**：harness 的沙箱是**"限制 agent 自己的进程权限"**（同内核、同世界）；
> 我们要的是**"把 agent 当成不可信工作负载"**（gVisor/microVM，**另一个内核**）。**两者不是强弱之分，是威胁模型不同。**
>
> → **所以沙箱这件事上，"可移植件"只有一半**：

| 借什么 | 不借什么 |
|---|---|
| ✅ **`SandboxProvider` 契约**（接口形状、"同世界约束词汇表"、模式语义） | ❌ **底层实现**——harness 那四个后端（bwrap/Landlock/Seatbelt/ACL）**满足不了 ADR-1 的不可信工作负载前提**，不能拿来当隔离层 |
| ✅ **`fail-closed + functionally probed`** 的做法（见 §1.1.1） | ❌ 把"harness 有沙箱"当成"沙箱问题已解决" |

**在 roni 里落地**：
- roni 现在的 `run_command` 是"进程裸跑"→ 改成**通过一个 `sandboxProvider` 接口执行**
- 接口定义（概念）：
  ```
  execute(命令, {模式, 工作区根, 网络}) → {结果, 是否被拒}
  ```
- **实现：直接 gVisor（runsc），一步到位**。理由：ADR-3 已定 gVisor 基线；服务器是阿里云 Linux；"本地文件策略"没有进程隔离，达不到"入驻客户环境"的硬门槛，**不做过渡方案**。
- ⚠️ **这条现在是"纯平台自研"，不是"移植"**——`20` 的标题是"移植 harness 零件"，**沙箱这一项要单独标注：接口借、实现自研**。

**结果**：命令不再裸跑；混合部署时数据面装进客户服务器，命令跑在受控圈里；**接口沿用 harness 的形状**，所以将来换实现（容器 → gVisor → microVM）不改上层代码。

#### 1.1.1 ⭐ 借一条做法：fail-closed + 功能探针（Day 4 第 3 轮自审补）

harness 的原话是 **"functionally probed, fail-closed"**——**不是"配上就当生效"，而是"先探测它真的能生效，探不出来就拒绝"**。

**为什么这条必须借**：沙箱"看起来配上了、实际没生效"是最危险的状态——**所有安全假设都建立在它生效之上**。

**在 roni/平台里落地**：沙箱 provider **启动时（及定期）做一次功能探针**：

| 探针 | 判什么 | 不通过的处置 |
|---|---|---|
| **真的隔离了吗** | 在沙箱内尝试写工作区外的路径 / 访问网络 → **应当失败** | **拒绝启动该 provider**（fail-closed） |
| **模式真的生效了吗** | `read-only` 下尝试写 → 应当被拒；`workspace-write` 下写工作区 → 应当成功 | 拒绝启动 |
| **拒绝是可区分的吗** | 返回的是"被拒"还是"执行失败"（`19` §3.5 的接口要能区分） | 拒绝启动 |

> **与 `36` §4.2 的 `data_view.probe` 是同一条思路**：**"声明"不算数，"探一次"才算数。**
> 一个是探隔离（数据视窗），一个是探沙箱（执行环境）——**两处都要探，都不能靠配置自我声明。**

### 1.2 可插拔工具系统

**借鉴 harness 的设计**：每个能力是**一个可装卸的包**（声明 + 装载），不是静态数组。

**在 roni 里落地**：
- 把 64 个工具从"1225 行文件 + 静态数组"→ 改成"**每个工具一份 manifest（名字、能力、权限要求、参数 schema）+ 一个装载器**"
- ⚠️ 这**就是**议题 1「抽边界」的第 3 个动作（工具声明化）——两者是同一件事，一起做

**结果**：工具能按客户/岗位装卸；三个 agent 各自的工具能通过统一方式登记，且都能被平台的权限/审计约束住（对应 `19` 的"agent 自带、平台托管"）。

### 1.3 大结果落盘（spill）

**借鉴 harness 的设计**：`dsh-spill` —— "**存下超大的工具文本，返回一个检索定位符**"。

**在 roni 里落地**：
- roni 现在是"工具结果最多 4000/12000 字符，超了截断"→ 改成：**超阈值 → 存盘 → 上下文里只放"结果在 spill://xxx，摘要：…，需要时 fetch"**

**结果**：上下文不再被大结果撑爆；agent **知道自己不知道什么**（比给它一个残缺数据强）。直接治 roni 总结里的"工具结果大"。

### 1.4 工具结果修剪（tool-result-pruner）

**借鉴 harness 的设计**：`dsh-compaction-tool-result-pruner` —— "**免模型的 head/middle/tail 修剪**"（保留头尾、中间占位，**不额外烧一次 LLM**）。

**在 roni 里落地**：roni 已有"头尾裁剪"，把它**组件化 + 加强**，成为独立可替换组件。

**结果**：修剪不花钱（免模型），且能单独调优。

#### 1.4.1 ⭐ 文件观测策略（Day 4 第 3 轮自审补：我早先判断错了）

**harness 有 `dsh-fs-observation-policy`**，原话是：
> "**observed-state, read-before-edit, and version-guarded write/edit** … through the `fs/*` event gate"

**我早先判断这份"不必要"——判断错了。** 它防的是三类会真出问题的情况：

| 机制 | 防什么 | roni 现在有没有 |
|---|---|---|
| **read-before-edit** | 模型**没读过这个文件就改它** | ❌ 没有 |
| **observed-state** | 模型基于**自己记忆里的旧内容**改文件（而不是刚读到的） | ❌ 没有 |
| **version-guarded write** | 读完之后**文件被别人改了**，模型的修改会覆盖掉别人的改动 | ❌ 没有 |

**为什么对我们是刚需**（三条理由，任何一条都够）：

1. **多 agent / 子代理并行**（`09`、`22`）：两个子代理同时碰同一批文件 → **后写的覆盖先写的**，而且**没人知道**
2. **混合部署下客户侧也会有并发**（客户自己的系统在动同一份数据）
3. **重放/恢复**（`13` §3）：从检查点恢复后，上下文里的文件内容可能已经过时 —— **不校验就会拿旧内容去写**

**在 roni 里落地**：
- 在文件能力上挂一个**事件门**（不需要新服务 API，harness 就是这个做法）
- 写/改之前校验：① 读过吗 ② 读到的是不是当前版本 ③ 版本变了就**拒绝并要求重读**

**结果**：**"基于过时内容做修改"这类静默错误被堵掉**——它的危害比"操作失败"大得多，因为**失败会报错，覆盖不会**。

#### 1.4.2 ⭐ 有界保留 + "省略了什么"必须可见（Day 4 第 3 轮自审补）

**harness 有 `dsh-output-retention`**，原话是：
> "**bounded-retention primitive**（`ItemRetainer`/`TextRetainer`）+ **neutral notice helpers（what did we keep, what did we omit）**"

**我们 `23` 讲了 spill 和修剪，但漏了后半句**：**"省略了什么"要有一条中立、可见的提示。**

| 少了这条会怎样 | 有了这条 |
|---|---|
| 模型**不知道自己少看了东西** → 拿着残缺信息当真 | 模型知道"还有 N 条被省略了"，**可以主动去取** |
| 人复核时看不出 agent 是不是"漏看了" | 交付物上的省略量可见（`23` 的"省略量明确"要**贯通到交付物**，不只是上下文里） |

**在 roni 里落地**：
- spill / 修剪 / 压缩**三个组件都产出统一格式的"保留声明"**（保留了什么、省略了多少、怎么取回）
- 这条声明是**中立的**（不是"我尽力了"这类话术，而是**结构化的计数 + 取回方式**）

**结果**：`23` 的"省略量明确"从"上下文里的一个数字"升级为**贯穿整个链路的契约**——包括最终交付给人时。

### 1.5 压缩（compaction）—— 只借鉴，不移植

**判断**：roni 已有两道压缩（轻压缩 + 语义折叠），功能上不缺。缺的是 harness 的"**组件化**"——现在硬编码在 agent.js/index.js 里。

**落地**：把压缩抽成独立组件（可替换），不搬 harness 的代码。

**结果**：以后调压缩策略不改核心代码。

### 1.6 workflow —— 拆成两半，一半早做、一半后置

**判断（已修正）**：原以为"用不上"，其实用户的业务有批量并行需求。要拆开：

- **批量并发**（16 平台备货、500 SKU 详情页、多账号广告 = 同一类任务 × N 份，并行跑、各自出交付物、汇总）→ **业务需要，应早期做**。它属于"触发方式 + 并发"机制，由岗位包的定时/批量触发管，不依赖脚本。
- **脚本化 workflow**（写 JS 扇出几十个**异构**子代理、分阶段依赖、结构化回收）→ **开发者工具，后置**。业务用户不写 JS。

**结论**：批量并发并入早期（随岗位包触发机制一起做）；脚本化 workflow 后置。

## 2. 顺序

```
① 沙箱（SandboxProvider 接口 + 本地文件策略实现）
② 可插拔工具系统（= 抽边界的第 3 动作，一起做）
③ spill + 工具结果修剪
④ 压缩组件化
⑤（后置）workflow
```

理由：**沙箱最硬、最优先**（混合部署的前提）；工具声明化和抽边界是同一件事，跟着边界走；spill/修剪治成本，紧跟；压缩只是重构，最后。
