# RW 事件契约（SSE / 事件环）v1

> **状态**：已确认 · 2026-09-15 · 对应《RW-Agent 架构 v1.1》§14.9 `RA-37`
> **这份文档回答什么**：一次 agent 执行期间，服务端向前端推的**事件流**到底是什么、每个事件什么语义、
> 客户端能否**仅靠事件流**重建全过程；以及断线重连时哪些东西靠事件、哪些必须另取。
> **读者要做的决定**：写新客户端（Web SDK / 内嵌 / IM 桥）时，按本契约消费事件；本契约之外的行为**不算契约**。
> **配套实现**：服务端 `server/index.js`（SSE 出口）+ `server/agent.js`（事件环）；
> 客户端重建器与保真判定 `src/eventstream.js`（纯函数）；夹具 `test/eventstream.test.mjs`；实测脚本 `scripts/ra37-rebuild.mjs`。

---

## §1 接口形态

| 项 | 值 |
|---|---|
| 端点 | `POST /api/chat`（**全站唯一 SSE 端点**；无 WebSocket、无 `/api/events`） |
| 鉴权 | `Authorization: Bearer <session token>`（`requireAuth`）；未通过时返回 **JSON**（非事件流） |
| 请求 | `{ conversationId, content, provider?, model? }` |
| 响应头 | `Content-Type: text/event-stream; charset=utf-8`、`Cache-Control: no-cache`、`Connection: keep-alive`、`X-Accel-Buffering: no` |
| 帧格式 | `[id: <seq>\n]data: <json>\n\n` —— **只有 `data:` 帧，没有 SSE `event:` 名**；判别字段是载荷里的 `type` |
| 保活 | 注释帧 `: ping`（空闲 15s 触发；**不是事件**，消费方必须忽略） |
| 序号 | 带序号的事件会同时写 `id: <seq>`；`seq` 是**进程内全局单调计数**（跨会话共享，见 §4） |
| 结束 | HTTP 流关闭。**没有 `data: [DONE]`** 这种哨兵 |
| 版本 | 每个 `run_start` / `run_end` 载荷带 `v`（当前 `1`）；契约**只增不改**（见 §6） |

> **请求前置失败不是事件**：参数缺失 `400`、会话不存在 `404`、并发上限 `429`、鉴权失败 `401/500` 一律返回 JSON，
> 客户端要在 `res.ok === false` 时按普通 HTTP 错误处理，不要试图从流里读。

## §2 事件清单（完备表）

`seq` 列：✅ = 会带 `id:` 序号（同时进事件环）；— = 不带序号、也不进环。

| `type` | seq | 语义 | 何时发 | 载荷字段（契约内） |
|---|---|---|---|---|
| `run_start` | — | **执行起点**。一次执行与下一次执行的边界 | 每次 `/api/chat` 进入 agent 路径后、发第一次 `intent` 之后，且**恰好一次** | `v` `conversationId` `runId`（可 null：轻量问答不登记现场） `light` `provider` `model` `preset` `permission` |
| `intent` | — | 意图识别灰字（**提示，不承载事实**） | 每轮最先尝试发一次；分类抛异常则**不发** | `label` `echo` `hit` |
| `route` | — | 路由/档案/壳默认灰字（**提示**） | 仅当命中档案或壳默认路由时，最多 1 条 | `profile`（null=壳默认） `suggestProvider` `suggestModel` `echo` |
| `thinking` | ✅ | 新一轮 LLM 调用开始 | agent 每轮护栏检查通过后发 1 次 | `round`（循环序号，**非 DB id**） |
| `think` | ✅ | 思考（reasoning）增量 | 厂商返回 reasoning 增量时，0..n 次 | `text` |
| `tool_start` | ✅ | 工具调用开始 | 每个工具调用 1 次 | `tool: { name, args, seq, status: 'running', sub? }` |
| `tool_done` | ✅ | 工具调用结束 | 每个工具调用 1 次（失败也有，`status='fail'`） | `tool: { name, args, seq, status: 'done'\|'fail', durationMs, result }` |
| `plan` | ✅ | 任务清单**全量快照** | 本轮调用了 `plan_tasks` / `plan_done` 时 | `plan: [{ index(1-based), text, done }]` |
| `approval` | ✅ | **等待人工确认**（RA-26 的独立状态） | guard 权限下命中需审批工具时，可多次 | `id` `desc` |
| `ask` | ✅ | **等待用户答复**（结构化问询） | 调用 `ask_user` 时，可多次 | `id` `question` `options: [{label, value}]` |
| `wait_start` | ✅ | **进入等待**（RA-26：与"执行中"是两个状态） | 审批卡/问询卡发出后立即发一次 | `wait: { kind:'approval'\|'ask', id, round }` |
| `wait_end` | ✅ | **离开等待**，恢复执行 | 用户裁决/超时/中止后发一次 | `wait: { kind, id, round, decision?\|reason?, ms }`（`ms`=本次等待毫秒数） |
| `delta` | ✅ | 正文增量 | 流式生成期间 0..n 次；收尾时若有"没流出去"的加工字节，**补发** | `delta` |
| `fake_done_warn` | ✅ | 假完成打回告知 | 模型声称完成但本轮无工具调用、已强制加注时 | `text` |
| `done` | — | **流终结**（老客户端只看它） | 正常完成 / 护栏挂起 / 异常之外的收尾，恰好 1 次 | `usage`（**最后一轮**） `messageId` `runId` `totals`（全量，见 §3） |
| `stopped` | — | 用户点停止 或 连接断开 | 仅 `result.stopped` 时；**不发 `done`** | 无（原因在 `run_end`） |
| `error` | — | 异常终结（**不发 `done`**） | `runAgent` 或收尾抛出时，恰好 1 次 | `message` |
| `run_end` | — | **一致性回执**：这一段已落定（含落库 id） | 上面三种终结**各发一次**；在**落库之后**发 | `v` `conversationId` `runId` `status`（`saved`\|`stopped`\|`error`） `reason`（`user`\|`disconnect`\|`exception`\|`saved`） `reasonText` `messageId` `contentLength` `finishReason` `guard` `usage` `totals` `spentYuan` |
| `llm_retry` | ✅ | **厂商侧失败后的重试**（统一失败分类/重试，2026-09-15 起可见） | 每轮流式请求失败且判定为可恢复时，可多次；等待时长优先用服务端 `Retry-After` | `retry: { attempt, max, reason, waitMs, error }` |
| `prefix_face` | — | **这一轮真实发出的前缀面指纹**（工具面 + 系统提示）。确定性投影/对账的一手数据：账本里唯一能回答"当时那条面是什么"的记录 | 每段第一轮发一次（段内面恒定，重复入账只是噪音） | `toolsHash` `sysHash` `nTools` `light` `preset` `permission` |

> **未知类型的处置**：客户端按契约**忽略**不认识的 `type`；但服务端**照发并入账**（见下方"事件账本"）——
> 账本是回放/投影的源，漏一种就少一种，所以这里刻意不做白名单过滤。

## 事件账本（append-only，2026-09-15）

**每一帧 `send(...)` 都同时追加进 `events` 表**（`server/eventlog.js` 是唯一写入点，挂在 `/api/chat` 的
`send` 上——run 边界与 agent 侧事件都经过它）。用途：**回放与确定性投影**（`scripts/replay-events.mjs`）。

| 口径 | 说明 |
|---|---|
| 只追加 | 账本不改写、不删除；投影/回放只读它 |
| 落什么 | **对外事件契约的每一帧**（与客户端看到的一致）。纯流式增量 `think`/`delta` **不入账**——它们是 UI 实时糖，最终文本已在 `messages.reasoning`/`content` 可查（§7.3 双投影） |
| 失败语义 | 落账失败**出声但不阻断**（事件属观测面，丢了要看得见，但不能让整轮失败） |
| 保留 | 沿用审计账本那条 90 天归档口径；**归档器尚未实现**（登记为未闭环，不另发明天数） |

**事件环里额外可见的**（`GET /api/conversations/:id/activity?after=<seq>`；SSE 断连后的兜底通道）：

| `type` | 语义 |
|---|---|
| `run_end` | 环收尾事件（`status: 'saved'`，由 `clearActivity` 追加）；**只有环有**，用于"这一段是否已落定" |
| 其余 | 环里的 `think`/`delta`/`tool_start`/`tool_done`/`plan`/`agent_thinking` 是 SSE 同名事件的镜像 |

> **两条投影不完全重合，这是已知并登记的事实**（不是 bug 而是当前边界）：
> 环里**没有** `intent`/`route`/`done`/`error`/`stopped`/`approval`/`ask`；
> 环里的子代理事件是**未改写版**（`name='read_file'`、`seq` 为子代理本地序号），
> 而 SSE 拿到的是改写过版（`name='子:read_file'`、`seq = 段基址+本地序号`、带 `sub`）。
> 因此**不要跨通道对账 seq**；要重建请固定用一条通道。

## §3 重建规则（"仅靠事件流重建全过程"的定义）

一个合规客户端只需事件流即可重建下列事实——每一条都给了重建算式：

| 重建目标 | 算式 |
|---|---|
| **执行边界** | `run_start` 开段；`run_end` 收段。一轮 = 一对 |
| **正文全文** | **顺序拼接全部 `delta`**。服务端保证该拼接结果与落库 `messages.content` **逐字一致**（见下方补流对账） |
| **工具轨迹** | 按 `tool_start`/`tool_done` 的 `tool.seq` 归并；`seq` 在一次执行内唯一（并行工具也不撞号） |
| **轮次** | `thinking.round` 的最大值 |
| **思考过程** | 顺序拼接全部 `think` |
| **待确认/待答复** | `approval` / `ask` 的在场集合，或 `wait_start`/`wait_end` 的配对 ⇒ 状态是 `waiting-approval` / `waiting-answer`，**不等于"还在跑"** |
| **等待时长** | `wait_end.wait.ms` 累加 ⇒ 与 `totals.waitedMs` 对账（RA-26 四面④：等待不算执行用时，也就不烧时间预算） |
| **结局与原因** | `run_end.status` + `run_end.reason`（`user` / `disconnect` / `exception` / `saved`） |
| **落库位置** | `run_end.messageId`（= `messages.id`） |
| **用量与成本** | `run_end.totals` / `done.totals`：`{tokens_in, tokens_out, cache_hit, cache_miss, cost, hit_rate}`，**本次执行全量**（含折叠/续写等所有计费调用） |

`done.usage` 保留**最后一轮**的原始口径（向后兼容，字段未改）；要总量请读 `totals`。

### 补流对账（为什么拼接结果能等于落库正文）

`delta` 原本只覆盖"模型真流出来的正文"。而落库正文还会被后置加工：C4 自动续写段、`finish_reason=length` 的截断提示、
假完成的强制加注前缀、空答兜底摘要。这些字节此前**从不经过 `delta`**，于是"事件流拼出来的 ≠ 落库的"。
现在服务端在落库前做一次对账（`server/index.js`）：

- 拼接结果 == 落库正文 → 什么都不补；
- 落库正文 = 拼接结果 + 后置追加 → **补发尾部**；
- 落库正文 = 前置加注 + 拼接结果 → **补发前缀**；
- 两者对不上账 → 整段补发并打 `[stream] ... 无法对账` 告警（宁可重复显示，也不让客户端与库不一致）。

**保真判定**由 `src/eventstream.js` 的 `verifyRebuild(view, truth)` 给出：正文逐字一致 / 落库 id / 轮次 / 全量成本 / 丢帧 / 未知类型。

## §4 序号、断线重连与停止/挂起/续跑

- `seq` 由事件环的全局计数器分配，**跨会话单调递增**，写进 SSE 的 `id:` 行。客户端应记录它并在跳变时告警（可能丢帧）。
- **断线后 SSE 不会有任何终结事件**（连接已关）。此时唯一可靠通道是
  `GET /api/conversations/:id/activity?after=<seq>`：它在环未被清理（60s 内）时给出遗漏的增量，
  并用环自己的 `run_end` 告诉你"这一段已落定"。
- **60s 之后环被删除**：重连只能走 `GET /api/conversations/:id/messages` 与 `/export`（此时事件流已不是事实源）。
  **这是当前边界，不是"重连不丢现场"已完全达成的证明。**
- **停 / 挂 / 续**：
  - 停（用户点停止）：`stopped` → `run_end{status:'stopped', reason:'user'}`；已流出的正文会作为占位消息落库。
  - 挂（时间预算 / 轮次上限 / 成本阈值 / 连续无进展）：以 `done` 收尾（正文即挂起文案），`run_end{status:'saved', guard:'budget'|'cap'|'budget-yuan'|...}`。
  - 续（用户回复"继续任务"）：是一次**新的执行**，会有新的 `run_start` / `run_end`；断点现场由 `agent_runs` 承载，不在事件流里。

## §5 客户端实现清单（照做即可）

1. `fetch('/api/chat', {headers:{Authorization:'Bearer '+token}, method:'POST', body:...})`，按 `\n\n` 分帧。
2. 每帧先取 `id:`（可选），再取 `data:` 做 `JSON.parse`；**忽略 `:` 开头的注释帧**。
3. 未知 `type` **忽略并留痕**（契约只增不改；不要抛错、不要终止消费）。
4. 正文只信 `delta` 的顺序拼接；**不要**用 `done.usage` 当总量（用 `totals`）。
5. 收到 `run_end` 才算这一段落定；此前任何 `messages` 读取都可能读不到该行（老版本曾在 `done` 之前落库，已修）。
6. 断线：记住最后的 `id:`，重连后先 `GET /activity?after=<seq>`；拿不到就以 `/messages` 兜底并如实告知用户"这段的实时轨迹已丢失"。

## §6 版本演进

- 载荷里的 `v` 是**协议版本**；当前 `1`。破坏性变更 → `v+1` 并行一段过渡期。
- **只增不改**：新增 `type`、新增字段允许；改名/改语义/删除字段不允许。
- 已知**未纳入 v1**的扩展项（留给 M2，登记在案）：`id:` 的断点续订（`Last-Event-ID`）服务端尚未实现、
  环容量 300 条且 60s 清理、跨会话 seq 共享、同会话并发执行未隔离（服务端只有账号级并发上限）。
