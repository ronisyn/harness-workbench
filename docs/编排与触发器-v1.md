## 1. 四档语义（谁在什么时刻算一次触发）

| 档位 | 一次触发＝什么 | 语义边界（**不算**的情况） |
|---|---|---|
| `manual` | **人主动点了"跑一次"**：`POST /api/tasks/:id/run` 收下一台定时任务的补跑（`task.__manual=true`） | 不算：cron 到点自动跑（那是 `schedule`）；人在 Web 里发一条对话（那是接入面，不是编排面的触发） |
| `schedule` | **调度器真的发起一轮执行**：扫描发现到期任务并推后 `next_run` 之后 | 不算：扫描了但没有任务到期（不制造"每 60s 一次空触发"）；`computeNextRuns` 给空 `next_run` 补算（那是维护动作，不是执行） |
| `external` | **进程外的东西调了我们的门面**：JSON-RPC 的每个方法被调用、MCP 的每个工具被调用 | 不算：门面自己内部的后续调用（例如 `session.chat` 内部再去建会话）；也**不说明这次调用成功**（见 §4） |
| `event` | **事件账本收下了一条事件**（`server/eventlog.js` 的唯一追加点） | 不算：transient 帧（`think`/`delta`）不进账本 ⇒ 不触发；没有会话 id 的账不写也不触发 |

四档的顺序就是 `TRIGGER_KINDS` 的顺序（`server/triggers.js:28`），**对外口径，不要随手改**。

`schedule` 档**两层都会投**（有意，不是重复计数）：

| 层 | 投递点 | 载荷带什么 |
|---|---|---|
| 扫描层 | `server/scheduler.js:209`（`runSchedulerTick`） | `{taskId, name, nextRun, due, scanned}`：本轮发起谁、推进到什么时候、本轮读数 |
| 执行层 | `server/scheduler.js:125`（`executeScheduledTask`，非 `__manual` 时） | `{taskId, name, conversationId}`：这一次执行落在哪个会话 |

两层都留的理由：执行层在"任务连账号都不存在"时**根本走不到**（`executeScheduledTask` 提前 return），
那时扫描层是唯一的记录。**去重不做**（见 §4 最后一条）。

## 2. handler 归谁写（"实现归使用方"）

- 接口层（`server/triggers.js`）**一个 handler 都不注册**，且这是被夹具锁住的现状：
  没人在听时 `fire` 直接早退（`{matched: 0}`），连快照都不做 ⇒ 零成本、不报错。
- 三处源（调度器 / 两个门面脚本）也**一个 handler 都不注册**——它们只负责"把一次触发交出去"。
  使用方要接就自己 `register(kind, handler, {id})`，拿到退订函数。
- **本仓当前没有生产 handler**（这是如实登记，不是漏项）：四档的"源"都接上了，但平台自己还没有
  "收到触发要干点什么"的业务。要接的第一个真实使用方按需 `register` 即可，接口无需再动。

## 3. 三处源（谁 fire、payload 带什么、失败怎么兜）

| 档位 | 源（file:line，2026-09-16 核） | 谁 fire | payload / meta | 失败怎么兜 |
|---|---|---|---|---|
| `manual` | `server/scheduler.js:125`（`executeScheduledTask` 的 `task.__manual` 分支） | 人经 `server/index.js` 的 `POST /api/tasks/:id/run`（任务列表的 ▶ 跑一次；`__manual: true` 只有这一处会置上） | `{taskId, name, conversationId}`／`{source:'http'}` | `fireSafely` |
| `schedule`（扫描层） | `server/scheduler.js:209`（`runSchedulerTick`，即原 `startScheduler` 的 `setInterval` 回调体） | 调度器每 60s 一轮，**真的发起执行时** | `{taskId, name, nextRun, due, scanned}`／`{source:'cron', due, scanned}` | `fireSafely` |
| `schedule`（执行层） | `server/scheduler.js:125`（非 `__manual` 分支） | 同上那一轮发起的那次执行 | `{taskId, name, conversationId}`／`{source:'cron'}` | `fireSafely` |
| `external` | `server/external-trigger.js:89`（`wrapExternalCalls`）——被两个适配器各自包一层：`scripts/rw-jsonrpc.mjs:234`、`scripts/rw-mcp-server.mjs:179` | 进程外调用进来时（JSON-RPC 的每个方法、MCP 的每个工具） | `{tool, ...白名单事实}`／`{source:'jsonrpc'\|'mcp'}` | 包装层自己 try/catch + `fireSafely` |
| `event` | `server/triggers.js` 末尾的 `onEventAppended` 订阅（先于本轮存在） | 事件账本追加点 | `{conversationId, type, seq, at, payload}`／`{source:'eventlog', ...}` | 订阅者自己的 try/catch（既有） |

**`fireSafely`（`server/triggers.js:102`）＝源用的那一层**：语义与 `fire` 完全一致，但**永不抛错、永不等待**——
它把 `fire` 推到微任务（`queueMicrotask`）里执行，连 `enqueue` 自己抛错都兜住（外层的 try。
夹具注入同步 `enqueue` 时就会走到那条路径）。为什么源必须走它：见 §4 第一条。

**payload 的纪律（"别塞密钥"）**：

- 定时/手动档只带**标识**：任务 id、任务名、会话 id、推进到的 `next_run`、本轮读数。
  **不带** `prompt` 正文（它可能很长、也可能含业务信息），**不带**任何凭据。
- 外部档走**白名单**（`server/external-trigger.js:46` 的 `externalCallPayload`）：
  只取 `conversationId`/`conversation_id`/`after`/`limit`/`waitSeconds`/`wait_seconds`；
  `message` **只带长度**；幂等键**只带"给没给"**这一格布尔（值本身是调用方的业务标识，不进触发载荷）；
  键名含 `pass`/`token`/`secret`/`authorization`/`apikey`/`api_key` 的一律**丢弃**；
  读不动的参数（getter 抛错、不是对象）标 `unreadable` 而不是把异常传出去。
- **不整体搬运参数对象**：参数里混进函数/BigInt/循环引用时，整体 `JSON.stringify` 会当场抛错或让触发面报错，
  而我们要的是"触发照样发生"。

## 4. 失败怎么算（四条口径）

1. **接线坏一次不许打断主流程**。源用的 `fireSafely` 承诺"调用方永远看不到异常"：
   档位写错、payload 不是无损 JSON、`enqueue` 自己抛错——都只记一行日志
   （`[trigger] <档位> 档投递失败（触发面自己兜住，不影响触发点）：…`，过 `redactSecretValues` 脱敏）。
   后果：调度器的一轮扫描照常跑完（读数照返回、`next_run` 照推进），门面的这次调用照常返回。
2. **handler 失败不影响源，也不饿死兄弟**。每个 handler 各自一条 promise 链，抛错/拒绝只记一行
   `[trigger] <id>（kind=…）失败：…`（同 DSH：logged without starving siblings）。
3. **触发≠成功**。`external` 档的触发发生在处理器**之前**：fire 只说明"有人从这个入口调了 `tool`"，
   **不说明这次调用成功**；超时/业务失败照样已经触发过（返回值与 `isError` 才是成败口径，逐字未动）。
4. **不重试、不去重、不排队、不落库**（照 DSH `dsh-webhook` 的进程内边界，逐条理由见
   `server/triggers.js` 文件头）：进程重启后没跑成的触发就是没跑；`schedule` 档两层各投一次
   **不去重**——需要幂等的使用方**自己判**。频率限制/去重窗口本档一律不设（凭空定阈值就是发明口径）。

## 5. 成批编排（`subagent_fanout`）的现状与边界

"补成批编排"这半句在**工具面**（`server/tools/index.js:923` 起的 `subagent_fanout`），不在触发面：

- **是什么**：对多个条目并行各派一个子代理跑**同一个任务模板**（模板里 `{{item}}` 占位），
  一批跑完再跑下一批，全部完成后统一汇总。
- **边界（照现有实现与契约，不是本文新定的）**：条目数上限 **12**（`slice(0, 12)`）；每批 **6** 条；
  在跑子代理数 **≥8** 当场报错；嵌套上限 **3** 层（`ctx.noSubagent`）；条目 <3 时逐条直接做更划算。
  契约行见 `docs/tool-contracts-v1.md:53`，参数面（收窄工具/切额度）的夹具在 `test/subagent-scope.test.mjs:144`。
- **与触发面的关系：没有关系（如实写清）**。`subagent_fanout` 是**模型在某一轮里自己调的**工具；
  它既不是四档触发，也不 fire 任何档位。四档管的是"**一轮执行怎么被启动**"，成批编排管的是
  "**启动之后这一轮里派几个子代理**"——两层不要混成一件（混了就会出现"定时任务 fire 一次＝自动 fanout"
  这种没人拍过板的语义）。
- **脚本式 workflow / 声明式编排模板不在本档**：v0.3 §4.5 只要求"成批编排"，本仓已有 `subagent_fanout`、
  `ralph`、契约驱动器（`server/driver.js`）三件；要不要再上一层脚本编排是另一件事，本文不承诺。
